## Purpose

Определяет модель данных ролей и прав iReports (User–Role–Permission), правила enforcement на
backend через guard'ы, отражение прав на frontend и поведение админ-страницы управления ролями,
включая немедленное применение изменений прав к активным сессиям.

## Requirements

### Requirement: Модель данных Role–Permission без хардкода ролей
Роли и права SHALL храниться в виде сущностей `Role`, `Permission`, связанных с существующим
`BitrixEmployee` через `EmployeeRole` и `RolePermission` (many-to-many в обе стороны); `Permission`
SHALL иметь формат строки `resource:action`. Создание и изменение РОЛЕЙ, а также назначение им
permissions ИЗ существующего каталога, SHALL быть возможно через UI/API без изменения кода и без
деплоя — в отличие от самого каталога permission-кодов (см. отдельное требование ниже).

#### Scenario: Новая роль с набором прав создаётся без деплоя
- **WHEN** администратор создаёт новую роль и назначает ей набор permissions ИЗ существующего
  каталога через UI/API
- **THEN** роль и её права становятся доступны для назначения сотрудникам немедленно, без
  изменений в коде или повторного деплоя

### Requirement: Каталог permission-кодов формируется из кода, не создаётся через UI
Каталог доступных permission-кодов (`Permission`) SHALL наполняться из типизированного реестра
permission-кодов, объявленного в коде backend модулями-владельцами, и синхронизироваться с ним при
деплое; UI/API SHALL позволять администратору только выбирать и назначать ролям permissions ИЗ уже
существующего каталога, но SHALL не позволять создавать новый permission-код, отсутствующий в
реестре кода.

#### Scenario: Администратор не может создать несуществующий в коде permission-код
- **WHEN** администратор пытается создать или назначить роли permission-код, которого нет в
  каталоге `Permission`
- **THEN** система отклоняет операцию — новый permission-код может появиться только через изменение
  реестра в коде и деплой

#### Scenario: Новый permission-код в коде без деплоя каталога не даёт прав
- **WHEN** в коде backend добавлен `@RequirePermissions('resource:new-action')`, но каталог
  `Permission` ещё не синхронизирован с реестром (деплой сида не выполнялся)
- **THEN** ни одна роль не может получить это право до тех пор, пока каталог не будет
  синхронизирован

### Requirement: Роли и права Bitrix24 не становятся ролями iReports
Должность, отдел и иные атрибуты пользователя в Bitrix24 SHALL оставаться независимыми от его ролей
и permissions в iReports — система SHALL не выводить и не изменять автоматически роли/permissions
iReports на основании данных Bitrix24.

#### Scenario: Изменение должности в Bitrix24 не меняет права в iReports
- **WHEN** у пользователя в Bitrix24 меняется должность или отдел
- **THEN** его роли и permissions в iReports остаются прежними, пока их явно не изменит
  администратор iReports

### Requirement: Требование валидной сессии для доступа к защищённым роутам
Все роуты, не помеченные как публичные, SHALL требовать валидную сессию пользователя; при её
отсутствии обработчик роута SHALL не выполняться.

#### Scenario: Защищённый роут без сессии не выполняет обработчик
- **WHEN** запрос к роуту без пометки `@Public()` приходит без валидной сессии
- **THEN** backend возвращает 401, и код обработчика роута не выполняется

### Requirement: Публичные роуты не требуют аутентификации
Роуты, помеченные декоратором `@Public()` (например, OAuth-callback, health-check), SHALL быть
доступны без проверки сессии.

#### Scenario: Публичный роут доступен без сессии
- **WHEN** запрос приходит на роут, помеченный `@Public()`, без session_id
- **THEN** backend выполняет обработчик роута, не требуя сессии

### Requirement: Проверка permission на уровне роута
Роут, помеченный `@RequirePermissions('resource:action', ...)`, SHALL быть доступен только
пользователю, чьи permissions (из валидной сессии) включают все указанные значения; иначе backend
SHALL возвращать 403.

#### Scenario: Доступ без нужного permission отклоняется
- **WHEN** пользователь с валидной сессией, но без permission `reports:edit`, обращается к роуту с
  `@RequirePermissions('reports:edit')`
- **THEN** backend возвращает 403

### Requirement: Роут без указанных permissions доступен любому аутентифицированному пользователю
Роут с валидной сессией, но без декоратора `@RequirePermissions`, SHALL быть доступен любому
аутентифицированному пользователю независимо от его конкретных permissions.

#### Scenario: Роут без RequirePermissions открыт любому вошедшему пользователю
- **WHEN** аутентифицированный пользователь с произвольным набором permissions обращается к роуту
  без `@RequirePermissions`
- **THEN** backend выполняет обработчик роута

### Requirement: Немедленное применение изменений прав роли к активным сессиям
При изменении набора permissions роли backend SHALL обновить или сбросить закэшированные
permissions во всех активных сессиях пользователей, имеющих эту роль, так чтобы новые ограничения
действовали без необходимости повторного входа.

#### Scenario: Снятое право перестаёт действовать без релогина
- **WHEN** администратор снимает permission `reports:edit` у роли, а пользователь с этой ролью уже
  имеет активную сессию
- **THEN** следующий запрос этого пользователя на действие, требующее `reports:edit`, получает 403
  без необходимости повторного входа

### Requirement: Получение текущего пользователя и его permissions
Backend SHALL предоставлять эндпоинт, возвращающий текущего аутентифицированного пользователя и
его permissions, для инициализации клиентского состояния после входа.

#### Scenario: Frontend получает пользователя и его права после входа
- **WHEN** frontend с валидной сессией запрашивает данные текущего пользователя
- **THEN** ответ содержит идентификатор пользователя и полный список его текущих permissions

### Requirement: Условная видимость элементов управления на основе permissions
Frontend SHALL предоставлять способ проверки наличия permission у текущего пользователя
(`useHasPermission(permission: string): boolean`) и SHALL использовать его для скрытия элементов
управления, недоступных пользователю.

#### Scenario: Элемент управления скрыт при отсутствии permission
- **WHEN** у текущего пользователя нет permission, необходимого для действия
- **THEN** соответствующий элемент управления не отображается в интерфейсе

### Requirement: Защита страниц/роутов на frontend
Пользователь без нужного permission SHALL не видеть соответствующий пункт меню и SHALL получать
явный экран "нет доступа" при прямом переходе по URL защищённой страницы; при этом backend SHALL
самостоятельно возвращать 403 при прямом обращении к соответствующему API, независимо от проверки
на frontend.

#### Scenario: Прямой переход по URL без прав показывает экран "нет доступа"
- **WHEN** пользователь без нужного permission переходит по прямой ссылке на защищённую страницу
- **THEN** frontend показывает экран "нет доступа", а не содержимое страницы

#### Scenario: Backend не полагается на проверку frontend
- **WHEN** пользователь без permission напрямую обращается к API защищённой страницы, минуя
  frontend
- **THEN** backend возвращает 403 независимо от того, что делает frontend

### Requirement: Админ-страница управления ролями доступна только с roles:manage
Админ-страница управления ролями (список ролей, матрица роль×permission, назначение ролей
пользователям) SHALL быть доступна только пользователям с permission `roles:manage`; изменения
матрицы прав SHALL сохраняться через `PATCH /roles/:id/permissions`.

#### Scenario: Пользователь без roles:manage не может открыть страницу управления ролями
- **WHEN** пользователь без permission `roles:manage` пытается открыть страницу управления ролями
  напрямую по URL
- **THEN** frontend показывает экран "нет доступа", а backend возвращает 403 при прямом обращении
  к соответствующим API

#### Scenario: Изменение матрицы роль×permission сохраняется
- **WHEN** администратор с permission `roles:manage` меняет чекбоксы в матрице роль×permission и
  сохраняет изменения
- **THEN** backend применяет изменение через `PATCH /roles/:id/permissions`, и обновлённый набор
  permissions роли сохраняется
