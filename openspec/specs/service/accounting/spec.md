## Purpose

Описывает бизнес-правила начисления зарплаты сотрудникам направления «Сервис»: из чего складывается
начисление, как ведёт себя расчётный период при закрытии/переоткрытии и что видно в зарплатных
отчётах сотрудника и отдела. Не описывает документ начисления `SalaryAccrual`/`Payout` (выплаты,
статусы `DRAFT`/`PARTIALLY_ACCRUED`/`ACCRUED`/`PAID`) — это отдельный пласт того же модуля,
задокументирован будет отдельным последующим change.

## Requirements

### Requirement: Мотивационная схема как набор зарплатных правил
Каждый сотрудник или должность SHALL иметь мотивационную схему — набор из одного или нескольких
зарплатных правил, каждое из которых рассчитывается независимо и не зависит от результата других
правил той же схемы.

#### Scenario: Итоговое начисление — сумма независимых правил
- **WHEN** у сотрудника в мотивационной схеме несколько зарплатных правил
- **THEN** итоговое начисление за период равно сумме результатов каждого правила, рассчитанного без
  учёта результатов остальных правил

### Requirement: Виды зарплатных правил
Зарплатное правило SHALL быть одного из семи видов: почасовая оплата, оплата за выполненную услугу,
вознаграждение за оплаченный заказ, оплата за выполнение задачи, процент от факта выручки/маржи
отдела/направления, бонус за выполнение плана продаж по выручке/марже, бонус за выполнение плана по
коэффициенту оборачиваемости.

#### Scenario: Почасовая оплата считается по отработанным часам
- **WHEN** правило сотрудника — почасовая оплата
- **THEN** начисление за период рассчитывается по количеству отработанных часов за этот период

#### Scenario: Оплата за услугу считается по факту выполнения
- **WHEN** правило сотрудника — оплата за выполненную услугу
- **THEN** начисление рассчитывается по услугам, выполненным сотрудником за период

#### Scenario: Вознаграждение за заказ считается по факту оплаты
- **WHEN** правило сотрудника — вознаграждение за оплаченный заказ
- **THEN** начисление рассчитывается по заказам, оплаченным за период

#### Scenario: Оплаченность заказа определяется его статусом, а не накопленной суммой
- **WHEN** определяется, считается ли заказ оплаченным для расчёта вознаграждения
- **THEN** решение принимается по тому, к какой группе статусов заказа он относится, а не по факту
  наличия ненулевой накопленной оплаты по заказу

#### Scenario: Оплата за выполнение задачи считается по статусу связанной задачи
- **WHEN** правило сотрудника — оплата за выполнение задачи
- **THEN** начисление по правилу доступно только после того, как связанная с правилом задача
  переведена в статус «Выполнено»

#### Scenario: Процент от факта считается без коэффициента выполнения плана
- **WHEN** правило сотрудника — процент от факта выручки/маржи отдела/направления
- **THEN** начисление за период равно фиксированному проценту от фактического значения выручки или
  маржи за этот период, без какого-либо множителя

#### Scenario: Бонус за план выручки/маржи считается с плавающим коэффициентом
- **WHEN** правило сотрудника — бонус за выполнение плана продаж по выручке/марже
- **THEN** начисление за период равно фиксированной сумме, умноженной на коэффициент, определяемый
  процентом выполнения плана выручки/маржи за этот период

#### Scenario: Бонус за оборачиваемость считается с плавающим коэффициентом
- **WHEN** правило сотрудника — бонус за выполнение плана по коэффициенту оборачиваемости
- **THEN** начисление за период равно фиксированной сумме, умноженной на коэффициент, определяемый
  отношением фактического коэффициента оборачиваемости к плановому значению, заданному в самом
  правиле

### Requirement: Строка правила «за выполнение задачи» появляется сразу и растёт по статусу задачи

Implements FR1-FR4 of task-completion-progressive-visibility.

Начиная с момента, когда связанная задача заведена на расчётный период (то есть уже существует, вне
зависимости от её статуса), строка по правилу «за выполнение задачи» SHALL присутствовать в
зарплатном отчёте сотрудника — как в фактическом, так и в прогнозном режиме. До задачи, заведённой на
период (правило ещё не породило задачу этого периода), строка SHALL отсутствовать полностью.

Сумма строки в каждом режиме определяется статусом задачи:
- **прогнозный режим (`prognose`)** — сумма начисления по умолчанию правила СРАЗУ, независимо от
  статуса задачи (в том числе для только что созданной, ещё не взятой в работу);
- **фактический режим (`fact`)** — 0, пока задача не переведена в статус «Выполнена»; начиная с этого
  статуса — сумма начисления по умолчанию правила. Дальнейшие переходы статуса задачи («Закрыта
  успешно», «Закрыта неуспешно», «На доработке» — все достижимы только через «Выполнена») SHALL NOT
  автоматически откатывать факт обратно к 0.

Это заменяет прежнее правило видимости (архивный change `replace-bitrix-task-integration`, design.md
решение 3) — раньше строка была полностью скрыта до статуса «Закрыта успешно» в обоих режимах;
теперь скрыта только строка ещё не заведённой задачи, прогноз виден с постановки задачи, а факт
капает раньше — на отметке исполнителя «Выполнена», не дожидаясь подтверждения руководителем.

#### Scenario: Строка появляется сразу после создания задачи, прогноз уже равен сумме начисления
- **WHEN** задача связанного правила «за выполнение задачи» только что заведена на текущий период
  (статус «Новая»)
- **THEN** строка по этому правилу присутствует в отчёте сотрудника с прогнозом, равным сумме
  начисления по умолчанию, и фактом 0

#### Scenario: Факт капает на статусе «Выполнена»
- **WHEN** ответственный сотрудник перевёл задачу в статус «Выполнена»
- **THEN** факт по строке этого правила становится равен сумме начисления по умолчанию — не дожидаясь
  подтверждения руководителем

#### Scenario: Дальнейшие переходы статуса не откатывают факт
- **WHEN** задача, уже находившаяся в статусе «Выполнена», переведена в статус «Закрыта успешно»,
  «Закрыта неуспешно» или «На доработке»
- **THEN** факт по строке этого правила остаётся равным сумме начисления по умолчанию — автоматического
  отката к 0 не происходит; при необходимости руководитель корректирует сумму вручную при закрытии
  периода

### Requirement: Сумма начисления по правилу «за выполнение задачи» задаётся руководителем вручную
В отличие от прочих видов зарплатных правил, начисление по правилу «за выполнение задачи» SHALL не
вычисляться автоматически по формуле. При проведении начисления руководитель SHALL указать сумму
начисления и обязательный комментарий; этот комментарий SHALL быть виден сотруднику в его начислении.

#### Scenario: Начисление требует ручного ввода суммы
- **WHEN** руководитель проводит начисление по строке правила «за выполнение задачи»
- **THEN** сумма начисления берётся из значения, введённого руководителем, а не из автоматического
  расчёта

#### Scenario: Комментарий обязателен и виден сотруднику
- **WHEN** руководитель проводит начисление по строке правила «за выполнение задачи» без комментария
- **THEN** проведение начисления отклоняется, пока комментарий не указан

#### Scenario: Сотрудник видит комментарий руководителя в своём начислении
- **WHEN** начисление по правилу «за выполнение задачи» проведено с комментарием
- **THEN** сотрудник видит этот комментарий при просмотре своего начисления за период

### Requirement: Разовое и регулярное правило «за выполнение задачи»
Руководитель SHALL иметь возможность создать правило «за выполнение задачи» как разовое (действует
только в расчётном периоде создания) или как регулярное (продолжает действовать в каждом следующем
расчётном периоде, пока не отменено). Расчётный период, к которому относится задача правила,
SHALL задаваться руководителем явно при создании правила (полем выбора периода в форме), а не
вычисляться неявно как текущий период на момент создания. При автосоздании новой задачи регулярного
правила на очередной период система SHALL обновлять расчётный период правила на этот новый период —
так поле всегда отражает период самой свежей заведённой задачи.

#### Scenario: Разовое правило действует один расчётный период
- **WHEN** правило «за выполнение задачи» создано как разовое, и наступает следующий расчётный период
- **THEN** правило больше не создаёт новую задачу и не участвует в начислении следующего периода

#### Scenario: Регулярное правило продолжает действовать в новых периодах
- **WHEN** правило «за выполнение задачи» создано как регулярное, и наступает следующий расчётный
  период
- **THEN** правило продолжает действовать — для него создаётся новая задача на новый период

#### Scenario: Период задачи задаётся явно при создании правила
- **WHEN** руководитель создаёт правило «за выполнение задачи» и выбирает в форме расчётный период,
  отличный от текущего (например, наступающий следующий или уже прошедший)
- **THEN** первая задача правила заводится на выбранный период, а не на текущий

#### Scenario: Автосоздание задачи регулярного правила обновляет период правила
- **WHEN** наступает новый расчётный период и для регулярного правила автоматически создаётся новая
  задача на этот период
- **THEN** расчётный период правила обновляется на период новой задачи

### Requirement: Оплату за услугу и вознаграждение за заказ можно ограничить типами заказа
Правила «оплата за выполненную услугу» и «вознаграждение за оплаченный заказ» SHALL поддерживать
опциональное ограничение по типам заказа: если для правила задан непустой список допустимых типов
заказа, в расчёт SHALL включаться только позиции/заказы этих типов; если список не задан или пуст,
ограничение SHALL не применяться.

#### Scenario: Без ограничения считаются все типы заказа
- **WHEN** у правила список допустимых типов заказа не задан или пуст
- **THEN** в расчёт включаются позиции/заказы всех типов

#### Scenario: С ограничением считаются только указанные типы заказа
- **WHEN** у правила задан непустой список допустимых типов заказа
- **THEN** в расчёт включаются только позиции/заказы этих типов, остальные исключаются

### Requirement: Источник отработанных часов для почасовой оплаты
Отработанные часы для правила почасовой оплаты SHALL браться из графика работы сотрудника — из смен
за период со статусом «отработана»; ручной ввод часов, не привязанный к графику работы, не
поддерживается.

#### Scenario: Смена не в статусе «отработана» не учитывается
- **WHEN** в графике работы сотрудника есть смена за период, у которой статус отличается от
  «отработана» (например, запланирована, но ещё не подтверждена)
- **THEN** часы этой смены не включаются в расчёт почасовой оплаты за период

#### Scenario: В расчёт входят только смены менеджерских ролей
- **WHEN** в графике работы сотрудника есть отработанная смена с ролью дня «Онлайн-менеджер»,
  «Оффлайн-менеджер» или «Соло-менеджер»
- **THEN** часы этой смены включаются в расчёт почасовой оплаты за период

#### Scenario: Смены прочих ролей дня в расчёт не входят
- **WHEN** в графике работы сотрудника есть отработанная смена с ролью дня, отличной от
  «Онлайн-менеджер»/«Оффлайн-менеджер»/«Соло-менеджер» (например, инженер или офисная роль)
- **THEN** часы этой смены не включаются в расчёт почасовой оплаты за период

#### Scenario: Отсутствие подходящих часов — начисление 0, а не ошибка
- **WHEN** у сотрудника с правилом почасовой оплаты за период нет ни одной подходящей отработанной
  смены
- **THEN** начисление по правилу равно нулю, расчёт не завершается ошибкой

### Requirement: Расчётный период идентифицируется направлением и месяцем
Расчётный период SHALL идентифицироваться парой (направление бизнеса, месяц) и SHALL закрываться и
переоткрываться независимо для каждого направления; период, для которого ещё нет явной записи о
закрытии, SHALL считаться открытым.

#### Scenario: Период без записи о статусе — открыт
- **WHEN** для пары (направление, месяц) ещё не создавалась запись о закрытии периода
- **THEN** период считается открытым

#### Scenario: Закрытие одного направления не влияет на другое
- **WHEN** расчётный период за один и тот же месяц закрыт для одного направления бизнеса
- **THEN** период за тот же месяц для другого направления бизнеса остаётся в своём независимом
  статусе (открыт/закрыт)

### Requirement: Закрытие периода требует утверждённого плана продаж
Расчётный период SHALL закрываться только если все относящиеся к этому периоду строки плана продаж
утверждены.

#### Scenario: Попытка закрыть период с неутверждённым планом отклоняется
- **WHEN** хотя бы одна строка плана продаж, относящаяся к закрываемому периоду, не утверждена
- **THEN** закрытие периода отклоняется

### Requirement: Закрыть можно только истёкший период, с актуальными данными ERP
Расчётный период SHALL закрываться только после того, как календарный месяц периода истёк, и только
если он ещё не закрыт; перед расчётом при закрытии данные из ERP-системы направления SHALL быть
синхронизированы за этот период. Если синхронизация не удалась, закрытие SHALL быть отклонено, и
период SHALL остаться открытым без каких-либо сохранённых изменений.

#### Scenario: Попытка закрыть ещё не истёкший период отклоняется
- **WHEN** запрашивается закрытие периода, календарный месяц которого ещё не закончился
- **THEN** закрытие периода отклоняется

#### Scenario: Попытка закрыть уже закрытый период отклоняется
- **WHEN** запрашивается закрытие периода, который уже закрыт
- **THEN** закрытие периода отклоняется

#### Scenario: Неудачная синхронизация ERP отменяет закрытие
- **WHEN** синхронизация данных ERP перед закрытием периода завершилась ошибкой или превысила
  отведённое время
- **THEN** закрытие периода отклоняется, период остаётся открытым, никакие данные закрытия не
  сохраняются

### Requirement: Закрытие периода фиксирует неизменяемый снапшот
При закрытии расчётного периода SHALL создаваться неизменяемый снапшот начисления по каждому
сотруднику, имеющему персональную мотивационную схему; снапшот SHALL содержать только фактические
значения, без прогнозных.

#### Scenario: Отчёт по закрытому периоду читается из снапшота
- **WHEN** запрашивается зарплатный отчёт сотрудника или отдела за уже закрытый период
- **THEN** данные отчёта берутся из зафиксированного при закрытии снапшота, а не пересчитываются
  заново

#### Scenario: Снапшот закрытого периода не содержит прогноза
- **WHEN** расчётный период закрыт и по нему создан снапшот
- **THEN** снапшот содержит только фактические значения начисления, прогнозные значения в нём
  отсутствуют

### Requirement: Открытый период пересчитывается по актуальным данным
Пока расчётный период открыт, зарплатный отчёт по нему SHALL отражать актуальный пересчёт по текущим
данным (мотивационная схема, данные ERP, план продаж), а не ранее сохранённое значение, если с
момента предыдущего расчёта что-либо из этого изменилось.

#### Scenario: Изменение мотивационной схемы отражается в отчёте открытого периода
- **WHEN** мотивационная схема сотрудника изменилась после предыдущего расчёта, а расчётный период
  ещё открыт
- **THEN** следующий запрос отчёта по этому периоду учитывает изменённую схему

#### Scenario: Обновление данных ERP отражается в отчёте открытого периода
- **WHEN** данные из ERP-системы направления обновились после предыдущего расчёта, а расчётный
  период ещё открыт
- **THEN** следующий запрос отчёта по этому периоду учитывает обновлённые данные ERP

#### Scenario: Изменение плана продаж отражается в отчёте открытого периода
- **WHEN** строка плана продаж, относящаяся к периоду, была изменена или утверждена после
  предыдущего расчёта, а расчётный период ещё открыт
- **THEN** следующий запрос отчёта по этому периоду учитывает изменённый план

### Requirement: Множитель по проценту выполнения плана — ступенчатый или линейный
Для зарплатных правил, зависящих от процента выполнения плана продаж, множитель начисления SHALL
определяться набором порогов процента выполнения; на участке от одного порога до следующего
множитель SHALL либо оставаться постоянным (равным множителю нижнего порога участка), либо
изменяться пропорционально проценту выполнения плана — равным множителю нижнего порога участка,
умноженному на процент выполнения плана и делённому на 100 — в зависимости от режима, заданного на
нижнем пороге участка. Множитель верхнего порога участка при пропорциональном режиме SHALL не
участвовать в расчёте на этом участке — он начинает влиять на множитель только тогда, когда сам
становится нижним порогом активного участка. Ниже самого нижнего порога множитель SHALL быть равен
нулю.

#### Scenario: Постоянный множитель на участке между порогами
- **WHEN** процент выполнения плана попадает на участок между двумя порогами, и нижний порог этого
  участка задаёт постоянный режим
- **THEN** множитель на всём участке равен множителю, заданному на нижнем пороге участка

#### Scenario: Линейно меняющийся множитель на участке между порогами
- **WHEN** процент выполнения плана попадает на участок между двумя порогами, и нижний порог этого
  участка задаёт линейный режим
- **THEN** множитель на этом участке равен множителю нижнего порога участка, умноженному на процент
  выполнения плана и делённому на 100 (например, при множителе нижнего порога, равном 1, и
  выполнении плана на 96% множитель равен 0.96), независимо от значения множителя верхнего порога
  участка

#### Scenario: Процент ниже самого нижнего порога — множитель равен нулю
- **WHEN** процент выполнения плана меньше значения самого нижнего порога
- **THEN** множитель равен нулю

### Requirement: Округление начислений до целого рубля
Денежные начисления, рассчитываемые как процент от базы, SHALL округляться до целого рубля
математическим округлением (значение 0.5 округляется в большую сторону); правило округления SHALL
быть одинаковым для всех зарплатных правил модуля.

#### Scenario: Дробная часть 0.5 и больше округляется вверх
- **WHEN** расчётное начисление по правилу содержит дробную часть 0.5 рубля или больше
- **THEN** итоговое начисление округляется до ближайшего целого рубля в большую сторону

### Requirement: Зарплатные отчёты сотрудника и отдела
Система SHALL предоставлять зарплатный отчёт по отдельному сотруднику и по отделу в целом за
расчётный период; отчёт по отделу SHALL быть суммой отчётов всех сотрудников этого отдела.

#### Scenario: Отчёт отдела равен сумме отчётов его сотрудников
- **WHEN** запрашивается зарплатный отчёт отдела за период
- **THEN** итоговые суммы отчёта равны сумме соответствующих значений отчётов всех сотрудников этого
  отдела за тот же период

### Requirement: Фактический и прогнозный режимы отчёта
Зарплатный отчёт SHALL поддерживать два независимо рассчитываемых режима — фактический (по уже
свершившимся показателям продаж) и прогнозный (по прогнозируемым показателям продаж); персональная
база сотрудника (не связанная с планом продаж) в прогнозном режиме не экстраполируется.

#### Scenario: Прогнозный режим использует прогноз выполнения плана
- **WHEN** отчёт рассчитывается в прогнозном режиме и зарплатное правило зависит от процента
  выполнения плана продаж
- **THEN** используется прогнозируемый процент выполнения плана, а не фактический на текущий момент

#### Scenario: Персональная база не экстраполируется в прогнозе
- **WHEN** отчёт рассчитывается в прогнозном режиме
- **THEN** значения, не зависящие от плана продаж (например, уже отработанные часы или уже
  выполненные услуги на момент расчёта), берутся как есть, а не проецируются вперёд до конца периода

### Requirement: Правила «процент от факта», «бонус за план» и «бонус за оборачиваемость» не привязаны к транзакциям сотрудника
В отличие от прочих видов зарплатного правила, три вида «процент от факта», «бонус за выполнение
плана продаж» и «бонус за выполнение плана по оборачиваемости» SHALL начислять всю рассчитанную
сумму целиком тому единственному сотруднику, которому назначена мотивационная схема с этим правилом,
без перебора и без сопоставления с отдельными заказами, услугами, задачами или отработанными часами
этого сотрудника.

#### Scenario: Начисление не зависит от количества и роли сотрудника в отдельных транзакциях
- **WHEN** рассчитывается начисление по правилу «бонус за выполнение плана продаж» для сотрудника
- **THEN** сумма начисления определяется только показателями плана продаж за период, а не тем,
  сколько заказов/услуг/задач этот сотрудник выполнил лично за период

### Requirement: Назначение правил уровня отдела/направления только конкретному сотруднику
Правила видов «процент от факта», «бонус за выполнение плана продаж» и «бонус за выполнение плана
по оборачиваемости» SHALL быть доступны для назначения только напрямую конкретному сотруднику (как
персональное правило его мотивационной схемы), а не отделу как таковому.

Для правил «процент от факта» и «бонус за выполнение плана продаж» показатель плана продаж, по
которому считается правило, SHALL относиться к тому отделу, к которому принадлежит назначенный
сотрудник, а не к отдельно указываемому в правиле отделу. Правило «бонус за выполнение плана по
оборачиваемости» от отдела сотрудника не зависит — его scope определяется явно заданным складом
(см. отдельное требование ниже), так как отчёт по оборачиваемости не привязан к оргструктуре отделов.

#### Scenario: Начисление по плану продаж считается по отделу назначенного сотрудника
- **WHEN** сотруднику назначено правило «процент от факта», а сам сотрудник состоит в определённом
  отделе организационной структуры
- **THEN** начисление считается по показателям плана продаж именно этого отдела сотрудника, а не
  какого-либо другого

### Requirement: Категория — единственный настраиваемый scope-параметр правил «процент от факта» и «бонус за план продаж»
Правила видов «процент от факта» и «бонус за выполнение плана продаж» SHALL поддерживать
опциональное ограничение по одной категории; если категория не указана, показатель факта/плана
выручки или маржи SHALL браться по всему отделу целиком, без разбивки по категориям.

#### Scenario: Категория не указана — показатель по всему отделу
- **WHEN** у правила «процент от факта» или «бонус за план продаж» категория не задана
- **THEN** для расчёта используется показатель выручки/маржи по всему отделу сотрудника целиком

#### Scenario: Категория указана — показатель только по ней
- **WHEN** у правила «процент от факта» или «бонус за план продаж» задана конкретная категория
- **THEN** для расчёта используется показатель только этой категории, без учёта остальных категорий
  отдела

### Requirement: Склад — обязательный параметр правила «бонус за выполнение плана по оборачиваемости», категория — опциональный
Правило «бонус за выполнение плана по оборачиваемости» SHALL требовать явного указания склада, к
которому относится план и факт коэффициента оборачиваемости — автоматической привязки сотрудника к
складу в системе нет. Категория внутри этого склада SHALL быть опциональной; если она не указана,
показатель коэффициента оборачиваемости SHALL браться по всему складу целиком (сумма показателей всех
категорий склада — см. `service/goods-turnover`), без разбивки по категориям.

#### Scenario: Правило нельзя создать без указания склада
- **WHEN** создаётся правило «бонус за выполнение плана по оборачиваемости» без указания склада
- **THEN** создание правила отклоняется

#### Scenario: Категория не указана — коэффициент по всему складу
- **WHEN** у правила «бонус за оборачиваемость» указан склад, но не указана категория
- **THEN** для расчёта используется коэффициент оборачиваемости по всему указанному складу целиком

#### Scenario: Категория указана — коэффициент только по ней в рамках склада
- **WHEN** у правила «бонус за оборачиваемость» указаны и склад, и категория
- **THEN** для расчёта используется коэффициент оборачиваемости только этой категории на этом складе

### Requirement: План коэффициента оборачиваемости — часть конфигурации правила «бонус за оборачиваемость»
В отличие от плана продаж по выручке/марже (который берётся из отдельно утверждаемого плана продаж),
плановое значение коэффициента оборачиваемости для правила «бонус за выполнение плана по
оборачиваемости» SHALL задаваться числом непосредственно в конфигурации самого правила при его
создании/редактировании, а не через отдельную сущность плана.

#### Scenario: Изменение планового коэффициента требует редактирования правила
- **WHEN** нужно изменить целевой коэффициент оборачиваемости для правила «бонус за оборачиваемость»
- **THEN** это делается редактированием числового значения в самом правиле, а не через отдельный
  экран плана оборачиваемости

### Requirement: Фактический коэффициент для правила «бонус за оборачиваемость» без категории берётся из итоговой строки склада отчёта
Когда правило «бонус за выполнение плана по оборачиваемости» не ограничено конкретной категорией,
фактический коэффициент оборачиваемости за период SHALL браться из итоговой строки указанного склада
отчёта «Оборачиваемость» (требование «Итоговая строка по складу» capability `service/goods-turnover`)
— без отдельного, самостоятельного расчёта агрегата зарплатным модулем.

#### Scenario: Недостаточно данных — коэффициент не считается, а не приравнивается к нулю
- **WHEN** итоговая строка указанного склада отчёта «Оборачиваемость» не содержит коэффициент (нет
  данных за предыдущий период)
- **THEN** фактический коэффициент для этого правила считается недоступным, а начисление по правилу —
  равным нулю без ошибки расчёта, а не приравнивается к нулевому коэффициенту

### Requirement: Роль «руководитель направления» в каталоге ролей зарплатных правил
Каталог допустимых ролей зарплатных правил направления «Сервис» SHALL включать роль «руководитель
направления»; эта роль SHALL быть доступна только правилам видов «процент от факта», «бонус за
выполнение плана продаж» и «бонус за выполнение плана по оборачиваемости».

#### Scenario: Роль «руководитель направления» недоступна транзакционным видам правил
- **WHEN** при создании правила почасовой оплаты, оплаты за услугу, вознаграждения за заказ или
  оплаты за задачу выбирается роль
- **THEN** роль «руководитель направления» не предлагается как допустимая для этих видов правил

### Requirement: Зарплатное правило и начисление доступны для поиска по идентификатору задачи
Зарплатное правило «за выполнение задачи» и, если оно уже отображается, связанное с ним начисление
за задачу SHALL быть доступны для получения по идентификатору задачи, на которую правило ссылается в
текущем расчётном периоде — без обращения к самой задаче (задача не хранит и не знает о правиле, см.
`tasks#Requirement: Задача — полностью самостоятельная сущность, не знающая о зарплатных правилах`).

#### Scenario: По задаче текущего периода находится ссылающееся на неё правило
- **WHEN** запрашивается зарплатное правило по идентификатору задачи, на которую правило ссылается в
  текущем расчётном периоде
- **THEN** возвращается это правило

#### Scenario: По задаче без правила ничего не находится
- **WHEN** запрашивается зарплатное правило по идентификатору задачи, на которую в текущем расчётном
  периоде не ссылается ни одно правило
- **THEN** правило не возвращается

#### Scenario: Начисление возвращается только когда оно уже отображается
- **WHEN** запрашивается начисление по идентификатору задачи, связанная с которой задача ещё не
  переведена в статус «Закрыта успешно»
- **THEN** начисление не возвращается, хотя связанное правило может быть найдено

### Requirement: Зарплатное правило доступно для получения по собственному идентификатору
Зарплатное правило SHALL быть доступно для получения по собственному идентификатору — без загрузки
всей мотивационной схемы, к которой оно принадлежит.

#### Scenario: Правило получено по своему идентификатору
- **WHEN** запрашивается зарплатное правило по его идентификатору
- **THEN** возвращается это правило (вид, роль, направление, параметры) без остальных правил
  мотивационной схемы

#### Scenario: Запрос несуществующего правила не находит результата
- **WHEN** запрашивается зарплатное правило по идентификатору, которому не соответствует ни одно
  существующее правило
- **THEN** правило не возвращается

### Requirement: Удаление мотивационной схемы направления «Сервис»
Пользователь SHALL иметь возможность полностью удалить мотивационную схему направления «Сервис» по
её идентификатору. Удаление необратимо — soft-delete не поддерживается. Удаление схемы одного
направления SHALL не затрагивать правила или имя другого направления той же физически общей строки
`motivation_schemas`; родительская строка SHALL удаляться только когда после удаления правил своего
направления у неё не осталось правил другого направления.

#### Scenario: Удаление схемы по id
- **WHEN** пользователь запрашивает удаление мотивационной схемы направления «Сервис» по
  существующему id
- **THEN** схема и все её зарплатные правила направления «Сервис» удаляются безвозвратно

#### Scenario: Удаление не затрагивает правила другого направления той же общей строки
- **WHEN** удаляется мотивационная схема направления «Сервис», а физически общая строка также
  содержит правила направления «Магазин»
- **THEN** правила и имя направления «Магазин» остаются нетронутыми, родительская строка не
  удаляется
