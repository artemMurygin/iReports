## Ключевые состояния экранов

Новые виды правила (FR2–FR4) и новая роль (FR1) реально меняют состав полей карточки правила внутри `SalaryRuleForm` — эти состояния показывают конкретный набор полей на выбор значения «Тип правила». Для наглядности каждое состояние вынесено отдельной карточкой-примером на канвас (top-level фрейм `oxTEG` — «Новые виды зарплатных правил уровня отдела/направления», ниже `tSYIw` на канвасе), а не только описано текстом — исполнители читают точную структуру полей через `execute`/`Get` по указанным Node ID. Правила применяются к `service` и `shop` идентично (архитектура, п. «Frontend — UI Model»), поэтому один визуальный пример на карточку покрывает оба направления.

## Отклонения от architecture.md

- **Мобильный артборд.** В файле не было существующего мобильного артборда для общей карточки правила `SalaryRuleForm` (мобильные варианты были только для отдельной страницы одного конкретного вида правила — «задача», `aS8yc`). По подтверждению пользователя мобильная поддержка для новых видов правил нужна — спроектированы 3 отдельных мобильных экрана-примера (390px, см. таблицу выше), поля выстроены в один столбец компонентом `z5csS` (ERP/Mobile/Field) вместо построчной десктопной раскладки; хедер/футер карточки переиспользуют существующий мобильный Sheet-паттерн (`PJnfQ`/`nwUGC` — Sheet Header/Actions).
- **Блок «Вариант награды» не переиспользован для FR2–FR4.** По подтверждению пользователя это ожидаемый UX: architecture.md моделирует 3 новых вида как самостоятельные entity-классы (не параметризованные award-осью), поэтому каждому значению «Тип правила» соответствует фиксированный набор полей без отдельного выбора «Вариант награды» (в отличие от 4 существующих видов правил, где такой селектор есть).
- Название правила в примерах — иллюстративный текст-плейсхолдер (например, «Премия за выполнение плана выручки»); реальные значения вводятся пользователем свободным текстом, как и в существующих 4 видах.
