## Context

Driven by FR1–FR5 from proposal.md.

Все существующие виды зарплатных правил (`PayPerHour`, `ServiceCompleted`/`ProductSold`,
`OrderPayed`/`UsedProductSold`, `TaskCompletion`) — транзакционные: они матчат роль сотрудника на
поля конкретного заказа/отгрузки/задачи (`role-source.ts`) и считаются по перебору таких транзакций
за период. У правил вида `FloatPercent` (например `ProductSoldEntity.calculate()`) есть
scope-параметр `category: string | null` (null = без фильтра по категории), но параметр
`department`, с которым реально резолвится `SalesPerformance` (`findForScope(period, department,
category)`), в конфиг правила не входит — он резолвится отдельно, на уровне
`BuildShopCalculationContextService`/`BuildServiceCalculationContextService`, вызовом
`findEmployeeDepartmentId(employeeId)`: department — это **собственный** `BitrixEmployee.departmentId`
сотрудника, которому принадлежит правило, а не что-то настраиваемое в самом правиле.

Это ключевое ограничение существующей архитектуры, которое определяет форму новых правил: department
для `SalesPerformance` неизбежно берётся из орг-структуры Bitrix24 того сотрудника, кому назначено
правило — обойти это без изменения `Build*CalculationContextService` нельзя.

Отчёт «Оборачиваемость» вообще не знает о `department` — его строки скоуплены только по
`categoryId` × `warehouseId`, план коэффициента оборачиваемости как отдельная сущность в системе не
существует. Ответ `GET .../goods-turnover-report/:period` уже сегодня различается по форме между
доменами: у **service** — `{period, lines}`, строка денормализована (`categoryName`,
`categoryParentId`, `warehouseName` уже в строке); у **shop** — голый массив строк без денормализации
(её достраивает frontend отдельным запросом каталога). Итоговая строка «по складу» (сумма/остаток/
коэффициент) существует уже сегодня, но **только на frontend**
(`summarizeGoodsTurnoverRows`/`summarizeShopGoodsTurnoverRows`, идентичная формула в обоих доменах):
сумма показателей только по «настоящим корневым» категориям склада (`categoryParentId === null` —
не суммировать все строки, иначе задвоятся показатели подкатегорий, уже включённые в показатель
родителя) + средневзвешенный по остатку коэффициент (`Σ ratio_i·stock_i / Σ stock_i`, только строки
с посчитанным коэффициентом, `null` если таких нет). У service «настоящий корень» уже виден прямо в
строке (`categoryParentId`); у shop то же самое поле есть только в справочнике категорий
(`MoySkladProductFolder.parentId`), не в самой строке отчёта — backend сегодня это никак не
использует (строит отчёт по всем папкам плоско, без понятия «корень»).

`service` и `shop` — независимые по коду домены (см. `backend/CLAUDE.md`), общий код между ними
ограничен `src/shared/*`; открытый параллельный change `extract-shared-salary-calculation` (ещё не
заархивирован) выносит `float-percent`/`money`/`scopeKey` в общий `src/shared/salary-calculation/`, но
на момент этого change ещё не применён.

Правило проекта (`CLAUDE.md`, «Межмодульные зависимости внутри backend»): модулю, которому нужны
данные другого модуля (даже соседнего внутри одного домена — как здесь `accounting` и `warehouse`),
запрещено импортировать чужой сервис/репозиторий напрямую; вместо этого модуль-потребитель заводит
собственную entity, восстанавливаемую из БД через свой собственный repository-порт, читающий те же
физические таблицы. Это прямо определяет форму Decision 6 ниже.

Существующая доменная модель отчёта неоднородна между доменами: у **service** уже есть агрегат
`GoodsTurnoverReport` (`period` + `lines`, только структурные инварианты — принадлежность периоду и
уникальность пары категория-склад), но он используется только на write-стороне (пересчёт/закрытие
периода); read-путь (`GetGoodsTurnoverReportService.get()`) сегодня восстанавливает только плоский
список `GoodsTurnoverReportLine[]`, без агрегата. У **shop** объединяющего агрегата за период нет
вовсе — согласно явно задокументированному в самом entity-файле решению, каждая строка
(категория×склад) является самостоятельным агрегатом; агрегация коэффициента там уже сегодня
оформлена отдельным VO (`TurnoverCoefficient.calculate()`), вызываемым из application-сервиса, а не
методом какого-либо агрегата.

## Goals / Non-Goals

**Goals:**
- Добавить 3 новых вида зарплатного правила, не привязанных к перебору транзакций, а считающихся по
  агрегированным показателям отдела/направления (`SalesPerformance`, коэффициент оборачиваемости).
- Переиспользовать существующий механизм плавающего коэффициента (`percentBorders`,
  `resolveFloatPercentMultiplier`/`FloatPercentSchedule`) без изменения его формулы.
- Добавить роль «руководитель направления» без новой инфраструктуры (без синка Bitrix `UF_HEAD`, без
  новой сущности «глава отдела»).
- Отчёт «Оборачиваемость» (оба направления) сам считает и отдаёт итоговую строку по складу — вместо
  того чтобы это дублирующим образом делал только frontend.

**Non-Goals:**
- Не вводится понятие «руководитель отдела» как сущность/связь в домене — назначение полностью
  ручное, через уже существующий `MotivationSchema.targetType = 'Employee'`.
- Не меняется формула плавающего коэффициента (FR2–FR4) и не меняется формула самого коэффициента
  оборачиваемости или период его расчёта — меняется только то, что итог по складу считается один раз
  на backend, а не дублируется на frontend.
- Не вводится понятие «основной склад»/ограничение глубины категорий для shop — это различие
  service/shop (см. Context) остаётся как есть, итог считается по одной и той же логике («сумма по
  настоящим корневым строкам») в обоих доменах поверх их сегодняшнего набора строк.
- Не документируется в этом change документ начисления (`SalaryAccrual`/`Payout`) и не меняется его
  поведение — новые правила участвуют в нём так же, как любой другой вид правила.
- Не решается пересечение с `extract-shared-salary-calculation` кодом — новые правила реализуются по
  сегодняшнему, дублирующему шаблону (см. Decision 5).

## Decisions

### 1. Назначение правила — `targetType = 'Employee'`, department — implicit через Bitrix (только FR2/FR3)

Это решение касается только `DepartmentPercent` (FR2) и `DepartmentPlanBonus` (FR3) — оба считаются
через `SalesPerformance`, скоуплен по (department, category). `DepartmentTurnoverBonus` (FR4) вообще
не использует `department` — оборачиваемость скоуплена по (category, **warehouse**), а не по отделу,
поэтому у него свой явный `warehouseId` в конфиге (см. Decision 2) вместо implicit-резолвинга.

Правило «руководителя» назначается напрямую сотруднику (`MotivationSchema.targetType = 'Employee'`,
`targetId = <employeeId>`), а не через `targetType = 'Department'` с новым role-матчингом. Scope
внутри самого правила — **только** `category: string | null` (null = без фильтра, «весь склад/
направление»), в точности форма `ProductSoldEntity.config.category` — без отдельного поля
`departmentId`.

`department`, с которым резолвится `SalesPerformance`, при этом остаётся собственным
`BitrixEmployee.departmentId` того сотрудника, которому назначена схема (существующий механизм
`findEmployeeDepartmentId`, без изменений) — то есть корректность работы правила зависит от того,
что в Bitrix24 у сотрудника-руководителя проставлен тот отдел, чей план он должен видеть. Это
осознанное ограничение (см. Risks), альтернатива — заводить явный `departmentId` в конфиге правила —
отклонена, чтобы не расходиться с уже устоявшимся паттерном `ProductSold`/`OrderPayed` и не
дублировать резолвинг department в двух местах.

**Альтернатива (отклонена):** синхронизировать `UF_HEAD` из Bitrix24, завести домен-сущность «глава
отдела» и новый role-source по отделу — существенно больше инфраструктуры, не даёт автоматической
актуальности (смена руководителя в Bitrix не должна автоматически покупать) — уже сформулировано как
NG в проекте (`openspec/specs/roles/spec.md`: «Роли и права Bitrix24 не становятся ролями iReports»,
тот же принцип применён здесь по аналогии).

### 2. Три новых вида правила — не транзакционные, без роли в `calculate()`

Все три новых вида (`DepartmentPercent`, `DepartmentPlanBonus`, `DepartmentTurnoverBonus`) не
итерируют заказы/задачи/часы и не вызывают `role-source.ts` — они читают агрегат за период (факт
`SalesPerformance`, коэффициент оборачиваемости) и всегда считаются целиком на того единственного
сотрудника, кому назначена схема правила. Поле `targetRole` в `SalaryRule` у них при этом сохраняется
(для консистентности схемы и для каталога ролей в UI — см. Decision 4), но не участвует в логике
`calculate()`.

Формулы:
- **`DepartmentPercent`** (FR2): `amount = round(fact.(turnover|margin для category) * percent / 100)`
  — без коэффициента.
- **`DepartmentPlanBonus`** (FR3): `amount = round(fixedAmount * resolveFloatPercentMultiplier(
  percentBorders, percentCompletion для category))` — тот же `percentBorders`/multiplier, что уже
  используют `OrderPayed`/`TaskCompletion`/`ProductSold`.
- **`DepartmentTurnoverBonus`** (FR4): `amount = round(fixedAmount * resolveFloatPercentMultiplier(
  percentBorders, (factTurnoverRatio / planTurnoverRatio) * 100))`, где `planTurnoverRatio` — число из
  конфига самого правила (не отдельная сущность плана), `factTurnoverRatio` — из Decision 6.
  Конфиг дополнительно содержит **обязательное** `warehouseId` (склад, на котором считается
  оборачиваемость — без него неизвестно, к какому из потенциально нескольких складов направления
  относится план/факт) и опциональное `category` (тот же по смыслу scope-параметр, что и у FR2/FR3,
  см. Decision 1) — при `category = null` берётся итог по всему складу (Decision 6), иначе —
  конкретная категория этого склада.

### 3. Расширение расчётного контекста: `salesPerformance`-карта отдаёт факт, не только percentCompletion

Сегодня `context.salesPerformance` (обоих доменов) — это `Map<category, number>`, где число — уже
готовый `percentCompletion`; `fact.turnover`/`fact.margin` до контекста не доходят (отбрасываются на
этапе построения контекста), хотя `GetSalesPerformanceService`/`GetShopSalesPerformanceService` их уже
вычисляют. Для `DepartmentPercent` (FR2, нужен именно факт, не процент выполнения) значение карты
меняется на `{ fact: { turnover, margin }, percentCompletion }` — без нового запроса к данным, только
без отбрасывания уже вычисленных полей при построении карты в `Build*CalculationContextService`.
Существующие потребители карты (`ProductSold`/`OrderPayed`/`TaskCompletion` — только
`percentCompletion`) обновляются на `.percentCompletion` вместо прямого числа.

### 4. Новая роль в общем `targetRoleSchema` + оба каталога, без нового role-source

Новый литерал (например `HEAD`, точное имя — открытый вопрос архитектуры) добавляется в общий
`targetRoleSchema` (`contracts/commands/salary-rule.ts`) по аналогии с существующими ролями, и в
`ALL_SERVICE_ROLES`/`ALL_SHOP_ROLES` — единственная цель добавления в каталог — чтобы UI показывал
роль как опцию для 3 новых видов правил; `role-source.ts` (`employeeMatchesServiceRole`/
`employeeMatchesShopDemandRole`) не расширяется, так как новые виды правил не вызывают эти функции.

### 5. Реализация — независимо по доменам, без ожидания `extract-shared-salary-calculation`

3 новых вида правила реализуются отдельно в `domains/service/modules/accounting/domain/entities/
salary-rules/` и `domains/shop/modules/accounting/domain/entities/salary-rules/`, каждый использует
свой существующий `resolveFloatPercentMultiplier`/`FloatPercentSchedule` (дублирование, как сегодня у
`OrderPayed`/`ProductSold`) — этот change не блокируется и не блокирует
`extract-shared-salary-calculation`. Если тот change будет заархивирован раньше, новые файлы при
следующем рефакторинге просто переключаются на общий модуль вместе с остальными вызовами
`float-percent` — отдельная последующая работа, не в рамках этого change.

### 6. Итог по складу — в двух местах независимо: сам отчёт (FR5) и своя entity в `accounting` (FR4), без вызова между ними

Два разных потребителя одной и той же формулы (Context: сумма по «настоящим корневым» строкам +
средневзвешенный по остатку коэффициент) — публичный ответ отчёта «Оборачиваемость» (`warehouse`) и
зарплатное правило `DepartmentTurnoverBonus` (`accounting`). Правило проекта из Context запрещает
второму читать первый напрямую — поэтому формула реализуется **дважды**, независимо, как и весь
остальной код `service`/`shop` (Decision 5), только на этот раз ось дублирования — «модуль», а не
«домен».

**(a) Внутри `warehouse` — для самого ответа отчёта (FR5):**
- **service**: доменный агрегат `GoodsTurnoverReport` (сегодня используется только на write-стороне,
  Context) получает новый метод `totals(): GoodsTurnoverWarehouseTotal[]` — считает `totals` по
  своим `lines` (критерий корня уже виден на строке — `categoryParentId === null`). `GetGoodsTurnoverReportService.get()` начинает **восстанавливать сам агрегат** через репозиторий (а не только
  плоский список строк) и вызывает `.totals()` — сумма/коэффициент больше не считаются инлайн в
  application-сервисе.
- **shop**: объединяющего агрегата нет и не планируется (осознанное решение, Context) — итог
  оформляется отдельным VO `GoodsTurnoverWarehouseTotal.calculate(lines)` в `domain/value-objects/`
  (по образцу уже существующего `TurnoverCoefficient`), вызываемым из
  `GetGoodsTurnoverReportService.getReport()`; критерий корня для shop-строки требует отдельного
  запроса корневых `MoySkladProductFolder.id` (`parentId IS NULL`), так как сама строка `parentId` не
  несёт.

Ответ обоих эндпоинтов меняется: **service** — аддитивно `{period, lines, totals}`; **shop** — со
сменой формы (**BREAKING**, proposal.md FR5) `{lines, totals}`.

**(b) Внутри `accounting` — для правила `DepartmentTurnoverBonus` (FR4), без обращения к `warehouse`:**
`accounting` каждого домена заводит собственную entity `TurnoverReportSnapshot` (per domain, своя
реализация), восстанавливаемую через собственный новый repository-порт
(`TURNOVER_REPORT_REPOSITORY`/`SHOP_TURNOVER_REPORT_REPOSITORY`), который читает **те же физические
таблицы**, что и `warehouse` (`goods_turnover_report_lines`/`moy_sklad_turnover_report_lines`), но
через свой собственный Prisma-делегат — ровно так же, как `service`/`shop` уже обращаются к общим
таблицам типа `SalesPlan` независимыми классами (`backend/CLAUDE.md`, «Общие таблицы между `service`
и `shop`»), только здесь общая таблица — между модулями одного домена, а не между доменами. Формула
агрегации (сумма по корневым строкам + средневзвешенный коэффициент) реализуется внутри `accounting`
второй раз, своим VO — независимо от VO/метода из пункта (a).

Зарплатное правило `DepartmentTurnoverBonus`: при `category = null` — берёт агрегат по всему складу
из своей `TurnoverReportSnapshot` (собственный расчёт, не вызов `warehouse`); при заданной `category`
— берёт коэффициент конкретной строки из той же, самостоятельно восстановленной entity.

**Альтернатива (отклонена):** `accounting` вызывает `GetGoodsTurnoverReportService`/использует
общий порт `warehouse`-модуля (так было в предыдущей версии design.md). Отклонена — прямо нарушает
правило проекта из Context (см. root `CLAUDE.md`): межмодульные данные — только через собственную
entity потребителя, восстановленную из БД, а не через вызов чужого сервиса, даже в границах одного
домена.

## Risks / Trade-offs

- **[Risk]** Department для `SalesPerformance` резолвится через собственный `BitrixEmployee.
  departmentId` сотрудника-руководителя (Decision 1) — если в Bitrix24 у него по ошибке или по
  оргструктуре указан не тот отдел, правило будет молча считать по чужому плану, а не по нужному
  направлению. → **Mitigation**: на этапе создания правила (architecture/ui-design) предупреждать в
  UI, если у выбранного сотрудника нет плана продаж по его текущему Bitrix-отделу за текущий период.
- **[Risk]** План коэффициента оборачиваемости хранится в конфиге каждого отдельного правила
  (Decision 2), не в едином месте — при изменении цели по обороту руководителю нужно вручную
  поменять значение в каждом правиле, где оно упомянуто, риска несогласованности. →
  **Mitigation**: осознанный trade-off по прямому решению пользователя (см. proposal), а не
  недосмотр; при накоплении нескольких таких правил можно вынести в отдельную сущность отдельным
  последующим change.
- **[Risk]** Параллельный `extract-shared-salary-calculation` меняет те же файлы `float-percent.ts`
  (service) — при слиянии веток возможен конфликт. → **Mitigation**: обычный rebase; т.к. новый код
  только *вызывает* существующие публичные функции, а не меняет их, конфликт ожидается
  тривиальным (не семантическим).
- **[Risk]** Смена формы ответа `GET .../shop/warehouse/goods-turnover-report/:period` с голого
  массива на `{lines, totals}` (Decision 6, **BREAKING**) ломает любой код, ожидающий массив
  напрямую. → **Mitigation**: единственный сегодняшний потребитель — frontend этого же
  приложения, обновляется в этом же change; внешних клиентов у эндпоинта нет.
- **[Risk]** У правила `DepartmentTurnoverBonus` `warehouseId` — обязательное явное поле без
  автопроверки (в отличие от department, который берётся из Bitrix-профиля сотрудника) — можно
  выбрать склад, на котором план/факт не формируются. → **Mitigation**: та же UI-подсказка, что и в
  риске выше про department (Q2, `ui-design.md`) — предупреждать, если для выбранного склада/периода
  нет данных отчёта.
- **[Risk]** Формула «итог по складу» теперь дублируется дважды (в `warehouse` для отчёта, в
  `accounting` для правила) вместо одного внутреннего агрегата, который читал бы уже готовый расчёт
  `warehouse` (Decision 6, пункт b) — больше поверхности для расхождения при будущих изменениях
  формулы. → **Mitigation**: осознанный trade-off, продиктованный правилом проекта о межмодульных
  зависимостях (root `CLAUDE.md`); зафиксировать формулу в спеках обоих капабилити
  (`*/goods-turnover`, `*/accounting`) и тестами с одинаковыми фикстурами по обе стороны, чтобы
  расхождение было заметно в code review.

## Migration Plan

Миграция БД не требуется — `SalaryRule.type`/`props` уже `String`/`Json` без enum на уровне схемы,
новый вид правила — это новое значение `type` и новая форма `props`, валидируемая только на уровне
Zod-контракта. Аналогично `targetRoleSchema` — просто новый литерал enum'а на уровне контракта, без
изменений Prisma-схемы.

Раскатка — чистый деплой нового кода (contracts → backend → frontend); откат — откат деплоя, так как
пока нет ни одной созданной записи `SalaryRule` нового вида, откатывать данные не нужно. После первого
использования в проде откат уже невозможен без явной миграции данных (как и для любого существующего
вида правила) — это стандартное для проекта поведение, не специфичное для этого change.

Смена формы ответа shop-отчёта (Decision 6) не требует отдельной координации раскатки — contracts,
backend и frontend монорепозитория деплоятся вместе, промежуточного состояния «старый frontend читает
новый backend» не возникает.
