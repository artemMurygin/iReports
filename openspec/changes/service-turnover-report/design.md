## Context

См. `proposal.md` — «Why» за мотивацией. Технический контекст, важный для выбора решения:

- В `domains/service/CLAUDE.md` модуль `warehouse` (склад/остатки) уже заявлен как целевой, но пока
  не существует («Не существует»). Этот change — первая функциональная часть этого модуля.
- Справочник категорий товаров уже синхронизируется из RoApp: `RoappProductCategory` (`id`, `name`,
  `parentId`, `prisma/schema/roapp.prisma`) — иерархия parent/child уже есть в БД. Синк выполняется
  только разовой командой `npm run initial` (`uploadProductCategories()` в `roapp-sync.service.ts`),
  а не 5-минутным кроном.
- Справочника складов в проекте пока нет нигде: ни отдельной Prisma-модели, ни обёртки в
  `integrations/roapp`. `warehouseId` встречается только в сыром типе `orderItems.schema.ts`
  (списание со склада заказа), но не персистится.
- Кастомный RoApp-эндпоинт `POST /getGoodsFlowReport` (интеграция `custom-api-roapp`, транспорт для
  собственного бэкенда-компаньона RoApp) принимает `startDate`/`endDate` (unix ms), `category_id`
  (одна категория) и `warehouses` (массив ID) и отдаёт агрегаты `outcome`/`stock` (`quantity`,
  `sum`) — то есть один вызов = один срез "категория × набор складов", а не сразу дерево/все склады.
- Существующий аналог "период + снэпшот при закрытии" — `AccountingPeriod`/`AccountingPeriodSnapshot`
  (`domains/service/modules/accounting`). Это зарплатный период, привязанный к `direction` и
  бизнес-условиям закрытия (утверждённый план продаж, истёкший период). По прямому указанию
  пользователя отчёт по оборачиваемости не заводит собственную таблицу/статус периода, а
  переиспользует статус именно этой таблицы (см. D5) — читает её через
  `ACCOUNTING_PERIOD_REPOSITORY`, ничего в неё не пишет.
- Закрытие `AccountingPeriod` публикует `AccountingPeriodClosedDomainEvent` (`direction`, `period`,
  `closedBy`, `employeeCount`) как доменное событие агрегата — `AccountingPeriod.close()` регистрирует
  его, событие реально доходит до `EventEmitter2` после коммита транзакции закрытия (см. тест
  `AccountingPeriodClosedEventHandler`). Уже есть один подписчик в самом модуле `accounting`
  (`@OnEvent('AccountingPeriodClosedDomainEvent')`, сейчас — временный лог-хендлер); ничто не мешает
  модулю `warehouse` подписаться на то же событие вторым независимым обработчиком — `@nestjs/cqrs`/
  `EventEmitter2` поддерживают несколько подписчиков на одно событие.
- По требованию заказчика закрытие отчёта по оборачиваемости — не самостоятельное действие
  пользователя над этим отчётом, а следствие закрытия расчётного (зарплатного) периода направления
  «Сервис» за тот же месяц: когда бухгалтер/руководитель закрывает зарплатный период, отчёт по
  оборачиваемости за этот же месяц должен зафиксироваться и перестать пересчитываться.

## Goals / Non-Goals

**Goals:**
- Определить архитектуру backend-модуля, который собирает, хранит и отдаёт отчёт по оборачиваемости
  за месяц по дереву категорий и складам.
- Определить, как получать недостающий справочник складов.
- Определить, как отслеживать открытый/закрытый месяц, переиспользуя статус `AccountingPeriod`
  вместо собственной таблицы периода.

**Non-Goals:**
- Не проектируем модули `purchasing`/`logistics` — только тот срез `warehouse`, который нужен для
  этого отчёта.
- Не проектируем UI (см. `ui-design.md`).
- Не добавляем запись данных обратно в RoApp — модуль read-only относительно ERP.
- Не переносим существующий синк `RoappProductCategory` на 5-минутный крон — вне скоупа.

## Decisions

### D1. Новый модуль `domains/service/modules/warehouse`, слоистость как у `accounting`/`sales`
Первая часть заявленного, но не реализованного модуля `warehouse` (см. `domains/service/CLAUDE.md`,
раздел «Целевой набор модулей домена»). Слои `domain/application/infrastructure/interface` — по
образцу `accounting`. Файлы без слова `service` в имени (правило домена).

**Альтернатива**: положить отчёт в `modules/accounting` или `modules/reports`. Отклонено — отчёт не
про зарплату и не про проданные услуги, а про остатки/расход товара; для него по документации домена
уже зарезервирован отдельный модуль.

### D2. Клиент к `getGoodsFlowReport` — новый метод в `CustomApiRoappService`, за портом `ROAPP_GATEWAY`
Метод `getGoodsFlowReport(params)` добавляется в
`integrations/custom-api-roapp/custom-api-roapp.service.ts` (по образцу существующих методов —
Zod-схема ответа, `BadGatewayException` при сбое), пробрасывается через
`RoappGatewayPort`/`RoappGatewayAdapter`. Модуль `warehouse` зависит только от `ROAPP_GATEWAY`, не от
конкретного сервиса — общее правило домена для потребителей RoApp-данных.

### D3. Справочник складов — новая Prisma-модель `RoappWarehouse` + синк из публичного API RoApp
Добавляется модель `RoappWarehouse` (`id`, `name`) в `roapp.prisma`, метод получения списка складов в
`integrations/roapp/roapp.service.ts` (аналог `fetchProductCategories`) и апсерт в
`roapp-sync.service.ts` (`uploadWarehouses()`), подключаемый в тот же разовый `npm run initial`, что
и категории (не в 5-минутный крон — по аналогии с категориями).

**Допущение, требующее проверки на этапе реализации**: публичный REST API RemOnline отдаёт список
складов отдельным ресурсом (аналогично категориям/сотрудникам). Если это не так — потребуется другой
источник (см. «Риски»).

**Альтернатива**: захардкодить список складов конфигурацией. Отклонено — противоречит требованию
проposal «формируется по каждому складу» без ручного сопровождения списка при появлении нового
склада.

### D4. Построение отчёта — перебор дерева категорий × складов, один вызов ERP-эндпоинта на пару
Сервис приложения строит отчёт месяца, рекурсивно обходя `RoappProductCategory` (все категории и
вложенные) и весь список `RoappWarehouse`, и для каждой пары «категория-склад» вызывает
`getGoodsFlowReport` с этой одной категорией и единственным складом в `warehouses`, за диапазон дат
месяца. Построчные результаты полностью перезаписывают строки периода (не инкрементальное
обновление) — так пересчёт всегда согласован с последним ответом ERP.

**Коэффициент оборачиваемости (уточнение пользователя)**: по каждой позиции (категория × склад)
дополнительно считается `расход(тек.мес, ₽) / ((остаток(прошл.мес, ₽) + остаток(тек.мес, ₽)) / 2)` —
**в рублях (по сумме)**, не в штуках, хотя обе метрики хранятся в обеих единицах (уточнение
пользователя). Остаток прошлого месяца по той же паре категория-склад читается из уже сохранённых
строк `GoodsTurnoverReportLine` за период `period - 1` (`GOODS_TURNOVER_REPORT_LINE_REPOSITORY.findByPeriod`)
— **без** дополнительных вызовов `getGoodsFlowReport` (данные прошлого месяца уже были получены и
сохранены при его собственном построении/закрытии). Если строки за прошлый месяц по этой паре нет,
или средний остаток равен нулю, — коэффициент не рассчитывается (`null`), а не подставляется 0 (см.
`service/goods-turnover` спек). Расчёт — метод сущности `GoodsTurnoverReportLine.calcRatio(stockPreviousSum:
number | undefined): number | null` (по указанию пользователя: метод на самой сущности, а не отдельный
доменный сервис/калькулятор) — чистый, без побочных эффектов и портов; вызывается из
`BuildGoodsTurnoverReportService` после того, как строка собрана из ответа ERP.

### D5. Хранение — только строки отчёта; статус периода не дублируется, читается из `AccountingPeriod`
Вводится ровно одна новая таблица — `GoodsTurnoverReportLine` (`period` — строка `YYYY-MM`,
`categoryId`, `warehouseId`, `outcomeQuantity`, `outcomeSum`, `stockQuantity`, `stockSum`,
уникальный индекс `(period, categoryId, warehouseId)`). Собственной таблицы/сущности «период отчёта
по оборачиваемости» со своим статусом **нет** — открыт месяц или закрыт, определяется чтением уже
существующей `AccountingPeriod` направления `service` за тот же месяц (порт
`ACCOUNTING_PERIOD_REPOSITORY` из `modules/accounting`, метод `findByDirectionAndPeriod('service',
period)`): нет записи или `.isOpen()` — месяц открыт, пересчёт разрешён; `.isClosed()` — пересчёт
пропускается, отдаются уже сохранённые строки как снэпшот. Пересчёт открытого месяца полностью
заменяет его строки в `GoodsTurnoverReportLine`.

**Указание пользователя**: не заводить отдельную таблицу периода для отчёта по оборачиваемости —
использовать таблицу `AccountingPeriod`. Технически это означает не связь по внешнему ключу (та
таблица — агрегат другого модуля/предметной области, см. D1), а чтение её статуса через
`ACCOUNTING_PERIOD_REPOSITORY` — модуль `warehouse` не пишет в `AccountingPeriod`, только читает.
Такая межмодульная зависимость на порт другого модуля в пределах домена `service` уже встречается
(`CloseAccountingPeriodHandler` зависит от `SALES_PLAN_REPOSITORY` модуля `sales`) — не нарушение
границы `service`/`shop` (см. `backend/CLAUDE.md`).

Механика на уровне Nest DI — по образцу того, как `AccountingModule` уже получает `SALES_PLAN_REPOSITORY`
от `SalesModule` (`accounting.module.ts`: `imports: [SalesModule, ...]`, `SalesModule` явно
экспортирует `SALES_PLAN_REPOSITORY` в своём `exports: [...]`): `WarehouseModule` делает
`imports: [AccountingModule]` и инжектит `ACCOUNTING_PERIOD_REPOSITORY`. Готовых `exports` у
`AccountingModule` для этого сейчас нет — модуль вообще не экспортирует провайдеров (`exports` в его
`@Module(...)` отсутствует), так что первым шагом реализации нужно добавить `ACCOUNTING_PERIOD_REPOSITORY`
в `exports` `AccountingModule` (маленькое, аддитивное изменение существующего модуля).

**Ранее рассмотренная и отклонённая альтернатива**: собственная `GoodsTurnoverPeriod` (месяц + статус
`OPEN`/`CLOSED`), синхронизируемая обработчиком события с `AccountingPeriod`. Отклонено — дублировала
бы статус, который и так уже есть в `AccountingPeriod`, требуя ручной синхронизации при закрытии *и*
при переоткрытии (см. D7 и снятый благодаря этому решению открытый вопрос про reopen ниже).

**Альтернатива**: зеркалировать `AccountingPeriodSnapshot` (отдельная таблица-копия, создаваемая при
закрытии). Отклонено — там снэпшот нужен, потому что отчёт «после закрытия» может отличаться по
составу от «живого» отчёта (прогнозный режим, пересчитываемые правила); здесь строки отчёта — это
всегда один и тот же формат данных, полностью перезаписываемых при каждом пересчёте, поэтому статус
`AccountingPeriod` уже даёт нужную гарантию неизменности без отдельной схемы хранения периода.

### D6. Пересчёт — крон раз в час, только пока `AccountingPeriod` этого месяца не закрыт
Новая крон-задача (`@ProdCron(CronExpression.EVERY_HOUR)`, `src/shared/cron/prod-cron.decorator.ts`)
в `modules/warehouse/infrastructure/cron/`, обёрнутая в `runInSystemRequestContext` (крон выполняется
вне HTTP-запроса — по аналогии с `SalesPlanAutoCreationCron`). Для текущего месяца читает статус
`AccountingPeriod` направления `service` (см. D5); если период закрыт — пересчёт этого месяца
пропускается (после закрытия его уже обновил обработчик события, см. D7), иначе пересчитывает (D4).
Ошибка вызова ERP на отдельной паре категория-склад не должна прерывать весь пересчёт целиком
(частичный успех лучше, чем полный сбой крона из-за одного проблемного склада/категории) — по
аналогии с try/catch в `RoappSyncCron`.

### D7. Закрытие — не отдельное действие, а подписка на `AccountingPeriodClosedDomainEvent`
У отчёта по оборачиваемости нет собственной команды/эндпоинта «закрыть месяц» и собственного статуса
периода (см. D5) — статус целиком определяется `AccountingPeriod`. Модуль `warehouse` регистрирует
обработчик, подписанный на уже существующее `AccountingPeriodClosedDomainEvent`
(`@OnEvent('AccountingPeriodClosedDomainEvent')`, как у соседнего лог-хендлера в `accounting`), и
реагирует только когда `event.direction === 'service'`: строит отчёт за `event.period` последний раз
по актуальным данным (тот же путь, что и часовой пересчёт, D4) и сохраняет пересчитанные строки в
`GoodsTurnoverReportLine` — чтобы зафиксированный снэпшот отражал самые свежие данные на момент
закрытия, а не устаревшие с последнего часового тика. Никакого отдельного статуса выставлять не
нужно: как только `AccountingPeriod` закрыт, крон (D6) сам перестаёт трогать этот период.

**Альтернатива**: независимый `POST /goods-turnover-report/:period/close`, вызываемый пользователем
из UI отчёта по оборачиваемости. Отклонено по прямому указанию: закрытие должно быть следствием
закрытия зарплатного периода того же месяца/направления, а не отдельным действием — иначе возможна
рассинхронизация (зарплатный период закрыт, а отчёт по оборачиваемости — ещё нет, или наоборот).

**Компромисс, принимаемый осознанно**: жизненный цикл отчёта по оборачиваемости становится зависим
от бизнес-условий закрытия зарплатного периода (утверждённый план продаж, истёкший период — см.
`service/accounting`), не имеющих отношения к остаткам/расходу товара. Если зарплатный период за
месяц никогда не закрывается — отчёт по оборачиваемости за этот месяц тоже никогда не
зафиксируется и продолжит пересчитываться почасово. Это принимается как заданное поведение, а не
дефект.

### D8. HTTP-поверхность
- `GET /v1/service/warehouse/goods-turnover-report/:period` (`period` = `YYYY-MM`) — строки отчёта
  за месяц (текущий открытый или любой уже посчитанный прошлый). Собственного эндпоинта закрытия нет
  (см. D7).
- Справочные `GET`-эндпоинты дерева категорий товаров и списка складов для построения UI (иначе
  фронтенду негде взять `parentId`/названия для построения дерева и списка складов).

## Risks / Trade-offs

- [Риск] Коэффициент оборачиваемости зависит от уже сохранённых строк прошлого месяца (D4) — для
  первого месяца использования отчёта, для новой категории/склада, появившихся впервые, или если
  прошлый месяц по какой-то причине не был посчитан, коэффициент этой позиции остаётся
  нерассчитанным (`null`) → [Митигация] осознанно принятое поведение (см. specs, сценарий «нет
  сохранённых данных за прошлый месяц»), а не дефект; фронтенд должен уметь показать «—»/пусто для
  `null`, а не `0` или ошибку.
- [Риск] Комбинаторика категория × склад даёт много вызовов кастомного ERP-эндпоинта за один
  пересчёт (например, 50 категорий × 5 складов = 250 запросов в час) → [Митигация] ограничить
  параллелизм вызовов, замерить реальную задержку `getGoodsFlowReport` перед включением часового
  крона в проде; в `tasks.md` учесть эту проверку до раскатки. Дополнительно снижено ограничением
  глубины категорий по складу (`GoodsTurnoverWarehouseScope`, см. spec.md "Глубина категорий в
  отчёте ограничивается по складу"): полное дерево категорий строится только для основного склада
  (глубина 0-1), для всех остальных складов — только корневые категории (глубина 0).
- [Риск] Кастомный эндпоинт — собственный бэкенд-компаньон RoApp (`rm.murygin.tech`), а не
  инфраструктура самого RemOnline; менее предсказуемая доступность → [Митигация] `BadGatewayException`
  на сбой вызова (как у соседних методов `custom-api-roapp`), сбой одной пары не должен ронять весь
  часовой пересчёт (см. D6).
- [Риск] Допущение о наличии в публичном RoApp API ресурса списка складов (D3) может не
  подтвердиться → [Митигация] проверить на этапе реализации; при отсутствии ресурса — резервный
  источник (например, разбор уже наблюдаемых `warehouseId` из ответов `getGoodsFlowReport`/списаний
  заказов, либо ручной справочник) как отдельная задача.
- [Риск] `RoappProductCategory` обновляется только разовой командой `npm run initial`, не кроном —
  дерево категорий в отчёте может отставать от актуального в RoApp → [Митигация] вне скоупа этого
  change; при необходимости — отдельная задача на периодический синк категорий.
- [Риск] Закрытие отчёта по оборачиваемости зависит от закрытия зарплатного `AccountingPeriod` (D7)
  — если зарплатный период за месяц не закрывается (спорный план продаж, ещё не истёк), отчёт по
  оборачиваемости тоже бессрочно остаётся открытым и почасово пересчитывается → [Митигация]
  осознанно принятое поведение (см. D7); при необходимости другого правила — отдельный change.
- [Риск] Финальный пересчёт внутри обработчика события (D7) добавляет к транзакции закрытия
  зарплатного периода дополнительную синхронную работу (перебор категория × склад, см. первый риск
  выше) → [Митигация] обработчик события — асинхронный подписчик (`EventEmitter2`, `emitAsync`),
  публикуется уже после коммита транзакции закрытия зарплатного периода (см. Context) — не удлиняет
  и не может откатить эту транзакцию; собственная запись строк идёт отдельной операцией.

## Migration Plan

- Аддитивная Prisma-миграция: новые модели `RoappWarehouse`, `GoodsTurnoverReportLine` —
  существующие таблицы, включая `AccountingPeriod`, не меняются (только читаются, см. D5).
- Перед первым построением отчёта нужно выполнить синк складов (расширить `npm run initial` новым
  шагом или добавить отдельную ручную команду).
- Отката не требует — новая функциональность, не затрагивающая существующее поведение; при
  необходимости откатывается удалением новых таблиц/модуля.

## Open Questions

- Закрытие месяца по оборачиваемости целиком унаследовано от условий закрытия `AccountingPeriod`
  (утверждённый план продаж, истёкший период — см. `service/accounting`) и не имеет собственных
  условий (см. D5/D7) — отдельного вопроса про условия закрытия для этого change больше нет.
- Reopen тоже не требует отдельной логики: поскольку статус не дублируется (D5), переоткрытие
  `AccountingPeriod` автоматически «размораживает» отчёт по оборачиваемости — крон снова видит период
  открытым и возобновляет почасовой пересчёт. Открытый вопрос лишь в том, нужно ли делать это
  немедленно (например, тоже подписаться на переоткрытие, если для него появится доменное событие —
  сейчас `ReopenAccountingPeriodHandler` его не публикует) или достаточно того, что подхватится в
  течение часа со следующим тиком крона. Не влияет на specs/выбранный подход — можно решить при
  реализации (`tasks.md`).
