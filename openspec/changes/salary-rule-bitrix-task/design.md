## Context

См. `proposal.md` — Why. Технический контекст (см. также отчёт исследования в PRD `docs/salary-rule-bitrix-task/prd-salary-rule-bitrix-task.md`, раздел «Технические ограничения»):

- `backend/src/integrations/bitrix/` сейчас — только чтение (сделки, сотрудники, справочники) через `BitrixHttpService` (webhook-клиент, `axios` + `_getWithRetry` с экспоненциальным бэкоффом, `BITRIX_DELAY_MS = 500` троттлинг). Методов записи (создание/изменение/удаление сущностей) нет вообще, для задач — тоже.
- Три бизнес-статуса PRD (Создана/Реализована/Закрыта) сверены с бизнесом и напрямую соответствуют трём штатным статусам задач Bitrix24 Tasks — «Ждёт выполнения», «Выполняется», «Завершена» (см. Decision 6).
- Кастомные поля (`UF_*`) на портале пользователя создать нельзя — расчётный месяц и признак «это зарплатная задача» кодируются тегами задачи (Bitrix24 Tasks `TAGS`) вместо кастомного поля (см. Decision 7).
- Готовый образец «крон + идемпотентный сервис + ленивое достраивание на GET» — `SalesPlanAutoCreationCron` + `EnsureSalesPlansForPeriodService` (`@ProdCron`, тикает только в проде; `runInSystemRequestContext` обязателен вне HTTP-запроса).
- `SalaryRule` хранит конфигурацию правила как `props: Json` (гибкая схема per-type) — см. `prisma/schema/salary.prisma`.

## Goals / Non-Goals

**Goals:**
- Определить, где и как хранится связь «правило → задача(и) Bitrix24» так, чтобы перенос месяца в Bitrix24 не требовал синхронизации на стороне iReports (источник правды по статусу/месяцу — всегда живой Bitrix).
- Держать запись в Bitrix (create/delete) и чтение (batch get) за одним новым сервисом, по образцу существующего `BitrixService`.
- Свести стоимость расчёта отчёта к одному пакетному HTTP-запросу к Bitrix24 независимо от числа правил-задач.
- Дать безопасный путь отключения старого `TaskCompletion`-воркфлоу без потери уже заработанных, но ещё не зафиксированных в снапшоте начислений.

**Non-Goals:**
- Двусторонняя синхронизация статусов через входящие вебхуки Bitrix24 (`ON_TASK_*` события) — используется только пакетное чтение по запросу (см. PRD, «Не в скоупе» пересекается с этим решением).
- Отчёт «выполнение задач по отделу» — не в скоупе (PRD).

## Decisions

### 1. Связь «правило → задача(и)» хранится в `SalaryRule.props`, без отдельной таблицы соответствий периодов
`taskCompletedSalaryConfigSchema` расширяется полями `description`, `dueDate`, `isRecurring`, `rewardAmount` (взамен `award`-union) и `bitrixTaskIds: number[]` — список ID задач, накопленных за всё время правила (один элемент для разового правила, по одному новому элементу на каждый регенерированный месяц для регулярного).

Расчётный месяц задачи **не дублируется** в iReports нигде — при расчёте отчёта за период `P` система пакетно запрашивает у Bitrix24 статус (нативное поле, см. Decision 6) и текущий расчётный месяц (тег `TAGS`, см. Decision 7) для всех `bitrixTaskIds` затронутых правил и на месте отбирает задачу, чей текущий месяц равен `P`. Перенос задачи в Bitrix24 меняет ответ на следующий же запрос — никакой отдельной синхронизации не требуется.

**Альтернатива (отклонена)**: отдельная таблица `(ruleId, period) → bitrixTaskId`, обновляемая при каждом переносе. Отклонена — потребовала бы либо синхронного вебхука от Bitrix при переносе (не в скоупе), либо периодического поллинга для поддержания таблицы в актуальном состоянии, что дублирует работу, которую и так придётся делать при расчёте отчёта.

### 2. Фактическая сумма и весь конфиг правила — в `SalaryRule.props`, без отдельной таблицы
Зарплатные правила в проекте намеренно спроектированы гибко: вся конфигурация правила живёт в одном JSON (`SalaryRule.props`), без выделенных колонок/таблиц под конкретные типы правил (см. `backend/src/domains/service/CLAUDE.md`). Фактическая сумма по закрытой задаче хранится по тому же принципу — как часть `props` правила `TaskCompleted`, в виде списка `actualAmounts: { period: string; amount: number }[]` (по одной записи на расчётный период, где руководитель её вводил), без отдельной Prisma-модели.

Валидация обязательных полей конфигурации (`description`, `dueDate`, `isRecurring`, `rewardAmount`) — на уровне Zod-схемы `taskCompletedSalaryConfigSchema` в `ireports-contracts`, применяемой `nestjs-zod`-DTO при создании/редактировании правила (см. задачу 4.1) — тот же паттерн, что и у остальных типов правил.

Иммутабельность снапшота при закрытии периода не зависит от того, где лежит `actualAmount`: `AccountingPeriodSnapshotPort` фиксирует уже посчитанное значение факта в момент закрытия, а не ссылку на `props` — последующее изменение `props` правила (например, при переносе задачи в другой месяц) не затрагивает уже закрытые снапшоты.

**Альтернатива (отклонена в этой ревизии)**: отдельная таблица `task_rule_actual_amounts`. Была выбрана в первой версии design.md как более строгая модель для оперативных per-period данных, но противоречит принципу проекта — вся гибкая конфигурация зарплатных правил хранится в JSON `SalaryRule.props`, без исключений под отдельные типы. Пересмотрено по фидбэку.

### 3. Новый write-доступ к Bitrix — `BitrixTasksService`, отдельный от `BitrixService`
Новый сервис в `backend/src/integrations/bitrix/`, использующий тот же `BitrixHttpService` (webhook-клиент) и тот же паттерн `_getWithRetry`, что и `BitrixService`. Методы: `createTask`, `deleteTask`, `getTasksBatch(taskIds: number[])`. Отдельный класс (не расширение `BitrixService`) — чтобы не смешивать read-only синковый функционал (`fetchCreatedDeals` и т.п., используемый кроном синхронизации) с новым write-путём, у которого другие требования к обработке ошибок (ошибка write обязана остановить транзакцию сохранения/удаления правила, ошибка read у синка — нет, см. `RoappSyncCron`-паттерн).

**Пакетность**: используется нативный метод Bitrix24 REST `batch` (до 50 под-команд за один HTTP-запрос) для `getTasksBatch` — оборачивает N вызовов `tasks.task.get` в один HTTP-запрос; при более чем 50 задачах в отчёте — несколько последовательных `batch`-запросов (редкий случай, отчёт на 30 правил уже покрывается одним).

### 4. Запись в Bitrix и сохранение правила — паттерн «сначала Bitrix, потом БД» с компенсацией при ошибке БД
При сохранении схемы с новым/изменённым правилом-задачей: (1) создать задачу в Bitrix24 → получить `bitrixTaskId`; (2) сохранить схему с этим ID в той же Prisma-транзакции, что и остальные правила схемы. Если шаг (2) падает — сервис синхронно вызывает `deleteTask` для только что созданной задачи (компенсирующее действие), чтобы не оставить «осиротевшую» задачу в Bitrix24 (PRD: «осиротевших» правил без ID задачи не появляется — симметрично не должно быть осиротевших задач в Bitrix без правила). Если компенсирующее удаление тоже падает — ошибка логируется с ID задачи для ручной зачистки, пользователь всё равно видит ошибку сохранения схемы.

**Альтернатива (отклонена)**: сначала сохранить схему с временным/пустым `bitrixTaskId`, затем создать задачу и обновить запись. Отклонена — оставляет валидное, но неполное состояние правила видимым между шагами (нарушает «схема не сохраняется, пока задача не создана» из PRD).

### 5. Автосоздание регулярных задач — крон по образцу `SalesPlanAutoCreationCron`
`TaskRuleAutoCreationCron` (`@ProdCron(CronExpression.EVERY_1ST_DAY_OF_MONTH_AT_MIDNIGHT)`, `runInSystemRequestContext`) вызывает `EnsureBitrixTaskForPeriodService.ensure(rule, period)`: пакетно получает периоды всех `bitrixTaskIds` правила, и если ни один не соответствует текущему периоду — создаёт новую задачу и добавляет её ID в `bitrixTaskIds`. Идемпотентность — за счёт этой проверки (а не БД-уникальности, т.к. решение принимается по живым данным Bitrix, не по локальной таблице). Как и у `SalesPlan`, добавляется ленивое достраивание при чтении схемы/отчёта — необходимо, потому что `@ProdCron` не тикает в dev.

### 6. Статус задачи — нативное поле Bitrix Tasks `status`
Три бизнес-статуса PRD реализуются напрямую нативным статусом задачи Bitrix24 Tasks: «Ждёт выполнения» = Создана, «Выполняется» = Реализована, «Завершена» = Закрыта. `BitrixTasksService.createTask`/`getTasksBatch` читают это поле напрямую; при создании статус отдельно не выставляется — новая задача создаётся Bitrix24 со штатным статусом «Ждёт выполнения».

### 7. Расчётный месяц и признак «зарплатная задача» — теги Bitrix24 Tasks, не кастомное поле
Кастомные поля (`UF_*`) недоступны для создания на портале пользователя (нет прав/возможности через `user.userfield.add` или админку) — использованы **теги задачи** (`TAGS`) вместо этого:
- Расчётный месяц — тег в фиксированном формате `<префикс>:<YYYY-MM>`, например `период:2026-08`; префикс захардкожен константой в конфиге интеграции (`backend/src/integrations/bitrix/bitrix.config.ts`).
- Признак типа — фиксированный тег `Зарплатная задача` на каждой задаче-правиле (замена отсутствующего в Bitrix24 Tasks понятия «тип задачи»); по этому тегу задачи видны/фильтруются в интерфейсе Bitrix24 отдельно от обычных.

`BitrixTasksService.createTask` выставляет оба тега при создании (`TAGS: ['Зарплатная задача', 'период:<YYYY-MM>']`); `getTasksBatch` парсит расчётный месяц из тега с префиксом `период:` в массиве `TAGS` ответа, а не из отдельного поля. Перенос задачи на другой месяц (PRD-сценарий) в этой схеме означает, что руководитель вручную меняет значение периода в теге задачи в Bitrix24 — это open UX-компромисс, принятый из-за недоступности кастомных полей (см. Risks/Trade-offs).

**Альтернатива (отклонена)**: кастомное поле `UF_*` — было первоначальным решением, но недоступно на портале пользователя; пересмотрено по фидбэку.

### 8. Переход в статус «Завершена» — доступен и сотруднику, и руководителю
Задачу в «Завершена» может перевести как исполнитель (сотрудник, отчитавшись о выполнении), так и постановщик (руководитель); если руководитель не согласен с результатом, он переводит задачу обратно в «Выполняется»/«Ждёт выполнения» — это отменяет факт по правилу для текущего открытого периода (расчёт снова видит статус, отличный от «Завершена»). iReports не проверяет и не ограничивает, кто именно выполнил переход, — читает только итоговый статус через `getTasksBatch`. Права на переходы статуса настраиваются в самом Bitrix24 (роль исполнителя/постановщика задачи), не в коде iReports.

### 9. Дедлайн — обязателен, должен попадать в границы расчётного месяца
`dueDate` обязателен при создании/редактировании правила-задачи. Валидация (Zod-схема `taskCompletedSalaryConfigSchema`, применяется и на клиенте, и через `nestjs-zod`-DTO на бэкенде) требует, чтобы дата дедлайна находилась в границах расчётного месяца правила — `[первое число, последнее число]` выбранного периода `YYYY-MM` — без привязки к конкретному дню (не обязательно последний день месяца). Дедлайн вне границ периода отклоняется с ошибкой валидации, задача не создаётся.

### 10. Вывод из эксплуатации `TaskCompletion` — управляемый cutover, не мгновенное удаление
Прямое немедленное удаление старого воркфлоу рискует «заморозить» уже заработанные, но ещё не закрытые в снапшоте начисления (записи `CONFIRMED` в открытом периоде сейчас учитываются в факте расчёта; расчёт `TaskCompleted`, переключённый на Bitrix24, их проигнорирует). Решение:
1. Эндпоинты `create`/`confirm`/`delete` `TaskCompletion` отключаются (410 Gone или удаляются) в этом же change — новых записей больше не появится.
2. Перед деплоем — ручной runbook-шаг (без кода): руководитель закрывает текущий расчётный период (что фиксирует существующие `CONFIRMED`-записи в неизменяемом снапшоте, как обычно) либо вручную заводит замещающие правила-задачи в Bitrix24 для сотрудников, у которых остались незакрытые `PENDING_CONFIRMATION`-начисления, которые он хочет сохранить.
3. После деплоя таблица `task_completions`, доменный код `TaskCompletion` (сущность, репозиторий, команды, HTTP-контроллеры, DTO) и контракт `contracts/commands/task-completion.ts` удаляются полностью, **одним атомарным шагом** — они не читаются новым расчётом `TaskCompleted` начиная с релиза. Контракт нельзя удалить раньше остального: он используется исключительно этим ещё не удалённым backend-кодом (сборка backend/contracts ломается — на практике словили это при реализации, см. журнал задачи 4.2 в tasks.md).

**Дополнение 2026-08-26 — шаг 3 пересмотрен, отложен на неопределённый срок.** При попытке выполнить шаг 3 (задача 11.2) обнаружено, что это Decision не учитывало: таблица `task_completions` — общая для `service` и `shop` (дискриминатор `direction`), и у `shop` есть собственный независимый CQRS-стек (`ShopTaskCompletion`, `domains/shop/modules/accounting`), который активно пишет в эту же таблицу и НЕ имеет замены на Bitrix24 (интеграция `TaskCompleted`↔Bitrix24 реализована этим change только для `service`, см. задачи 7.1/7.2 — "Направление shop НЕ покрыто"). Буквальное выполнение шага 3 сломало бы у `shop` единственный работающий механизм начисления за задачи без какой-либо замены. Решение: шаг 3 (весь вырез — таблица, доменный код `service`-стороны, контракт) откладывается целиком до появления у `shop` собственной Bitrix24-интеграции `TaskCompleted` (отдельный будущий change). Шаги 1 и 2 остаются в силе и выполнены.

## Risks / Trade-offs

- [Риск] Cutover без переходного периода может «потерять» уже заработанные, но не подтверждённые (`PENDING_CONFIRMATION`) начисления, если runbook-шаг перед деплоем пропущен → Mitigation: шаг закрытия периода/ручного переноса — обязательный пункт в tasks.md перед задачей удаления старого кода; в этом change это ручная процедура, а не автоматическая миграция данных.
- [Риск] Компенсирующее удаление задачи Bitrix24 при ошибке сохранения схемы (Decision 4) само может упасть (сеть, повторная недоступность Bitrix) → Mitigation: логирование ID «осиротевшей» задачи для ручной зачистки; пользователь в любом случае видит ошибку сохранения и не считает операцию успешной.
- [Риск] Лимиты Bitrix24 REST (в т.ч. на `batch`) при большом числе правил-задач в отчёте отдела → Mitigation: `getTasksBatch` чанкуется по 50 команд; троттлинг `BITRIX_DELAY_MS` между чанками, как у существующего `_getWithRetry`.
- [Trade-off] Отсутствие локального дублирования расчётного месяца задачи (Decision 1) означает, что расчёт отчёта всегда требует живого обращения к Bitrix24 (нет офлайн-режима для открытого периода) → принято осознанно: закрытый период не зависит от Bitrix (снапшот), только открытый.
- [Trade-off] `bitrixTaskIds` и `actualAmounts` в `props` (Decision 2) — накапливающиеся со временем массивы, размер JSON правила растёт с каждым новым месяцем регулярного правила → рост линейный и небольшой (десятки байт в месяц), пренебрежим для реалистичного срока жизни правила; при необходимости историю можно позже вынести в отдельную таблицу без изменения контракта чтения текущего периода.
- [Риск] Расчётный месяц хранится в теге задачи (Decision 7) — свободном текстовом поле Bitrix24 Tasks, которое можно случайно удалить, задвоить или ввести с опечаткой (например, не тем разделителем) при ручном переносе задачи на другой месяц → Mitigation: строгий парсинг тега по фиксированному префиксу в `getTasksBatch`; тег без совпадения формата или отсутствующий трактуется как «задача недоступна» (Requirement «Обработка недоступной задачи» в `spec.md`), а не как ошибка расчёта — не даёт начисления, но и не роняет отчёт.
