## 13. Баги, найденные при ручной проверке 2026-08-26

- [x] 13.1 **[ИСПРАВЛЕНО] `BitrixTasksService.getTasksBatch` всегда возвращал `isAvailable: false`/`period: null` для ЛЮБОЙ реальной задачи Bitrix24** — из-за этого КАЖДОЕ правило `TaskCompleted`, для любого сотрудника и периода, всегда считалось недоступным (0 в факте и прогнозе), независимо от реального статуса задачи в Bitrix. Обнаружено на живых данных пользователя (тестовая задача за июль 2026, отмеченная выполненной, показывала «недоступна» при закрытии месяца). Две независимые причины, проверены вручную через реальный webhook (`curl`/`batch`):
  1. `TASK_GET_SELECT` в `backend/src/integrations/bitrix/bitrix-tasks.service.ts` использовал camelCase-имена полей (`id`, `title`, `status`, `responsibleId`, `tags`), а `tasks.task.get` у `select[]` понимает только классические `UPPER_SNAKE_CASE`-имена (`ID`, `TITLE`, `STATUS`, `RESPONSIBLE_ID`, `TAGS`); при нераспознанном имени Bitrix молча возвращает урезанный fallback-набор полей без статуса и тегов вообще.
  2. Результат под-запроса `tasks.task.get` внутри `batch`-ответа читался как `result.task_N.item`, а Bitrix реально кладёт задачу под ключ `result.task_N.task` — из-за этого `getTasksBatch` буквально ВСЕГДА считал задачу «не найденной» (`isAvailable: false`), даже если бы баг (1) починили отдельно.
  3. Заодно исправлена форма `tags` в парсере (`parseBitrixTaskPeriodTag`, `bitrix.config.ts`) — Bitrix отдаёt их объектом по ID тега (`{"16": {id, title}, ...}`), а не массивом строк, как предполагал старый код.

  Исправлено: `bitrix-tasks.service.ts` (`TASK_GET_SELECT` → uppercase, `.task` вместо `.item`), `bitrix.config.ts` (`parseBitrixTaskPeriodTag`), `bitrix-api.types.ts` (`BitrixTaskTagsField`, `BitrixTaskGetBatchResult.task`), тесты `bitrix-tasks.service.spec.ts` обновлены под реальные формы ответа. - [ ] 13.2 **[ОТКРЫТО, НЕ ИСПРАВЛЕНО] Любое сохранение схемы мотивации (`PATCH /v1/service/motivation-schema/:id`) сбрасывает накопленные `bitrixTaskIds` у ВСЕХ правил-задач схемы, даже нетронутых.** `UpdateMotivationSchemaHandler` реализован как полная замена набора правил: перед сохранением удаляет в Bitrix24 задачи ВСЕХ существующих правил `TaskCompleted` схемы (`deleteExistingTaskRuleBitrixTasks`), затем пересоздаёт каждое правило из присланного списка через `CreateSalaryRuleCommand`, который создаёт ровно одну новую задачу.
