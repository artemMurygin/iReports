## Context

- Задача (`Task`) живёт в отдельном сквозном модуле `backend/src/modules/tasks/`, общем для всех
  направлений — намеренно без знания о зарплатных правилах (`tasks#Requirement: Задача — полностью
  самостоятельная сущность, не знающая о зарплатных правилах`). У `Task` есть nullable-поле
  `direction`, но связь «задача → правило» она не хранит.
- Зарплатное правило «за выполнение задачи» хранит связь в обратную сторону — JSON-поле
  `props.config.taskIdByPeriod` внутри `SalaryRule` (`domains/{service,shop}/modules/accounting`).
  Отдельного индекса/обратной таблицы «задача → правило» в БД нет.
- Начисление за задачу — строка `SalaryAccrualLine` с `sources: [{type: 'taskCompletion', id: taskId}]`
  внутри `SalaryAccrual` того же домена.
- Каждое направление (`service`, `shop`) — независимый Prisma-домен со своим репозиторием правил и
  начислений; правило межмодульной изоляции (`backend/CLAUDE.md`) запрещает одному backend-модулю
  напрямую вызывать application-сервисы другого — потребитель обязан восстанавливать собственную
  сущность из БД через свой собственный доступ.
- На фронтенде уже есть готовый паттерн боковой панели: `shared/ui-kit/organisms/SidePanel` +
  фича `features/TaskStatusControl` (панель карточки задачи) и пример кросс-фичевой оркестровки двух
  панелей через `taskId` — `features/SalaryRuleForm/model/useTaskLinkPanels.ts`.
- См. `proposal.md` — мотивация; `specs/tasks/salary-rule-panel`, `specs/tasks/links`,
  `specs/tasks/comments`, `specs/service/accounting`, `specs/shop/accounting` — требования.

## Goals / Non-Goals

**Goals:**
- Показать на карточке задачи связанное правило и начисление, не нарушая инвариант «Task не знает о
  правиле» и не создавая прямых backend-зависимостей между `modules/tasks` и `domains/{service,shop}`.
- Дать карточке задачи собственные ссылки и комментарии как независимые от `accounting` сущности.
- Переиспользовать существующий UI-паттерн боковой панели для описания правила.

**Non-Goals:**
- Редактирование зарплатного правила из панели, открытой с карточки задачи — панель read-only,
  редактирование правила остаётся на странице `SalaryRuleDetailPage`.
- Редактирование и удаление уже оставленных комментариев.
- Вложения, форматирование или превью ссылок (favicon, OpenGraph и т.п.) — только адрес и подпись.
- Уведомления о новых комментариях/ссылках.
- Отдельная индексированная таблица «задача → правило» в БД — поиск делается запросом по уже
  существующим таблицам `accounting`-домена.

## Decisions

### 1. `TaskComment` и `TaskLink` — новые таблицы в `modules/tasks`, без Prisma-`@relation`
Обе сущности хранятся как собственные Prisma-модели в `modules/tasks` (где уже живёт `Task`), с
`taskId` как обычным полем, не foreign-key-`@relation` — по тому же прецеденту, что и
`assigneeEmployeeId` в `task.prisma` (комментарий в схеме: без `@relation`, т.к. источник сотрудника
внешний, Bitrix). Автор комментария — `authorEmployeeId: Int`, тем же способом, каким уже
разрешается `assigneeEmployeeId` на фронтенде (переиспользуется существующий хук резолва имени
сотрудника, а не пишется новый).

**Альтернатива:** держать комментарии/ссылки в JSON-поле на самой `Task` — отклонено: список
неограниченной длины, добавление/удаление отдельной записи было бы неатомарным без отдельной таблицы,
и это ломает возможность в будущем добавить постраничную выдачу комментариев.

### 2. Данные о правиле/начислении получает фронтенд, не backend `modules/tasks`
`modules/tasks` НЕ получает нового кода, читающего таблицы `accounting`-домена, и НЕ вызывает
application-сервисы `domains/{service,shop}/modules/accounting` — это добавило бы прямую
межмодульную зависимость, запрещённую `backend/CLAUDE.md`. Вместо этого:
- `domains/service/modules/accounting` и `domains/shop/modules/accounting` каждый добавляют у себя
  (внутри своего домена, без нового межмодульного взаимодействия) два новых HTTP-эндпоинта:
  «правило/начисление по `taskId`» и «правило по собственному `id`» (см. delta-спеки).
- Фронтенд (блок на карточке задачи) сам делает HTTP-запрос к нужному домену, определяя направление
  по `task.direction`, и объединяет результат с данными задачи — так же, как `useTaskLinkPanels.ts`
  уже сегодня оркеструет две независимые фичи через `taskId`, не создавая связи между ними на
  backend.

**Альтернатива:** завести в `modules/tasks` собственный read-репозиторий, читающий таблицы
`salary_rule`/`salary_accrual_line` напрямую из БД (по аналогии с изоляцией между `service` и `shop`
на общих таблицах) — отклонено как более сложная альтернатива для этой задачи: `accounting`-домены и
так владеют этими таблицами и уже предоставляют HTTP-слой; повторять доступ к их таблицам ещё и из
`modules/tasks` увеличивает поверхность синхронизации при последующих изменениях схемы `SalaryRule`
без выигрыша в производительности (это некритичный, редко запрашиваемый read-путь одной карточки).

### 3. Направление резолвится через `task.direction`, с последовательным fallback
Панель запрашивает правило в домене `task.direction`, если оно заполнено. Если `direction` не
заполнено (встречается у части существующих задач), панель последовательно опрашивает `service`,
затем `shop`, и использует первый непустой результат — простой и приемлемый компромисс, так как
такой запрос выполняется один раз при открытии карточки задачи, не в горячем пути.

### 4. Поиск правила по `taskId` — прямым сравнением по JSON-полю, без новой индексной таблицы
Реализуется как запрос по уже существующим правилам домена с фильтром по виду `TaskCompletion` и
сравнением `taskIdByPeriod`-значений с искомым `taskId` (см. Non-Goals — отдельная индексированная
таблица «задача → правило» не заводится). Количество правил вида «за выполнение задачи» на домен
ожидаемо небольшое, полного сканирования достаточно для этого read-пути.

### 5. Панель зарплатного правила — новая фича, читающая только «правило по id»
Новая фронтенд-фича (аналог `features/TaskStatusControl`, обёрнута в тот же `SidePanel`) получает
`ruleId` + направление и запрашивает эндпоинт «правило по собственному `id`» — не переиспользует
`SalaryRuleDetailPage` (той нужен `motivationSchemaId`, и она — полноценный редактор, а не read-only
панель).

## Risks / Trade-offs

- **[Risk]** Полное сканирование правил домена по `taskId` может стать медленным при большом числе
  правил «за выполнение задачи». → **Mitigation**: сейчас объём мал; если станет узким местом —
  завести отдельное индексируемое поле/таблицу в последующем изменении, спек уже описывает поведение,
  не реализацию, так что это не потребует правки специфи.
- **[Risk]** Задачи без заполненного `direction` требуют двух последовательных запросов вместо одного
  → чуть медленнее открытие панели для таких задач. → **Mitigation**: затрагивает только устаревшие
  задачи без direction; для новых задач (создаваемых через мастер привязки правила) `direction`
  всегда заполняется.
- **[Trade-off]** Комментарии и ссылки — не переиспользуют возможную будущую общую сущность
  «комментарий»/«ссылка» для других сущностей iReports (сделки, зарплатные правила и т.п.) — они
  специфичны для `Task`. → Осознанный выбор: нет второго потребителя сейчас, обобщать преждевременно.

## Migration Plan

- Prisma-миграция добавляет таблицы `task_comments` (`task_id`, `author_employee_id`, `body`,
  `created_at`) и `task_links` (`task_id`, `url`, `label?`, `created_at`) — только новые таблицы, без
  изменения существующих.
- Изменения в `domains/{service,shop}/modules/accounting` — только новые read-эндпоинты, без миграций
  схемы.
- Обратная совместимость: существующие клиенты API не затрагиваются, все новые эндпоинты аддитивны.
- Откат — удаление новых таблиц/эндпоинтов не требует отдельной стратегии данных, т.к. это новые,
  ранее не существовавшие сущности без внешних потребителей.
