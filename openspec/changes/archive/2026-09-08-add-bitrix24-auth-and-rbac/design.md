## Context

См. `proposal.md` за мотивацией. Ниже — только то, что реально найдено в коде и влияет на подход.

- В backend нет ни одной сущности сессионного слоя и RBAC — обе капабилити вводятся с нуля. Для
  идентичности пользователя отдельная новая сущность НЕ вводится вовсе — см. Decision 2.
- **Redis в проекте сегодня не используется вообще**: нет сервиса `redis` в `docker-compose.yml`,
  нет зависимости `ioredis`/`cache-manager` в `backend/package.json`, нет ни одного обращения к
  Redis в коде. Формулировка "Redis используется для кэша" из исходного запроса не подтверждается
  текущим состоянием репозитория — эта фича вводит Redis в проект впервые, а не расширяет
  существующий кэш. Это не меняет требование (Redis для сессий задан явно и предметно — TTL,
  sliding expiration, SET-структура для обратного индекса), но добавляет инфраструктурный шаг
  (см. Decisions/Migration Plan).
- Существующая интеграция `backend/src/integrations/bitrix/**` решает соседнюю, но другую задачу:
  `BitrixInstallation` — одна строка НА ПОРТАЛ (уникальность по `memberId`), хранит токен,
  полученный при установке приложения. `BitrixPortalAdminCheckService.checkViaBitrix` — рабочий
  образец прямого REST-вызова Bitrix24 (`${installation.clientEndpoint}user.admin?auth=<token>`,
  таймаут 5с, fail-closed при любой ошибке) — этот же приём переиспользуется для валидации
  embedded-токена (`user.current`) и для bootstrap первого администратора (см. Decisions).
- Приложение single-tenant: домен портала (`irepair.bitrix24.ru`) захардкожен в
  `BitrixAuthService.saveInstallation`, второго портала не предполагается. Это существенно для
  Decision 2 ниже: `member_id` (идентификатор ПОРТАЛА в терминологии Bitrix24, одинаковый для всех
  его пользователей) в данном приложении константен и не нужен как часть ключа идентичности
  пользователя.
- **Ключевая находка**: в проекте уже есть `BitrixEmployee` (`backend/prisma/schema/bitrix.prisma`)
  — существующий справочник сотрудников, чей `id: Int` — это и есть числовой ID пользователя
  Bitrix24 (`bitrix-sync.service.ts` мапит `id: Number(e.ID)` из ответа `user.get`, не суррогатный
  ключ). Заводить для аутентификации отдельную сущность `User` с собственным `bitrixUserId` означало
  бы завести вторую сущность для того же самого человека — см. Decision 2 (пересмотрено по
  замечанию пользователя после первой версии этого документа).
- `BitrixEmployee` наполняется через `src/sync/bitrix` (`BitrixSyncService.uploadEmployees()`) —
  это СКВОЗНОЙ синк (сиблинг `src/domains/service/sync`/`src/domains/shop/sync`, а не часть
  HR/payroll-домена `service`), так что зависимость на него из новых сквозных модулей не нарушает
  границу `service`/`shop`. **Важный риск**: `uploadEmployees()` НЕ висит ни на каком recurring-
  кроне — вызывается только вручную через `npm run initial` (`UploadInitialBitrixDataHandler`).
  Значит новый сотрудник, заведённый в Bitrix24 сегодня, не получит строку `BitrixEmployee`
  автоматически — см. Decision 11 (самовосстановление при логине).
- В проекте уже есть сквозной (вне `domains/{service,shop}`) модуль `src/modules/directory` с
  портом `DIRECTORY_REPOSITORY` (`findEmployees`, `findDepartments`, ...), которым уже пользуются
  другие модули через DI-токен, не копируя код, — готовый источник списка сотрудников для
  админ-страницы ролей, отдельный `USER_DIRECTORY_PORT` заводить не нужно (см. Decision 1).
- Кросс-модульные вызовы в проекте оформляются как порт + `Symbol`-токен в стиле
  `src/shared/application/ports/erp-period-sync.port.ts`/`UNIT_OF_WORK`: потребитель зависит только
  от интерфейса, реализацию регистрирует модуль-владелец в своём `*.module.ts`.
- `AppRequestContext` (`AsyncLocalStorage`) сегодня хранит `requestId`/`transactionConnection`/
  `pendingAggregates`, наполняется `RequestContextMiddleware` (выполняется первым для всех роутов) и
  `ContextInterceptor`; guard'ы выполняются позже в цепочке — контекст уже открыт к моменту их
  работы.
- `DomainExceptionFilter` сопоставляет `code` доменных исключений (`ExceptionBase`) с HTTP-статусом
  через таблицу в `exception.codes.ts`; кодов для 401/403 там пока нет.
- `APP_GUARD`, кастомные декораторы метаданных и `Reflector` в проекте пока нигде не используются —
  эта фича вводит первый такой пример.
- FK-конвенция в существующей схеме — `employeeId`/`bitrixEmployeeId` (см. `employee-identity.prisma`),
  не `userId`; новые таблицы следуют этой же конвенции (см. Decision 2/3).

## Goals / Non-Goals

**Goals:**
- Зафиксировать границы двух новых модулей (`auth`, `session`) и модуля `roles`,
  и порты между ними (переиспользуя уже существующие порты там, где они уже решают задачу), без
  циклических зависимостей.
- Зафиксировать, что идентичность пользователя — существующий `BitrixEmployee`, не новая сущность
  `User`, и как это соотносится с тем, что `BitrixEmployee`-синк не на кроне.
- Зафиксировать механизм немедленного применения изменений прав к активным сессиям (push, а не
  polling).
- Зафиксировать, как Redis появляется в инфраструктуре проекта (это первое его использование).
- Зафиксировать bootstrap первого администратора — иначе некому будет назначить первую роль.

**Non-Goals:**
- Детали конкретных Zod DTO, шагов контроллеров — это `tasks.md`.
- Изменение существующей интеграции `integrations/bitrix/**` (установка приложения) — не
  затрагивается.
- Перевод `BitrixSyncService.uploadEmployees()` на recurring-крон — существующий пробел вне scope
  этого change; эта фича лишь добавляет точечный self-heal на пути логина (см. Decision 11), не
  чинит расписание синка в целом.
- Автоматический вывод ролей/permissions iReports из `department`/`position` сотрудника — не
  проектируется (согласуется с non-goal proposal.md об отсутствии автосинхронизации по Bitrix24).

## Decisions

### 1. Два новых модуля + `roles` вне доменов `opt/service/shop`, связь через порты (в т.ч. уже существующие)
По аналогии со сквозными модулями вроде `src/modules/employee-identity`:
- `src/modules/auth` — владеет токенами Bitrix конкретного сотрудника, оркестрирует вход
  (единая точка сборки, которую требует proposal.md); НЕ владеет идентичностью — она уже есть
  (`BitrixEmployee`).
- `src/modules/session` — владеет Redis-сессиями.
- `src/modules/roles` — владеет ролями/правами, guard'ами, админ-API.

Альтернатива — один модуль `auth` на все способности — отклонена: proposal.md уже разделил их на
независимые capability со своим жизненным циклом (например, замена сессионного бэкенда не должна
требовать трогать RBAC); общий модуль усложнил бы это разделение и границы будущих changes.

Порты (по образцу `ERP_PERIOD_SYNC`/`UNIT_OF_WORK` — `Symbol`-токен + интерфейс, реализация
регистрируется модулем-владельцем):
- `PERMISSIONS_RESOLVER_PORT` (владелец `roles`) — `resolvePermissions(bitrixEmployeeId): string[]`;
  потребитель — оркестрация логина в `auth` (посчитать permissions прямо перед созданием
  сессии).
- `SESSION_PORT` (владелец `session`) — `createSession(bitrixEmployeeId, permissions,
  delivery)`, `invalidateSession(sessionId)`, `invalidateAllSessionsForEmployee(bitrixEmployeeId)`,
  `refreshPermissionsForEmployee(bitrixEmployeeId, permissions)`; потребители — `auth`
  (создание сессии при логине) и `roles` (проталкивание новых permissions/принудительная
  инвалидация после смены прав роли).
- `DIRECTORY_REPOSITORY` (**уже существует**, владелец `src/modules/directory`) —
  `findEmployees(...)`; потребитель — `roles` (список сотрудников на админ-странице ролей). Новый
  порт под это заводить не нужно — используется существующий, как это уже делают другие модули.
- `BITRIX_EMPLOYEE_UPSERT_PORT` (владелец `src/sync/bitrix`, новый — точечное расширение
  существующего синка, см. Decision 11) — `upsertOne(bitrixUserId): Promise<void>`; потребитель —
  `auth` (самовосстановление отсутствующей строки `BitrixEmployee` на пути логина).

Граф зависимостей — DAG без циклов: `auth → roles` (PERMISSIONS_RESOLVER_PORT),
`auth → session` (SESSION_PORT), `auth → src/sync/bitrix`
(BITRIX_EMPLOYEE_UPSERT_PORT), `roles → session` (SESSION_PORT), `roles →
src/modules/directory` (DIRECTORY_REPOSITORY). `session` и `src/modules/directory`/
`src/sync/bitrix` ни от кого из новых модулей не зависят.

### 2. Идентичность — существующий `BitrixEmployee`, отдельная сущность `User` НЕ заводится
`BitrixEmployee.id` уже является числовым ID пользователя Bitrix24 (см. Context). Заводить новую
`User` с собственным `bitrixUserId` дублировало бы одну и ту же сущность двумя таблицами — ровно то,
на что справедливо указал пользователь при разборе первой версии `architecture.md`. Приложение
single-tenant (один портал), поэтому `member_id` не нужен как часть ключа идентичности — он
сохраняется только в таблице токенов (Decision 3), пригодится там для вызовов Bitrix REST от имени
сотрудника.

`bitrixUserId` (= `BitrixEmployee.id`) резолвится ОДНИМ и тем же шагом для обоих сценариев входа —
вызовом `user.current` сразу после получения/подтверждения токена (для embedded это и есть
обязательная по спеку валидация; для OAuth — дополнительный вызов сразу после обмена `code` на
токены). Это даёт proposal.md-нужную "единую точку сборки": оба сценария сходятся к одному и тому
же `BitrixEmployee.id`.

Побочный эффект решения — `BitrixEmployee.isActive` (false у уволенного сотрудника, уже
поддерживается существующим синком) даёт проверку "уволенный не может войти" бесплатно, без
дублирования этой логики во второй сущности.

Альтернатива (первая версия этого документа) — отдельная сущность `User`, ключуемая составным
`(memberId, bitrixUserId)`, независимая от `BitrixEmployee` ради "изоляции доменов". Отклонена: как
показала проверка, `BitrixEmployee` — уже сквозная (не доменная) сущность, зависимость на неё не
нарушает границу `service`/`shop`; а раздельное хранение одного и того же человека в двух таблицах
создаёт риск рассинхронизации (например, `isActive` пришлось бы дублировать и поддерживать в двух
местах) без какого-либо выигрыша.

### 3. Токены Bitrix24 сотрудника — новая таблица, привязанная к `BitrixEmployee.id`, не `User` и не `BitrixInstallation`
`BitrixInstallation` — одна строка на ПОРТАЛ (уникальность по `memberId`), обслуживает установку
приложения. Использование её для токенов конкретного сотрудника привело бы к конфликту уникальности
при входе второго сотрудника того же портала.

Новая модель `BitrixEmployeeCredentials` (1:1 с `BitrixEmployee`, FK `bitrixEmployeeId` —
конвенция репозитория, см. `EmployeeIdentity.bitrixEmployeeId`): `bitrixEmployeeId`, `memberId`,
`accessToken`, `refreshToken`, `accessExpiresAt`. Обновление — тот же паттерн "проверить
`accessExpiresAt` → если истёк, обновить через `refresh_token` → повторить исходный запрос", что
уже реализован в `BitrixAuthService.getValidAccessToken`/`refreshTokens` (переиспользуется паттерн,
не таблица). Обмен `code`/обновление `refresh_token` для этой фичи идёт через
`oauth.bitrix24.tech/oauth/token/` (см. спек `auth`), а не через легаси
`oauth.bitrix.info` из install-flow — это два независимых клиента к двум разным OAuth-эндпоинтам
Bitrix24 (для приложения и для сотрудника), объединять их не нужно.

### 4. Guard'ы бросают нативные `UnauthorizedException`/`ForbiddenException`, не доменные исключения
`SessionAuthGuard`/`PermissionsGuard` — интерфейсный (interface) слой, а не бизнес-правило
конкретного DDD-модуля; их отказ — инфраструктурная проверка доступа на границе HTTP, а не аггрегат.
Заводить `AuthenticationFailedException extends ExceptionBase` с новыми кодами в
`exception.codes.ts` было бы избыточно для сквозного механизма, применяемого сразу ко всем модулям,
а не к бизнес-логике одного домена.

### 5. Guard'ы — глобальные через `APP_GUARD`, порядок `SessionAuthGuard` → `PermissionsGuard`
`SessionAuthGuard` наполняет `request.user = { employeeId, permissions }` до того, как
`PermissionsGuard` читает `request.user.permissions` — порядок в массиве провайдеров `APP_GUARD`
определяет порядок выполнения в Nest. `@Public()` — `SetMetadata` + `Reflector.getAllAndOverride` в
обоих guard'ах (первый пример такого паттерна в проекте — задаёт конвенцию для будущих guard'ов).

### 6. Redis вводится этой фичей как новая инфраструктура
Добавляется сервис `redis` в `docker-compose.yml`, зависимость `ioredis`, `RedisModule` с клиентом
за DI-токеном (`REDIS_CLIENT`) — по аналогии с `DatabaseModule`/`UNIT_OF_WORK`. Пространство ключей:
`session:<session_id>` (хэш `bitrixEmployeeId`/`permissions`, TTL = sliding expiration) и
`employee_sessions:<bitrixEmployeeId>` (Redis SET из `session_id`, без собственного TTL —
существует, пока жива хотя бы одна сессия внутри; удаляется вместе с последним `session_id`). Так
как это первое использование Redis в проекте, будущие задачи на кэширование переиспользуют тот же
`RedisModule`, а не заводят второй клиент.

### 7. CSRF: double-submit cookie, не synchronizer token
Double-submit не требует серверного хранения токена на форму/пользователя (в отличие от
synchronizer token). Сессия и так уже в Redis, но привязывать к ней ещё и CSRF-токен усложнило бы
модель без выигрыша в безопасности для этого случая (SPA с единой cookie на весь сайт, а не набор
отдельных форм). Значение CSRF-токена — производное от `session_id` (HMAC), отдельная запись в
Redis не заводится.

### 8. Определение контекста запуска на frontend
Признак embedded-контекста — `window.self !== window.top` (внутри iframe) И наличие BX24 SDK
одновременно, а не только один из признаков (защита от случайного открытия сайта в постороннем
iframe). Иначе — standalone/iOS.

### 9. Bootstrap первого администратора
При логине сотрудника, у которого ещё нет ни одной роли, backend вызывает Bitrix24 REST
`user.admin` с токеном вошедшего сотрудника — тот же приём, что и `BitrixPortalAdminCheckService`.
Если сотрудник — администратор портала Bitrix24, ему автоматически назначается системная роль
`Administrator` (создаётся сидом при выкате фичи, включает `roles:manage`/`users:manage`), дальше
все остальные права/роли администрирует уже человек через UI. Если сотрудник не администратор
портала — роль не назначается, доступ ограничивается тем, что доступно без специфичных permissions
(см. спек `roles`, "роут без permissions доступен любому аутентифицированному").

Альтернатива — ручной сид роли через прямой SQL/скрипт при каждом деплое. Отклонена как единственный
способ: требует ручного вмешательства в каждом окружении (dev/stage/prod), тогда как проверка
`user.admin` уже есть в кодовой базе и решает задачу автоматически и безопасно (fail-closed). Это не
постоянный механизм синхронизации ролей (см. non-goal) — проверка выполняется один раз, только пока
у сотрудника нет ни одной роли.

### 10. Поведение при недоступности Redis — fail-closed
Если Redis недоступен (сеть, рестарт), `SessionAuthGuard` SHALL трактовать это как отсутствие
валидной сессии (401), а не пропускать запрос. Открытый по умолчанию доступ при сбое
инфраструктуры хуже кратковременной недоступности защищённых роутов — согласуется с fail-closed
паттерном, уже принятым в `BitrixPortalAdminCheckService`.

### 11. Самовосстановление `BitrixEmployee` на пути логина
`BitrixSyncService.uploadEmployees()` — не recurring-крон, а только ручной скрипт `npm run initial`
(см. Context) — то есть новый сотрудник, добавленный в Bitrix24, НЕ получает строку `BitrixEmployee`
автоматически, и без дополнительной меры не смог бы войти в iReports вовсе, пока кто-то вручную не
перезапустит скрипт. Так как Decision 2 делает `BitrixEmployee` обязательной точкой опоры для
идентичности, логин-флоу `auth` обязан сам устранять этот пробел: если после резолва
`bitrixUserId` через `user.current` строки `BitrixEmployee` с таким `id` не существует, backend
вызывает `BITRIX_EMPLOYEE_UPSERT_PORT.upsertOne(bitrixUserId)` (новый порт, реализация — извлечённая
в отдельный метод часть существующей логики `uploadEmployees()`, без изменения её текущего
поведения для остальных вызывающих) и только затем продолжает логин.

Альтернатива — ничего не делать и полагаться на то, что кто-то вспомнит перезапустить `npm run
initial`. Отклонена: это либо блокирует выход нового сотрудника, либо требует операционного
процесса ("не забыть при онбординге"), который ничем не защищён от человеческой ошибки. Другая
альтернатива — перевести `uploadEmployees()` на recurring-крон целиком. Отклонена для ЭТОГО change
(см. non-goal) — более широкое изменение с более широким blast radius (влияет на все фичи,
читающие `BitrixEmployee`, не только на логин), уместное как отдельный change.

### 12. Каталог permission-кодов — типизированный реестр в коде, не сканирование рантайма и не свободный ввод через UI

`Permission` — справочник (Decision из proposal.md: `resource:action`), но остаётся открытым, ОТКУДА
берутся сами строки, которые видит администратор в матрице на странице "Роли и права". Два
отклонённых варианта и выбранный:

- Отклонено — **сканирование метаданных `@RequirePermissions` при старте приложения**: сервис на
  `OnModuleInit` проходит по всем контроллерам и сам upsert'ит `Permission` из реально
  зарегистрированных декораторов. Технически исключает рассинхрон, но добавляет рантайм-магию
  (поведение таблицы `Permission` зависит от порядка/факта регистрации модулей Nest, а не от
  явного шага деплоя) и усложняет ревью PR — разработчик не видит "чем это обернётся" до запуска.
- Отклонено — **свободный CRUD `Permission` через UI, как у `Role`**: буквально соответствует
  формулировке proposal.md "без хардкода в коде", но небезопасно — ничто не мешает администратору
  создать код, который ни один guard не проверяет (галочка ничего не защищает), опечататься
  (`role:manage` вместо `roles:manage` — тихо никогда не сработает) или создать право раньше, чем
  разработчик добавит соответствующую проверку в код.
- **Выбрано** — типизированный реестр-константа в коде, один файл на модуль-владелец (например
  `backend/src/modules/roles/roles.permissions.ts`, `backend/src/modules/directory/...` и т.д.),
  экспортирующий `{ code, label, group }` для каждого права этого модуля. `@RequirePermissions(...)`
  ссылается на `.code` константы, а не на голую строку — опечатка ловится TypeScript'ом на этапе
  компиляции. Prisma-сид (Migration Plan, шаг 3) при деплое агрегирует реестры всех модулей и
  делает `upsert` в таблицу `Permission` — админ-UI читает уже готовый, стабильный каталог (новая
  строка каталога появляется только через код + деплой, без рантайм-сканирования). Отдельный
  contract-тест на CI (`permissions-catalog.contract.spec.ts`) статически обходит исходники в
  поиске всех использований `@RequirePermissions('...')` и падает, если встретилась строка без
  соответствующей записи в объединённом реестре — рассинхрон ловится на PR, а не в проде.

Формулировка "без хардкода в коде и без деплоя" из proposal.md относится к созданию/изменению
**ролей** и назначению им прав ИЗ каталога (это действительно не требует деплоя) — не к самому
каталогу permission-кодов, который принципиально не может существовать без соответствующей
проверки в коде backend.

### 13. OAuth `state` — генерируется и хранится на frontend, сверяется backend'ом на callback

Первая версия этого документа (и `proposal.md`/`specs/auth/spec.md`) описывала OAuth authorization
code flow, упоминая параметр `state`, но НЕ описывала его валидацию — пробел, обнаруженный при
реализации (фронтенд-агент, раздел 16 tasks.md) и подтверждённый пользователем как требующий
исправления в рамках этого же change, а не отдельного. Без проверки `state` flow уязвим к
login-CSRF: злоумышленник может инициировать OAuth-авторизацию под СВОИМ Bitrix24-аккаунтом,
подсунуть жертве получившийся `redirect_uri?code=...` (например, через фишинговую ссылку), и если
жертва просто открывает эту ссылку в браузере со своей активной сессией iReports — её сессия
окажется привязана к аккаунту атакующего.

Решение:
- Frontend (`useBitrixLogin().login()`) перед редиректом на `{portal}/oauth/authorize/` генерирует
  случайный `state` (криптографически случайная строка, тот же уровень энтропии что `SessionId`,
  Decision/VO из раздела 2) и сохраняет его в `sessionStorage` (переживает сам редирект на Bitrix24
  и обратно в пределах одной вкладки; НЕ `localStorage` — не должен переживать вкладку/сессию
  браузера дольше, чем нужно для одного логин-флоу) до передачи в query-параметр `state` при
  редиректе.
- Frontend-страница приёма callback (`?code=&state=`, добавлена по итогам реализации — см. Impact
  proposal.md/tasks.md) читает `state` из `sessionStorage`, сверяет его с тем, что вернулся в URL
  ДО отправки `code` на backend, и очищает `sessionStorage` сразу после сверки (одноразовое
  использование). Несовпадение или отсутствие сохранённого `state` — ошибка, `code` на backend не
  отправляется, пользователю показывается сообщение "не удалось войти, попробуйте снова".
- Backend (`BitrixOAuthLoginHandler.execute(code, state)`) НЕ хранит и НЕ проверяет `state`
  самостоятельно — сверка полностью на frontend, backend принимает `state` только транзитом (для
  логов/диагностики). Это сознательный выбор: backend не имеет своего состояния между "редирект
  на Bitrix24" и "callback" (нет пользовательской сессии на этот момент — в этом и весь смысл
  логина), а вводить для этого отдельное серверное хранилище одноразовых `state`-токенов
  (например, в Redis с коротким TTL) — оверинжиниринг для риска, который полностью закрывается на
  клиенте: `state` в этой схеме защищает БРАУЗЕР пользователя от подмены ответа, а не backend от
  подделки запроса (это делает уже валидация `code` через реальный обмен токенами на стороне
  Bitrix24 — подделать чужой `code` нельзя).

Альтернатива — серверное хранение `state` (Redis, TTL 5-10 минут, ключ `oauth_state:<state>`).
Отклонена для этого change: не даёт дополнительной защиты сверх клиентской проверки (описанной
выше) при этой модели угроз, добавляет ещё один Redis-namespace и сетевой вызов в критичный путь
логина. Пересмотреть, если появится сценарий, где frontend не заслуживает доверия (например,
полностью серверный OAuth-flow без SPA) — не применимо к текущей архитектуре.

## Risks / Trade-offs

- [Redis — новая точка отказа инфраструктуры, которой раньше не было] → docker-compose healthcheck
  + fail-closed поведение guard'а (Decision 10).
- [`user.current` на каждый embedded-вход — дополнительная сетевая зависимость от Bitrix24 в
  критичном пути логина] → тот же fail-closed паттерн, что и в `BitrixPortalAdminCheckService`,
  таймаут ограничен (5с, как в существующем коде).
- [Проталкивание новых permissions во все активные сессии сотрудников роли может быть дорогим при
  большом числе сотрудников в одной роли] → для масштаба iReports (сотрудники одной компании, не
  миллионы пользователей) синхронный push через `employee_sessions:<bitrixEmployeeId>` приемлем;
  асинхронная очередь — преждевременная оптимизация на данном этапе.
- [Два похожих, но разных набора Bitrix-токенов в системе — `BitrixInstallation` (установка
  приложения) и `BitrixEmployeeCredentials` (вход сотрудника) — риск спутать при дальнейшей
  разработке] → явное разделение зафиксировано в Decision 3 и в Impact proposal.md; наименование
  таблиц и портов избегает общих слов ("installation" vs "employee credentials").
- [Расширение `src/sync/bitrix` новым портом (`BITRIX_EMPLOYEE_UPSERT_PORT`) — код вне трёх новых
  модулей, общий для всего приложения] → изменение аддитивное (извлечение существующей логики в
  переиспользуемый метод, без изменения поведения `uploadEmployees()` для существующих вызывающих);
  покрывается тестом на то, что бывший путь (`npm run initial`) продолжает работать как раньше.
- [Самовосстановление `BitrixEmployee` на логине создаёт запись с неполными данными (например,
  `position` не читается синком — см. TODO в `bitrix.prisma`), пока `npm run initial` не перезапишет
  её полными данными] → приемлемо: для аутентификации/RBAC нужны только `id`/`isActive`/имя, которые
  `user.current` отдаёт полностью; остальные поля дозаполнятся при следующем ручном запуске синка,
  как и сегодня для всех новых сотрудников.
- [Новое право требует правки кода (реестр + `@RequirePermissions`) и деплоя, а не только действия
  через UI — медленнее, чем "свободный" вариант каталога] → сознательный компромисс (Decision 12):
  право без соответствующей проверки в коде всё равно ничего не защищает, так что более быстрый путь
  создавал бы ложное чувство защищённости; ролями и назначением прав ИЗ каталога администратор
  по-прежнему управляет без деплоя.

## Migration Plan

1. Инфраструктура: сервис `redis` в `docker-compose.yml`, зависимость `ioredis`, `RedisModule`
   (`REDIS_URL` в конфиг/`.env`).
2. `src/sync/bitrix`: извлечь одноэлементный апсерт из `uploadEmployees()` в отдельный метод,
   выставить его через новый порт `BITRIX_EMPLOYEE_UPSERT_PORT` — без изменения поведения текущего
   массового пути.
3. Prisma-миграция: новые модели `Role`, `Permission`, `EmployeeRole` (FK `bitrixEmployeeId` →
   `BitrixEmployee.id`, FK `roleId` → `Role.id`), `RolePermission`, `BitrixEmployeeCredentials` (FK
   `bitrixEmployeeId`) — новый файл `backend/prisma/schema/auth.prisma`; сид агрегирует
   permission-реестры всех модулей-владельцев в таблицу `Permission` (Decision 12) и создаёт
   системную роль `Administrator` со всеми правами каталога (используется в bootstrap, Decision 9).
   Новая сущность `User` не заводится.
4. Реализовать `auth` (эндпоинты входа + самовосстановление `BitrixEmployee`, без
   глобальных guard'ов) — протестировать оба сценария входа изолированно, включая случай
   отсутствующей строки `BitrixEmployee`.
5. Реализовать `session` поверх готового `auth`.
6. Реализовать `roles`: модель данных, guard'ы, переиспользование `DIRECTORY_REPOSITORY` для
   списка сотрудников — но зарегистрировать `SessionAuthGuard`/`PermissionsGuard` как `APP_GUARD`
   последним шагом, когда весь frontend уже готов ходить через сессию. До этого момента система
   эффективно открыта, как сейчас; переключение на "закрыто по умолчанию" происходит одномоментно
   одним PR/релизом, а не постепенно (постепенное включение per-route создало бы окно, где часть
   роутов защищена, часть — нет, без явного критерия).
7. Роллбек: регистрация `APP_GUARD` — последний коммит перед релизом; при проблеме откатывается
   отдельным revert без отката схемы БД/Redis (guard-код выключается, данные не трогаются).
