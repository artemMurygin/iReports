## Purpose

Определяет поведение персонального API-ключа сотрудника: автогенерацию при создании записи
сотрудника, регенерацию, и аутентификацию HTTP-запросов к backend по ключу как альтернативу
Bitrix-сессии, без изменения существующего RBAC.

## ADDED Requirements

### Requirement: Автогенерация ключа при первом создании записи сотрудника
Backend SHALL генерировать уникальный API-ключ для сотрудника автоматически в момент первого
появления его записи в базе (первый upsert записи `BitrixEmployee`, ранее не существовавшей) и
SHALL сохранять его без участия пользователя. При последующих обновлениях уже существующей записи
сотрудника (например, повторной синхронизации из Bitrix24) ключ SHALL оставаться неизменным.

#### Scenario: Ключ появляется при первом создании сотрудника
- **WHEN** в базе впервые создаётся запись сотрудника (синхронизация из Bitrix24 или self-heal при
  логине)
- **THEN** у сотрудника сразу есть непустой, уникальный API-ключ, не требующий отдельного действия
  для выпуска

#### Scenario: Повторная синхронизация не меняет существующий ключ
- **WHEN** уже существующая запись сотрудника обновляется очередной синхронизацией из Bitrix24
- **THEN** значение API-ключа сотрудника остаётся тем же, что было до обновления

### Requirement: Уникальность ключа
Backend SHALL гарантировать, что значение API-ключа уникально среди всех сотрудников — по значению
ключа однозначно определяется не более одного сотрудника.

#### Scenario: Коллизия ключей невозможна
- **WHEN** backend генерирует новый API-ключ (при создании сотрудника или регенерации)
- **THEN** сгенерированное значение не совпадает ни с одним существующим ключом другого сотрудника

### Requirement: Аутентификация запроса по API-ключу
Backend SHALL принимать API-ключ в выделенном HTTP-заголовке `X-Api-Key` и SHALL, при совпадении
значения с ключом активного сотрудника, аутентифицировать запрос от имени этого сотрудника с его
текущими правами (permissions), не требуя сессии, cookie или CSRF-токена.

#### Scenario: Валидный ключ аутентифицирует запрос
- **WHEN** запрос к backend содержит заголовок `X-Api-Key` со значением, совпадающим с ключом
  активного сотрудника
- **THEN** backend обрабатывает запрос от имени этого сотрудника с его текущими permissions, без
  проверки сессии и CSRF

#### Scenario: Невалидный или отсутствующий ключ отклоняется на защищённом маршруте
- **WHEN** запрос к маршруту, требующему аутентификации, содержит заголовок `X-Api-Key` с
  значением, не совпадающим ни с одним ключом сотрудника (или заголовок отсутствует и нет валидной
  сессии)
- **THEN** backend отклоняет запрос с ошибкой аутентификации (401), не выполняя обработчик маршрута

### Requirement: Ключ уволенного сотрудника перестаёт действовать
Backend SHALL отклонять аутентификацию по API-ключу сотрудника, для которого `isActive = false`, не
удаляя при этом сам ключ из базы.

#### Scenario: Ключ уволенного сотрудника не проходит аутентификацию
- **WHEN** запрос содержит `X-Api-Key` со значением ключа сотрудника, у которого `isActive =
  false`
- **THEN** backend отклоняет запрос с ошибкой аутентификации (401)

### Requirement: Регенерация ключа
Backend SHALL предоставлять отдельный HTTP-эндпоинт регенерации собственного API-ключа, доступный
только аутентифицированному (через Bitrix-сессию) сотруднику для своего же ключа. При регенерации
backend SHALL немедленно инвалидировать предыдущее значение ключа и вернуть новое значение
непосредственно в теле ответа.

#### Scenario: Регенерация выдаёт новый ключ и деактивирует старый
- **WHEN** аутентифицированный через сессию сотрудник вызывает эндпоинт регенерации своего
  API-ключа
- **THEN** backend сохраняет новое значение ключа, возвращает его в ответе, и последующие запросы
  со старым значением ключа больше не аутентифицируются

#### Scenario: Регенерация недоступна без сессии
- **WHEN** запрос на регенерацию ключа не содержит валидной Bitrix-сессии
- **THEN** backend отклоняет запрос с ошибкой аутентификации, новый ключ не генерируется
