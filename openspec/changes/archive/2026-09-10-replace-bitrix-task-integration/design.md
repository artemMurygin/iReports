## Context

Сегодня задача правила `TaskCompletion` целиком живёт в Bitrix24 (`tasks.task.*`), а локально в
таблице `salary_tasks` хранится только зеркальная копия (`bitrixTaskId`, синкнутый `taskStatus`,
`lastSyncedAt`) — по независимой реализации на каждое направление (`SalaryTaskRepositoryPort` в
`domains/service`, `ShopSalaryTaskRepositoryPort` в `domains/shop`, общая таблица только на уровне
Prisma-схемы с дискриминатором `direction`, без переиспользования кода — паттерн `SalesPlan`/
`SalaryAccrual`, см. `backend/CLAUDE.md`).

По итогам обсуждения задача-сущность SHALL стать по-настоящему общей — не второй копией per-domain
паттерна, а сквозным модулем, как уже есть в проекте прецедент: `src/modules/employee-balance` и
`src/modules/employee-dismissal` (вне `domains/service`/`domains/shop`, единая реализация,
потребляется обоими доменами). Разведка этого прецедента (структура/DI-токены/потребление) описана
в решениях ниже.

Мотивация полного отказа от Bitrix24 — см. `proposal.md` → Why. Согласованные в этой сессии решения:
`shop` входит в объём итерации (см. `proposal.md`), сущность Task общая для всех направлений (не
per-domain), спек-контракт `service/accounting`/`shop/accounting` не меняется — меняется только то,
где живёт задача (см. `specs/tasks/spec.md`, `specs/integrations/bitrix-tasks/spec.md`).

## Goals / Non-Goals

**Goals:**
- Единая сущность «Задача» в новом сквозном модуле `src/modules/tasks`, без дублирования кода между
  `service` и `shop`.
- Полное удаление интеграции с Bitrix24 Tasks API (push и poll) — задача больше не существует нигде,
  кроме iReports.
- Задача видна и управляема в интерфейсе iReports на любой стадии жизненного цикла, независимо от
  того, показывается ли уже строка начисления в зарплатном отчёте.
- Мгновенная реакция расчёта начисления на завершение задачи — без 5-минутной задержки поллинга.

**Non-Goals:**
- Не строим общесистемный task-management (подзадачи, комментарии, вложения, шаблоны задач,
  назначение нескольким исполнителям) — только то, что нужно правилу `TaskCompletion`: заголовок,
  описание, дедлайн, один ответственный, статус.
- Не переносим исторические данные `salary_tasks` (Bitrix task id, синкнутые статусы) — см. Migration
  Plan.
- Не трогаем домен `opt` (пуст, вне скоупа проекта в целом).
- Не вводим новую модель авторизации — переиспользуем существующий RBAC-механизм проекта (см.
  недавний прецедент `work-schedule:view`/`work-schedule:manage` в git-истории).
- Не проектируем напоминания/уведомления о дедлайне — Bitrix24 мог показывать их в своём интерфейсе;
  iReports пока этого не делает (см. Open Questions).

## Decisions

### 1. Модуль `src/modules/tasks` — сквозной, по прецеденту `employee-balance`, не по прецеденту `SalaryTask`

**Выбрано**: новый модуль `src/modules/tasks/` вне `domains/service`/`domains/shop`, с классической
DDD/CQRS-слоистостью (`domain/entities`, `domain/value-objects`, `application/command`,
`application/ports`, `application/services`, `infrastructure/repositories`, `interface/dto`,
`interface/http-controllers`) — зеркалирует `employee-balance` (полноценный модуль), а не
`employee-dismissal` (минимальный, без своего API).

**Почему не текущий паттерн `SalaryTask`** (общая таблица + независимый порт/репозиторий на каждый
домен, как `SalesPlan`/`SalaryAccrual`): этот паттерн подразумевает, что бизнес-логика каждого
направления самостоятельна и лишь физически делит таблицу. У задачи такой самостоятельности нет —
логика идентична для `service`/`shop` (это и была причина решения «сущность общая», см. Context), а
не просто совпадение полей. Дублировать код правила, которое ничем не отличается между направлениями,
не имеет смысла — только сложнее поддерживать при следующем изменении.

**DI-провайдинг — стандартизируем, а не копируем непоследовательность `employee-balance`**:
разведка показала, что даже сам `employee-balance` подключается непоследовательно —
`domains/shop/modules/accounting.module.ts` импортирует `EmployeeBalanceModule` целиком, а
`domains/service/modules/accounting.module.ts` вместо импорта заново регистрирует тот же класс под
тем же токеном. Для `tasks` оба домена (`service`/`shop`) SHALL импортировать `TasksModule` и
инжектить экспортированный порт (`@Inject(TASK_REPOSITORY)`/`CommandBus`) — единообразно, без
повторной регистрации класса-реализации в каждом accounting-модуле. `TasksModule` экспортирует:
репозиторий (`TASK_REPOSITORY`) и регистрирует свои CQRS-хендлеры на общем `CommandBus`
(`CqrsModule`) — см. решение 4 ниже: `accounting` создаёт задачу либо через публичный HTTP `tasks`
(с фронта), либо, для автосоздания на новый период, диспатчем команды через `CommandBus` — `tasks`
не экспортирует отдельного «сервиса создания для accounting», это принципиально (см. решение 4).

### 2. Prisma-модель `Task` — полностью доменно-агностичная, БЕЗ ссылки на `SalaryRule`

**Пересмотрено пользователем**: `tasks` не должен ничего знать про зарплатные правила — задача
создаётся отдельным, самостоятельным запросом с фронта (см. решение 4), а не как побочный эффект
создания правила. Значит `Task` физически не может и не должен хранить `salaryRuleId`/`period`/
`isRecurring` — это понятия зарплатного расчёта, не задачи как таковой. Заменяет `salary_tasks`.
Поля:
- `id` (uuid)
- `direction` (string `service`/`shop`, nullable) — необязательный тег для фильтрации в общем списке
  задач (`/tasks`); НЕ используется для связи с зарплатным правилом и не имеет отношения к тому, кто
  и как эту задачу использует — по прецеденту `BalanceTransaction.direction` (атрибут происхождения,
  не дискриминатор доступа)
- `title` (string), `description` (string, nullable), `deadline` (DateTime)
- `assigneeEmployeeId` (int, БЕЗ FK — ссылается на `bitrix_employees.id`, общую для доменов таблицу,
  без физического ограничения, по прецеденту `MotivationSchema.targetId`)
- `status` (string: `NEW`/`IN_PROGRESS`/`DONE`/`CLOSED_SUCCESSFULLY`/`CLOSED_UNSUCCESSFULLY`/`REWORK`
  — value object `TaskStatus` в домене, см. решение 3)
- `closedSuccessfullyAt` (DateTime, nullable) — момент перевода в `CLOSED_SUCCESSFULLY`
- `createdAt`, `updatedAt`

Убираются полностью: `salaryRuleId`, `period`, `isRecurring`, а также прежние Bitrix-поля
(`bitrixTaskId`, `taskStatus`, `lastSyncedAt`) — все бессмысленны для доменно-агностичной задачи.
Уникального индекса `(salaryRuleId, period)` больше нет — идемпотентность «одна задача на правило за
период» переезжает на сторону `accounting` (см. решение 4).

**Где теперь живёт связь «правило ↔ задача за период»**: не в `tasks`, а в самом `SalaryRule` — поле
`TaskCompletionSalaryConfig.taskIdByPeriod: Record<period, taskId>` (JSON-карта внутри уже
существующей `salary_rules.props`, доп. таблица не нужна). Запись в эту карту — обычный локальный
`UPDATE salary_rules`, без единой транзакции/похода в `tasks` в момент создания правила (см. решение 4).

### 3. Статусная модель — value object `TaskStatus`, шесть состояний с ревью-циклом

Уточнено пользователем: статусная модель богаче исходно спроектированной (`NEW`/`DONE`/`CANCELLED`,
3 состояния) — реальный процесс включает исполнение ответственным и отдельную проверку/приёмку
руководителем:

| Код (домен)             | Отображение          | Терминальный | Кто переводит          |
|--------------------------|-----------------------|:---:|-------------------------|
| `NEW`                     | Новая                 | нет | (создание задачи)       |
| `IN_PROGRESS`              | В работе              | нет | ответственный сотрудник |
| `DONE`                      | Выполнена             | нет | ответственный сотрудник |
| `CLOSED_SUCCESSFULLY`         | Закрыта успешно        | да  | руководитель (проверяющий) |
| `CLOSED_UNSUCCESSFULLY`         | Закрыто неуспешно      | да  | руководитель (проверяющий), либо система при удалении правила |
| `REWORK`                          | На доработку           | нет | руководитель (проверяющий) |

Граф переходов — линейный, с возвратом из ревью на доработку:

```
Новая ──▶ В работе ──▶ Выполнена ──┬─▶ Закрыта успешно        (терминал, ЗАПУСКАЕТ начисление)
                  ▲                 ├─▶ Закрыто неуспешно      (терминал, начисления не будет)
                  │                 └─▶ На доработку
                  └─────────────────────────┘
```

`Выполнена` — это заявление ответственного «я сделал», ещё не финальное состояние: именно
руководитель решает, закрыть успешно, отклонить или вернуть на доработку. `На доработку` ведёт назад
в `В работе` — ответственный переоткрывает работу и снова доводит до `Выполнена`, цикл повторяется
сколько угодно раз.

**Какой статус запускает начисление** (решено пользователем): только `CLOSED_SUCCESSFULLY`
(«Закрыта успешно») — НЕ `DONE`(«Выполнена»). Это бизнес-правило описано не на уровне `TaskStatus` VO
модуля `tasks`, а внутри `accounting`-локальной Entity `SalaryTask.isCompleted()` (см. решение 5
ниже — пересмотрено пользователем: `TaskCompletion.calculate()` вызывает именно этот метод, не чужой
VO), поведенчески описано в `specs/tasks/spec.md` (требование «Проверка и закрытие
задачи руководителем»).

**Отмена при удалении правила**: отдельного состояния `CANCELLED` не заводим — при удалении/отмене
зарплатного правила незавершённая задача (в любом нетерминальном статусе — `NEW`/`IN_PROGRESS`/
`DONE`/`REWORK`) переводится в уже существующий терминальный статус `CLOSED_UNSUCCESSFULLY`
(«Закрыто неуспешно»), инициатор перехода — система, а не руководитель вручную. Это переиспользует
терминальное состояние вместо седьмого статуса; в записи истории задачи разница видна по тому, что
переход инициирован системой, а не проверяющим (см. `specs/tasks/spec.md`).

### 4. Создание задачи — БЕЗ связи между модулями: два отдельных запроса с фронта, без общей транзакции

**Пересмотрено пользователем** относительно первоначального решения (было: `CreateSalaryRuleHandler`
атомарно вставляет `SalaryRule` и вызывает `tasks` внутри одной транзакции). Явное требование:
фронт создаёт задачу и зарплатное правило ДВУМЯ отдельными HTTP-запросами — backend `accounting` не
должен делать ни одного вызова (ни HTTP, ни in-process DI) в `tasks` в момент создания правила.

**Первая задача правила (создание руками через UI)**:
1. Фронт: `POST /v1/tasks` (публичный HTTP-эндпоинт `tasks`, тот же, что и общий раздел `/tasks`) —
   создаёт самостоятельную, ничем не привязанную `Task` (заголовок/описание/дедлайн/ответственный).
   Ответ: `{ id: taskId }`.
2. Фронт: `POST /v1/service/motivation-schema` (создание правила `TaskCompletion`) — в `config`
   передаётся уже полученный `taskId`. `CreateSalaryRuleHandler` НЕ вызывает `tasks` вообще —
   он просто сохраняет `taskId` в `config.taskIdByPeriod[текущийПериод] = taskId` как часть ОДНОГО,
   уже существующего локального `insert(rule)` (см. решение 2 — это JSON-поле внутри `salary_rules.props`,
   отдельного запроса на запись не требует).
3. Единственная связь между двумя запросами — значение `taskId`, которое фронт сам передаёт из ответа
   первого запроса во второй; backend их не связывает и не проверяет друг против друга в момент
   создания (см. Risks — обоснование, почему это приемлемо).

Раньше действовавшая атомарность («правило и первая задача коммитятся вместе или обе откатываются»)
и Bitrix-компенсация (`closeTask` при сбое БД) ОТМЕНЯЮТСЯ этим решением — они были нужны именно
из-за совместного создания в одном запросе, которого больше нет.

**Регулярное правило, новый расчётный период (решено пользователем: остаётся автоматикой бэкенда)**:
для разового правила ничего не происходит (как и раньше). Для регулярного — `accounting` (per domain,
`service`/`shop` независимо) заводит свой сервис `EnsureRuleTaskForPeriodService`
(`application/services/`, ЖИВЁТ В `accounting`, а не в `tasks` — переносится сюда именно потому, что
идемпотентность «одна задача на правило за период» теперь описывается картой в самом
`SalaryRule.config`, которую знает только `accounting`):

```
ensure(rule, period):
  if config.taskIdByPeriod[period] exists → return it (идемпотентно)
  if !config.isRecurring → return null (как и раньше)
  deadline = computeDeadlineForPeriod(config.deadlineTemplate, period)
  taskId = commandBus.execute(CreateTaskCommand({
      title: config.taskTitleTemplate, description: config.taskDescriptionTemplate,
      deadline, assigneeEmployeeId: <employeeId отчёта>, direction,
  }))  // единственный оставшийся межмодульный вызов — через общий CommandBus,
       // тот же публичный use-case tasks, что и HTTP POST /v1/tasks, не отдельный "бэкдор" для accounting
  config.taskIdByPeriod[period] = taskId
  salaryRuleRepo.update(rule)  // локальная запись accounting
  return taskId
```

Вызывается из `GetEmployeeSalaryReportService`/`GetDepartmentSalaryReportService` при открытии отчёта
за новый период — тот же триггер, что и раньше (`@ProdCron` не тикает вне прода). Это единственное
место, где `accounting` всё ещё обращается к `tasks` (через `CommandBus`, публичный use-case,
не приватный сервис только для `accounting`) — потому что создание задачи для АВТОМАТИЧЕСКОГО
периода объективно не может пройти через форму на фронте (никто её руками не открывает).

**Шаблонные поля для автосоздания** (нужны только для регулярных правил, начиная со второго
периода): `TaskCompletionSalaryConfig` получает `taskTitleTemplate`/`taskDescriptionTemplate`/
`deadlineTemplate` — по смыслу то же, что раньше `bitrixTaskTitle`/`taskDescription`/
`deadlineTemplate`, но используются ТОЛЬКО для авто-пересоздания, не для самой первой задачи (та
создана руками с произвольными заголовком/описанием на шаге 1 выше — расхождение между шаблоном и
фактическим содержанием первой задачи — осознанный и допустимый компромисс).

### 5. Чтение статуса задачи расчётом — доменная Entity `SalaryTask` (accounting), создаётся прямо из данных БД, без Port/Adapter

**Пересмотрено пользователем повторно** — предыдущий вариант (Port `TaskClosureStatusPort` +
Adapter-класс `TaskClosureStatusAdapter`, реализующий этот порт) признан избыточной церемонией для
такой простой задачи. Явное указание пользователя: `accounting` (в `service` и `shop` — каждый
независимо) заводит доменную **Entity `SalaryTask`** — не VO, не порт с отдельной реализацией.
Экземпляр `SalaryTask` создаётся ПРЯМО в момент получения данных из БД (внутри
`task-completion-statuses.builder.ts`, без промежуточного класса-переводчика) и несёт метод
`isCompleted(): boolean`, внутри которого описано бизнес-правило accounting — какой статус задачи
считается «выполненным» для целей начисления. Правило не делегируется в `TaskStatus`/`Task` модуля
`tasks` — `accounting` сам, локально, знает и проверяет нужный код статуса; это и есть суть
anti-corruption layer (downstream сам решает, что для него значит «выполнено»), но без формального
Port/Adapter как отдельных классов.

**Устройство** (`service`/`shop` — каждый независимо, свой класс `SalaryTask`, без переиспользования
кода между доменами, как и везде в проекте):

- **Entity `SalaryTask`** (`domain/entities/salary-task/`, accounting, наследует `Entity<SalaryTaskProps>`
  из `src/shared/domain/entity.base.ts` — по тому же паттерну, что и `TaskCompletion`) — поля:
  `taskId` (identity), `status` (сырой код статуса, `string`, ПОЛУЧЕННЫЙ из данных `tasks`, не через
  `TaskStatus` VO модуля `tasks`). Метод `isCompleted(): boolean` возвращает
  `this.props.status === 'CLOSED_SUCCESSFULLY'` — бизнес-правило «что считается выполненным» описано
  ЗДЕСЬ, локально в `accounting`, а не переиспользует поведение чужого `TaskStatus.isClosedSuccessfully()`.
  Не персистентный — создаётся заново на каждый расчёт (в т.ч. при пересчёте открытого периода),
  таблицы под него нет.
- **Фабрика** — статический метод `SalaryTask.create({ taskId, status })`, вызывается прямо там, где
  получены сырые данные (см. ниже) — отдельного класса-адаптера/маппера не заводим.

`task-completion-statuses.builder.ts`/`BuildServiceCalculationContextService` (и shop-аналог) —
единственное место, что всё ещё инжектит `TASK_REPOSITORY` из `src/modules/tasks` (напрямую, без
Port-обёртки поверх): собирает список `taskId` из `config.taskIdByPeriod[period]` каждого своего
`TaskCompletion`-правила, зовёт `TASK_REPOSITORY.findManyByIds(taskIds)`, и для каждого полученного
`Task` сразу конструирует `SalaryTask.create({ taskId: task.id, status: task.status.code })` — в
том же месте, без промежуточного слоя. Дальше строит `erpData.taskCompletionStatuses` по `ruleId`,
как и раньше. `TaskCompletion.calculate()` меняется минимально — вызов `entry.status.isDone()`
становится `entry.isCompleted()` (метод переехал с чужого VO на свою Entity, см. решение 3: начисление
реагирует только на статус, который `SalaryTask.isCompleted()` считает выполненным — сейчас это код
`CLOSED_SUCCESSFULLY`, не любой терминальный/промежуточный статус).

### 6. RBAC — новые права `tasks:view`/`tasks:manage`, по прецеденту `work-schedule:*`

Задача теперь показывается и управляется своим собственным разделом интерфейса (не только внутри
формы зарплатного правила) — по прецеденту недавнего `work-schedule:view`/`work-schedule:manage`
(см. git-историю проекта) заводим аналогичную пару прав для `tasks`. Кто именно получает `manage`
(руководитель, ответственный сотрудник, оба) — решается в `ui-design.md`/`tasks.md`, здесь фиксируем
только сам факт заведения отдельных прав, а не переиспользования общих `accounting:*`.

## Risks / Trade-offs

- **[Risk]** Сотрудники, привыкшие работать со списком задач в Bitrix24 (уведомления, мобильное
  приложение), теряют этот интерфейс — задача видна только в iReports.
  → **Mitigation**: осознанный компромисс, следует из Why в proposal.md (Bitrix-интеграция и так
  ненадёжна/невидима большую часть времени); нужна коммуникация пользователям при выкатке, отдельный
  функционал напоминаний — вне скоупа этого change (см. Open Questions).
- **[Risk]** Ещё одна, третья по счёту, схема DI-подключения сквозного модуля (после двух
  расходящихся вариантов у `employee-balance`) увеличила бы бессистемность кодовой базы.
  → **Mitigation**: решение 1 явно стандартизирует единый способ (импорт `TasksModule` обоими
  доменами) вместо копирования уже существующей непоследовательности.
- **[Risk]** Удаление `salary_tasks` без переноса данных необратимо теряет историю уже созданных (в
  т.ч. тестовых, наблюдавшихся в этой сессии) задач.
  → **Mitigation**: см. Migration Plan — записи признаны непригодными для переноса (привязаны к
  Bitrix task id, вне БД которого не имеют смысла), объём на момент написания design.md — единицы
  строк, все явно тестовые/dev.
- **[Risk]** Два отдельных запроса (создать задачу → создать правило, см. решение 4) не атомарны:
  пользователь может создать задачу и не завершить создание правила (бросить форму, ошибка сети на
  втором запросе) — получаем «осиротевшую» задачу без правила. Backend также не проверяет на шаге 2,
  что переданный `taskId` вообще существует (сознательно, ради нулевой связанности между модулями).
  → **Mitigation**: осознанный компромисс в пользу декаплинга — осиротевшая задача не ломает ничего
  (она просто задача без привязки, видна в общем `/tasks`, её можно удалить вручную или переиспользовать
  для другого правила); фронт UX должен вести пользователя через обе формы как один логический шаг
  (не два независимых действия из разных мест интерфейса) — детали в `ui-design.md`. Ссылка на
  несуществующий `taskId` в `config.taskIdByPeriod` (кто-то вручную подставил чужой ID через API)
  сама себя проявит на первом же расчёте отчёта — `TASK_REPOSITORY.findManyByIds()` просто не вернёт
  такую задачу, `SalaryTask` для этого правила не будет создан, и `TaskCompletion.calculate()`
  останется в состоянии «не выполнено» (тот же код пути, что и для обычной невыполненной задачи, — не
  требует отдельной обработки ошибки).

## Migration Plan

1. Добавить Prisma-модель `Task` (`prisma/schema/task.prisma`) — аддитивная миграция.
2. Реализовать `src/modules/tasks` (domain → application → infrastructure → interface).
3. Переключить `domains/service/modules/accounting` и `domains/shop/modules/accounting` на новую
   модель: `CreateSalaryRuleHandler` перестаёт вызывать `tasks` вообще (принимает `taskId` из тела
   запроса, см. решение 4); `EnsureSalaryTaskForPeriodService` каждого домена заменяется на
   `EnsureRuleTaskForPeriodService` (по-прежнему свой независимый класс на домен, но теперь вызывает
   `tasks` через `CommandBus`, а не через прежний `BitrixTasksGatewayPort`);
   `GetEmployeeSalaryReportService`/`GetDepartmentSalaryReportService`/`task-completion-statuses.builder.ts`
   переключаются на прямой `TASK_REPOSITORY.findManyByIds()` + конструирование `SalaryTask` на
   месте (без Port/Adapter) — удалить домен-специфичные `SalaryTaskRepositoryPort` и их shop-копии.
4. Удалить Bitrix-ветку: `src/sync/bitrix-tasks/*` целиком, task-write-методы `BitrixService`
   (`createTask`/`closeTask`/`updateTaskDeadline`), `BitrixTasksGatewayPort`, связанные Zod-схемы
   (`schema.ts`: `BitrixCreateTaskRequestSchema`, `BitrixTaskAddResponseSchema`,
   `BitrixTaskUpdateResponseSchema`, `BitrixBatchTaskStatusResponseSchema`,
   `BitrixTaskStatusEntrySchema`, `BITRIX_TASK_STATUS_*`).
5. Удалить модель `SalaryTask`/таблицу `salary_tasks` (down-миграция, `DROP TABLE`) — без переноса
   данных (см. Risks). **Требует явного подтверждения перед прогоном в любой среде, где могут быть
   не-тестовые данные** — на момент этого change таких не наблюдалось.
6. Frontend: новый раздел/страница задач + обновление `SalaryRuleForm`/`SalaryReportV2` (детали —
   `ui-design.md`).
7. Откат: пока изменение не влито в `main`, откат — стандартный git-откат ветки/PR. Отдельного
   feature-флага/dual-write между старой и новой веткой не проектируем — текущая Bitrix-интеграция
   уже ненадёжна (см. proposal.md → Why), сохранять её работающей параллельно не имеет ценности.
