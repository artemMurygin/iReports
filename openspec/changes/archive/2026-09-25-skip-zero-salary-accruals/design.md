## Context

См. proposal.md - Why. Оба домена (`service`, `shop`) реализуют закрытие периода и зарплатный отчёт
независимо и без общего кода (`backend/CLAUDE.md`), поэтому решения ниже применяются к каждому домену
симметрично, отдельными изменениями в параллельных файлах.

Ключевые точки существующего кода (обе реализации структурно идентичны, различаются только неймспейсом
домена):

- `CloseAccountingPeriodHandler.buildAccrualDocuments(period, rows)` — по одной строке снапшота
  (`AccountingPeriodSnapshotRow`, одна на сотрудника) вызывает `SalaryAccrual.createFromSnapshot({...})`,
  который строит `SalaryAccrualLine[]` документа из построчной разбивки правил этого сотрудника.
- `PeriodCalculationOrchestrator.calculate(rules, context)` — считает `CalculationLine[]` (в т.ч.
  `amount`) независимо по каждому правилу; `buildRuleBreakdown()` превращает их в `RuleBreakdownLine[]`
  (поля `ruleId, type, name, targetRole, amount, ...`), пропуская только те правила, чей `calculate()`
  вернул `null` (сейчас это только «за выполнение задачи» до того, как для него заведена задача).
- `buildSalaryReportRules()` (`to-salary-report-rules.ts`) вызывает `buildRuleBreakdown()` дважды
  (FACT и PROGNOSE) и сводит результат по `ruleId` в `EmployeeSalaryReportRule[]` — плоский список,
  который отдаётся в ответе `salary_report/employee/:id/:period` и `.../department/:id/:period` и
  рендерится в `pages/SalaryReportV2`.
- Суммы везде — обычный `number` (целые рубли), не Money value-object; итоговая сумма периода
  считается отдельно (`PeriodCalculationOrchestrator.total()`), не через длину массива строк.

## Goals / Non-Goals

**Goals:**
- Убрать строки с нулевой суммой правила из документа начисления и из построчной разбивки зарплатного
  отчёта, не трогая расчёт самих сумм и не трогая существующую видимость строки правила «за выполнение
  задачи».
- Сохранить симметрию между `service` и `shop`.

**Non-Goals:**
- Не меняется расчёт суммы ни одного вида правила — это чисто фильтрация уже посчитанного результата
  перед его материализацией в строку.
- Не меняется поведение `Payout`/`BalanceTransaction.forPayout`/ERP cash-документов — там нулевая сумма
  и так запрещена существующим инвариантом.
- Не документируется целиком капабилити `SalaryAccrual`/`Payout` (по-прежнему отложено на отдельный
  change, см. `Purpose` в `openspec/specs/service/accounting/spec.md`) — этот change добавляет только
  два узких требования поверх существующего пробела.

## Decisions

### 1. Фильтрация — на границе построения строки, не в domain-инварианте сущности

Строка `SalaryAccrualLine` для правила с `amount === 0` не создаётся вовсе (не создаётся и сразу не
отбрасывается) — фильтр применяется в цикле, который сейчас строит массив строк перед вызовом
`SalaryAccrual.createFromSnapshot`/конструктора линии, а не как исключение/инвариант внутри самой
`SalaryAccrualLine`. Причина: `amount === 0` — не invalid state (это не бракованная строка, просто её
не нужно создавать), а `Number.isInteger(amount)`-инвариант сущности не должен знать о том, скрывать
её или нет — это ответственность вызывающего кода, а не сущности.

Альтернатива (отклонена): проверять в конструкторе/инварианте `SalaryAccrualLine.validate()` и кидать
исключение или молча пропускать. Отклонено — инвариант сущности не место для решения о видимости,
плюс это усложнило бы читаемость `validate()` веткой, не относящейся к целостности данных.

### 2. В отчёте фильтр — после сведения FACT/PROGNOSE, по паре значений

`buildSalaryReportRules()` уже сводит по `ruleId` результат двух вызовов `buildRuleBreakdown()`
(FACT и PROGNOSE) в `EmployeeSalaryReportRule` с полем `amount: {fact, prognose}`. Фильтр «скрыть,
если оба равны нулю» применяется к этому уже свёденному списку — после сведения, а не к каждому из
двух черновых `RuleBreakdownLine[]` по отдельности. Причина: только после сведения известны оба
значения одновременно; фильтрация до сведения потребовала бы прокидывать значение из одного прогона
в другой, усложняя `buildRuleBreakdown()`, у которого сейчас нет и не должно быть знания о втором
режиме.

### 3. Явное исключение правила «за выполнение задачи» из общего фильтра по типу, а не по побочному эффекту

Строка правила «за выполнение задачи» и так почти всегда переживёт фильтр «оба значения — ноль», так
как в прогнозном режиме по умолчанию сразу видна ненулевая сумма (см. существующее требование). Но в
редком случае, когда руководитель сам задал сумму начисления по умолчанию правила равной нулю, оба
значения (`fact`, `prognose`) окажутся нулевыми, и общий фильтр ошибочно скрыл бы уже заведённую и
обязанную быть видимой строку. Поэтому фильтр явно проверяет `type` строки (дискриминатор
`RuleBreakdownLine.type`/`EmployeeSalaryReportRule.type`) и не применяется к правилу «за выполнение
задачи» — видимость этого типа строки полностью остаётся во власти уже существующей, отдельно
задокументированной логики (наличие/статус задачи), а не значения суммы.

Альтернатива (отклонена): полагаться на то, что прогноз почти всегда ненулевой, без явной проверки
типа. Отклонена — оставляет скрытый край, где поведение регрессирует именно в момент, когда сумма
правила настроена в 0, что прямо противоречит существующему тестируемому требованию видимости.

### 4. Симметричная, независимая правка в `service` и `shop`

Оба домена получают одинаковое по сути изменение как отдельные правки в параллельных файлах (без
общего хелпера/сервиса) — в соответствии с правилом изоляции модулей/доменов проекта (`CLAUDE.md`,
«Межмодульные зависимости внутри backend»). Расхождение реализаций между доменами уже существует
(разные наборы видов правил), общий код создал бы связность, которую архитектура проекта явно
запрещает.

## Risks / Trade-offs

- **[Риск] Существующие тесты и снапшот-фикстуры ожидают строку/документ с нулевой суммой** →
  **Митигация**: точечно обновить `close-accounting-period.handler.spec.ts` (блок «документы
  начисления») и тесты `rule-breakdown.builder`/`to-salary-report-rules` под новое поведение; это
  ожидаемое, осознанное изменение контракта, а не побочный эффект.
- **[Риск] Отчёт по уже закрытому периоду читается из зафиксированного снапшота (см. requirement
  «Закрытие периода фиксирует неизменяемый снапшот») — старые снапшоты, созданные до этого change,
  всё ещё содержат нулевые строки** → **Митигация**: не выполняется ретроактивная миграция/переписывание
  старых снапшотов — фильтрация факта из снапшота на чтение не производится, только на записи новых
  документов при будущих закрытиях. Явно фиксируется как принятое ограничение, не баг.
- **[Риск] Фронтенд (`RuleGroupDetailsPanel`/`LedgerRuleRow`) может рассчитывать на непустой список строк
  группы правила** → **Митигация**: проверить при реализации, что группа с пустым списком строк (все
  её правила отфильтрованы) корректно не рендерится/не даёт пустую панель — это поведенческая проверка
  на этапе `tasks`, изменений контракта не требует.

## Migration Plan

Обратной миграции данных нет — изменение влияет только на вновь создаваемые документы начисления и на
результат чтения зарплатного отчёта за счёт новых правил фильтрации в момент запроса (для ещё открытых
периодов) или в момент следующего закрытия (для снапшота). Откат — снятие фильтра в тех же точках, без
данных для отката.
