## Context

См. `proposal.md` — Why. Технически смещение дедлайна нужно провести через три слоя, дублирующих
логику между направлениями `service`/`shop` (см. `backend/CLAUDE.md`, «Межмодульные зависимости» —
`service`/`shop` не переиспользуют код друг друга, каждое направление обновляется независимо своей
копией):

- домен: `computeDeadlineForPeriod` (`domains/service/.../ensure-rule-task-for-period.service.ts`) и
  `computeRecurringTaskDeadline` (`domains/shop/.../domain/services/task-deadline.ts`) — сейчас всегда
  берут год/месяц из `period.getBounds().from`, число месяца — из `deadlineTemplate`, зажатое
  `period.getTotalCalendarDays()`;
- персистентность: `deadlineTemplate: string` в `TaskCompletion{Service,Shop}SalaryConfig` и
  соответствующих zod-схемах (`infrastructure/schemas/salary-rule.schema.ts`) — хранится как часть
  JSON-конфигурации правила, отдельной колонки/миграции БД не требует;
- фронтенд: `TaskCompletionRuleFields.tsx`, `ruleDraft.ts`, `ruleFormSchema.ts` (`service`/`shop`).

`Period` (`src/shared/domain/period.value-object.ts`) уже даёт `previous()` для сдвига на месяц назад
(используется автосозданием плана продаж), но не имеет операции сдвига вперёд/на N месяцев.

## Goals / Non-Goals

**Goals:**
- Дать возможность задать дедлайн автосоздаваемой регулярной задачи в месяце ПОСЛЕ месяца периода
  (смещение ≥ 0 расчётных периодов), сохранив текущее поведение как смещение по умолчанию (0).
- Не менять поведение разового правила (`isRecurring: false`) — дедлайн там по-прежнему буквальная
  дата шаблона.
- Обратная совместимость с уже сохранёнными правилами без нового поля — без ручной миграции данных.

**Non-Goals:**
- Отрицательное смещение (дедлайн раньше периода) — сценарий не запрошен.
- Изменение момента/частоты автосоздания задачи (крон/оркестрация) — меняется только вычисление
  даты дедлайна внутри уже существующего потока автосоздания.
- Произвольные пользовательские правила повторения (не «через N периодов», а, например, «второй
  вторник месяца») — вне рамок этого изменения.

## Decisions

### 1. Новое поле `deadlinePeriodOffset`, а не переосмысление `deadlineTemplate`
В `TaskCompletionSalaryConfig` (service) и `TaskCompletionShopSalaryConfig` (shop) добавляется
`deadlinePeriodOffset: number` (целое, ≥ 0) рядом с существующим `deadlineTemplate`. `deadlineTemplate`
не меняет формат (ISO-дата) — для регулярного правила из неё, как и раньше, берётся число месяца и
время суток, но целевой месяц/год теперь вычисляется от периода со сдвигом на `deadlinePeriodOffset`,
а не всегда равен месяцу периода.
Альтернатива — заменить `deadlineTemplate` на пару «число месяца + время» без ISO-обёртки: отклонена,
это ломает формат хранения без выигрыша в выразительности и требует более инвазивной миграции формы
(два новых независимых поля вместо одного дополнительного).

### 2. Верхняя граница смещения — 0..3 периода
Смещение ограничивается диапазоном `[0, 3]` (валидация на уровне zod-схемы контракта и формы).
Реальный кейс — «сверка после закрытия месяца», это единицы, не десятки периодов; жёсткая граница
защищает от опечатки (например, ввода года вместо числа периодов) и позволяет фронтенду использовать
явный select вместо произвольного числового поля. Значение выбрано с запасом сверх упомянутого в
задаче кейса «до 5 февраля за январь» (смещение 1).

### 3. `Period.shiftMonths(offset: number): Period`
В `src/shared/domain/period.value-object.ts` добавляется метод `shiftMonths`, обобщающий уже
существующий `previous()` (`previous()` эквивалентен `shiftMonths(-1)`, но остаётся отдельным методом
ради обратной совместимости вызовов и понятности их сайтов использования). `computeDeadlineForPeriod`/
`computeRecurringTaskDeadline` вызывают `period.shiftMonths(offset)` и берут год/месяц из
`targetPeriod.getBounds().from`, число дней для зажатия — из `targetPeriod.getTotalCalendarDays()`
(вместо текущего `period.getTotalCalendarDays()` от исходного периода) — иначе клэмп 31 числа считался
бы по длине января, а не февраля, для смещения в короткий месяц.
Это единственное общее место между `service`/`shop` — `Period` уже используется как общий (не
бизнес-специфичный для одного направления) строительный блок в `src/shared/domain/`; сама функция
вычисления дедлайна по-прежнему дублируется по направлениям, как и раньше.

### 4. Обратная совместимость легаси-строк
Правила, сохранённые до этого изменения, не имеют `deadlinePeriodOffset` в персистентном JSON.
Мапперы (`ServiceSalaryRuleMapper`/`ShopSalaryRuleMapper`, аналог уже существующей деривации
`accountingPeriod` для легаси-строк) подставляют `deadlinePeriodOffset: 0` при отсутствии поля в
`toDomain` — воспроизводит точное текущее поведение для всех существующих правил, без скрипта
миграции данных.

### 5. Контракты и форма
`commands/salary-rule.ts`/`commands/shop-salary-rule.ts`: `deadlinePeriodOffset: z.number().int().min(0).max(3).default(0)`
рядом с `deadlineTemplate`. Форма (`TaskCompletionRuleFields.tsx`) добавляет `Select`/`SegmentedControl`
«Дедлайн относится к» с вариантами «этому периоду» (0) / «следующему периоду» (1) / «через 2 периода» (2)
/ «через 3 периода» (3), видимый только при `isRecurring: true`, рядом с существующим полем даты —
подпись существующего поля даты уточняется («Число и время дедлайна»), само поле не убирается.

## Risks / Trade-offs

- [Изменение дедлайна уже существующего регулярного правила задним числом] → не относится к этому
  изменению: смещение применяется только при автосоздании НОВОЙ задачи на будущий период; уже
  созданные задачи прошлых периодов не пересчитываются (как и сегодня при правке `deadlineTemplate`).
- [Рассинхронизация service/shop копий] → обе копии (`domain/services/task-deadline.ts` в shop,
  `computeDeadlineForPeriod` в service) правятся в одном PR по одному и тому же принципу, как и при
  предыдущих изменениях этой пары функций (см. комментарии-перекрёстные ссылки в текущем коде).
- [Легаси-строки без поля] → закрыто решением 4 (дефолт 0 на границе маппера, не требует бэкфилла).

## Migration Plan

Миграции БД не требуется — поле лежит внутри существующей JSON-конфигурации правила. Деплой:
1. Выкатить бэкенд (домен + мапперы с дефолтом `deadlinePeriodOffset: 0` для легаси-строк) и
   обновлённые контракты.
2. Выкатить фронтенд с новым контролом формы.
Откат: откат обоих деплоев независим и безопасен — старые записи не содержат нового поля и не
зависят от него; при откате бэкенда новое поле в свежесохранённых правилах просто игнорируется старым
кодом (та же логика, что и сейчас, без смещения).
