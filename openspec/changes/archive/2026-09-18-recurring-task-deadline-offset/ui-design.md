# UI Design: recurring-task-deadline-offset

## Источник дизайна

Дизайн-пасс в Pencil сознательно не делался (решение пользователя): `architecture.md` не вводит ни

`design/sallary-first-iteration.pen`, собственного фрейма там не имеет). Полноценный дизайн-пасс не
добавил бы информации сверх описания ниже.

Новых экранов/фреймов нет — см. выше.

## Описание изменения разметки

В `TaskCompletionRuleFields.tsx`, блок «Шаблон для автосоздания задачи на новый период» (виден только
при `isRecurring: true`), рядом с существующим полем «Дедлайн шаблона» (`<input type="date">`, поле
`task-deadline-template`):

- Подпись существующего поля даты уточняется: «Дедлайн шаблона» → **«Число и время дедлайна»** —
  чтобы явно отделить его от нового контрола ниже (само поле, его тип `date` и обработчик `onChange`
  не меняются).
- Под ним добавляется новый контрол **«Дедлайн относится к»** — `Select` из `shared/ui` (тот же
  примитив, что уже используют соседние поля этого блока, например `taskLinkTemplates`/периодичность
  выше по форме), с 4 пунктами:
  - «этому периоду» (`deadlinePeriodOffset: 0`, значение по умолчанию),
  - «следующему периоду» (`1`),
  - «через 2 периода» (`2`),
  - «через 3 периода» (`3`).
- Под контролом — пояснительный текст мелким шрифтом (тот же стиль, что у существующей подсказки
  «Число месяца — дедлайн каждого периода»), например: «Например, для правила за январь и смещения
  „следующему периоду“ дедлайн — выбранное число месяца в феврале».
- Оба контрола (дата + смещение) укладываются в существующую сетку `grid-cols-1 sm:grid-cols-2` —
  либо в одну ячейку друг под другом, либо третьей ячейкой сетки (уточняется на этапе реализации по
  фактической ширине блока, решение не влияет на бизнес-логику).
- Контрол не показывается при `isRecurring: false` (одноразовое правило) — как и весь окружающий блок
  уже сегодня.
- Валидация: как и у соседних полей блока, ошибка (если backend её вернёт) отображается через
  существующий `FieldError`.

## Ключевые состояния экранов

Дополнительных состояний, влияющих на разметку, нет — контрол всегда в одном из 4 фиксированных
значений, невалидных промежуточных состояний в UI не возникает (кроме уже существующей общей ошибки
валидации формы).
