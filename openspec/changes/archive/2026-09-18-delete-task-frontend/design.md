## Context

`DELETE /v1/tasks/:id` уже реализован (`backend/src/modules/tasks/interface/http-controllers/delete-task.http.controller.ts`) — удаляет задачу безвозвратно, каскадно чистит `TaskComment`/`TaskLink`, возвращает `204`/`404`. Он уже вызывается с фронтенда, но только косвенно — из `features/SalaryRuleForm/model/taskApi.ts` (`salaryRuleTaskApi.remove`), в контексте удаления задачи зарплатного правила. Кросс-импорт между `features` запрещён FSD-правилами проекта, поэтому переиспользовать этот клиент из `features/TaskStatusControl` нельзя — нужен свой аналогичный API-метод.

Задача (`Task`) по дизайну не знает о зарплатном правиле, которое может на неё ссылаться (см. `openspec/specs/tasks/spec.md`, «Задача — полностью самостоятельная сущность»). Backend уже осознанно допускает удаление задачи, на которую ссылается активное правило `TaskCompletion` — обратной связи «задача → правило» не существует. Если такую задачу удалить, при следующем формировании зарплатного отчёта строка начисления по правилу просто не появится (тот же код-путь, что и «задача ещё не создана»), без ошибки — это уже принятое поведение, не предмет данного изменения.

## Goals / Non-Goals

**Goals:**
- Дать пользователю прямой способ удалить произвольную задачу из карточки задачи (`TaskDetailsPanel`).
- Явно предупредить о безвозвратности удаления перед выполнением действия.

**Non-Goals:**
- Не добавлять на backend проверку/запрет удаления задачи, связанной с активным зарплатным правилом — это уже принятое, задокументированное поведение вне скоупа этого изменения.
- Не добавлять действия удаления в список задач (`pages/Tasks`) — карточка/строка там целиком кликабельна для открытия деталей, per-row действий в списке нет и раньше не было; удаление остаётся только внутри карточки деталей.
- Не менять поведение уже существующего удаления «задачи для зарплатного правила» в `features/SalaryRuleForm` — это отдельный, самостоятельный UI-поток.

## Decisions

**Расположение кнопки — заголовок `TaskStatusCard`, рядом с «Редактировать»/«Закрыть».**
Альтернатива — выносить в отдельное меню (kebab-menu). Отклонено: в проекте нет паттерна kebab-меню для карточек такого рода, а действий всего три (редактировать/закрыть панель/удалить) — прямые `IconButton` читаются проще и следуют существующему прецеденту (`TaskCompletionRuleFields.tsx`, `Trash2` + `variant="danger"`).

**Кнопка удаления доступна всегда, независимо от статуса задачи** (в отличие от «Редактировать», которая скрыта в терминальном статусе).
Редактирование скрыто в терминальном статусе, потому что менять содержание уже закрытой задачи противоречит семантике «закрыта». Удаление — другое действие: пользователю всё ещё может понадобиться убрать более неактуальную или ошибочно оставленную задачу независимо от того, в каком она статусе. Ограничивать удаление по статусу не требуется ни одним существующим requirement.

**Confirm — модальный диалог по существующему паттерну хук+диалог (`Modal` + `useDelete*`), не `window.confirm`.**
В проекте уже устоявшийся, единообразный паттерн для деструктивных действий (`DeleteRuleTaskDialog`/`useDeleteRuleTask`, `DeleteMotivationSchemaDialog`/`useDeleteMotivationSchema` и др.), явно задокументированный в коде как обязательный («Confirm — не `window.confirm`»). shadcn `AlertDialog` в проекте не используется вообще — переиспользуется имеющийся `shared/ui-kit/organisms/Modal`.

**Свой `tasksApi.remove` + `useDeleteTask` внутри `features/TaskStatusControl`, а не переиспользование `salaryRuleTaskApi.remove` из `features/SalaryRuleForm`.**
FSD запрещает кросс-импорт между `features`. Дублирование тонкого API-метода (`DELETE /v1/tasks/:id`, без тела) — принятая в проекте цена изоляции слайсов; сам метод — однострочный fetch-вызов, как и остальные в `TaskStatusControl/model/api.ts`.

**После успешного удаления — закрыть `TaskDetailsPanel` (`onClose()`) и инвалидировать `TASKS_QUERY_KEY_PREFIX`.**
Панель детали не может показывать удалённую задачу; инвалидация (а не точечный `removeQueries`) достаточна и проще — список `pages/Tasks` и так перезапрашивается по тому же префиксу при любом мутирующем действии над задачами (см. `useUpdateTask`).

## Risks / Trade-offs

[Пользователь удаляет задачу, на которую всё ещё ссылается активное зарплатное правило] → диалог подтверждения явно предупреждает о безвозвратности удаления; специальной проверки/блокировки на этот случай не вводится, т.к. это уже принятое поведение на уровне backend (см. Context) и не входит в цели этого изменения.
