## Context

См. `proposal.md` — «Why» за мотивацией. Технический контекст, важный для выбора решения:

- `domains/shop/modules/warehouse/` уже существует и отдаёт `GET /shop/warehouse/catalog` — дерево
  категорий каталога из уже засинканных `MoySkladProductFolder` (иерархия `parentId`,
  `ProductFolderTreeService` уже умеет обходить дерево). Остатков и оборота в этом модуле пока нет.
- Справочника складов МойСклад (`MoySkladStore`) в проекте нет — ни модели, ни синка.
- `MoySkladDemand`/`MoySkladDemandPosition` синкаются каждые 5 минут (`MoySkladSyncCron`) ради
  расчёта зарплаты. МойСклад отдаёт по `Demand` поле `store` (`domains/shop/integrations/moySklad/
  schemas/demands.schema.ts`), но синк (`moysklad-sync.service.ts`, апсерт `Demand`) его не читает и
  не сохраняет. `MoySkladDemandPosition` уже хранит посчитанные `quantity`, `price`, `discount`,
  а также готовые `sum`, `cost`, `profit` — пересчитывать сумму позиции вручную не нужно.
- Готового отчёта «Обороты» в JSON API МойСклад нет — это только раздел UI. `/report/sales/
  plotseries` даёт агрегаты продаж, но группировка только по `organization`/`store`/`project`/
  `retailStore`, не по категории товара — не подходит.
- `/report/stock/all` и `/report/stock/bystore` поддерживают асинхронный режим (`async=true`);
  подтверждено документацией, что с `async=true` нельзя передавать `limit`/`offset` (ошибка 61001) —
  то есть весь отчёт по всей номенклатуре отдаётся одной задачей, без ручной пагинации. Строка
  отчёта (`StockAll`) содержит `folder` (прямая категория, не путь до корня), `stock` (шт.), `price`
  (себестоимость, коп.), `salePrice`. Точный формат опроса статуса и получения готового результата
  асинхронной задачи документацией, доступной через использованный инструмент, подтверждён не
  полностью (см. «Открытые вопросы»).
- Аналог "период + снэпшот при закрытии" для направления «Магазин» — общая с `service` Prisma-таблица
  `AccountingPeriod` (дискриминатор `direction`), но свой доменный агрегат `ShopAccountingPeriod`
  (`domains/shop/modules/accounting/domain/entities/accounting-period/accounting-period.entity.ts`)
  и своё доменное событие `ShopAccountingPeriodClosedDomainEvent`
  (`domains/shop/modules/accounting/domain/events/accounting-period-closed.domain-event.ts`) — в
  отличие от сервисной версии, у события нет поля `direction` (оно и так только про «Магазин»).
  Порт `SHOP_ACCOUNTING_PERIOD_REPOSITORY` существует, но **не экспортируется** из
  `ShopAccountingModule` — инжектить его из другого shop-модуля сейчас нельзя. Готовый пример такого
  межмодульного экспорта в shop уже есть: `ShopAccountingModule` реэкспортирует `ShopSalesModule`
  целиком, чтобы `CloseShopAccountingPeriodHandler` мог получить `SHOP_SALES_PLAN_REPOSITORY`.

## Goals / Non-Goals

**Goals:**
- Определить архитектуру backend-модуля, который считает, хранит и отдаёт отчёт по оборачиваемости
  магазина за месяц: оборот и остаток по дереву категорий и складам, коэффициент оборачиваемости по
  каждой паре «категория × склад».
- Определить, как получить недостающий справочник складов и привязать к нему уже синкаемые
  `Demand`.
- Определить источники данных: оборот — целиком из уже засинканных данных БД; остаток — из
  асинхронного отчёта МойСклад.
- Определить, как отслеживать открытый/закрытый месяц, переиспользуя статус `ShopAccountingPeriod`
  вместо собственной таблицы периода.

**Non-Goals:**
- Не учитываем розничные продажи (`RetailDemand`) и отчёты комиссионера (`CommissionReportIn`) в
  обороте — по прямому указанию пользователя.
- Не проектируем UI (см. `ui-design.md`, если потребуется отдельно).
- Не добавляем запись данных обратно в МойСклад — модуль read-only относительно ERP.
- Не переносим существующий 5-минутный синк `Demand`/`ProductFolder` на другую периодичность.
- Не делаем backfill за периоды, для которых пользователь не запросит отчёт — только то, что
  описано в Migration Plan.

## Decisions

### D1. Расширение существующего модуля `domains/shop/modules/warehouse`, без нового модуля
`warehouse` уже отвечает за каталог/дерево категорий (`GET /shop/warehouse/catalog`) — отчёт по
оборачиваемости логически продолжает эту же ответственность (остатки и обороты товара), а не
заводит собственный домен. Слои `domain/application/infrastructure/interface` — по образцу
`accounting`/`sales`. Файлы без слова `shop` в имени, классы/DI-токены — с префиксом `Shop`/`SHOP_`.

**Альтернатива**: новый модуль `stock`/`turnover-report`. Отклонено — дублировало бы уже начатую
ответственность `warehouse` за остатки/каталог без выгоды от разделения.

### D2. Справочник складов — новая Prisma-модель `MoySkladStore` + периодический синк
Новая модель `MoySkladStore` (`id`, `name`) в `moySklad.prisma`, метод получения списка складов в
`MoyskladService` (`GET /entity/store`, обычный постраничный справочник — не кастомный эндпоинт, как
у RoApp), апсерт в `MoySkladSyncService`, подключаемый к тому же 5-минутному `MoySkladSyncCron`, что
и остальные справочники shop (в отличие от сервисного аналога, где склады синкались бы разово —
здесь для единообразия с уже принятой в shop моделью синка). Тот же вызов синка складов добавляется
и в `UploadInitialMoySkladDataHandler` (`domains/shop/sync/moySklad/application/command/
upload-initial-moysklad-data.handler.ts`) — обработчик команды, которую диспетчит скрипт
`backend/src/scripts/initialUploadData.ts` (запускается как `npm run initial`/`npm run initialProd
<date> M`) — рядом с уже имеющимися там вызовами `uploadEmployees`/`uploadProductFolders`/
`uploadProducts`/`uploadServices`, чтобы первоначальная раскатка на продакшен не требовала ждать
первый тик 5-минутного крона.

**Альтернатива**: получать список складов на лету при построении отчёта. Отклонено — нужен стабильный
внешний ключ для связи со строками `MoySkladDemand`/отчётом об остатках, и склады меняются редко —
периодический синк в БД дешевле и единообразнее.

### D3. Привязка склада к `Demand` — используем уже приходящее, но отбрасываемое поле
`MoySkladDemand` дополняется только полем `storeId` (без дублирования названия склада). Значение уже
приходит в ответе МойСклад (`demands.schema.ts`: `store: MetaWrapperSchema`), но сейчас не читается в
`moysklad-sync.service.ts` при апсерте — правится маппинг апсерта, без изменения структуры ответа
МойСклад. Название склада не хранится на `Demand` — оно получается join'ом на `MoySkladStore` по
`storeId` (см. D2), чтобы не дублировать и не рассинхронизировать название при переименовании склада
в МойСклад. Аддитивная миграция (nullable-колонка).

Бэкфилл `storeId` для уже засинканных прошлых `Demand` не требует отдельного миграционного скрипта:
`UploadInitialMoySkladDataHandler` уже вызывает `uploadCreatedDemands(fromDate)` — тот же метод
апсерта `MoySkladSyncService`, что использует и 5-минутный крон. После того как маппинг апсерта
дополнен `storeId`, разовый повторный запуск `npm run initialProd <дата> M` на продакшене с датой в
прошлом переисполнит эту же историческую выгрузку `Demand` и проставит `storeId` во всех
перезапрошенных записях как часть обычного upsert (см. Migration Plan о том, насколько далеко в
прошлое нужно указать дату).

### D4. Оборот — чистая агрегация уже засинканных данных, без обращений к МойСклад
Оборот и количество проданного за месяц по категории/складу считаются SQL-агрегацией:
`MoySkladDemandPosition` (готовые `sum`, `quantity`) → join `MoySkladDemand` (период по `moment`,
`storeId` после D3) → join `MoySkladProduct` → `productFolderId`. Строки суммируются, категория
получает суммы своих товаров и товаров всех вложенных подкатегорий (обход дерева — см. D6).

**Альтернатива**: пересчитывать сумму позиции вручную (`price × quantity × (1 − discount/100)`).
Отклонено — `MoySkladDemandPosition.sum` уже хранит именно эту величину; ручной пересчёт дублировал
бы логику синка и рисковал разойтись с ней при изменении зависимого расчёта (`cost`/`profit` там же).

### D5. Остаток — почасовая фоновая синхронизация в БД через асинхронный отчёт об остатках,
### с хранением истории выгрузок
Отдельная новая крон-задача (`@ProdCron(CronExpression.EVERY_HOUR)`) раз в час запрашивает
`GET /report/stock/bystore?async=true&groupBy=product` (без `limit`/`offset`) и **добавляет** новый
снимок в таблицу `MoySkladStock` (см. D7.1) — строки не перезаписываются, каждый прогон крона
пишет свою порцию строк с меткой времени снимка (`snapshotAt`), помечающей, к какому именно запуску
относится набор строк. Строки ответа МойСклад содержат `folder` (прямая категория), `store`,
`stock` (шт.), `price` (себестоимость, коп.).

Это отдельный шаг от построения самого отчёта: синхронизация остатков только пополняет
`MoySkladStock` новыми снимками, а рулап по дереву категорий и запись строк отчёта
(`MoySkladTurnoverReportLine`) делает отдельная крон-задача пересчёта отчёта (см. D9), читая
**последний по времени** снимок (`MAX(snapshotAt)`) из `MoySkladStock` — так же, как она читает уже
засинканный `MoySkladDemand` для оборота (см. D4). Обе крон-задачи независимы: пересчёт отчёта не
обязан быть "приклеен" к тому же тику, что и синк остатков — важно только, чтобы самый свежий снимок
не был старше часа, что и обеспечивает почасовой синк.

Хранение истории (а не одного перезаписываемого снимка) даёт: возможность аудита/отладки — увидеть
остатки на любой прошедший час, а не только "текущее" состояние; при закрытии периода (D9) —
возможность зафиксировать снэпшот отчёта по снимку остатков, максимально близкому к моменту
закрытия, а не по случайно последнему перезаписанному значению; возможность пересчитать отчёт за
прошлый час/день задним числом при обнаружении ошибки в расчёте, без необходимости заново
опрашивать МойСклад (данные уже есть в истории).

Асинхронный режим (`async=true`) сохраняется, а не заменяется на постраничную синхронную выгрузку —
несмотря на то, что теперь это фоновая задача без давления на латентность HTTP-ответа, один запрос
на весь каталог снижает нагрузку на API МойСклад по сравнению с постраничным перебором.

**Альтернатива**: `/report/stock/all` (без разбивки по складам) + отдельный подбор склада на
основании других данных. Отклонено — `/report/stock/bystore` уже даёт разбивку по складам напрямую,
без дополнительных join'ов или допущений.

**Альтернатива**: не персистить `MoySkladStock`, использовать ответ отчёта транзитно прямо во время
пересчёта отчёта (без промежуточной таблицы). Отклонено по прямому указанию — раздельные
крон-задачи синка и пересчёта проще устроены, переживают друг друга при сбое одной из них, и дают
возможность отлаживать/инспектировать сырые остатки отдельно от готового отчёта — по аналогии с тем,
как уже устроены `MoySkladDemand`/`MoySkladProductFolder` (сырой синк → отдельная агрегация).

**Альтернатива**: перезаписывать единственный текущий снимок (upsert по `productId`/`warehouseId`)
без истории. Отклонено по прямому указанию — история снимков нужна для аудита и для более точной
привязки остатка к моменту закрытия периода (см. выше).

**Риск, требующий проверки на этапе реализации**: точный контракт опроса статуса асинхронной задачи
и получения итогового результата — см. «Открытые вопросы» и «Риски». Поскольку это теперь фоновая
задача, а не часть ответа на пользовательский запрос, неопределённость длительности/повторных
попыток опроса не влияет на отзывчивость отчёта для пользователя — только на своевременность
появления нового снимка в `MoySkladStock`.

### D5.1. Бэкфилл исторического остатка за прошлые периоды — легаси-эндпоинт ассортимента
`/report/stock/bystore`/`/report/stock/all` не имеют параметра «на дату» (в спецификации эндпоинта —
только `limit/offset/filter/order/groupBy/includeRelated`) и отдают остаток только на текущий
момент — почасовой синк (D5) не может создать историю снимков за периоды до своего запуска.

Для запрошенного года истории используется отдельный (легаси, но пока действующий) эндпоинт
`GET /entity/assortment` с фильтром `stockMoment`/`stockStore` (`filter=stockMoment=<конец
месяца>;stockStore=<id склада>`) — он умеет считать `stock`/`quantity` на произвольный момент в
прошлом и для конкретного склада. Разовый шаг бэкфилла (см. Migration Plan) обходит каждый из
запрошенных прошлых месяцев × каждый склад и пишет в `MoySkladStock` **один снимок на конец
месяца** (`snapshotAt` = последний момент месяца), а не почасовые снимки, как для текущего периода
— так и было запрошено. С момента раскатки почасовой синк (D5) продолжает с той плотностью снимков,
которая ему свойственна; таблица `MoySkladStock` в результате содержит смешанную плотность: месячные
снимки в прошлом, часовые — начиная с раскатки. Это ожидаемо, не является дефектом.

Этот же бэкфилл-шаг добавляется в тот же `UploadInitialMoySkladDataHandler`/`npm run initialProd
<date> M`, что и бэкфилл `storeId` на `Demand` (см. D3) — пользователь явно просил единый механизм
раскатки через `initialUpload`, а не отдельный одноразовый скрипт.

**Альтернатива**: не восстанавливать остаток за прошлые периоды вообще, показывать отчёт только с
момента внедрения. Отклонено по прямому указанию — нужен год истории.

**Риск, требующий проверки на этапе реализации**: точные имена полей себестоимости/остатка в ответе
`/entity/assortment` (в отличие от `StockAll`, где поле называется `price`) документацией,
доступной через использованный инструмент, до конца не подтверждены — требуют проверки перед
реализацией. Эндпоинт помечен как выводимый из эксплуатации в 2027 году — для разового бэкфилла это
приемлемо (не постоянная зависимость), в отличие от использования его на постоянной основе.

**Отмеченное ограничение, не блокирующее реализацию**: самый ранний из забэкфилленных месяцев не
будет иметь предыдущего месяца для расчёта коэффициента (см. D8) — коэффициент для него будет
`null`, как и для любой новой категории без истории. При необходимости коэффициента и для самого
раннего месяца дата бэкфилла может быть сдвинута на один месяц раньше запрошенного диапазона.

### D6. Рулап по дереву категорий — переиспользование `ProductFolderTreeService`
И для оборота, и для остатка каждая категория (включая корневые и вложенные любого уровня) получает
сумму показателей своих товаров плюс всех вложенных подкатегорий — переиспользуется уже существующая
логика обхода дерева `MoySkladProductFolder` (`ProductFolderTreeService`, уже используется для
`GET /shop/warehouse/catalog`), а не пишется заново. Для остатка источником построчных данных при
построении отчёта периода `P` является снимок `MoySkladStock` с максимальным `snapshotAt`, не
превышающим конец `P` (для текущего открытого месяца это просто последний доступный снимок; для
прошлого месяца — снимок на его конец, включая забэкфилленные месячные снимки, см. D5.1), а не
прямой ответ отчёта МойСклад. Разбивка по складам не объединяется — отдельная строка на каждую пару
«категория × склад» (как в `service-turnover-report`).

### D7. Хранение — две новые таблицы; статус периода не дублируется

**D7.1 `MoySkladStock`** — история снимков остатков по товару и складу: `productId`, `warehouseId`,
`quantity`, `costSum` (себестоимость, коп.), `snapshotAt` (момент, к которому относится снимок —
общий для всех строк одного прогона крона синка из D5, либо конец месяца для строк, записанных
разовым бэкфиллом истории — см. D5.1). Уникальный индекс `(productId, warehouseId, snapshotAt)`,
индекс по `snapshotAt` для быстрого получения нужного снимка (`MAX(snapshotAt)` не превышающего
конец периода отчёта) при пересчёте отчёта (D6/D9). Плотность снимков со временем неравномерна:
раз в месяц для забэкфилленной истории, раз в час — начиная с раскатки; это ожидаемо. Каждый час
крон **добавляет** новый набор
строк, не перезаписывая предыдущие — таблица накопительная (append-only), в отличие от обычного
паттерна upsert-справочников в проекте. Историзация по месяцам для самого отчёта происходит на
уровне `MoySkladTurnoverReportLine` (D7.2) — `MoySkladStock` историзирует более гранулярно (по
часам, а не по месяцам) для аудита и точной привязки к моменту закрытия периода (см. D5).

**D7.2 `MoySkladTurnoverReportLine`** — строки самого отчёта: `period` (строка `YYYY-MM`),
`categoryId`, `warehouseId`, `turnoverQuantity`, `turnoverSum` (коп.), `stockQuantity`, `stockSum`
(коп.), уникальный индекс `(period, categoryId, warehouseId)`. Статус периода (открыт/закрыт) не
хранится отдельной таблицей — читается из `ShopAccountingPeriod` через
`SHOP_ACCOUNTING_PERIOD_REPOSITORY`. Этот порт сейчас не входит в `exports` `ShopAccountingModule` —
первым шагом реализации нужно добавить его туда (аддитивное изменение, аналогичное уже принятому в
проекте паттерну реэкспорта `ShopSalesModule`). Пересчёт открытого месяца полностью заменяет его
строки, беря `stockQuantity`/`stockSum` из актуального на момент пересчёта `MoySkladStock` (D7.1).

**Отклонённая альтернатива**: собственная таблица периода со статусом `OPEN`/`CLOSED`,
синхронизируемая с `ShopAccountingPeriod`. Отклонено по тем же причинам, что и в сервисном
change, — дублировала бы уже существующий статус и требовала бы ручной синхронизации.

### D8. Коэффициент оборачиваемости — вычисляется при чтении, по паре «категория × склад»
`turnoverSum(текущий месяц) / ((stockSum(предыдущий месяц, та же категория и склад) +
stockSum(текущий месяц)) / 2)`. Коэффициент не хранится в таблице — вычисляется на лету при чтении
отчёта, подтягивая строку предыдущего периода по тому же уникальному ключу `(categoryId,
warehouseId)`. Если строки за предыдущий месяц нет (первый месяц данных или новая категория) —
коэффициент возвращается как отсутствующий (`null`), а не `0` — ноль в знаменателе не означает
нулевую оборачиваемость, а означает отсутствие данных для сравнения.

**Альтернатива**: хранить посчитанный коэффициент в самой строке отчёта. Отклонено — коэффициент
зависит от строки предыдущего периода, которая теоретически может быть пересчитана позже (закрытие
периода уже после того, как строка текущего месяца была записана); вычисление при чтении исключает
рассинхронизацию.

### D9. Пересчёт и закрытие — тот же паттерн, что в `service-turnover-report`
Две независимые почасовые крон-задачи: синк остатков в `MoySkladStock` (D5) и пересчёт отчёта.
Крон-задача пересчёта (`@ProdCron(CronExpression.EVERY_HOUR)`) пересчитывает текущий открытый месяц
из уже засинканных `MoySkladDemand`/`MoySkladStock`, читая статус `ShopAccountingPeriod`; если
период закрыт — пересчёт пропускается. Обработчик, подписанный на
`ShopAccountingPeriodClosedDomainEvent` (`@OnEvent(...)`), при закрытии периода направления
«Магазин» строит отчёт этого месяца в последний раз по актуальным данным и сохраняет как
неизменяемый снэпшот. Собственного действия «закрыть отчёт» нет.

### D10. HTTP-поверхность
- `GET /v1/shop/warehouse/goods-turnover-report/:period` (`period` = `YYYY-MM`) — строки отчёта
  (оборот, остаток, коэффициент) за месяц.
- `GET /v1/shop/warehouse/stores` — справочный список складов (для построения UI, аналогично уже
  существующему `GET /shop/warehouse/catalog` для дерева категорий).

## Risks / Trade-offs

- [Риск] У уже засинканных в прошлом `Demand` нет `storeId` — отчёт за периоды до внедрения будет
  неполным по разбивке складов, пока не выполнен бэкфилл → [Митигация] разовый повторный запуск
  `npm run initialProd <дата> M` за нужный период (см. Migration Plan, D3); новые данные с этого
  момента синкаются с `storeId` уже штатно.
- [Риск] Легаси `GET /entity/assortment` (используется только для разового бэкфилла истории
  остатков, см. D5.1) помечен к выводу из эксплуатации в 2027 году, а точные имена полей
  себестоимости в его ответе документацией, доступной через использованный инструмент, не
  подтверждены до конца → [Митигация] проверить вручную перед реализацией; для полного года истории
  по всем складам это разовый набор запросов (месяцы × склады), не постоянная нагрузка — при
  недоступности эндпоинта к моменту реализации бэкфилл истории остатков можно отложить отдельным
  change, не блокируя сам отчёт (турновер по обороту при этом всё равно доступен).
- [Риск] Точный контракт опроса асинхронной задачи МойСклад (`async=true`) для `/report/stock/
  bystore` не подтверждён документацией, доступной через использованный инструмент, до конца →
  [Митигация] проверить вручную перед реализацией клиента; при недоступности/нестабильности
  асинхронного режима — синхронный fallback с постраничной выгрузкой (`limit`/`offset`),
  функционально эквивалентный, но медленнее на больших каталогах. Так как синк остатков — фоновая
  часовая задача (D5), а не часть ответа на пользовательский запрос, этот риск не влияет на
  отзывчивость отчёта для конечного пользователя — только на своевременность обновления
  `MoySkladStock`.
- [Риск] Синк остатков (D5) и пересчёт отчёта (D9) — независимые часовые крон-задачи без явной
  привязки друг к другу → пересчёт отчёта в отдельные моменты может использовать `MoySkladStock`
  почти часовой давности → [Митигация] осознанно допустимо: требование к отчёту — «не реже одного
  раза в час», а не «в реальном времени»; при необходимости более тесной синхронизации порядок
  можно ужесточить на этапе `tasks.md` (например, явно запускать пересчёт отчёта сразу после
  успешного завершения синка остатков вместо двух независимых расписаний).
- [Риск] Коэффициент делит на среднее двух остатков; если оба нулевые (категория никогда не имела
  остатка) — деление на ноль → [Митигация] коэффициент в этом случае — `null`, не `0` и не ошибка.
- [Риск] Оборот считается по цене продажи (`MoySkladDemandPosition.sum`), а остаток — по себестоимости
  (`price` из отчёта об остатках) — разные ценовые базы в числителе и знаменателе коэффициента.
  Подтверждено пользователем как осознанный выбор, не дефект — фиксируется здесь, чтобы не было
  переосмыслено как баг при реализации.
- [Риск] Обход полного дерева категорий на каждый пересчёт может быть затратным на большом каталоге
  → [Митигация] переиспользование уже оптимизированного `ProductFolderTreeService`, а не отдельная
  реализация обхода.
- [Риск] `MoySkladStock` — накопительная (append-only) история почасовых снимков, а не
  перезаписываемая таблица → растёт без ограничения (порядок величины: количество товаров × складов
  × 24 снимка в сутки); при большом каталоге может стать существенной по объёму за месяцы работы →
  [Митигация] по прямому указанию пользователя пока храним все снимки без прореживания/удаления;
  политику хранения (TTL, прореживание старых снимков и т.п.) вводим позже отдельным change, если
  объём данных на практике станет проблемой — сейчас это осознанно принятый риск, а не открытый
  вопрос. Таблица состоит из простых числовых полей и не требует сложных индексов сверх
  `(productId, warehouseId, snapshotAt)`.

## Migration Plan

Раскатка на продакшен выполняется существующим механизмом `initialUpload`
(`backend/src/scripts/initialUploadData.ts`, команда `npm run initialProd <date> M`), в который
добавляются новые шаги — отдельного одноразового скрипта не заводится.

1. Аддитивная Prisma-миграция: новые модели `MoySkladStore`, `MoySkladStock`,
   `MoySkladTurnoverReportLine`; новая nullable-колонка `storeId` в `MoySkladDemand` — существующие
   данные не ломаются.
2. Добавить `SHOP_ACCOUNTING_PERIOD_REPOSITORY` в `exports` `ShopAccountingModule` (маленькое
   аддитивное изменение существующего модуля).
3. В `UploadInitialMoySkladDataHandler` добавляются два новых шага (см. D2, D5.1):
   синк справочника складов (`uploadStores()`) и разовый бэкфилл истории остатков за прошлые месяцы
   через легаси `GET /entity/assortment` (`stockMoment`/`stockStore`), по одному снимку на конец
   месяца в `MoySkladStock`.
4. Деплой кода на продакшен.
5. Разовый запуск `npm run initialProd <дата ~1 год назад> M` на продакшене — переисполняет
   `uploadCreatedDemands(fromDate)` (проставляя `storeId` в исторических `Demand`, см. D3), синкает
   справочник складов и выполняет бэкфилл месячных снимков `MoySkladStock` за этот же год (см. D5.1)
   за один прогон.
6. С этого момента почасовые крон-задачи (синк остатков — D5, пересчёт отчёта — D9) поддерживают
   данные актуальными самостоятельно; первый пересчёт отчёта для текущего открытого месяца может
   запускаться сразу после шага 5, не дожидаясь первого тика почасового крона.
7. Отката не требует — новая функциональность, аддитивная по данным; при необходимости откатывается
   удалением новых таблиц/колонок и кода модуля. Повторный запуск шага 5 идемпотентен (перезаписывает
   те же исторические строки), поэтому безопасен для повтора при сбое.

## Open Questions

- Точный контракт опроса статуса асинхронной задачи МойСклад и получения итогового результата
  (`/report/stock/bystore?async=true`) — не подтверждён до конца доступной документацией; требует
  ручной проверки на этапе реализации. Не меняет выбранный подход — есть синхронный fallback
  (см. Risks), поэтому не блокирует specs/tasks.
- Точные имена полей себестоимости/остатка в ответе легаси `GET /entity/assortment` (используется
  только для разового бэкфилла истории, см. D5.1) — требуют проверки на этапе реализации; не меняют
  выбранный подход (сам факт наличия исторического среза через `stockMoment`/`stockStore`
  подтверждён документацией).
