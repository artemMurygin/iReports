## Context

`motivation_schemas` — таблица, физически общая для направлений `service` и `shop`: одна строка может
адресовать общего `targetType`/`targetId` (сотрудник с идентичностями в обеих ERP), и тогда содержит
`SalaryRule`-правила ОБОИХ направлений одновременно, различаемые колонкой `direction` на каждом
правиле, и два независимых имени — `serviceName`/`shopName` (см. комментарии в
`backend/prisma/schema/salary.prisma`, модель `MotivationSchema`). `findById()` каждого направления
уже фильтрует `rules` по своему `direction` и трактует схему с 0 правилами этого направления как
не найденную (см. `GetMotivationSchemaService`) — то же должен делать `DeleteMotivationSchemaHandler`.

Это значит: «удалить схему» с экрана `service` не может быть безусловным `DELETE FROM
motivation_schemas WHERE id = ...` — если та же строка ещё держит правила направления `shop` (тот же
сотрудник состоит и в МойСклад), такое удаление стёрло бы чужую, не показанную пользователю схему.
Направление `shop` симметрично.

Каждый домен (`service`/`shop`) уже реализует `MotivationSchemaRepositoryPort`/
`SalaryRuleRepositoryPort` отдельно, без взаимных импортов (см. `backend/CLAUDE.md`, «Общие таблицы
между service и shop»). Delete следует тому же правилу: код удаления и его direction-условие живут в
data-access слое (Prisma-репозитории) каждого домена по отдельности; ни один хендлер не импортирует
классы другого домена.

## Goals / Non-Goals

**Goals:**
- Удаление мотивационной схемы одного направления (`service` или `shop`) не должно затрагивать
  правила/имя ДРУГОГО направления той же общей строки `motivation_schemas`, если они есть.
- Строка `motivation_schemas` физически удаляется, когда после удаления правил своего направления у
  неё не осталось правил другого направления (иначе — осиротевшая пустая строка навсегда).
- Операция необратима (без soft-delete/корзины) — соответствует remove-семантике, а не архивации.

**Non-Goals:**
- Массовое/пакетное удаление нескольких схем разом — вне скоупа, удаляется только одна схема по id.
- Изменение модели данных (`direction` на `MotivationSchema` и т.п.) — используется существующая
  структура таблицы.

## Decisions

- **Удаление — атомарная операция в репозитории, а не diff в хендлере.** Вместо того чтобы хендлер
  вызывал `salaryRuleRepo.findAll()` + `deleteByIds()` + отдельно решал, удалять ли родительскую
  строку, `MotivationSchemaRepositoryPort` каждого домена получает один метод
  `deleteDirectionSchema(id: string): Promise<void>`, который внутри одной транзакции (`write()`,
  как и остальные мутации репозитория):
  1. удаляет все `SalaryRule` с `motivationSchemaId = id AND direction = 'service'` (соотв. `'shop'`);
  2. если у строки не осталось правил другого направления — удаляет саму строку `motivation_schemas`;
  3. иначе — только очищает своё direction-специфичное имя (`serviceName`/`shopName` → `NULL`), не
     трогая строку и правила другого направления.

  Альтернатива (диф по id, как в `UpdateMotivationSchemaHandler`) отвергнута: удаление — не частичная
  синхронизация набора, а полное обнуление своей стороны, и наличие отдельного метода в репозитории
  переиспользует уже принятое разделение ответственности (репозиторий знает физическую форму общей
  таблицы, хендлер — только доменный сценарий).

- **Handler проверяет "не найдено" тем же способом, что и Get/List.** `DeleteMotivationSchemaHandler`
  вызывает `repo.findById(id)` и, если схемы нет ИЛИ `rules.length === 0` для своего направления,
  бросает `NotFoundException` — не выполняет удаление и не молчит (идемпотентный DELETE на
  несуществующий ресурс здесь сознательно не выбран: 404 явно сигналит фронту о рассинхронизации
  списка).

- **HTTP: `DELETE` на уже существующий маршрут `byId`.** `GET`/`PATCH .../motivation-schema/:id` уже
  используют `routesV1.service.motivationSchema.byId` (соотв. `shop...`) — новых записей в
  `app.routes.ts` не требуется, только новый контроллер `@Delete(...byId)` с `@HttpCode(204)`,
  по образцу `DeleteSalesPlanHttpController`.

- **Frontend: жёсткое подтверждение через модалку, без `window.confirm`.** Проект уже отказался от
  браузерного confirm в пользу `shared/ui-kit` `Modal` + `danger`-кнопки с объяснением последствий
  (см. `DeletePayoutDialog`/`DeleteIdentityModal`) — тот же паттерн, без введения `shadcn AlertDialog`
  (его в проекте нет). Мутация — отдельный хук `useDeleteMotivationSchema` по образцу
  `useUpdateMotivationSchema`; при успехе — инвалидация `['salary-rule-list']` и `navigate()` на
  список схем (`SalaryRuleList`) для соответствующего направления.

- **Contracts: без нового response-типа.** `DELETE` возвращает `204 No Content` без тела — как
  `DeleteSalesPlanHttpController` — новых Zod-схем в `contracts/` не требуется.

## Risks / Trade-offs

- [Гонка: PATCH/GET читают схему параллельно с DELETE другого направления] → `deleteDirectionSchema`
  выполняется в транзакции репозитория (`write()`), как и остальные мутации этого модуля; в худшем
  случае конкурентный запрос увидит схему уже без правил своего направления и получит штатный 404 —
  тот же уровень консистентности, что и у существующего `update()`/`insert()`.
- [Пользователь удаляет схему по ошибке, необратимо] → модалка подтверждения с явным текстом
  последствия («правила будут удалены безвозвратно») — тот же UX-паттерн, что уже принят для
  `DeleteIdentityModal`; отдельной корзины/восстановления проект для подобных сущностей не вводит
  (см. `delete-sales-plan`, `delete-role`, `delete-payout` — тоже без soft-delete).
- [Уже начисленные зарплаты (`SalaryAccrualLine`), ссылающиеся на правило удалённой схемы] →
  вне скоупа: `SalaryAccrualLine` — снапшот на момент закрытия периода (копия расчёта, не foreign key
  на живое правило), удаление схемы на него не влияет; это существующее свойство модели, не решение
  этого change.
