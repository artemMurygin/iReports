# Находки задач 1.1 / 1.2 (верификация допущений)

Дата проверки: 2026-09-08. Выполнено в рамках группы задач 1–2 change
`service-turnover-report` (диапазон агента: 1.1, 1.2, 2.1–2.3).

## 1.1 — публичный REST API RemOnline: есть ли ресурс списка складов?

**Результат: ресурса складов в публичном REST API RemOnline нет.** Допущение design.md D3 не
подтвердилось — нужен резервный источник (см. ниже рекомендацию для задачи 4.3).

Проверка выполнена через официальный индекс документации `https://roapp.readme.io/llms.txt`
(полный список страниц/эндпоинтов публичного API, сгруппированный по разделам — прямой вызов
живого API из этого окружения недоступен, см. `custom-api-roapp` ниже про сетевые ограничения; сама
документация была доступна). Раздел `Catalog & Inventory` содержит: `Get Legal Entities`,
`Get Taxes`, `Get Directories`/`Get Directory Items`, `Get Service Categories`,
`Get Service Unit Of Measure`, `Get Services`, `Get Product Categories`, `Get Product Unit Of
Measures`, `Get Product Types`, `Get Products`, `Get Bundle Categories`, `Get Bundles` — то есть
ровно то, что уже используется в проекте (`RoappProductCategory` и т.п.), но **без** отдельного
`Get Warehouses`/аналога. Раздел `Company & Location Management` содержит `Get Locations`/`Get
Location by ID`/`Get Location Resources` — это точки обслуживания (физические локации/филиалы), а
не склад товара; на прямую связь с сущностью "склад" (в терминах RemOnline это отдельная,
UI-видимая сущность — см. справочные статьи RemOnline "How To Create And Set Up A Product
Warehouse") в документе указаний нет. Итоговый ответ модели, суммирующей индекс документации:
"the documentation index contains no endpoints explicitly mentioning warehouse, stock, store, or
related inventory location management features".

Проверка сделана по документации (WebFetch/WebSearch), а не прямым тестовым вызовом живого API —
см. блокер сети в разделе 1.2 ниже, тот же блокер препятствовал бы и прямому вызову публичного
`api.roapp.io` с валидным `ROAPP_TOKEN` из этого окружения. Достаточно уверенный результат: полный
официальный индекс страниц документации не даёт оснований считать, что склад отдаётся отдельным
ресурсом.

**Рекомендация для задачи 4.3** (резервный источник, как и предполагает design.md, раздел
«Риски», пункт про допущение D3): не реализовывать `fetchWarehouses` как вызов несуществующего
ресурса `api.roapp.io`. Вместо этого — один из вариантов design.md:
- **Предпочтительно**: если `getGoodsFlowReport` (`custom-api-roapp`) в ответе или в собственной
  документации бэкенда-компаньона (`rm.murygin.tech`) отдаёт список валидных `warehouse_id`
  (например, отдельным вспомогательным эндпоинтом на том же кастомном бэкенде — стоит запросить
  у автора `rm.murygin.tech`, так как это тот же человек/компания, что и сам custom-api) — это
  единственный транспорт, который реально знает о складах (см. `warehouseId` уже наблюдаемый в
  `orderItems.schema.ts`, списание со склада заказа).
  Проверить наличие подобного вспомогательного ресурса на `rm.murygin.tech` до реализации.
- **Фолбэк**: если такого ресурса тоже нет — собрать список уникальных `warehouseId` из уже
  засинканных `roapp_products_orders`/сырых ответов `/orders/{id}/items` (`orderItems.schema.ts`,
  поле `warehouseId`), либо завести ручной справочник (админится вручную, обновляется редко) —
  оба варианта прямо упомянуты в design.md как приемлемые резервные источники.

## 1.2 — задержка `POST https://rm.murygin.tech/getGoodsFlowReport`

**Результат: эндпоинт (и весь бэкенд `rm.murygin.tech`) недоступен из этого окружения — задержку
успешного ответа замерить не удалось.** Это не специфично для `/getGoodsFlowReport`: та же ошибка
воспроизводится и на уже существующем, рабочем в проде методе `/getServicesBonuses`
(`CustomApiRoappService.getServiceBonusesForEngeneers`), и даже на `GET`-запросе без тела:

```
$ curl -s -o /dev/null -w "HTTP:%{http_code} TIME:%{time_total}\n" https://rm.murygin.tech/getServicesBonuses
HTTP:502 TIME:0.44s
$ curl -s -X POST https://rm.murygin.tech/getGoodsFlowReport -H "Content-Type: application/json" \
    -d '{"startDate":1735689600000,"endDate":1738368000000,"category_id":1,"warehouses":[1]}' \
    -w "HTTP:%{http_code} TIME:%{time_total}\n"
HTTP:502 TIME:0.5s   (повторено 5 раз подряд — стабильно 502, ~0.4-0.55s)
```

`502 Bad Gateway` от `openresty` — это сетевой инфраструктурный сбой (сам upstream-бэкенд
`rm.murygin.tech` недоступен из этого CI/sandbox-окружения или временно лежит), а не ошибка
формата запроса. Кредов сверх `ROAPP_TOKEN`/базового URL в `backend/.env` для этого хоста нет —
`custom-api-roapp.instance.ts` вообще не добавляет заголовков авторизации к `axios`-инстансу,
так что проверка не блокировалась отсутствием креда, только сетевой доступностью самого хоста.

**Отложено до задачи 9.3.** Следующему агенту: перед включением часового крона (задача 11) в
проде нужно повторить эти замеры из окружения, у которого действительно есть сетевой доступ к
`rm.murygin.tech` (staging/прод, а не эта песочница), и на реальных `category_id`/`warehouse_id`.

**Безопасный дефолт параллелизма для задачи 9.3** (до появления реальных цифр): **3** одновременных
запроса к `getGoodsFlowReport` (нижняя граница диапазона 3-5, предложенного в задаче 1.2) —
консервативный выбор, так как:
- `rm.murygin.tech` — собственный бэкенд-компаньон, а не инфраструктура самого RemOnline
  (design.md, «Риски») — не production-grade API с гарантированной пропускной способностью.
- Комбинаторика категория × склад уже может давать сотни вызовов за один пересчёт (design.md,
  пример 50 категорий × 5 складов = 250 запросов/час) — при неизвестной задержке безопаснее начать
  с меньшего параллелизма и поднять его после реальных замеров на проде/стейдже, чем сразу
  перегрузить и без того менее предсказуемый хост.
- Существующий паттерн синка (`RoappSyncService._fetchOrdersByParams` и др.) уже держит паузу
  `delay(500)` между последовательными вызовами публичного API — параллелизм 3 с одновременным
  `BadGatewayException` per-pair try/catch (design.md D6, частичный успех) держится в том же духе
  умеренной нагрузки на ERP-совместимые хосты.

## Аддендум (после мерджа в feat/salary) — 1.1 пересмотрено

Вывод «ресурса складов в публичном REST API RemOnline нет» был сделан по официальному индексу
документации актуальной (v2) версии API. У RemOnline есть отдельная, более старая версия
документации — **v1.4** (`https://roapp.readme.io/v1.4/...`, отличается от индекса, проверенного
выше) — с рабочим, хоть и не описанным в v2-индексе эндпоинтом:
`GET https://api.roapp.io/warehouse/` (см. `https://roapp.readme.io/v1.4/reference/get-warehouses`).
Подтверждено прямым вызовом с реальным `ROAPP_TOKEN` компании — `200 OK`, 6 реальных складов
iRepair (`id`/`title`/`is_global`/`type`), тот же Bearer-токен, что и у v2. Резервный источник
(`ROAPP_WAREHOUSES`, задача 4.3) заменён этим вызовом — подробности в `tasks.md`, аддендум к
задаче 4.3.
