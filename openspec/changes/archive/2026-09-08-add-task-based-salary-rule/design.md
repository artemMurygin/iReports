## Context

См. `proposal.md` — «Why»/«What Changes» — за мотивацией и общим описанием. Здесь фиксируются
технические решения, необходимые до реализации.

Релевантные ограничения текущей архитектуры (см. также `backend/CLAUDE.md`):

- `src/integrations/bitrix/` сейчас полностью read-only: `BitrixService` оборачивает только GET-методы
  (`crm.deal.list`, `user.get`, `department.get`, `crm.status.list`); ни одного write-вызова
  (`*.add`/`*.update`) в проекте ещё нет, `task.*`/`tasks.task.*` не используются вовсе.
- В проекте нет входящих вебхуков от Bitrix24 — только исходящий `POST /install` (установка
  приложения). Вся текущая синхронизация с Bitrix24 (`src/sync/bitrix/bitrix-sync.cron.ts`) —
  поллинг по `@ProdCron(CronExpression.EVERY_5_MINUTES)` с фильтром `>=DATE_MODIFY`.
- `SalaryRuleRegistry`/`SalaryRuleFactory` в `service` и `shop` — независимые
  `Map<SalaryRuleTypes, SalaryRuleClass>` в каждом домене (issue #57, направления не переиспользуют
  доменный код друг друга); новый тип правила регистрируется в обоих реестрах отдельными классами.
- `PeriodCalculationOrchestrator.calculate()` — «глупый» оркестратор: вызывает `rule.calculate(context)`
  для каждого правила и суммирует; различие FACT/PROGNOSE целиком на совести самого правила через
  `context.mode`.
- Общие между `service`/`shop` таблицы (`AccountingPeriod`, `SalaryAccrual`, `SalesPlan`, ...) —
  единая Prisma-модель с полем `direction`, но раздельные Entity/Repository-классы по доменам (см.
  «Общие таблицы между service и shop» в `backend/CLAUDE.md`). Новая таблица задач следует этому же
  паттерну.
- Идемпотентное автосоздание «на каждый новый период» уже есть как паттерн:
  `EnsureSalesPlansForPeriodService.ensure()`, вызываемый и по cron (`SalesPlanAutoCreationCron`), и
  лениво при чтении (`ListSalesPlansService`) — нужен, так как `@ProdCron` не тикает вне prod.

## Goals / Non-Goals

**Goals:**
- Единая инфраструктура работы с задачами Bitrix24 (создание/обновление/чтение статуса,
  двусторонний sync, автопересоздание регулярных задач), используемая обоими направлениями без
  дублирования кода интеграции.
- Независимая доменная реализация правила `TaskCompletion` в `service` и `shop` (по образцу
  остальных типов правил — раздельные Entity-классы, единый Prisma-агрегат задачи).
- Гейтинг видимости строки правила в отчёте (FACT и PROGNOSE) статусом «Выполнено» в Bitrix24.
- Ручной ввод суммы начисления и обязательного комментария руководителем для строк этого типа.

**Non-Goals:**
- Приём входящих вебхуков от Bitrix24 (push-уведомления о смене статуса задачи). Синхронизация —
  только поллингом, как и весь остальной Bitrix-контур проекта; push — возможное будущее развитие,
  не в скоупе этого change.
- Автоматическая обработка просроченных разовых задач (перенос/списание) — по продуктовому решению,
  это ручное действие руководителя, вне скоупа автоматизации.
- Изменение расчётной логики существующих типов правил (`PayPerHour`, `ServiceCompleted`,
  `OrderPayed`, `ProductSold`, `UsedProductSold`).
- Расширение `src/integrations/bitrix/` до универсального клиента произвольных REST-методов —
  добавляются только точечные write-обёртки под задачи, симметрично тому, как уже читаются сделки.
- Детальный UI/UX (макеты, компоненты) — предмет отдельного артефакта `ui-design.md`.

## Decisions

### 1. Единая таблица `SalaryTask`, раздельные Entity/Repository по направлениям
Новая Prisma-модель `SalaryTask` (черновое имя) — общая для `service`/`shop`, с полем `direction`,
по паттерну `AccountingPeriod`/`SalaryAccrual`. Поля: `id`, `salaryRuleId` (FK → `SalaryRule`),
`direction`, `period` (`YYYY-MM`), `deadline`, `isRecurring`, `bitrixTaskId`, `taskStatus` (снапшот
последнего известного статуса задачи Bitrix24), `lastSyncedAt`.

Уникальный ключ `(salaryRuleId, period)` — одно правило имеет не более одной задачи в расчётном
периоде (разовое — одна запись за всё время жизни правила, регулярное — по одной на каждый период).

**Альтернатива**: отдельные таблицы `service_salary_tasks`/`shop_salary_tasks`. Отклонено — проект
последовательно использует общую таблицу с дискриминатором `direction` для этого класса сущностей
(см. Context), заводить исключение без причины не нужно.

Как и для остальных общих таблиц, изоляция направлений — на уровне кода: у `service` и `shop` свои
независимые Port/Repository/Entity-классы поверх одной и той же Prisma-модели, каждый фильтрует свой
`direction`. `TaskCompletion` (доменная Entity правила), `SalaryTask`/`SalaryTaskRepository` и
`EnsureSalaryTaskForPeriodService`/`SetTaskCompletionLineRewardHandler` — раздельные независимые
классы в `service` и `shop`, по прецеденту остальных типов правил (`PayPerHour`/`ServiceCompleted`/
`OrderPayed` в `service`, `PayPerHour`/`ProductSold`/`UsedProductSold` в `shop`), issue #57 не
пересматривается. Общей (единой, не дублируемой) остаётся только инфраструктура интеграции с
Bitrix24 (`BitrixTasksGatewayPort`/`BitrixTasksGatewayAdapter`, новые методы существующего
`BitrixService`, `SalaryTaskStatusSyncCron`) — она не содержит доменных данных/бизнес-правил
направления, только write/read-обёртку над Bitrix24 REST, поэтому дублировать её незачем (см.
Decision 2/3).

### 2. Bitrix24 Tasks API — `tasks.task.*`, а не `task.item.*`; без отдельного класса-клиента
Новые write-методы добавляются в уже существующий `BitrixService` (`src/integrations/bitrix/
bitrix.service.ts`) — рядом с текущими read-методами (`fetchCreatedDeals`, `fetchEmployees`, ...), а
не в отдельный `BitrixTasksClient`/`BitrixTasksService`: заводить новый класс ради ещё одной группы
методов над тем же самым транспортом (`BitrixHttpService`) избыточно, когда есть подходящий
существующий. Используется актуальное пространство методов `tasks.task.add`/`tasks.task.update`/
`tasks.task.get` (batch-чтение статусов — через существующий батч-механизм Bitrix24 REST, как уже
используется постраничная выгрузка сделок). Устаревший `task.item.*` не используется — он в статусе
deprecated в самом Bitrix24.

Ответственный (`RESPONSIBLE_ID`) в создаваемой задаче — Bitrix-пользователь сотрудника, на которого
оформлено правило (тот же маппинг сотрудников, что уже используется для `BitrixEmployee`); постановщик
(`CREATED_BY`) — технический пользователь вебхука.

### 3. Синхронизация статуса — поллинг, не входящий вебхук
Статус задачи Bitrix24 подтягивается в iReports **поллингом** (новая cron-задача по аналогии с
`bitrix-sync.cron.ts`), а не приёмом события от Bitrix24 (`event.bind` на `ONTASKUPDATE` и т.п.).

**Альтернатива**: входящий вебхук от Bitrix24 — даёт мгновенное обновление статуса, но требует
публичного входящего эндпоинта (которого в проекте сейчас нет вовсе, кроме `POST /install`),
верификации подлинности запроса и отдельной инфраструктуры обработки ошибок доставки. Отклонено для
этого change в пользу консистентности с единственным существующим паттерном синхронизации Bitrix24 в
проекте; задержка в пределах интервала поллинга приемлема, так как начисление зарплаты — процесс с
гранулярностью расчётного периода (месяц), а не реального времени. Возврат к вебхуку — возможное
отдельное улучшение в будущем.

Одним запросом (batch) опрашиваются статусы всех активных (не архивных) задач правил `TaskCompletion`
обоих направлений сразу — не по одному вызову на задачу.

### 4. Автопересоздание регулярной задачи — идемпотентный `ensure()`, cron + ленивый вызов
Повторяется паттерн `EnsureSalesPlansForPeriodService`: `ensure(direction, period)` для регулярных
`TaskCompletion`-правил вызывается и по cron (первое число месяца), и лениво при первом обращении к
задачам/отчёту за период в текущем месяце (обязательно, так как `@ProdCron` не тикает вне prod).
Идемпотентность обеспечивается тем же уникальным ключом `(salaryRuleId, period)`, что и в решении 1.

### 5. Сумма начисления — ручной ввод на уровне `SalaryAccrualLine`, не в `props` правила
`props: Json` правила `TaskCompletion` хранит только конфигурацию самого правила (период/дедлайн/
признак регулярности — то, что уже отражено в `SalaryTask`, плюс возможные ролевые атрибуты, общие с
другими правилами). Сумма начисления — не формула, а решение руководителя на конкретный период,
поэтому она принадлежит документу начисления, а не конфигурации правила.

`SalaryAccrualLine` для типа `TaskCompletion` создаётся оркестратором расчёта с `originalAmount = 0`
и новым полем-флагом «требует ручного ввода» (`amount`/`comment` не заполнены), а не пропускается —
строка обязана быть видна руководителю на экране начисления. Существующее поле-паттерн
`comment`/`adjustedBy`, сейчас живущее только на `SalaryAccrualLineAdjustment` (корректировках после
факта), расширяется на саму `SalaryAccrualLine`: комментарий, введённый руководителем при первом
проведении строки этого типа, хранится на строке и виден сотруднику — использование
`SalaryAccrualLineAdjustment` для этого не подходит, так как та таблица — история *изменений* уже
проведённой суммы, а не первичный ввод.

**Альтернатива**: считать первичный ввод суммы для `TaskCompletion`-строки корректировкой (0 → сумма)
через существующий `SalaryAccrualLineAdjustment`. Отклонено — семантически это не «корректировка»
(предыдущего расчётного значения не существовало), и потребовало бы обязательного комментария только
для этого одного типа adjustment, что усложняет общий инвариант таблицы.

### 6. Создание/закрытие задачи в Bitrix24 — вызов до записи в БД, с компенсацией
При создании правила `TaskCompletion`: сначала создаётся задача в Bitrix24 (`tasks.task.add`), только
после успешного ответа с `bitrixTaskId` — сохраняется `SalaryRule` + `SalaryTask` в одной транзакции.
Если запись в БД после этого не удалась — компенсирующий вызов закрывает/удаляет только что созданную
задачу в Bitrix24, чтобы не оставлять в CRM задачу без соответствующего правила в iReports.

Симметрично при удалении/отмене правила: сначала закрывается задача в Bitrix24, затем удаляется
запись. Если вызов Bitrix24 недоступен — удаление правила в iReports не блокируется (Bitrix24 —
внешняя система, её недоступность не должна останавливать локальную операцию), но событие
логируется, а рассинхронизация обнаруживается и подсвечивается ближайшим циклом синхронизации статуса
(решение 3) как несоответствие «правила нет — задача в Bitrix24 всё ещё открыта».

### 7. Детализация строки — задача и ссылка на неё, через существующий `CalculationSourceRef`
В детализации зарплатной строки (и в документе начисления, и в отчёте) `TaskCompletion` должен
показывать название/номер связанной задачи и кликабельную ссылку на неё в Bitrix24 — по той же
аналогии, что уже работает для заказа у `OrderPayed`/`ServiceCompleted` (там `buildErpOrderLink()`
формирует прямую ссылку на карточку заказа в RemOnline). Механизм для этого уже существует и не
требует нового UI: `CalculationLine.sources: CalculationSourceRef[]`
(`src/shared/domain/calculation-line.ts`) — `TaskCompletion.calculate()` заполняет его одним
элементом `{ type: 'taskCompletion', id: bitrixTaskId, label: <название/номер задачи>, link:
<ссылка на задачу в Bitrix24> }`.

Ссылка строится новым утилитарным хелпером `buildBitrixTaskLink(bitrixTaskId)` — по аналогии с
`erp-order-link-builder.ts`, но, в отличие от него, **общим** (не ×2 по направлениям): URL задачи
Bitrix24 строится одинаково независимо от направления (`https://<портал>.bitrix24.ru/company/
personal/user/0/tasks/task/view/<id>/`), доменных данных в построении ссылки нет — та же логика, что
уже применена к `BitrixTasksGatewayPort` (Decision 1) — общей делается только направление-агностичная
инфраструктура, а не бизнес-правило.

Фронтенд **не меняется**: `AccrualLineSources.tsx` (документ начисления) и `RuleSourcesRail.tsx`
(отчёт) уже рендерят любой источник по `label`/`link` универсально (ссылка, если `link` задан, иначе
обычный текст) — тот же компонент, что уже показывает ссылку на заказ. У `RuleSourcesRail.tsx` в
`SOURCE_TYPE_LABELS` уже даже есть запись `taskCompletion: 'Задача'` — остаток предыдущей (удалённой)
реализации фичи, оказавшийся переиспользуемым без изменений.

## Risks / Trade-offs

- **[Риск] Задержка отражения статуса «Выполнено» на интервал поллинга** → Смягчение: интервал
  синхронизации статуса задач — 5 минут, как у существующего `bitrix-sync.cron.ts`; дополнительно
  статус освежается лениво при открытии отчёта/списка задач текущего периода.
- **[Риск] Недоступность Bitrix24 REST API в момент создания правила блокирует создание правила** →
  Смягчение: осознанный trade-off решения 6 — правило `TaskCompletion` без задачи Bitrix24
  бессмысленно, поэтому создание правила должно отказывать, а не создавать «повисшее» правило без
  привязанной задачи.
- **[Риск] Рассинхронизация при сбое компенсирующего вызова закрытия задачи** → Смягчение: не
  критично для целостности iReports (правило корректно удалено), обнаруживается и логируется
  следующим циклом синхронизации; ручное закрытие задачи в Bitrix24 остаётся доступно руководителю
  напрямую в CRM.
- **[Риск] Дублирование доменной логики между `service` и `shop`** → Осознанный, уже принятый в
  проекте trade-off (issue #57, см. Context) — не пересматривается этим change. Разделяется только
  доменный код (`TaskCompletion`, `SalaryTaskRepository`, `EnsureSalaryTaskForPeriodService`,
  `SetTaskCompletionLineRewardHandler`); инфраструктура интеграции с Bitrix24 остаётся общей (см.
  Decision 2/3) — это не противоречие, а разные основания: направление участвует в доменных данных,
  но не в вызовах внешнего REST API.
- **[Риск] Забытая руководителем строка начисления без введённой суммы** → Смягчение: строка
  остаётся в `DRAFT` и блокирует проведение документа начисления целиком (существующая семантика
  статусов `SalaryAccrualLine`), то есть незаполненная строка заметна на этапе начисления, а не
  теряется молча.

## Migration Plan

1. Prisma-миграция: новая таблица `SalaryTask` (аддитивная, без изменений существующих таблиц) +
   расширение `SalaryAccrualLine` полем комментария для первичного ввода (аддитивная колонка).
2. Backend: интеграция Bitrix Tasks API → доменные Entity/реестр `service` → зеркально `shop` → cron
   синхронизации статуса и автопересоздания регулярных задач.
3. Frontend (после стабилизации backend в staging): добавление типа `TaskCompletion` в форму создания
   зарплатного правила и полей ручного ввода суммы/комментария в экране начисления. До этого шага
   бэкендная функциональность не имеет UI-входа и не влияет на существующих пользователей.
4. Роллбэк: изменения аддитивны и не трогают существующие таблицы/типы правил — откат сводится к
   откату миграции (drop новой таблицы/колонки) и удалению регистрации типа `TaskCompletion` из
   реестров. Если к моменту отката уже существуют реальные задачи в Bitrix24 — их закрытие вручную в
   CRM не автоматизируется откатом (внешняя система, вне транзакционной границы приложения).
