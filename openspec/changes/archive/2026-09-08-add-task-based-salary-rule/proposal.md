## Why

Руководители обоих направлений (`service` и `shop`) сейчас не могут привязать зарплатное начисление к
выполнению разовой или регулярной задачи сотрудника — весь набор зарплатных правил
(`PayPerHour`/`ServiceCompleted`/`OrderPayed` в service, `PayPerHour`/`ProductSold`/`UsedProductSold`
в shop) рассчитывается автоматически по данным ERP (RemOnline/МойСклад), без ручной постановки задач и
без привязки к Bitrix24. Нужен новый тип правила, который создаёт задачу в Bitrix24, ждёт, пока
сотрудник закроет её со статусом «Выполнено», и только после этого допускает ручное начисление суммы
руководителем с комментарием, видимым сотруднику. Задача должна оставаться синхронизированной в обе
стороны между iReports и Bitrix24.

## What Changes

- Новый общий Prisma-агрегат "задача под зарплатное правило" (общая для `service` и `shop` таблица с
  дискриминатором `direction`, по аналогии с `AccountingPeriod`/`SalaryAccrual` — см.
  `backend/CLAUDE.md`, раздел «Общие таблицы между service и shop»): хранит `salaryRuleId`,
  `bitrixTaskId`, расчётный период, дедлайн выполнения, признак `isRecurring`, статус синхронизации.
- Новый тип зарплатного правила `TaskCompletion`, зарегистрированный независимо в
  `SalaryRuleRegistry` **обоих** доменов (`service` и `shop`) — по аналогии с существующими типами
  (`PayPerHour`, `ServiceCompleted`/`ProductSold`, ...), с собственной Entity-реализацией в каждом
  домене (реализации зеркальные, независимость направлений не пересматривается — см. issue #57 в
  комментариях `SalaryRule.direction`).
- Создание зарплатного правила типа `TaskCompletion` (через существующий поток
  `CreateSalaryRuleCommand`/`CreateMotivationSchemaHandler`/`UpdateMotivationSchemaHandler`) синхронно
  создаёт задачу в Bitrix24 (нужен новый write-метод в интеграции Bitrix — сейчас
  `src/integrations/bitrix/bitrix.service.ts` умеет только читать данные через GET, `task.add` в
  Bitrix24 REST API отсутствует полностью) и запись в общей таблице задач с привязкой к правилу.
- Разовая задача существует только в одном расчётном периоде. Регулярная задача автоматически
  пересоздаётся на каждый новый расчётный период (по аналогии с `SalesPlanAutoCreationCron` +
  идемпотентным `ensure()`, вызываемым и по cron, и лениво при чтении, см.
  `EnsureSalesPlansForPeriodService`) — новая задача в Bitrix24 создаётся заново на новый период,
  прошлая закрывается/архивируется.
- Двусторонняя синхронизация статуса и данных задачи между iReports и Bitrix24: изменения в iReports
  (например, правка дедлайна) уходят в Bitrix24 через новый write-клиент; изменения статуса в
  Bitrix24 (в первую очередь — перевод в «Выполнено») подтягиваются в iReports через polling/cron (в
  проекте нет входящих вебхуков от Bitrix24 — только исходящий `POST /install`, см.
  `src/sync/bitrix/bitrix-sync.cron.ts` как референс паттерна поллинга).
- В прогнозе начисления зарплаты (`PROGNOSE`, см. `CalculationContext.mode` /
  `PeriodCalculationOrchestrator`) строка по правилу `TaskCompletion` появляется **только** после того,
  как связанная задача переведена в Bitrix24 в статус «Выполнено»; до этого правило не участвует ни в
  `FACT`, ни в `PROGNOSE`.
- Просроченная (дедлайн прошёл, задача не выполнена) разовая задача **не** обрабатывается автоматически
  — остаётся видимой в Bitrix24 как просроченная, решение (списать/перенести/поставить вручную) — на
  усмотрение руководителя, без специального FR на автоматическую обработку.
- Начисление по правилу `TaskCompletion` не считается по формуле: руководитель сам вводит сумму
  начисления и обязательный комментарий, который увидит сотрудник в своём начислении (используется/
  расширяется существующий механизм `SalaryAccrualLineAdjustment.comment`, либо для строки, изначально
  создаваемой без суммы, — новый эквивалентный путь ручного ввода на этапе `SalaryAccrualLine`, детали
  — в design.md).
- Удаление/отмена зарплатного правила `TaskCompletion` в iReports закрывает/отменяет связанную задачу в
  Bitrix24 (та же двусторонняя синхронизация, применённая к терминальному состоянию).
- Реализация выполняется зеркально для `service` и `shop`: общая инфраструктура (Bitrix-клиент задач,
  таблица задач, механика пересоздания/синхронизации) — одна на оба направления; доменные Entity
  правила, реестр и интеграция в расчёт — раздельные независимые классы в каждом домене, как и для
  существующих типов правил.

## Capabilities

### New Capabilities
- `integrations/bitrix-tasks`: create/update/read задач в Bitrix24 (`task.add`/`task.update`/
  `task.get`), общая для `service`/`shop` таблица задач под зарплатные правила (direction-дискриминатор),
  двусторонняя синхронизация статуса, автоматическое пересоздание регулярных задач на новый расчётный
  период.
- `shop/accounting`: тип зарплатного правила `TaskCompletion` для направления `shop` — создание задачи,
  условие появления в прогнозе по статусу Bitrix24, ручное начисление суммы с комментарием сотруднику.

### Modified Capabilities
- `service/accounting`: добавляется тип зарплатного правила `TaskCompletion` — создание задачи,
  условие появления в прогнозе по статусу Bitrix24, ручное начисление суммы с комментарием сотруднику
  (симметрично `shop/accounting`).

## Impact

- **Prisma**: новая модель (рабочее имя `SalaryTask`) в `prisma/schema/` — общая таблица с
  `direction`, `salaryRuleId`, `bitrixTaskId`, `period`, `deadline`, `isRecurring`, статусом синка;
  новая миграция.
- **`src/integrations/bitrix/`**: новый write-клиент для Bitrix24 Tasks API (`task.add`/`task.update`/
  `task.get`) — сейчас интеграция полностью read-only (только `GET`-обёртки над `crm.deal.list`,
  `user.get`, `department.get`, `crm.status.list`).
- **`src/domains/service/modules/accounting/`** и **`src/domains/shop/modules/accounting/`**: новая
  Entity `TaskCompletion` + запись в `SalaryRuleRegistry`/`SalaryRuleFactory` каждого домена; новая
  `TaskCompletionSalaryConfig` в `props: Json`; изменение `.calculate()`-контракта или отдельная ветка
  оркестратора для условия «есть в PROGNOSE только если задача Done».
- **Общий cron-слой** (по аналогии с `src/sync/bitrix/bitrix-sync.cron.ts` и
  `SalesPlanAutoCreationCron`): новая cron-задача пуллинга статусов задач Bitrix24 + идемпотентный
  `ensure()` пересоздания регулярных задач на новый период.
- **`SalaryAccrualLine`/`SalaryAccrualLineAdjustment`**: возможное расширение под ручной ввод суммы +
  обязательный комментарий для строк типа `TaskCompletion` на этапе начисления (не автоматический
  расчёт, как у остальных типов правил).
- **`ireports-contracts`**: новые Zod-схемы конфига правила `TaskCompletion`, DTO создания/обновления
  задачи, статуса синхронизации.
- **Frontend**: UI создания зарплатного правила (обе схемы мотивации, service/shop) — новый тип
  `TaskCompletion` с полями дедлайна/периодичности; UI начисления зарплаты — ручной ввод суммы и
  комментария для строк этого типа.
- Никаких изменений в существующих типах правил (`PayPerHour`, `ServiceCompleted`, `ProductSold` и
  т.д.) и их расчётной логике не предполагается.
