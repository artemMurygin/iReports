## Why

Сегодня зарплатные правила рассчитываются только по индивидуальным транзакциям сотрудника (часы,
услуга, заказ, задача) и привязаны к его собственной работе. У компании появилась новая
управленческая роль — «руководитель направления» (service или shop), мотивация которого зависит не
от его личных транзакций, а от результата отдела/категории/направления целиком: от процента
выручки/маржи, от выполнения плана продаж с плавающим коэффициентом и от выполнения плана по
оборачиваемости склада. Для этого нужен новый класс зарплатных правил уровня отдела/направления, а
не уровня транзакции.

## What Changes

- **FR1**: Новая мотивационная роль «руководитель направления» — назначается вручную через уже
  существующий `MotivationSchema.targetType = 'Employee'` (без синхронизации Bitrix24 `UF_HEAD` и без
  новой сущности «руководитель отдела»); отдел/категория/направление, по которым считается правило,
  задаются явно в конфигурации самого правила, а не выводятся из формальной принадлежности сотрудника
  отделу.
- **FR2**: Новый вид зарплатного правила — **процент от факта** выручки или маржи отдела/категории/
  направления, без какого-либо коэффициента (простой фиксированный процент от фактического значения
  плана продаж за период).
- **FR3**: Новый вид зарплатного правила — **фиксированная сумма × плавающий коэффициент** выполнения
  плана продаж по выручке/марже (по категории или по всему направлению), переиспользующий уже
  существующий механизм ступенчатого/линейного множителя (`percentBorders`,
  `resolveFloatPercentMultiplier`/`FloatPercentSchedule`) и уже существующий процент выполнения плана
  (`SalesPerformance.percentCompletion`).
- **FR4**: Новый вид зарплатного правила — **фиксированная сумма × плавающий коэффициент** выполнения
  плана по коэффициенту оборачиваемости, привязанный к конкретному **складу** (обязательное поле
  конфигурации — оборачиваемость скоуплена по категории × складу, автоматической привязки
  сотрудник→склад в системе нет, в отличие от отдела) и опционально к категории внутри него. План
  коэффициента оборачиваемости (например `1.0`) хранится не как отдельная сущность/справочник, а
  прямо в конфигурации самого правила; факт — берётся из отчёта «Оборачиваемость» (FR5).
- **FR5** (**BREAKING** для контракта ответа отчёта shop): Отчёт «Оборачиваемость» (оба направления)
  сам возвращает готовую итоговую строку по складу — сумму, количество и коэффициент по всем
  категориям склада — по той же формуле, что сегодня считает только frontend
  (`summarizeGoodsTurnoverRows`/`summarizeShopGoodsTurnoverRows`: сумма по «настоящим» корневым
  категориям + средневзвешенный по остатку коэффициент). Formula переезжает на backend, чтобы:
  (a) её мог переиспользовать зарплатный расчёт правила FR4 при `category = null` («весь склад»);
  (b) frontend отчёта не дублировал и не мог разойтись с зарплатным расчётом в формуле. Ответ
  `GET .../goods-turnover-report/:period`: у **service** — аддитивно (новое поле `totals` в уже
  существующем `{period, lines}`); у **shop** — с изменением формы (сегодня голый массив строк,
  становится `{lines, totals}`) — единственный потребитель сегодня это же приложение (frontend +
  внутренний port зарплатного расчёта), внешних клиентов у эндпоинта нет.
- Новые виды правил (FR2–FR4) применяются одинаково к обоим направлениям — **service** и **shop**.

## Capabilities

### New Capabilities
_(нет — фича расширяет существующую предметную область начисления зарплаты, отдельной новой
capability не заводится)_

### Modified Capabilities
- `service/accounting`: добавляются виды зарплатного правила уровня отдела/направления (FR2, FR3,
  FR4) и роль «руководитель направления» (FR1); требование «Виды зарплатных правил» расширяется этими
  новыми видами.
- `shop/accounting`: симметрично то же самое (FR1–FR4) — новые виды правил и роль применимы к
  направлению shop так же, как к service.
- `service/goods-turnover`: ответ отчёта дополняется итоговой строкой по складу (FR5).
- `shop/goods-turnover`: то же самое, с изменением формы ответа (FR5, **BREAKING**).

## Impact

- `contracts/commands/salary-rule.ts`, `contracts/commands/shop-salary-rule.ts` — новый литерал роли
  в общем `targetRoleSchema`, новые члены discriminated union для 3 новых видов правил (базис
  выручка/маржа, `percentBorders`, план оборачиваемости как число в конфиге).
- `backend/src/domains/{service,shop}/modules/accounting/domain/entities/salary-rules/` — 3 новые
  сущности правила (без транзакционной итерации, в отличие от существующих 4+4 видов), каждая
  считается по `SalesPerformance`/агрегату оборачиваемости, а не по перебору заказов/задач/часов.
- `backend/src/domains/{service,shop}/modules/accounting/domain/services/salary-rule-role-catalog.ts`
  — новая роль добавляется в `ALL_SERVICE_ROLES`/`ALL_SHOP_ROLES`; матчинг по заказу (`role-source.ts`)
  для этой роли не используется — правило матчится напрямую на сотрудника, которому назначена схема.
- `contracts/commands/goods-turnover-report.ts`, `contracts/commands/shop-goods-turnover-report.ts` —
  новое поле/форма ответа `totals` (FR5); `GetGoodsTurnoverReportService`/аналог shop в
  `domains/{service,shop}/modules/warehouse` — считают итог по складу тем же проходом, что уже строит
  `lines`, без дополнительных запросов к данным.
- `frontend/src/pages/GoodsTurnoverReport` — `summarizeGoodsTurnoverRows`/
  `summarizeShopGoodsTurnoverRows` заменяются на потребление готового `totals` из ответа API вместо
  локального пересчёта (устраняет риск расхождения формулы, отмеченный в `design.md`); shop-сторона
  дополнительно обновляется под новую форму ответа (`{lines, totals}` вместо голого массива).
- `frontend/src/pages/SalaryRules` — новые формы создания/редактирования для 3 новых видов правил,
  выбор роли «руководитель направления» при `targetType = 'Employee'`, выбор склада для FR4.
- Пересекается с открытым параллельным change `extract-shared-salary-calculation` (выносит
  `float-percent`/`money`/`scopeKey` в общий модуль) — координация, куда класть общую для service/shop
  логику новых правил, уточняется в `design.md`.
