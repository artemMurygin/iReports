## Purpose

Описывает наблюдаемое поведение модуля аналитики проданных услуг направления «Сервис»: отчёт по
проданным услугам за период с разбивкой по времени, плоский справочник категорий услуг и справочник
типов заказов. Не описывает воронку сервисных сделок (отдельный модуль `service/sales`, источник
данных — сделки Bitrix24, а не проданные услуги) и не описывает зарплатные правила, использующие типы
заказов как фильтр, — это часть `service/accounting`.

## ADDED Requirements

### Requirement: Отчёт по проданным услугам строится по дате закрытия заказа
Отчёт по проданным услугам за период SHALL включать только те строки «услуга в заказе», чей заказ
закрыт в границах запрошенного диапазона дат (включительно); строки заказов, закрытых вне диапазона,
или заказов без даты закрытия, SHALL быть исключены из отчёта.

#### Scenario: Заказ закрыт в границах диапазона — строка включена
- **WHEN** заказ, содержащий проданную услугу, закрыт датой внутри запрошенного диапазона `from`—`to`
- **THEN** строки этого заказа учитываются при построении отчёта

#### Scenario: Заказ закрыт вне диапазона — строка исключена
- **WHEN** заказ, содержащий проданную услугу, закрыт датой за пределами запрошенного диапазона
- **THEN** строки этого заказа не участвуют в отчёте за этот период

### Requirement: Отчёт группируется по услуге
Отчёт по проданным услугам SHALL быть сгруппирован по проданной услуге: каждая позиция отчёта
соответствует одной услуге и агрегирует все её строки из подходящих под фильтры заказов за период.

#### Scenario: Несколько строк одной услуги объединяются в одну позицию отчёта
- **WHEN** за период услуга продавалась в нескольких разных заказах (или несколько раз в одном заказе)
- **THEN** в отчёте по ней ровно одна позиция с агрегированными по всем её строкам показателями

### Requirement: Показатели количества и бонуса считаются по всем строкам услуги
Количество проданного и суммарное вознаграждение инженера по услуге SHALL считаться по всем её
строкам за период, включая несколько строк в одном и том же заказе.

#### Scenario: Несколько строк услуги в одном заказе суммируются
- **WHEN** услуга встречается в одном и том же заказе несколькими отдельными строками
- **THEN** количество и вознаграждение инженера по каждой из этих строк складываются в общий итог по
  услуге

### Requirement: Выручка, прибыль и средний чек считаются по уникальным заказам, а не по строкам
Выручка, прибыль и средний чек по услуге SHALL рассчитываться по уникальным заказам, содержащим эту
услугу, а не по количеству её строк — сумма оплаты и себестоимости одного заказа SHALL учитываться в
расчёте ровно один раз, даже если в этом заказе несколько строк рассчитываемой услуги.

#### Scenario: Заказ с несколькими строками одной услуги не задваивает выручку
- **WHEN** заказ содержит несколько строк одной и той же услуги
- **THEN** оплата и себестоимость этого заказа учитываются в выручке/прибыли услуги ровно один раз,
  а не по разу на каждую строку

#### Scenario: Прибыль — разница между оплатой и себестоимостью заказа
- **WHEN** считается прибыль по услуге за период
- **THEN** прибыль равна сумме (оплата заказа минус себестоимость заказа) по каждому уникальному
  заказу, содержащему эту услугу

#### Scenario: Средний чек — выручка, делённая на количество уникальных заказов
- **WHEN** считается средний чек по услуге за период
- **THEN** средний чек равен суммарной выручке услуги, делённой на количество уникальных заказов,
  давших эту выручку, а не на количество строк услуги

### Requirement: Средняя цена услуги — средневзвешенная по количеству
Средняя цена услуги и средняя цена в разбивке по периодам SHALL рассчитываться как средневзвешенная
по количеству цена входящих строк, а не как простое среднее цен строк.

#### Scenario: Строка с большим количеством сильнее влияет на среднюю цену
- **WHEN** у услуги за период есть строки с разными ценами и разным количеством
- **THEN** средняя цена ближе к цене строки с большим количеством, чем к цене строки с меньшим
  количеством, — расчёт учитывает вес каждой строки по количеству

### Requirement: Разбивка по периодам содержит все периоды диапазона, включая пустые
Отчёт SHALL включать разбивку показателей услуги по периодам времени внутри запрошенного диапазона;
разбивка SHALL содержать точку на каждый период диапазона, даже если в этом периоде не было ни одной
продажи услуги — с нулевым количеством и нулевой средней ценой.

#### Scenario: Период без продаж присутствует в разбивке с нулями
- **WHEN** в запрошенном диапазоне есть период (день/неделя/месяц — в зависимости от выбранной
  гранулярности), в котором услуга не продавалась
- **THEN** в разбивке по периодам этот период присутствует с количеством и средней ценой, равными
  нулю

### Requirement: Гранулярность разбивки по периодам
Разбивка отчёта по проданным услугам SHALL поддерживать три гранулярности периода — день, неделя,
месяц; при отсутствии явного выбора SHALL применяться гранулярность «день». Неделя SHALL начинаться
с понедельника, месяц — с первого числа.

#### Scenario: Гранулярность по умолчанию — день
- **WHEN** запрашивается отчёт по проданным услугам без явного указания гранулярности разбивки
- **THEN** разбивка строится по дням

#### Scenario: Продажа в середине недели относится к периоду, начавшемуся в понедельник
- **WHEN** выбрана недельная гранулярность и услуга продана в любой день недели, кроме понедельника
- **THEN** продажа относится к периоду, ключ которого — понедельник этой же календарной недели

### Requirement: Отчёт по проданным услугам можно ограничить категориями и конкретными услугами
Отчёт по проданным услугам SHALL поддерживать опциональную фильтрацию по списку категорий услуг и по
списку конкретных услуг; при отсутствии фильтра (не задан или пуст) SHALL учитываться все услуги/все
категории.

#### Scenario: Без фильтров учитываются все услуги
- **WHEN** фильтры по категориям и по услугам не заданы
- **THEN** в отчёт попадают строки всех услуг за период

#### Scenario: Фильтр по категориям ограничивает отчёт услугами этих категорий
- **WHEN** задан непустой список категорий услуг
- **THEN** в отчёт попадают только услуги, чья собственная категория входит в этот список

#### Scenario: Фильтр по конкретным услугам ограничивает отчёт этими услугами
- **WHEN** задан непустой список конкретных услуг
- **THEN** в отчёт попадают только строки указанных услуг

### Requirement: Диапазон дат отчёта обязателен и валиден
Запрос отчёта по проданным услугам SHALL требовать обе границы диапазона дат; запрос с отсутствующей
границей, нераспознаваемым форматом даты, либо с началом диапазона позже конца, SHALL быть отклонён.

#### Scenario: Отсутствие начала диапазона отклоняется
- **WHEN** запрашивается отчёт без указания начала диапазона дат
- **THEN** запрос отклоняется

#### Scenario: Нераспознаваемый формат даты отклоняется
- **WHEN** граница диапазона дат не распознаётся как дата
- **THEN** запрос отклоняется

#### Scenario: Начало диапазона позже конца отклоняется
- **WHEN** начало запрошенного диапазона дат позже его конца
- **THEN** запрос отклоняется

### Requirement: Пустая выборка не считается ошибкой
Отсутствие проданных услуг, подходящих под период/фильтры, SHALL приводить к отчёту с пустым списком
услуг, а не к ошибке; аналогично отсутствие категорий услуг SHALL приводить к пустому справочнику.

#### Scenario: Нет продаж за период — пустой отчёт
- **WHEN** за запрошенный период и фильтры не нашлось ни одной подходящей строки продажи услуги
- **THEN** отчёт возвращается успешно с пустым списком услуг

### Requirement: Справочник категорий услуг — плоский список с указателем на родителя
Справочник категорий услуг SHALL отдаваться плоским списком (не вложенной структурой), где иерархия
выражена только ссылкой каждой категории на родителя и её глубиной в дереве; категория верхнего
уровня SHALL не иметь родителя.

#### Scenario: Категория верхнего уровня без родителя
- **WHEN** категория услуг не имеет родительской категории
- **THEN** в справочнике у неё родитель не указан

#### Scenario: Дочерняя категория ссылается на родителя
- **WHEN** категория услуг является дочерней по отношению к другой категории
- **THEN** в справочнике у неё указан идентификатор родительской категории и глубина в дереве больше,
  чем у родителя

### Requirement: Справочник типов заказов — самостоятельный список без фильтров
Система SHALL предоставлять справочник типов заказов направления «Сервис» целиком, без параметров
фильтрации; справочник SHALL быть плоским (без иерархии).

#### Scenario: Запрос справочника типов заказов возвращает все типы
- **WHEN** запрашивается справочник типов заказов
- **THEN** возвращаются все типы заказов без фильтрации по каким-либо критериям

  `application/services/list-order-types.service.spec.ts`.
- **Не покрыто тестами** (явный пробел, зафиксирован, а не молчаливо опущен): HTTP/e2e-тест для
  `GET /v1/service/reports/order-type` отсутствует — при этом обнаружено расхождение между e2e-файлом
  модуля и интерфейсом порта источника данных (тестовая заглушка порта не реализует метод получения
  типов заказов, что не ловится текущим прогоном `npm run test`, но всплывает при отдельной проверке
  типов `tsc --noEmit`) — не блокирует использование модуля, но тестовая заглушка нуждается в
  актуализации отдельной задачей вне переноса документации. Собственных unit-тестов уровня
  application-сервиса для отчёта по услугам и справочника категорий нет (покрыты только через e2e и
  через доменные калькуляторы/VO); Prisma-запрос источника данных не имеет отдельного теста;
  нетривиальность фильтра по категориям (что он реально ограничивает выборку) не проверена ни одним
  тестом.
