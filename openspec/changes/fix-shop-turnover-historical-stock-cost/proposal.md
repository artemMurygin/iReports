## Why

Остаток на конец периода в отчёте по оборачиваемости магазина считается неверно для всех
исторически забэкфилленных месяцев (июнь–август 2026): себестоимость остатка вычисляется как
`историческое_количество × ТЕКУЩАЯ закупочная цена` вместо исторической себестоимости на момент
снапшота. Расхождение подтверждено эмпирически — сравнение отчёта за август 2026 с отчётом
«Остатки» в интерфейсе МойСклад на ту же дату дало точное совпадение количества (1749 = 1749), но
разное значение стоимости (1 557 731 ₽ у нас против 1 483 167,16 ₽ в МойСклад, ~5% расхождение),
что однозначно указывает на ошибку в расчёте себестоимости, а не количества. Корректный источник
исторической себестоимости — эндпоинт МойСклад `GET /report/turnover/all` (поле
`onPeriodEnd.sum`) — был найден и проверен: при правильных параметрах он воспроизводит эталонную
сумму МойСклад с точностью до копейки.

## What Changes

- Историческая себестоимость и количество остатка (`MoySkladStock.quantity`/`costSum` для снимков,
  созданных `backfillHistoricalStockSnapshots`) вычисляются через отчёты МойСклад семейства
  «Обороты» (`GET /report/turnover/all` и `GET /report/turnover/bystore`, поле `onPeriodEnd`), а не
  через легаси `GET /entity/assortment` (`buyPrice.value` на текущий момент — см. Why).
- **Важное уточнение, найденное в процессе (меняет первоначальный план)**: `GET /report/stock/all`
  и `GET /report/stock/bystore` — даже с параметром `moment` — не отдают историю: поля
  `stock`/`price` всегда отражают ТЕКУЩИЙ остаток независимо от переданного `moment` (проверено
  эмпирически: запрос с `moment` в прошлом году вернул то же количество, что и запрос вовсе без
  `moment`). Эти эндпоинты для получения исторических данных непригодны. Только отчёты `/report/
  turnover/*` (поле `onPeriodEnd`) действительно учитывают исторический момент — подтверждено
  точным совпадением с отчётом «Остатки» в интерфейсе МойСклад.
- `/report/turnover/bystore` отдаёт разбивку по складам, но принимает фильтр только по одному
  товару за раз (`filter=product=<href>`, повторение поля `product` запрещено API) — поэтому нельзя
  выгрузить сразу весь ассортимент одним вызовом, как раньше через `/report/stock/bystore`.
  Итоговая двухшаговая схема на каждый месяц бэкфилла:
  1. `GET /report/turnover/all?momentFrom=<якорь>&momentTo=<конец месяца>&withoutTurnover=true` —
     одним постраничным проходом получить список товаров с ненулевым остатком на конец месяца
     (`onPeriodEnd.quantity > 0`) и их account-wide себестоимость (для сверки на шаге 2).
  2. Для каждого товара из списка — `GET /report/turnover/bystore?filter=product=<href>&
     momentFrom=<тот же якорь>&momentTo=<тот же конец месяца>&withoutTurnover=true` — получить
     разбивку `stockByStore[].onPeriodEnd.{quantity,sum}` по каждому складу этого товара.
  Сумма `onPeriodEnd` по складам из шага 2 сверяется с account-wide значением из шага 1 (лог
  предупреждения при расхождении, без падения бэкфилла).
- `momentFrom` в обоих запросах берётся заведомо раньше начала работы компании в МойСклад (не
  начало отчётного месяца) — иначе отчёт теряет товары с остатком, но без оборота внутри узкого
  окна `momentFrom..momentTo` (подтверждено эмпирически: с `momentFrom` = начало отчётного месяца
  выборка теряла ~77% товаров с фактическим остатком).
- Легаси-метод получения себестоимости через `/entity/assortment`
  (`assortment-stock.schema.ts`, соответствующий fetch-метод в `moysklad.service.ts`) удаляется —
  он использовался только в `backfillHistoricalStockSnapshots` и появившаяся замена делает его
  ненужным. Часовая синхронизация в реальном времени (`uploadStockSnapshot`, `fetchStockByStore`,
  `stock-report.schema.ts`) не меняется: она и раньше не использовала ни легаси-эндпоинт, ни
  `moment` (снимок всегда «текущий», проблема относилась только к историческому бэкфиллу).
- **BREAKING (данные, не API)**: уже забэкфилленные снимки `MoySkladStock` за июнь–август 2026
  посчитаны неверно и должны быть пересчитаны новым методом как часть раскатки этого изменения
  (не отдельная задача на будущее) — иначе исправление применится только к новым периодам, а уже
  показанные пользователю (и обсуждённые в этой сессии) месяцы останутся с неверными числами.

### Modified Capabilities
- `shop/goods-turnover`: явное требование — себестоимость остатка на конец периода считается по
  исторической себестоимости на момент снапшота (МойСклад `onPeriodEnd.sum`), а не по текущей
  закупочной цене товара. Раньше это подразумевалось формулировкой «остаток... по себестоимости»,
  но не было явным требованием и не проверялось тестами, что и позволило этой ошибке остаться
  незамеченной.

## Impact

- **Backend**:
  - `backend/src/domains/shop/sync/moySklad/moysklad-sync.service.ts` —
    `backfillHistoricalStockSnapshots` переписывается на новый источник себестоимости;
    `_monthEndsFrom` без изменений (снимки по-прежнему на конец каждого месяца).
  - `backend/src/domains/shop/integrations/moySklad/moysklad.service.ts` — два новых метода:
    получение списка товаров с остатком на момент (`GET /report/turnover/all`, постраничное) и
    получение разбивки по складам для одного товара (`GET /report/turnover/bystore?filter=
    product=...`); старый метод получения `/entity/assortment` удаляется вместе с использующей его
    логикой.
  - `backend/src/domains/shop/integrations/moySklad/schemas/assortment-stock.schema.ts` —
    удаляется (заменяется новыми zod-схемами ответов `/report/turnover/all` и `/report/turnover/
    bystore`).
  - Данные: одноразовый пересчёт (по образцу `recalcShopGoodsTurnoverOnce.ts`) снимков
    `MoySkladStock` за уже забэкфилленные месяцы и последующий `RebuildGoodsTurnoverReportService`
    для затронутых периодов — на dev и на проде при раскатке.
- **Specs**: `openspec/specs/shop/goods-turnover/spec.md` — новое явное требование к источнику
  себестоимости остатка.
- **Внешняя зависимость**: `GET /report/turnover/all` и `GET /report/turnover/bystore` с
  параметрами `momentFrom`/`momentTo` — расхождение с ранее задокументированным (design.md D5.1
  прежнего change) и с описанием параметров в MCP-инструменте `moysklad`, оба ошибочно утверждали
  отсутствие исторического параметра у отчётов об остатках/оборотах; проверено прямыми запросами к
  боевому API в этой сессии (включая контрольную сверку `onPeriodEnd` по складам с account-wide
  значением и с эталонной суммой из интерфейса МойСклад), отдельная проверка при реализации не
  нужна. Отдельно подтверждено обратное для `GET /report/stock/all`/`GET /report/stock/bystore`:
  параметр `moment` этими двумя эндпоинтами принимается, но фактически игнорируется — поля
  `stock`/`price` всегда отражают текущий остаток; эти эндпоинты не используются в этом изменении,
  и их параметр `moment` не должен использоваться для получения истории нигде в проекте впредь.
