## Context

`backfillHistoricalStockSnapshots` (`moysklad-sync.service.ts`) сейчас, для каждого месяца от
`fromDate` и каждого склада, вызывает `MoyskladService.fetchAssortmentStockAt(monthEnd, storeId)` —
легаси `GET /entity/assortment?filter=stockMoment=...;stockStore=...` — и парсит `costSum` как
`quantity × buyPrice.value` (`assortment-stock.schema.ts`). `buyPrice` — это ТЕКУЩАЯ закупочная цена
карточки товара на момент запроса, не историческая цена на `stockMoment`. См. proposal.md — Why.

В процессе подготовки этого изменения (прямые запросы к боевому API текущего аккаунта, вне
кодовой базы) проверено следующее о доступных МойСклад-эндпоинтах остатков/оборотов:

- `GET /report/stock/all` и `GET /report/stock/bystore` принимают параметр `moment`, не возвращая
  ошибку, но **фактически игнорируют его** для полей `stock`/`price`/`stockByStore[].stock`: запрос
  с `moment` в прошлом (проверено на дате более чем за год до текущей) вернул те же итоговые числа
  количества, что и запрос вообще без `moment` (текущий остаток). Это расходится с тем, что было
  предположено раньше в этой же сессии (и с чем ранее согласился пользователь) — на практике эти
  два эндпоинта для истории непригодны в принципе, а не только "не проверены документацией".
- `GET /report/turnover/all` и `GET /report/turnover/bystore` (поле `onPeriodEnd.{quantity,sum}`)
  — единственные проверенные источники, реально учитывающие `momentTo`: сумма `onPeriodEnd.sum` по
  `/report/turnover/all` за август 2026 (при достаточно раннем `momentFrom`) совпала с суммой
  отчёта «Остатки» в интерфейсе МойСклад на ту же дату с точностью до копейки (1 483 167,16 ₽).
- `/report/turnover/all` листит СРАЗУ ВЕСЬ ассортимент (постранично, `limit`/`offset` работают
  как обычно), но без разбивки по складам.
- `/report/turnover/bystore` даёт разбивку по складам (`stockByStore[]`, с тем же `onPeriodEnd` на
  запись), но обязателен фильтр `filter=product=<href>` или `filter=variant=<href>`, и это поле
  фильтра **нельзя указать больше одного раза** в одном запросе (API возвращает ошибку 1030) —
  то есть один вызов = один товар, разбивка по всем его складам сразу.
- Сверка (один и тот же товар, один и тот же `momentTo`): сумма `stockByStore[].onPeriodEnd` по
  `/report/turnover/bystore` в точности равна `onPeriodEnd` того же товара по `/report/turnover/
  all` — оба эндпоинта одной "оборотной" механикой, значит их можно комбинировать без риска
  систематического расхождения между шагами.
- Оба `/report/turnover/*`-отчёта по умолчанию включают в выборку только товары, у которых было
  движение (приход/расход) внутри окна `momentFrom..momentTo`. Узкий `momentFrom` (например, начало
  отчётного месяца) теряет товары с остатком, но без оборота внутри этого окна — на реальных данных
  узкое окно вернуло 115 из ожидаемых ~509-511 товаров с остатком (потеря ~78%). `withoutTurnover=
  true` в параметрах запроса на это в проверенных данных влияния не оказал (тот же результат с
  `true`/`false`/без параметра) — тем не менее параметр оставляем переданным (`true`): по смыслу
  названия он предназначен именно для этого случая, и в аккаунте могут быть товары, для которых
  разница проявится (первое поступление без единой продажи).

## Goals / Non-Goals

**Goals:**
- Исторические снимки `MoySkladStock`, создаваемые бэкфиллом, содержат себестоимость и количество,
  соответствующие фактическому состоянию склада на конец отчётного месяца — не текущему.
- Уже существующие (неверные) снимки за июнь–август 2026 заменяются пересчитанными в рамках
  раскатки этого изменения, а не оставляются как есть.
- Часовая синхронизация в реальном времени не меняется и не может регрессировать.

**Non-Goals:**
- Не переиспользуется никакая версия `moment`-параметра `/report/stock/*` — эти эндпоинты для
  истории признаны непригодными (см. Context), а не временно отложенными.
- Не вводится общий "универсальный" клиент отчётов МойСклад — два новых метода в
  `MoyskladService` следуют уже принятому в файле стилю (по методу на конкретный вызов API).
- Не меняется частота/расписание бэкфилла (`fromDate` по-прежнему передаётся вызывающим кодом —
  `initialUploadData.ts`/`recalcShopGoodsTurnoverOnce.ts`), не меняется гранулярность снимка
  (конец календарного месяца).

## Decisions

### D1. Источник данных бэкфилла: связка `turnover/all` (обнаружение) + `turnover/bystore` (разбивка)
На каждый месяц бэкфилла:
1. `GET /report/turnover/all?momentFrom=<якорь>&momentTo=<конец месяца>&withoutTurnover=true`,
   постранично (как уже делает `_fetchPaged`) — собрать список товаров, у которых
   `onPeriodEnd.quantity > 0`, вместе с account-wide `onPeriodEnd.sum` (используется только для
   сверки на шаге 2, не пишется в БД).
2. Для каждого товара из этого списка — `GET /report/turnover/bystore?filter=product=<href>&
   momentFrom=<тот же якорь>&momentTo=<тот же конец месяца>&withoutTurnover=true` — получить
   `stockByStore[]` (склад → `onPeriodEnd.{quantity,sum}`) и апсертнуть по одной строке
   `MoySkladStock` на каждую пару (товар, склад) с ненулевым количеством.

**Альтернатива (отклонена)**: сохранить двухэтапную идею "количество из `stock/bystore` +
себестоимость из `turnover/all`", предложенную до эмпирической проверки — отклонена, т.к.
`stock/bystore` игнорирует `moment` (Context) и дал бы неверное количество, из-за чего пришлось бы
делить неверный account-wide `costSum` на неверное количество склада — двойная ошибка вместо
одной.

**Альтернатива (отклонена)**: вызывать `/report/turnover/bystore` для всех 3046 товаров локальной
таблицы `MoySkladProduct` за каждый месяц, без предварительного отбора через `turnover/all` —
отклонена по производительности (3046 × число месяцев вызовов вместо ~505-511 × число месяцев;
почти всегда >80% товаров не имеют остатка в конкретном месяце).

### D2. Значение `momentFrom` — фиксированная константа, а не связанная с отчётным месяцем
`momentFrom` для обоих запросов — фиксированная дата, заведомо раньше начала работы компании в
МойСклад (не зависит от того, какой месяц бэкфиллится). Обоснование: чтобы отчёт не терял товары с
остатком, но без оборота внутри отчётного месяца (Context), окно должно быть широким; фиксированная
константа проще, чем вычислять "самое раннее движение" по локальной БД, и не может случайно
сузиться, если локальные данные синхронизированы не с самого начала. Названная константа с
комментарием, откуда взято значение (эмпирическая проверка в рамках этого change) — не магическое
число без объяснения.

### D3. Только товары с `onPeriodEnd.quantity > 0` на шаге 1 идут на шаг 2
Товары, у которых на конец месяца остаток нулевой, не запрашиваются повторно через
`turnover/bystore` и не создают строк `MoySkladStock` — это симметрично уже существующему поведению
(товар без снимка на этот месяц просто отсутствует в `MoySkladStock`, `RebuildGoodsTurnoverReportService`
не требует присутствия строки для нулевого остатка).

### D4. Сверка account-wide и по-складской суммы — предупреждение, не ошибка
После шага 2 для каждого товара сравнивается сумма `onPeriodEnd` по складам (шаг 2) с account-wide
`onPeriodEnd` того же товара (шаг 1). При расхождении — `Logger.warn` с id товара и обоими
значениями, бэкфилл продолжается (не падает) — по аналогии с существующим стилем `stock-report.
schema.ts`/`assortment-stock.schema.ts` (лог предупреждения + разумное значение по умолчанию, а не
исключение, останавливающее весь прогон одной аномальной строки).

### D5. Удаление легаси-пути целиком, а не пометка deprecated
`fetchAssortmentStockAt`, `assortment-stock.schema.ts` и импорт `AssortmentStockRow`/
`toAssortmentStockRow` в `moysklad.service.ts` удаляются полностью (не помечаются `@deprecated`) —
единственный вызывающий код (`backfillHistoricalStockSnapshots`) переписывается на новый источник в
этом же изменении, оставлять неиспользуемый код нет смысла (проектное правило: если код точно не
используется — удалить, а не оставлять с пометкой).

### D6. Пересчёт уже забэкфилленных месяцев — часть Migration Plan, не отдельная задача
См. Migration Plan.

## Risks / Trade-offs

- **[Риск] Скорость бэкфилла**: шаг 2 — один HTTP-вызов на товар с остатком (~505-511 при текущем
  объёме данных) на каждый месяц, последовательно с задержкой (как и остальные постраничные
  вызовы в `moysklad.service.ts`, см. `delay(400)`/`delay(500)`) → **Митигация**: для разового
  скрипта миграции (не крон, не пользовательский HTTP-запрос) несколько минут на месяц приемлемо;
  если объём вырастет на порядок — рассмотреть ограниченный параллелизм (`p-limit`-подобный
  паттерн), не требуется сейчас.
- **[Риск] `filter=product=` не работает для товаров типа `variant` (модификаций)** — локальная
  `MoySkladProduct` хранит только товары типа `product`; если в ассортименте есть `variant`,
  `/report/turnover/all` вернёт его строку с `assortment.meta.type === 'variant'`, а фильтр,
  видимо, потребует `filter=variant=<href>` вместо `filter=product=<href>` → **Митигация**: новый
  fetch-метод выбирает имя параметра фильтра по `assortment.meta.type` строки, аналогично тому, как
  `_uploadDemands` уже различает `type === 'variant'` при импорте позиций отгрузки; для
  неожиданного третьего типа — `Logger.warn` и пропуск товара (не падение всего бэкфилла).
- **[Риск] Отклонение account-wide и по-складской суммы (D4)** может маскировать реальную проблему
  данных вместо явной ошибки → **Митигация**: уровень `warn`, а не `debug` — виден в проде;
  дальнейшее расследование расхождений — по мере появления, не блокирует эту раскатку.
- **[Trade-off] Бэкфилл больше не идемпотентен "бесплатно" в смысле нагрузки** — раньше один вызов
  на склад на месяц (`fetchAssortmentStockAt`), теперь до ~511 вызовов на месяц; upsert-семантика
  (идемпотентность результата) не меняется, меняется только число запросов к внешнему API.

## Migration Plan

1. Выкатить код (новые fetch-методы, переписанный `backfillHistoricalStockSnapshots`, удалённый
   легаси-путь) — сам по себе не меняет уже существующие строки `MoySkladStock`.
2. Запустить разовый пересчёт для уже забэкфилленных месяцев (июнь–август 2026 на момент этого
   изменения) — сначала на dev, затем на проде: точное количество месяцев определяется по
   фактическому состоянию `MoySkladStock` на момент выката (`SELECT DISTINCT snapshotAt FROM
   moy_sklad_stock WHERE snapshotAt отдаёт конец месяца`), а не жёстко "три месяца". Скрипт по
   образцу `recalcShopGoodsTurnoverOnce.ts`/временного скрипта из этой сессии
   (`backend/src/scripts/_tmp-rebuild-shop-turnover-aug.ts`, уже удалён) — вызывает
   `backfillHistoricalStockSnapshots` заново (upsert перезапишет старые `quantity`/`costSum` теми
   же ключами `productId_warehouseId_snapshotAt`, не создавая дублей) и затем
   `RebuildGoodsTurnoverReportService.rebuild(period)` для каждого затронутого периода.
3. После пересчёта — точечная сверка хотя бы одного периода (август 2026) с отчётом «Остатки» в
   интерфейсе МойСклад на ту же дату, аналогично проверке, сделанной вручную в этой сессии.
4. Откат: поскольку изменение затрагивает только исторические данные (не текущий открытый месяц,
   который пересчитывается почасовым кроном из реального времени и этим изменением не
   затрагивается), откат — просто откат кода; ранее пересчитанные строки `MoySkladStock` неверными
   не станут (новый метод корректнее старого), откатывать данные назад не требуется.
