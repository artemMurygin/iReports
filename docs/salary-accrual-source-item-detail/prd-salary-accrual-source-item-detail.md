# PRD: Детализация начисления зарплаты — название проданного товара/услуги и ссылка на документ ERP

**Дата**: 2026-08-24
**Статус**: Draft

## Цель

На странице зарплатного отчёта сотрудника, в раскрывающейся детализации по зарплатному правилу, вместо родового лейбла "Позиция" показывать название конкретного товара или услуги, за которую начислена сумма, и обеспечить однозначную ссылку на документ ERP-системы (заказ RemOnline / отгрузку МойСклад), к которому привязано начисление — чтобы бухгалтер и руководитель могли проверить каждую строку начисления без ручного запроса в ERP.

## Пользовательские сценарии

- Бухгалтер открывает отчёт по зарплате сотрудника → разворачивает правило "Оплата за услугу" (`ServiceCompleted`, направление service) → по каждому источнику начисления видит название услуги (например, "Замена дисплея iPhone 13"), сумму и переходит по ссылке на заказ в RemOnline, к которому услуга относится.
- Руководитель магазина открывает отчёт по зарплате сотрудника → разворачивает правило "Вознаграждение за проданный товар" (`ProductSold`, направление shop) → по каждому источнику начисления видит название товара, сумму начисления и переходит по ссылке на отгрузку в МойСклад, в которой товар продан.
- Руководитель магазина открывает правило "Вознаграждение закупщику Б/У техники" (`UsedProductSold`, направление shop) → видит название конкретного проданного Б/У устройства и ссылку на документ отгрузки.
- (Существующий сценарий, поведение не меняется) Бухгалтер разворачивает правило "Оплата заказа" (`OrderPayed`, направление service) → видит устройство (бренд/модель/цвет) и ссылку на заказ целиком — правило платит за заказ как за единицу, отдельных позиций внутри него не показывает.

## В скоупе

- **Backend, направление service**: прокинуть название услуги (`RoappService.name`) от источника данных (`ServiceCalculationDataRepository.findServiceCompletedItems`) через `ServiceCompletedErpItem` → `CalculationSourceRef` (`ServiceCompletedEntity.buildSources`) → `EmployeeSalaryReportSource` (маппер `to-salary-report-rules.ts`) → контракт.
- **Backend, направление shop**: прокинуть название товара (или конкретного Б/У устройства) в источник начисления для правил `ProductSold` и `UsedProductSold` — от данных позиции отгрузки МойСклад (`ShopProductSoldErpItem`) до итогового ответа отчёта (`to-shop-salary-report-rules.ts`).
- **Backend, направление shop**: добавить ссылку на исходный документ ERP (отгрузка МойСклад) в источник начисления для `ProductSold` и `UsedProductSold`, по аналогии с уже существующей ссылкой на заказ RemOnline (`buildRoappOrderLink`) у направления service.
- **Контракт (`ireports-contracts`)**: добавить в `calculationSourceRefSchema`/`employeeSalaryReportSourceSchema` опциональное поле названия проданного товара/услуги, общее для обоих направлений.
- **Frontend**: в детализации по правилу (компонент, отвечающий за раскрывающийся список источников начисления на странице `/salaries`) выводить название товара/услуги там, где оно доступно, сохранив текущую ссылку на документ и уже отображаемые данные устройства (для service).
- Для правил, где название физически недоступно по архитектуре (`OrderPayed`, `PayPerHour`, `TaskCompleted`) — поведение детализации не меняется.

## Не в скоупе

- Разбивка правила "Оплата заказа" (`OrderPayedEntity`, направление service) по отдельным позициям/товарам внутри заказа — правило по архитектуре начисляет за заказ целиком, у отдельной позиции внутри заказа в RemOnline нет собственного документа/номера.
- Правило `TaskCompleted` (оба направления) — ручная внутренняя отметка выполнения задачи, не привязана к документу ERP, детализация не меняется.
- Изменение логики расчёта суммы начисления по любому правилу — фича затрагивает только отображение и трассируемость источника, суммы не пересчитываются.
- Направление `opt` (оптовые продажи) — функциональность там не реализована.

## Технические ограничения

- В направлении service название услуги (`RoappService.name`) сейчас не выбирается в `ServiceCalculationDataRepository.findServiceCompletedItems` (select ограничен `engeneerBonus`) — требуется расширение select и прокидывание поля по всей цепочке entity → mapper → контракт.
- В направлении shop у `ShopProductSoldErpItem` сейчас нет ни названия товара, ни ссылки на документ — оба поля нужно добавить в тип и в источник данных (application-слой, сборщик `erpData` для shop-калькуляции).
- В проекте нет готового builder'а ссылки на документ МойСклад (аналога `buildRoappOrderLink` у service) — его нужно создать заново; точный формат URL карточки отгрузки МойСклад требует отдельного уточнения.
- Товары-модификации (`variant`) в МойСклад могут не иметь собственного названия в локальной БД синхронизации (при синке они наследуют только `folderId` от родительского товара, см. `MoySkladSyncService.uploadDemand`) — нужно проверить, что название корректно резолвится и для таких позиций.
- Схема источника начисления в `ireports-contracts` общая для обоих направлений — новое поле должно быть опциональным и одинаково типизированным для service и shop.

## Критерии готовности

- [ ] В детализации правила "Оплата за услугу" (service) по каждому источнику начисления отображается название услуги.
- [ ] В детализации правил "Вознаграждение за проданный товар" и "Вознаграждение закупщику Б/У техники" (shop) по каждому источнику начисления отображается название товара/устройства.
- [ ] В детализации правил `ProductSold` и `UsedProductSold` (shop) по каждому источнику начисления есть кликабельная ссылка на исходный документ отгрузки в МойСклад.
- [ ] В детализации правила "Оплата за услугу" (service) ссылка на заказ RemOnline продолжает работать без изменений.
- [ ] Поведение правил `OrderPayed`, `PayPerHour`, `TaskCompleted` (оба направления) не изменилось — существующие юнит- и e2e-тесты проходят без модификации ожидаемого поведения (кроме добавления новых опциональных полей).
- [ ] Новое поле названия товара/услуги добавлено в `ireports-contracts` как опциональное и покрыто тестами маппера (`to-salary-report-rules.ts`, `to-shop-salary-report-rules.ts`).
- [ ] Ручная проверка на тестовых данных: для сотрудника с начислениями и по service, и по shop открыт отчёт зарплаты — детализация каждого затронутого правила показывает корректное название и рабочую ссылку на документ.
