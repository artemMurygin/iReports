# Исследование: авторизация вне Bitrix24 + роли доступа

Конспект разбора (explore-режим), не PRD и не готовый план — фиксирует находки по коду и принятые по ходу разговора решения. Дата: 2026-08-26.

## Проблема

Приложение сейчас фактически работает как отдельный сайт/ссылка, а не как встроенное во фрейм Bitrix24 приложение (см. «Текущее состояние»). Автор хочет:
1. Чтобы приложение полноценно поддерживало **оба** сценария входа — и встроенный во фрейм Bitrix24, и как самостоятельный веб-ресурс, открытый напрямую.
2. Защитить backend-роуты реальной проверкой личности.
3. Ввести роли доступа (сотрудник / руководитель / администратор), совпадающие с оргструктурой Bitrix24.

## Текущее состояние (по факту, найдено чтением кода)

- Фронтенд не инициализирует BX24-фрейм — только CDN-скрипт `//api.bitrix24.com/api/v1/`, единственное использование — `BX24.openPath(...)` в `DealsTable`. `BX24.init()` нигде не вызывается.
- Backend-роуты **полностью открыты**. Единственный задел под auth — `PortalAdminGuard` + заголовок `x-bitrix-auth` + `BitrixPortalAdminCheckService` (вызывает Bitrix REST `user.admin` с токеном из заголовка, fail-closed, TTL-кэш 60с) — но он **закомментирован на всех контроллерах модуля `employee-identity`** с пометкой в коде: страница работает вне встроенного контекста и не может передать `x-bitrix-auth`.
- Нет JWT/Passport/сессий, нет `ProtectedRoute`/`AuthContext` на фронте, нет модели ролей в проекте.
- В ветке `main` уже реализована установка Bitrix24 Local-приложения: `POST /bitrix/install`, `BitrixAuthService`, таблица `BitrixInstallation` (`memberId → accessToken/refreshToken`, обновляется через реальные `client_id`/`client_secret`, уже настроенные на портале). **Важно**: `BitrixInstallation` — это app-level (портал-level) токен, ключ — `memberId`, а не пользователь; таблица перезаписывается при каждом открытии фрейма любым сотрудником — для персональной идентификации не годится, нужна отдельная сущность.
- Данных для резолва ролей локально тоже нет:
  - `modules/directory/` — тонкий read-only справочник (`BitrixDepartment{id,name}`, `BitrixEmployee`) только для селектов в форме зарплатной схемы; понятия «руководитель отдела» нет вообще.
  - Синхронизация сотрудников (`uploadEmployees()` → `/user.get`) не по крону — запускается только вручную (`npm run initial`).
  - `department.get`/`UF_HEAD` нигде не вызывается — нет метода в `BitrixService`, нет поля в Prisma-модели `BitrixDepartment`.
  - Админ-флаг (`user.admin`) не персистится — резолвится живым запросом на лету.

## Ключевая развилка: embedded auth принципиально не работает вне фрейма

При открытии приложения внутри iframe Bitrix24 сам передаёт во фрейм POST-данные (`AUTH_ID`/`REFRESH_ID`/`member_id`) — это «бесплатная» авторизация, завязанная на факт, что окно породил сам портал. Вне фрейма (прямой заход по URL) взять эти данные неоткуда — это не баг текущей интеграции, а архитектурное ограничение механизма.

Для входа вне фрейма нужен отдельный путь — полноценный **OAuth Authorization Code redirect** («Войти через Bitrix24»): редирект на `<портал>/oauth/authorize/` → логин на портале (если сотрудник уже залогинен в Bitrix24 в браузере — редирект почти мгновенный) → callback с `code` → обмен на access/refresh token → определение личности (`user.current`/`profile`).

**Решено**: нужны оба сценария (не заменять фреймовый на редиректный) — оба сходятся в одну точку выдачи собственной сессии.

## Целевая архитектура (набросок)

```
Embedded (POST при каждом открытии iframe)      Standalone (/auth/bitrix/authorize → callback)
                    │                                          │
                    └──────────────────┬───────────────────────┘
                                        ▼
                     resolve identity (REST-вызов персональным токеном)
                                        ▼
        BitrixUserToken (НОВАЯ таблица, ключ memberId+bitrixUserId,
        персональные access/refresh, хранится на бэкенде — не путать
        с app-level BitrixInstallation)
                                        ▼
              employee-identity: bitrixUserId → employeeId (уже есть)
                                        ▼
        resolve roles:
         • employee — всегда
         • head     — BitrixDepartment.headId == userId (ТРЕБУЕТ новой синхронизации department.get/UF_HEAD)
         • admin    — user.admin, живой вызов при выдаче/рефреше сессии
                                        ▼
        своя сессия (cookie/JWT), claims: employeeId, roles[], departmentIds[]
                                        ▼
        единый AuthGuard + RolesGuard на всех backend-роутах
        + ProtectedRoute на фронте
```

## Решения, принятые по ходу разговора

1. Нужны оба сценария входа (embedded + standalone) — не выбираем один вместо другого.
2. Нужна разница в правах: сотрудник / руководитель / администратор.
3. Персональные Bitrix-токены хранить на бэкенде (не короткоживущий JWT без refresh — сессия с server-side хранением, аналогично тому, как уже сделано для app-level токенов в `BitrixInstallation`, но с отдельной таблицей и ключом на пользователя).
4. Регистрация Bitrix24 Local-приложения (`client_id`/`client_secret`) уже сделана в `main` — переиспользуем, не создаём заново.
5. Роли доступа полностью совпадают с оргструктурой Bitrix24 (не отдельная таблица прав внутри iReports) — источник правды: `department.get`/`UF_HEAD` для руководителей, `user.admin` для администраторов.

## Что обнаружилось как побочная, но связанная проблема

Контроль доступа теперь опирается на актуальность оргструктуры (кто в каком отделе, кто руководитель) — а синхронизация сотрудников сейчас не по расписанию, только вручную. Если это не починить, staleness данных станет проблемой безопасности (уволенный сотрудник или недавно назначенный руководитель), а не просто неточным списком в дропдауне. Скорее всего, эта часть должна войти в тот же change: сделать `department.get`(с `UF_HEAD`) + синхронизацию сотрудников регулярной (крон), а не разовым скриптом.

## Открытые вопросы (не решены, требуют ответа перед/во время проектирования)

- **Иерархия отделов**: в Bitrix24 отделы могут быть вложенными. Руководитель видит только свой отдел или ещё и все дочерние отделы под ним? Влияет на то, что кладём в `departmentIds[]` сессии — плоский список или развёрнутое поддерево.
- Нужен ли отдельный `BitrixIframeGuard`/эндпоинт для embedded-обмена токена (по аналогии с `bitrixAuth.md`, шаг 6 — «опционально, но рекомендовано»), или встроить эту логику прямо в middleware на основном URL приложения.
- TTL/логика инвалидации собственной сессии: как часто пере-резолвить роли (на случай, если сотрудника разжаловали/повысили) — на каждый рефреш токена, по таймеру, или только по повторному логину.
