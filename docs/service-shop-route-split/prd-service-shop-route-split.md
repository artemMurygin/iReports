# PRD: Разделение backend-роутов по направлениям `/service` и `/shop`

**Дата**: 2026-08-12
**Статус**: Draft

## Цель

Привести все HTTP-роуты backend к единому правилу: каждый эндпоинт домена `service` начинается с
`/v1/service`, каждый эндпоинт домена `shop` — с `/v1/shop`. Часть роутов сейчас не имеет префикса
направления (`/accounting/*`, `/v1/sales/plan*`, `/v1/motivation-schema`) или префиксована
непоследовательно (`/shop/accounting/*`, `/v1/sales/salesPerformance/shop/:period` — направление в
хвосте пути, а не в префиксе). Часть эндпоинтов при этом версионируется (`/v1/...`), часть — нет
(`/accounting/*`, `/shop/accounting/*`, `/shop/warehouse/catalog`). Разработчику и потребителю API
должно быть видно по структуре пути (версия, затем направление), какому направлению бизнеса и какой
версии API принадлежит эндпоинт, без чтения тела запроса или query-параметров.

## Пользовательские сценарии

- Разработчик открывает Swagger/`ENDPOINTS.md` -> по префиксу пути сразу понимает версию API и
  направление (`service`/`shop`) эндпоинта, без чтения описания или тела запроса.
- Фронтенд-разработчик добавляет экран плана продаж/зарплатного отчёта магазина -> вызывает
  `/v1/shop/...`-эндпоинт напрямую, без параметра `direction`, которым сегодня можно случайно запросить
  чужое направление.
- Руководитель закрывает расчётный период направления `shop` через `/v1/shop/accounting/period/...` ->
  запрос физически не может задеть данные направления `service` (не только по значению `direction` в
  пути, но и потому что это два независимых обработчика).

## В скоупе

- Единая карта роутов: все эндпоинты `domains/service/*` — под префиксом `/v1/service`, все эндпоинты
  `domains/shop/*` — под префиксом `/v1/shop`.
- Единая версия API у всех переписываемых эндпоинтов: `/v1` добавляется и там, где его сегодня нет
  (`accounting/*`, `shop/accounting/*`, `shop/warehouse/catalog`), и остаётся там, где уже есть
  (`sales/*`, `motivation-schema`) — расхождение в версионировании между модулями устраняется полностью
  в рамках этой фичи, а не только для новых роутов.
- Разделение `SalesPlan`/`SalesPlanTemplate` CRUD (`POST/GET/PATCH/DELETE .../sales/plan`,
  `.../sales/plan/approve`, `GET/PUT .../sales/plan_template`) на два независимых набора эндпоинтов —
  `/v1/service/sales/plan*` и новый `/v1/shop/sales/plan*`. Направление задаётся местом эндпоинта, а не
  передаётся клиентом в теле/query — один запрос больше не может одновременно создать/утвердить строки
  разных направлений.
- Защита операций по id (`PATCH`/`DELETE`/`POST .../approve` c `ids`) от применения к строке чужого
  направления: обращение к `/v1/service/sales/plan/:id` с id строки направления `shop` (и наоборот)
  должно вести себя как "строка не найдена".
- Разделение эндпоинтов расчётного периода (`GET .../period/:direction/:period`,
  `POST .../period/:direction/:period/close|reopen|recalculate`) на `/v1/service/accounting/period/*` и
  `/v1/shop/accounting/period/*`, включая разнесение бизнес-логики закрытия периода (`close`) на два
  независимых обработчика — без общего кода, который сегодня внутри себя выбирает направление.
- Разделение отчёта по зарплате (`GET .../salary_report/employee/:id/:period`,
  `.../salary_report/department/:id/:period`) на `/v1/service/accounting/salary_report/*` и
  `/v1/shop/accounting/salary_report/*` — каждый эндпоинт отдаёт отчёт только своего направления.
- Перенос под `/v1/service`: `POST /v1/motivation-schema`, `GET /accounting/salary_role_types`,
  `/accounting/task_completions*`, `/accounting/employee_hours*` — переходят на путь
  `/v1/service/accounting/...`, разделения логики не требуют, только смена пути. Для
  `employee_hours*` это решение принято явно, несмотря на то что у данных физически нет понятия
  направления (см. "Технические ограничения") — вторая, `/shop`-версия этого CRUD не заводится, т.к.
  сущность одна на оба направления.
- Перенос уже существующих `/shop/accounting/*` и `/shop/warehouse/catalog` на `/v1/shop/accounting/*`
  и `/v1/shop/warehouse/catalog` — сами роуты уже в целевом виде по направлению, добавляется только
  версия.
- Обновление `ENDPOINTS.md` под новую карту роутов.
- Обновление комментариев/разделов `backend/src/domains/service/CLAUDE.md` и
  `backend/src/domains/shop/CLAUDE.md`, фиксирующих текущее (устаревающее после этой фичи) решение
  Фазы 11 о едином CRUD плана продаж на оба направления.

## Не в скоупе

- Роуты, не относящиеся однозначно ни к одному направлению: `employee-identity`
  (`/v1/employee-identity`), `bitrix` (`/bitrix`) — остаются без изменений, включая версионирование.
- Легаси-роуты, ещё не перенесённые в доменную структуру: `TODO/deals`, `TODO/reports`,
  `TODO/priceMonitoring` — вне скоупа до их будущего переноса в `domains/service`/`domains/shop`.
- Интеграционные роуты RoApp (`/roapp`, `/custom-api-roapp`) — служебные эндпоинты интеграции, не
  HTTP API для фронтенда.
- Изменение формата ответа `SalesPlan`/`SalesPlanTemplate` (поле `direction` в ответе остаётся —
  меняется только то, что клиент больше не передаёт его в запросе).
- Любые изменения на фронтенде — ни один из переписываемых эндпоинтов сегодня не используется
  фронтендом (проверено).
- Права доступа/авторизация для новых `/shop`-эндпоинтов — наследуют текущее поведение "без гарда",
  как и остальные эндпоинты `domains/shop` (`accounting`, `sales`); модель прав не входит в эту фичу.

## Технические ограничения

- `SalesPlan`/`SalesPlanTemplate` — общая Prisma-модель для обоих направлений (поле `direction` на
  каждой строке), без отдельных таблиц на направление. Разделение эндпоинтов не разделяет данные —
  оба новых набора роутов пишут/читают одну и ту же таблицу, различаясь только тем, какое значение
  `direction` подставляется на сервере.
- `CloseAccountingPeriodHandler` — сегодня единственное место в проекте, где код домена `service`
  напрямую импортирует классы домена `shop` (нарушение общего правила "домены не импортируют друг
  друга напрямую", описанного в `backend/CLAUDE.md` и `domains/service/CLAUDE.md`). Разделение на два
  независимых обработчика устраняет этот кросс-доменный импорт.
- Отчёт по зарплате сегодня — единственное место, где `service` вычисляет и объединяет данные обоих
  направлений в одном ответе (`grandTotal`, общий `isClosed`). После разделения понятие "итог по обоим
  направлениям сразу" в API исчезает: у каждого направления свой независимый отчёт, свой независимый
  статус закрытия.
- `EmployeeHoursEntry` не имеет поля `direction` — часы сотрудника не привязаны к направлению бизнеса
  на уровне данных, оба направления (в т.ч. расчёт `PayPerHour` у `shop`) читают один и тот же
  источник. По решению — эндпоинт всё равно размещается под `/v1/service/accounting/employee_hours*`
  без отдельной `/shop`-копии; это разделение по пути, не по данным — сущность и данные остаются
  общими, `shop` продолжает читать те же записи через сервисный путь.
- Сегодня версия API (`/v1`) задаётся на уровне `@Controller(routesV1.version)` в одних модулях
  (`sales`, `motivation-schema`, `employee-identity`, `shop/accounting`*, `shop/warehouse`* — часть из
  них уже читает константу `routesV1.version`, но не включает её в свой путь единообразно) и вовсе
  отсутствует в других (`accounting/*` — литеральный `@Controller('accounting')` без версии). Приведение
  всех переписываемых роутов к `/v1/...` — часть этой фичи, а не отдельная фаза.

## Критерии готовности

- [ ] Каждый HTTP-эндпоинт `domains/service/*` (кроме вынесенных в "не в скоупе") отвечает по пути,
      начинающемуся с `/v1/service`.
- [ ] Каждый HTTP-эндпоинт `domains/shop/*` отвечает по пути, начинающемуся с `/v1/shop`.
- [ ] `POST /v1/service/sales/plan` и `POST /v1/shop/sales/plan` — независимые эндпоинты; ни один не
      принимает `direction` в теле запроса.
- [ ] Запрос `PATCH`/`DELETE /v1/service/sales/plan/:id` с id строки, реально принадлежащей направлению
      `shop` (и симметрично для `/v1/shop/sales/plan/:id` с id строки `service`), возвращает "не
      найдено", а не изменяет/удаляет чужую строку.
- [ ] `POST /v1/service/sales/plan/approve` c `{ ids }`, где хотя бы один id принадлежит направлению
      `shop` (и симметрично), отклоняется целиком, не утверждая ни одной строки.
- [ ] `GET/PUT /v1/service/sales/plan_template` и `GET/PUT /v1/shop/sales/plan_template` — независимые
      эндпоинты, ни один не принимает `direction` в query/теле запроса.
- [ ] `GET/POST /v1/service/accounting/period/:period(/close|reopen|recalculate)` и аналогичные
      `/v1/shop/accounting/period/*` — независимые эндпоинты без параметра `:direction` в пути.
- [ ] Закрытие периода направления `service` через `/v1/service/accounting/period/:period/close` не
      создаёт и не изменяет снапшот/статус периода направления `shop` за тот же месяц, и наоборот.
- [ ] `GET /v1/service/accounting/salary_report/employee/:id/:period` и
      `GET /v1/shop/accounting/salary_report/employee/:id/:period` — независимые эндпоинты, каждый
      возвращает отчёт только своего направления; аналогично для `salary_report/department`.
- [ ] `POST /v1/service/motivation-schema`, `GET /v1/service/accounting/salary_role_types`,
      `/v1/service/accounting/task_completions*` отвечают по новым путям; старые (`/v1/motivation-schema`,
      `/accounting/salary_role_types`, `/accounting/task_completions*`) удалены.
- [ ] `GET/POST/PATCH/DELETE /v1/service/accounting/employee_hours*` отвечает по новому пути (старый
      `/accounting/employee_hours*` удалён); отдельной `/shop`-копии эндпоинта нет — данные остаются
      общими для обоих направлений.
- [ ] `GET/POST /v1/shop/accounting/*` (типы правил, мотивационная схема, задачи) и
      `GET /v1/shop/warehouse/catalog` отвечают по путям с `/v1`; старые версии без `/v1` удалены.
- [ ] Ни один переписанный эндпоинт (`service` или `shop`) не отвечает по пути без `/v1`.
- [ ] `ENDPOINTS.md` отражает полную новую карту роутов.
- [ ] `backend/src/domains/service/CLAUDE.md` и `backend/src/domains/shop/CLAUDE.md` не содержат
      устаревших утверждений о едином CRUD плана продаж на оба направления (решение Фазы 11).
