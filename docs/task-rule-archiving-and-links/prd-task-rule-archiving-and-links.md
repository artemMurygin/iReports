# PRD: Task Rule Archiving and Links

**Дата**: 2026-09-03
**Статус**: Draft

## Цель

После получения итогового результата по разовому зарплатному правилу-задаче (`TaskCompleted` с `isRecurring: false`) правило должно автоматически переставать быть частью активной мотивационной схемы сотрудника, не требуя от руководителя ручного захода и удаления. Дополнительно — руководитель и сотрудник должны иметь возможность перейти по ссылке на связанную задачу в Bitrix24 не только из открытого периода (уже реализовано), но и из списка задач перед закрытием периода, и из уже закрытого (исторического) периода — для проверки/аудита постфактум.

## Пользовательские сценарии

- Руководитель закрывает расчётный период, в котором было разовое правило-задача с зафиксированным результатом (задача выполнена, либо дедлайн прошёл без выполнения) → правило автоматически архивируется и больше не отображается в мотивационной схеме сотрудника.
- Руководитель переоткрывает уже закрытый период → ранее заархивированное разовое правило остаётся заархивированным (архив необратим).
- Руководитель открывает список незакрытых задач перед закрытием периода → видит для каждой задачи-правила кликабельную ссылку на задачу в Bitrix24, а не только её числовой ID.
- Руководитель открывает отчёт за уже закрытый расчётный период → видит у каждого правила-задачи ссылку на связанную задачу в Bitrix24 и переходит по ней, чтобы проверить её текущий статус.
- Сотрудник открывает свой зарплатный отчёт за текущий (открытый) месяц → видит ссылку на задачу, которую нужно выполнить (уже реализовано; фиксируется здесь как критерий регрессии, а не новая работа).
- Руководитель добавляет новое разовое правило-задачу в персональную мотивационную схему сотрудника → правило ведёт себя как раньше (создание задачи в Bitrix, ссылка в открытом отчёте) вплоть до момента закрытия периода, когда впервые применяется новое поведение.

## В скоупе

- Новое состояние правила `SalaryRule` для типа `TaskCompleted` с `isRecurring: false`: `ACTIVE` / `ARCHIVED`.
- Автоматический перевод разового правила в `ARCHIVED` в момент закрытия расчётного периода, к которому относится `dueDate` правила — независимо от того, была ли задача выполнена (статус «Закрыта» в Bitrix) или дедлайн прошёл без выполнения.
- Архив необратим: `reopen()` периода не возвращает правило обратно в `ACTIVE`.
- Заархивированные правила полностью исключаются из ответа эндпоинта(ов), отдающих мотивационную схему для просмотра/редактирования — они не должны попадать на клиент ни в каком виде (без «истории»/«архива» в интерфейсе).
- Расчёт зарплаты (в т.ч. для ещё открытых периодов) не меняется и продолжает учитывать все правила схемы независимо от статуса `ACTIVE`/`ARCHIVED` — фильтрация по статусу применяется только к эндпоинту(ам) отображения/редактирования схемы, не к расчёту.
- Регулярные правила (`isRecurring: true`) не затрагиваются этой фичей вообще — статус им не присваивается, они никогда не архивируются.
- Ссылка на задачу Bitrix24 (`bitrixTaskUrl`) добавляется в ответ сервиса «Список незакрытых задач перед закрытием периода».
- Ссылка на задачу Bitrix24 фиксируется в неизменяемом снапшоте расчётного периода в момент его закрытия (конкретный `bitrixTaskId`, соответствующий закрываемому периоду) и отдаётся в отчёте по уже закрытому периоду.

## Не в скоупе

- Изменение поведения регулярных (`isRecurring: true`) правил-задач — они продолжают работать как сейчас (крон/ленивое достраивание, накопление `bitrixTaskIds`, без архивации).
- Новые команды/кнопки в интерфейсе iReports для подтверждения или отклонения результата задачи — переход между статусами «Завершена»/«Выполняется» руководитель или сотрудник делает напрямую в Bitrix24 (уже так работает, design.md существующего change, Decision 8); эта фича туда не вмешивается.
- Автоматическое изменение статуса задачи в Bitrix24 со стороны iReports (переоткрытие, повторное создание и т.п.).
- Ручное или автоматическое восстановление (`unarchive`) заархивированного правила.
- Отображение заархивированных правил где-либо на клиенте в любом виде — явно отклонено при обсуждении фичи.
- Аналогичная функциональность для направления `shop` — интеграция `TaskCompleted`↔Bitrix24 у `shop` не реализована (см. design.md существующего change, Decision 10, дополнение от 2026-08-26).

## Технические ограничения

- Закрытый период не пересчитывается заново по live-правилам — данные читаются из `AccountingPeriodSnapshot` (`buildClosedServiceDirection`), поэтому архивация правила безопасна для уже закрытых периодов. При этом фильтрация по статусу не должна применяться к расчёту ещё открытого периода (`ResolveEmployeeSalaryRulesService`) — иначе живой отчёт за не закрытый месяц потеряет только что подтверждённую сумму сразу после архивации.
- `AccountingPeriodSnapshot.lines` — JSON-поле; добавление `bitrixTaskId` в строку снапшота не требует Prisma-миграции. Снапшоты, созданные до этого изменения, не будут иметь этого поля — ссылка для них не отображается, тот же паттерн обратной совместимости, что уже используется для других полей строки снапшота.
- `bitrixTaskUrl` в открытом периоде и в мотивационной схеме сегодня строится от последней (текущей) задачи из `bitrixTaskIds` правила, а не от задачи, привязанной к конкретному периоду — для закрытого периода этот приём не годится (у регулярного правила «текущая» задача к моменту просмотра истории уже может относиться к другому, более позднему месяцу). Поэтому в снапшот должен сохраняться именно тот `bitrixTaskId`, который был определён для этого периода в момент закрытия (`findTaskForPeriod`), а не последний элемент массива.
- В проекте нет отдельного паттерна «мягкого удаления» — используется явный enum-статус на сущности с методом-переходом (см. `AccountingPeriodStatus`, `TaskCompletion.confirm()/reject()`). Новый статус `SalaryRule` должен следовать этому же паттерну.
- Единственная точка входа в расчёт (`ResolveEmployeeSalaryRulesService`) сегодня не фильтрует правила ни по периоду, ни по статусу — это поведение должно сохраниться без изменений.

## Критерии готовности

- [ ] У `SalaryRule` типа `TaskCompleted` с `isRecurring: false` есть персистентный статус `ACTIVE`/`ARCHIVED`; у правил с `isRecurring: true` статус не используется.
- [ ] При закрытии расчётного периода все разовые `TaskCompleted`-правила, чей `dueDate` относится к этому периоду, переводятся в `ARCHIVED` — независимо от финального статуса задачи в Bitrix24 (выполнена или нет).
- [ ] Заархивированное правило не возвращается в ответе эндпоинта(ов) мотивационной схемы ни при каких условиях, включая повторное открытие (`reopen()`) периода, к которому оно относилось.
- [ ] Расчёт зарплаты за ещё открытый период (включая период, в котором правило только что было подтверждено/выполнено) продолжает корректно включать сумму по этому правилу без изменений в поведении.
- [ ] Регулярные правила-задачи после этой фичи ведут себя идентично поведению до неё (крон, ленивое достраивание, накопление `bitrixTaskIds`, без статуса и без архивации) — покрыто регрессионным тестом.
- [ ] В ответе сервиса «список незакрытых задач перед закрытием периода» для каждой задачи с известным `bitrixTaskId` присутствует рабочая `bitrixTaskUrl`.
- [ ] В отчёте за уже закрытый период у каждого правила-задачи, для которого при закрытии был определён `bitrixTaskId`, отображается рабочая ссылка на соответствующую задачу в Bitrix24.
- [ ] Снапшоты, созданные до этой фичи, продолжают корректно отображаться (без ссылки на задачу, без ошибок).
- [ ] Ссылка в открытом периоде (в т.ч. в отчёте сотрудника за текущий месяц) и в мотивационной схеме продолжает работать без изменений (регрессия).
