# Plan: Task Rule Archiving and Links

**PRD**: docs/task-rule-archiving-and-links/prd-task-rule-archiving-and-links.md
**Дата**: 2026-09-03

## Фазы реализации

### Фаза 1: Жизненный цикл статуса разового правила (Tracer Bullet)
**Цель**: Разовое `TaskCompleted`-правило получает персистентный статус и реально переходит в `ARCHIVED` при закрытии расчётного периода — минимальный сквозной путь, доказывающий, что механизм архивации работает от начала до конца, ещё без скрытия от клиента и без ссылок.
**Что затрагивает?**: backend
**Задачи:**
- [ ] Добавить `status: 'ACTIVE' | 'ARCHIVED'` в `TaskCompletedSalaryConfig` (props.config, дефолт `ACTIVE`) и в zod-схему `taskCompletedSalaryConfigSchema` (`ireports-contracts`); для `isRecurring: true` статус не используется.
- [ ] Добавить метод `archive()` на `TaskCompletedEntity` (переход `ACTIVE → ARCHIVED`, по аналогии с `AccountingPeriodEntity.close()`) и геттер текущего статуса.
- [ ] Реализовать обработчик `AccountingPeriodClosedDomainEvent` (application/events/), который находит все разовые `ACTIVE`-правила, чей `dueDate` относится к закрытому периоду, и архивирует их — независимо от того, была задача выполнена или дедлайн пропущен.
- [ ] Регрессионный тест: `ResolveEmployeeSalaryRulesService` продолжает отдавать все правила независимо от статуса (расчёт не меняется).
- [ ] Тест: `reopen()` периода не возвращает заархивированное правило в `ACTIVE`.
**Когда готово**: unit-тесты `task-completed.entity.spec.ts` и интеграционный тест «закрытие периода архивирует разовое правило (выполненное и просроченное), переоткрытие не восстанавливает» — зелёные; существующие тесты `accounting` не регрессируют.

### Фаза 2: Скрытие заархивированных правил от клиента
**Цель**: Заархивированные правила перестают попадать в ответ API мотивационной схемы — решает исходную проблему «нужно заходить и удалять руками».
**Что затрагивает?**: backend
**Задачи:**
- [ ] Отфильтровать `ARCHIVED`-правила в чтении/маппинге мотивационной схемы для HTTP-ответа (`motivation-schema.mapper.ts` и/или репозиторий чтения схемы).
- [ ] Убедиться, что фильтрация не затрагивает путь расчёта зарплаты (`ResolveEmployeeSalaryRulesService`/`PeriodCalculationOrchestrator` используют схему без этого фильтра).
- [ ] e2e-тест: `GET` мотивационной схемы после закрытия периода не содержит заархивированное правило; `GET` отчёта за тот же (уже закрытый) период по-прежнему показывает корректную сумму по этому правилу.
**Когда готово**: e2e-тест на HTTP-контроллер схемы подтверждает полное отсутствие заархивированных правил в ответе при сохранении корректной суммы в отчёте.

### Фаза 3: Ссылка на задачу в списке перед закрытием периода
**Цель**: Руководитель может провалиться в задачу прямо с экрана предзакрытия периода, а не только по числовому ID.
**Что затрагивает?**: backend
**Задачи:**
- [ ] Добавить `bitrixTaskUrl` в `UnclosedTaskRule` (`list-unclosed-task-rules-for-period.service.ts`), построив её через существующий `buildBitrixTaskLink()`.
- [ ] Обновить контракт/zod-схему ответа этого эндпоинта новым полем.
- [ ] Unit-тест сервиса: `bitrixTaskUrl` присутствует для доступной задачи и отсутствует при `isUnavailable: true`.
**Когда готово**: unit- и e2e-тест эндпоинта зелёные, поле `bitrixTaskUrl` присутствует в ответе для каждой доступной задачи списка.

### Фаза 4: Ссылка на задачу в уже закрытом периоде
**Цель**: Ссылка на задачу переживает закрытие периода — руководитель может провалиться в неё и проверить текущий статус постфактум (аудит).
**Что затрагивает?**: backend, database (новое поле в существующем JSON, без миграции схемы)
**Задачи:**
- [ ] При построении строк снапшота (`CalculateServiceSnapshotRowsService`) сохранить `bitrixTaskId`, определённый для правила именно на этот период (`findTaskForPeriod`, а не последний элемент `bitrixTaskIds`), в `AccountingPeriodSnapshot.lines[]`.
- [ ] В `buildClosedServiceDirection` построить `bitrixTaskUrl` из сохранённого `bitrixTaskId` через `buildBitrixTaskLink()`; добавить поле в тип/контракт closed-отчёта.
- [ ] Обеспечить обратную совместимость: снапшоты, созданные до этого изменения, отдают `bitrixTaskUrl: undefined` без ошибок.
- [ ] e2e-тест: закрыть период с разовым правилом → в снапшоте сохранён `bitrixTaskId` → `GET` отчёта за закрытый период отдаёт рабочую `bitrixTaskUrl`.
- [ ] Тест на старом снапшоте (без поля `bitrixTaskId` в JSON) — отчёт строится без ошибок, ссылка отсутствует.
**Когда готово**: e2e-тест «закрыть период → открыть отчёт за этот период → ссылка на задачу присутствует и валидна» зелёный; тест на legacy-снапшоте без поля не падает.

### Фаза 5: Отображение ссылок в интерфейсе
**Цель**: Пользователь реально видит и может кликнуть по ссылке в двух новых местах UI, а не только в API-ответе.
**Что затрагивает?**: frontend
**Задачи:**
- [ ] Экран «незакрытые задачи перед закрытием периода» — отрендерить `bitrixTaskUrl` как кликабельную ссылку (открытие в новой вкладке), переиспользуя существующий компонент/паттерн ссылки из открытого отчёта/схемы.
- [ ] Отчёт за закрытый период — отрендерить `bitrixTaskUrl`, если поле присутствует; для legacy-снапшотов без поля — не показывать блок ссылки, без сломанной вёрстки.
- [ ] Ручная/e2e-проверка обоих экранов на деве.
**Когда готово**: визуально проверено на деве — обе ссылки кликабельны и ведут в Bitrix24; для старого снапшота ссылка корректно отсутствует.
