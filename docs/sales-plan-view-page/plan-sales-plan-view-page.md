# Plan: Страница просмотра плана продаж

**PRD**: Перенеси дизайн текущих макетов из pencil (Node IDs: `x2soj`, `J7p0C`, `T0FMcE`, `XRMZu`, файл `design/sallary-first-iteration.pen`) в проект. Создай страницу просмотра плана продаж. Всю необходимую информацию по эндпоинтам для данной страницы найти в backend/contracts. Для тестовых данных использовать период `2026-06`, по другим периодам данных может не быть.
**Дата**: 2026-08-14

## Контекст из дизайна

Файл `design/sallary-first-iteration.pen`. Переданные 4 Node ID — это два экрана:

- **`x2soj`** («План продаж · Список») — десктопная версия: Page Header (заголовок + статус периода) → Direction Tabs (Сервис/Магазин) + Period Chip + кнопка «Изменить план» → KPI Row (5 карточек: Выручка·план/факт/прогноз, Маржа·план/факт) → Selection Bar (групповые действия) → Plan Table (колонки: Категория, План/Факт/Прогноз/Осталось ₽, Выполнение %, Статус, Действия — по одной строке на категорию: Ремонт Apple, Ремонт Android, Диагностика, Выездной сервис, Аксессуары, Доп. гарантия, Trade-in).
- **`hYl0B`** («План продаж · Мобильный») — мобильная версия, три прямых потомка: **`J7p0C`** (App Bar, инстанс уже существующего компонента), **`T0FMcE`** (Content: тот же Page Header/Tabs/KPI в вертикальной раскладке 2×2 + список карточек `i4Qz8y` вместо таблицы), **`XRMZu`** (Bottom Nav, инстанс компонента `XXiyY` — 5 пунктов: Продажи/Аналитика/Зарплата/График/Ещё).

## Ключевые находки и решения (см. переписку с пользователем)

- **`J7p0C` уже реализован.** Это инстанс компонента `kXibe` (`ERP/Mobile/App Bar`), который уже перенесён в код как `shared/ui-kit/organisms/Header/HeaderMobile.tsx` и используется глобально через `app/Header.tsx` → `Layout.tsx`. В `app/Header.tsx` уже заведён пункт навигации `{ label: 'План продаж', to: '/sales-plan', disabled: true }` — эта страница ждёт своей реализации. Ничего дополнительно строить для App Bar не нужно — просто нужно, чтобы `activeLeaf` для маршрута `/sales-plan` резолвился в `{ section: 'Продажи', page: 'План продаж' }` (уже так и произойдёт по существующей логике) и снять `disabled: true`.
- **`XRMZu` (Bottom Nav) не реализован нигде** — это новый **глобальный** элемент мобильного шелла (не специфичный для этой страницы), которого сейчас в приложении нет вообще (на мобильном сейчас только гамбургер-меню). Строим его как переиспользуемый `ui-kit`-организм и подключаем в `app/Layout.tsx`, а не только на странице плана продаж.
- **Бэкенд ничего дорабатывать не нужно** — весь необходимый функционал уже есть:
  - `GET /v1/service/sales/salesPerformance/:period` — план+факт+прогноз по `(department, category)` за период, направление service.
  - `GET /v1/shop/sales/salesPerformance/:period` — то же для направления shop (без query, direction зашит в путь).
  - `GET /v1/service/reports/service-categories` — плоский список категорий услуг `{id: number, name, parentId, depth}` для резолва имён категорий service.
  - `GET /v1/shop/warehouse/catalog` — дерево категорий каталога магазина `{id: string, name, pathName, children}` для резолва имён категорий shop.
  - Контракты: `contracts/commands/sales-performance.ts` (`salesPerformanceSchema`), `contracts/commands/sales-plan.ts` (`salesPlanSchema`, `periodSchema`), `contracts/commands/report.ts` (`serviceCategorySchema`), `contracts/commands/catalog.ts` (`catalogCategorySchema`).
- **Отдел захардкожен как `department: 160`** (решение пользователя) — `SalesPlan`/`SalesPerformance` реально возвращают строки по нескольким разным отделам на одно направление, а макет отдела не показывает вовсе. Фронт запрашивает данные за период и локально фильтрует по `department === 160`, дизайн-агрегация по отделам не нужна.
- **Страница строится как view-only** («страница **просмотра** плана продаж» в задаче): реализуем чтение и визуальное отображение данных. Интерактивные элементы дизайна, требующие мутаций (чекбоксы выбора строк, Selection Bar с «Утвердить»/«Удалить»/«Снять выбор», иконки редактирования/удаления в строке, кнопка «Изменить план») переносятся визуально (для верности дизайну), но не подключаются к бэкенду — это отдельная будущая задача (создание/правка/утверждение плана уже описаны как отдельные эндпоинты, но не входят в эту фичу).
- Поле `category` в `salesPerformanceSchema` (наш источник данных) — `string | null`, без изменений. Замеченный незакоммиченный `.tmp`-файл правит **другую** схему (`salesPerformanceSummarySchema` в `salary-rule.ts`, используется в зарплатных отчётах) — эта страница её не использует, риска рассинхронизации нет.
- Резолв категорий отличается по направлению: у `service` — числовой `id` в `service-categories`, а `category` в плане — строка (`String(id) === category`); у `shop` — `category` это UUID папки МойСклад, резолвится через дерево `warehouse/catalog` (нужно развернуть дерево в плоскую map `id → pathName`). `category === null` — отображаем как «Без категории».
- Тестовые данные гарантированно есть только за `2026-06`; страница не должна падать на пустом ответе за другие периоды — нужен явный empty-state.

## Фазы реализации

### Фаза 1: Маршрут + сквозной поток данных (tracer bullet)
**Цель**: Доказать, что вся цепочка «роут → запрос к бэкенду → типизированные данные → отрисовка» работает целиком на реальных данных периода `2026-06`, направление `service`.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Завести `pages/SalesPlan` (по аналогии с `pages/ServicesReport`), зарегистрировать маршрут `/sales-plan` в `router.tsx`; в `app/Header.tsx` убрать `disabled: true` у пункта «План продаж»
- [ ] `features/SalesPlan/model/api.ts` — `queryOptions` для `GET /v1/service/sales/salesPerformance/:period?direction=service` и `GET /v1/service/reports/service-categories`, типы из `ireports-contracts`
- [ ] `features/SalesPlan/model/useSalesPlan.ts` — хук: тянет performance-строки за период `2026-06`, фильтрует `department === 160`, резолвит имя категории через map по `service-categories`, считает `remaining = plan.turnover - fact.turnover`
- [ ] Минимальный read-only рендер (можно на существующих примитивах `shared/ui/table.tsx`, без финальной вёрстки) — таблица категория/план/факт/прогноз, только чтобы проверить данные в браузере
**Когда готово**: переход на `/sales-plan` показывает реальные строки за `2026-06` (department 160, direction service) с именами категорий вместо id; `npm run build`/`npm run lint` без ошибок; лично проверено в браузере.

### Фаза 2: Десктопная вёрстка по макету `x2soj`
**Цель**: Страница на десктопе визуально соответствует `x2soj` (без интерактивных мутаций).
**Что затрагивает?** frontend, design
**Задачи:**
- [ ] Молекулы `shared/ui-kit/molecules/`: `KpiCard` (используется 5×), `CellProgress` (полоса выполнения %), `CellStatus` (бейдж `CREATED`→«Черновик»/`APPROVED`→«Утверждён»), `ColumnHeader`
- [ ] `features/SalesPlan/ui/SalesPlanTable.tsx` — таблица по структуре `x2soj` (Header Row + Entity-строки), колонки Категория/План/Факт/Прогноз/Осталось/Выполнение/Статус; без чекбоксов, Selection Bar и иконок действий (view-only)
- [ ] `pages/SalesPlan/ui/PageHeader.tsx` — заголовок «План продаж», подзаголовок, индикатор «Период открыт/закрыт» (точка + текст), Period Chip (статичное отображение периода, не кликабельно), Direction Tabs (Сервис/Магазин), переключающие фильтр `direction` в `useSalesPlan`
- [ ] `features/SalesPlan/ui/KpiRow.tsx` — 5 карточек, считаются агрегацией отфильтрованных строк (сумма `plan.turnover`/`fact.turnover`/`prognose.turnover`/`plan.margin`/`fact.margin`)
- [ ] Обработка `category === null` → «Без категории» в таблице и во всех агрегатах
**Когда готово**: скриншот страницы на ширине ≥1440px визуально совпадает со скриншотом `x2soj` (сверено `mcp__pencil__get_screenshot`); переключение вкладки направления обновляет данные; `npm run build`/`npm run lint` без ошибок.

### Фаза 3: Мобильная вёрстка (`T0FMcE`) + глобальный Bottom Nav (`XRMZu`)
**Цель**: Страница на мобильном визуально соответствует `hYl0B`, в приложении появляется нижняя навигация.
**Что затрагивает?** frontend, design
**Задачи:**
- [ ] `shared/ui-kit/molecules/PlanCard.tsx` по компоненту `i4Qz8y` (`ERP/Mobile/Plan Card`) — карточка категории (шапка категория+статус, значения план/факт/%, полоса прогресса, строка маржи)
- [ ] `features/SalesPlan/ui/SalesPlanCardList.tsx` — список `PlanCard` + счётчик «N категорий · Направление» вместо таблицы, переиспользует тот же `useSalesPlan`
- [ ] `pages/SalesPlan/ui/SalesPlanPage.tsx` — адаптивная сборка: KPI Grid 2×2 на мобильном / KPI Row на десктопе, `SalesPlanCardList`/`SalesPlanTable` по брейкпоинту (как переключение `HeaderDesktop`/`HeaderMobile`)
- [ ] `shared/ui-kit/organisms/BottomNav.tsx` по компоненту `XXiyY` (5 пунктов: Продажи/Аналитика/Зарплата/График/Ещё, «Ещё» открывает существующий `NavDrawer`) — подключить в `app/Layout.tsx` как глобальный элемент (виден на всех страницах на мобильной ширине), переиспользуя `SECTIONS`-конфиг из `app/Header.tsx`
**Когда готово**: на ширине 390px страница визуально совпадает со скриншотом `hYl0B`/`T0FMcE`; хлебная крошка в App Bar показывает «Продажи / План продаж»; Bottom Nav виден и кликабелен на любой странице на мобильной ширине; `npm run build`/`npm run lint` без ошибок.

### Фаза 4: Направление «Магазин» (shop)
**Цель**: Вкладка «Магазин» показывает реальные данные направления shop с корректными именами категорий.
**Что затрагивает?** frontend
**Задачи:**
- [ ] `features/SalesPlan/model/api.ts` — добавить `queryOptions` для `GET /v1/shop/sales/salesPerformance/:period` и `GET /v1/shop/warehouse/catalog`
- [ ] `useSalesPlan` — при `direction === 'shop'` переключать источник данных; развернуть дерево каталога в плоскую map `id → pathName` для резолва названий категорий
- [ ] Свести форму данных `service`/`shop` к единому виду, потребляемому `SalesPlanTable`/`SalesPlanCardList`/`KpiRow` без разветвлений в UI-компонентах
**Когда готово**: вкладка «Магазин» на `2026-06` показывает реальные строки с резолвленными названиями категорий каталога; переключение между вкладками не ломает KPI/таблицу/карточки; проверено в браузере на обоих брейкпоинтах.

### Фаза 5: Пустые состояния, загрузка, ошибки
**Цель**: Страница корректно ведёт себя за пределами тестового периода `2026-06` и во время сети.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Empty-state при пустом ответе `salesPerformance` (ожидаемо для периодов, отличных от `2026-06`) — понятное сообщение вместо пустой таблицы/списка
- [ ] `isInitialLoad`/`isRefreshing` по конвенции проекта (скелетон при первой загрузке, лёгкий индикатор при фоновом рефетче)
- [ ] Error-state через `ApiError.message` (сеть/бэкенд недоступен)
- [ ] Финальный визуальный проход: сравнение со скриншотами `x2soj`/`hYl0B` на 1440px и 390px, устранение расхождений
**Когда готово**: вручную проверены три состояния (пусто/загрузка/ошибка) на обоих брейкпоинтах; `npm run build`, `npm run lint`, `tsc -b --noEmit` без ошибок.
