## Порядок фаз

Фазы сгруппированы по PRD и идут строго последовательно: PRD 1 (фазы 1–5) → PRD 2 (фазы 6–10) → PRD 3 (фазы 11–15).
```
PRD 1:  1 BE tracer → 2 BE синк+блокировка часов → 3 Design → 4 FE закрытие → 5 FE начисления

PRD 3: 11 BE адаптеры ERP → 12 BE выплата → 13 Design → 14 FE выплата → 15 FE удаление/ERP в формах
```

## PRD 1 — Закрытие месяца и документы начисления

### Фаза 1: Документы начисления при закрытии (tracer bullet)
**Цель**: Закрытие периода по API порождает документы начисления `DRAFT` по каждому сотруднику снапшота — сквозной путь «закрыть → документы в БД → прочитать списком» работает для `service` и `shop`.
**Что затрагивает?** backend, database, contracts
**Задачи:**
- [x] `contracts`: `salaryAccrualStatusSchema` (`DRAFT | PARTIALLY_ACCRUED | ACCRUED | PAID`), `salaryAccrualLineStatusSchema`, `salaryAccrualLineSchema`, `salaryAccrualSchema` (с `isDismissed`), ответы списка и карточки
- [x] Prisma: `SalaryAccrual` (уникальность `(direction, period, employeeId)`, `isDismissed`, `total`) и `SalaryAccrualLine` (нормализованные поля `RuleBreakdownLine` + `originalAmount`/`amount`); миграция
- [x] В `CloseAccountingPeriodHandler` и `CloseShopAccountingPeriodHandler` (независимо, без общего кода): сброс кэша периода перед расчётом, создание документов в той же транзакции `UnitOfWork`, что снапшот и `CLOSED`; `isDismissed` — из активности `BitrixEmployee`; событие `SalaryAccrualDocumentsCreated`
- [x] `GET /v1/{direction}/accounting/salary_accruals?period`, `GET .../salary_accruals/:id`; ответ зарплатного отчёта за закрытый период дополняется статусом документа
- [x] `reopen`: через порт проверяет документы периода — все `DRAFT` → удаляет документы и снапшот, иначе `409` с перечнем
**Тесты**: unit на хендлеры закрытия (документ на каждого сотрудника снапшота, включая нулевых и уволенных; сумма = `total` снапшота, строки = `lines`; кэш сброшен — тест с изменением данных после прогрева; инъекция ошибки → период открыт, ничего не создано); e2e `close → list → reopen`, `reopen` с документом не в `DRAFT` → `409`; закрытие `service` не трогает `shop`.
**Когда готово**: `POST .../period/:period/close` создаёт документы, `GET .../salary_accruals?period` их отдаёт, `reopen` их удаляет; все перечисленные тесты зелёные; `ENDPOINTS.md` обновлён.

### Фаза 2: Неявная синхронизация ERP, сводка закрытия, блокировка часов
**Цель**: Закрытие само дотягивает данные из ERP за месяц и отклоняется при ошибке синка; есть `close-preview` для окна подтверждения; часы закрытого месяца заблокированы.
**Что затрагивает?** backend, contracts
**Задачи:**
- [x] Вызов синка по требованию из хендлеров закрытия: `service` — заказы RemOnline за месяц, `shop` — отгрузки МойСклада за месяц; таймаут (2 мин), блокировка по направлению от параллельного тика крона; ошибка синка → закрытие отклоняется, период открыт
- [x] Ограничение «только истёкший месяц» в хендлерах закрытия (текущий/будущий → `409`)
- [x] `GET /v1/{direction}/accounting/period/:period/close-preview` → `{ employeesCount, dismissedEmployeesCount, totalAmount, unapprovedPlanRows, employeesWithoutHours }` (контракт `closePeriodPreviewSchema`)
- [x] Единый переиспользуемый гард/доменный сервис «период закрыт» по `AccountingPeriod`; подключить к `POST/PATCH/DELETE employee_hours*` → `409` с `closedBy`/`closedAt`
**Тесты**: синк вызван до расчёта и новый заказ попадает в снапшот (замоканная ERP); ошибка/таймаут синка → `409`, ничего не создано; параллельный запуск синка и крона по направлению — один выполняется; `close-preview` совпадает с результатом реального закрытия; часы закрытого месяца → `409`, другого месяца/направления — ок; после `reopen` часы снова редактируются.
**Когда готово**: закрытие в dev-среде (где крон не тикает) даёт актуальные данные; `employee_hours` закрытого месяца не редактируются; тесты зелёные.

## PRD 2 — Начисление на баланс и баланс сотрудника

### Фаза 6: Проведение строк и лента баланса (tracer bullet PRD 2)
**Цель**: «Начислить» строку создаёт движение на балансе; остаток читается как сумма ленты; отмена удаляет движение.
**Что затрагивает?** backend, database, contracts
**Задачи:**
- [x] `contracts`: `balanceTransactionTypeSchema` (полный перечень, включая `ACCRUAL_ADJUSTMENT`, `MANUAL_REVERSAL`, `PAYOUT`), `balanceTransactionSchema`, ответ баланса сотрудника, запросы accrue/unaccrue/корректировки
- [x] Prisma: `BalanceTransaction` (`employeeId`, `direction`, `type`, `amount` со знаком, `occurredAt`, `createdBy`, `comment`, `period?`, `accrualId?`, `lineId?`, `ruleId?`, `reversedTransactionId?`, `erpSyncRequired`); уникальный индекс `(lineId, type)` для идемпотентности; `SalaryAccrualLine.status`, история корректировок
- [x] Команды `AccrueLine` (движение `SALARY_ACCRUAL` на сумму снапшота + `ACCRUAL_ADJUSTMENT` на разницу при корректировке, одна транзакция), `UnaccrueLine` (удаление обоих движений + `DRAFT`, `409` для `PAID`), `AdjustLine` (только `DRAFT`, обязательный комментарий); пересчёт статуса документа из строк
- [x] `GET /v1/{direction}/accounting/balance/employee/:id?from&to&types` — остаток = `SUM`, лента с фильтрами и итогом по выборке, раскрытие начисления до строки документа
- [x] `reopen` периода: проверка документов не в `DRAFT` (уже из фазы 1) — сквозной тест с проведённой строкой
**Тесты**: unit на команды (ровно одно движение; параллельный двойной accrue → одно движение по индексу; корректировка → два движения, сумма = новая; unaccrue удаляет оба; корректировка в `ACCRUED` → `409`; без комментария → `400`); остаток = сумма смешанной ленты; e2e `close → accrue → balance → unaccrue → reopen`.
**Когда готово**: через API можно провести строку, увидеть остаток, отменить; тесты зелёные; `ENDPOINTS.md` обновлён.

### Фаза 7: Массовое проведение, ручные движения, сторно, сводка по отделу
**Цель**: Полный набор операций PRD 2 на бэкенде.
**Что затрагивает?** backend, contracts
**Задачи:**
- [x] `POST .../salary_accruals/:id/accrue` (документ) и `POST .../salary_accruals/accrue?period` (месяц) — построчно в своих транзакциях, ответ с перечнем неудачных

### Фаза 12: Выплата, удаление, ERP для ручных движений (tracer bullet PRD 3)
**Цель**: Полный бэкенд PRD 3: выплата = документ ERP + движение `PAYOUT` атомарно; удаление зеркально; ручные движения с `erpSyncRequired` проходят через тот же механизм.
**Что затрагивает?** backend, contracts
**Задачи:**

- [x] Создание ручного движения с `erpSyncRequired = true` (фаза 7) переводится на тот же порядок «ERP → транзакция → компенсация»; `INCOME`/`OUTCOME` по знаку; сторно для таких движений запрещено

## Что требует решения до старта соответствующих фаз

- ~~**Фаза 11 — блокер**: подтвердить в API RemOnline и МойСклада удаление кассового документа/ордера.~~ Снято 2026-08-24: `DELETE /finance/accounts/{id}/transactions/{id}` (RemOnline) и `DELETE /entity/{cashout,cashin}/{id}` (МойСклад) подтверждены через MCP и покрыты адаптерами Фазы 11.
- **Фаза 11**: одна статья расходов МойСклада «Зарплата» на все типы движений или отдельные (единственный открытый вопрос PRD 3) — предварительно одна.
- **Фаза 13+ — перенесено из Фазы 11, ещё не снято**: `agent` кассового ордера МойСклада документирован API как «контрагент или юрлицо», Employee не упомянут явно; адаптер сейчас best-effort ссылается на Employee через `EmployeeIdentity` — требует проверки на реальном стенде перед тем, как выплата `shop` пойдёт в прод (иначе может понадобиться резолв «сотрудник → контрагент»). Фаза 12 этот вопрос не трогала (нет доступа к реальному стенду в рамках автоматизации, то же ограничение безопасности) — переносится дальше.
- **Фаза 2**: таймаут синка при закрытии (предварительно 2 минуты).
- Ограничение доступа (кто видит действия руководителя) — отдельная задача после фазы 15, в плане не учитывается.
- **Для Фазы 13 (дизайн) и 14/15 (фронтенд) — важно знать про API Фазы 12**:
  - Код «требуется подтверждение» — `409 Conflict`, тело `{ message, metadata: { employeeId, balance, balanceAfter } }` (не `422`).
  - Ответ `POST .../payout` и `POST .../payout/batch` (одиночный) — `{ transaction: BalanceTransaction, erpDocument: ErpCashDocument }`; ответ batch — `{ direction, outcomes: [{ employeeId, employeeName, status: PAID|NEEDS_CONFIRMATION|FAILED, balance, amount, message }], paidCount, totalPaidAmount }`. В batch нулевой/отрицательный остаток ВСЕГДА даёт `NEEDS_CONFIRMATION` (не `FAILED`), независимо от `confirmNegativeBalance` — этот флаг в batch подтверждает только «выплатить остальным выбранным», а не позволяет заплатить сотруднику без остатка.
  - `PayoutEmployeeRow.paid` и `.advances`/`.manual` — сырые суммы СО ЗНАКОМ (как в ленте баланса), не «модуль выплаченного»: `paid` для реальной выплаты — ОТРИЦАТЕЛЬНОЕ число. Фронт сам решает, показывать ли `Math.abs()`.
  - `paid` на странице выплаты считается по `occurredAt` движения `PAYOUT` ВНУТРИ месяца страницы (у `PAYOUT` нет поля `period`) — если выплата за июль фактически создаётся в августе с датой по умолчанию «сегодня» (август), страница июля покажет `paid: 0` для этого сотрудника, хотя `payoutStatus` (считается по общему остатку, не по `paid`) корректно покажет `PAID`. Стоит решить на дизайне: либо форма выплаты в другом месяце обязывает выбрать дату оплачиваемого периода, либо `paid` пересчитать иначе — открытый вопрос для Фазы 13.
  - `PAID` документов начисления — СТРОГО по своему направлению (открытый архитектурный вопрос закрыт как вариант (а), см. заметку проверки Фазы 12 выше): выплата `service` никогда не переводит в `PAID` документ `shop` того же сотрудника, даже если общий остаток уже ≤ 0.
  - `DELETE .../payout/:id` возвращает в `ACCRUED` **все** `PAID`-документы сотрудника своего направления, не только те, что закрыла именно эта выплата (нет обратной связи «выплата → закрытые документы», `PAYOUT` не хранит `accrualId`) — если остаток сотрудника закрывался несколькими операциями подряд, UI должен быть готов, что удаление одной выплаты может вернуть в `ACCRUED` больше документов, чем ожидает руководитель.
  - Обычное `DELETE /v1/accounting/balance/transactions/:id` (ручное движение) НЕ откатывает `PAID → ACCRUED`, даже если само это движение когда-то вызвало переход, — откат есть только у `DELETE .../payout/:id`.
  - В ленте баланса (`GET /v1/accounting/balance/employee/:id`) у движения появилось поле `erp: { system, externalId } | null` — источник данных для колонки/иконки ERP, запланированной на Фазу 15.
