# PRD: Начисление зарплаты на баланс и баланс сотрудника

**Дата**: 2026-08-20
**Статус**: Draft
**Часть**: 2 из 3, см. [README](./README.md)
**Зависит от**: [PRD 1 — документы начисления](./prd-accounting-period-closing-pipeline.md)

---

## Цель

Руководитель после закрытия месяца проверяет документы начисления и проводит их — построчно по каждому зарплатному правилу или документом целиком; каждая проведённая строка становится деньгами на балансе сотрудника. У сотрудника появляется баланс — лента всех движений денег между ним и компанией (начисления, авансы, премии, штрафы, больничные, отпускные) с текущим остатком, видимая в личном кабинете. Это единое место, через которое проходят все ручные движения денег по сотруднику.

---

## Пользовательские сценарии

### Проведение начисления

- Руководитель открывает документ начисления в статусе «Черновик» → видит по каждой строке-правилу кнопку «Начислить» и общую кнопку «Начислить всё».
- Руководитель нажимает «Начислить» у строки → на общий баланс сотрудника записывается движение «Начисление зарплаты» на сумму строки с ссылкой на правило и период; строка переходит в «Начислено» и больше не редактируется.
- Руководитель нажимает «Начислить всё» → все ещё не проведённые строки проводятся за один шаг; документ переходит в статус «Ожидает выплаты».
- Руководитель проверил строку и не согласен с суммой → вносит корректировку строки (новая сумма + обязательный комментарий) до проведения; исходная сумма из снапшота остаётся видна рядом с корректированной. При проведении такой строки на баланс ложатся два движения: начисление на сумму снапшота и корректировка на разницу с комментарием руководителя — сотрудник в ленте видит, сколько насчитала система и на сколько и почему руководитель изменил.
- Руководитель проводит строку повторно (двойной клик, повторный запрос) → второго движения на балансе не появляется.
- Руководитель ошибся и хочет отменить уже проведённую строку → нажимает «Отменить начисление»: движение `SALARY_ACCRUAL` этой строки (и движение корректировки, если было) удаляется с баланса, остаток уменьшается на их сумму, строка возвращается в «Черновик» и снова доступна для корректировки и проведения. Отмена невозможна, если документ уже выплачен (PRD 3).
- Руководитель открывает список начислений за месяц → видит по каждому документу статус и прогресс проведения («3 из 5 правил начислено»), а также кнопку «Начислить все документы месяца» с подтверждением.
- Сотрудник открывает личный кабинет после проведения → видит в балансе новые движения по каждому правилу и обновлённый остаток.

### Баланс сотрудника

- Сотрудник открывает страницу баланса → видит один общий остаток (главная цифра страницы), ленту движений по датам: тип, сумма, комментарий, период, кто создал. Детализация начисления по правилам и источникам живёт в документе начисления, строка ленты не раскрывается.
- Сотрудник фильтрует ленту по месяцу и типу движения → видит только нужные записи и итог по выборке.
- Руководитель открывает баланс сотрудника → видит то же, плюс действия «Добавить приход» / «Добавить расход».
- Руководитель добавляет аванс (расход с баланса) → остаток уменьшается, движение помечено типом «Аванс», в день выплаты сумма к выплате уже учитывает его.
- Руководитель добавляет доп. аванс в середине месяца → отдельное движение типа «Доп. аванс».
- Руководитель добавляет премию / больничный / отпускные (приход) → остаток растёт, движение с типом и комментарием.
- Руководитель добавляет штраф (расход) → остаток уменьшается; у штрафа обязателен комментарий с причиной.
- Руководитель создаёт движение задним числом (дата внутри закрытого месяца) → движение записывается на указанную дату, ничего в снапшоте закрытого месяца не меняется; в ленте видно, что запись создана позже даты движения.
- Руководитель ошибся в ручном движении → удаляет его: запись исчезает из ленты, остаток пересчитывается. Терминов «сторно»/«сторнировано» в интерфейсе нет.
- Руководитель открывает сводку балансов по отделу → видит по каждому сотруднику остаток, сумму начислений за месяц, сумму авансов, сумму ручных движений.
- Сотрудник пытается создать движение на своём балансе → действие недоступно (ограничение доступа — отдельной задачей после готовности модуля, см. «Не в скоупе»).

## В скоупе

### Проведение строк начисления

- Статусы строки документа: `DRAFT` ⇄ `ACCRUED`; обратный переход — действие «Отменить начисление».
- Статусы документа: `DRAFT` (ни одна строка не проведена), `PARTIALLY_ACCRUED` (часть строк), `ACCRUED` («Ожидает выплаты» — все строки проведены), `PAID` (PRD 3).
- Проведение строки создаёт ровно одно движение баланса типа `SALARY_ACCRUAL` со ссылками на документ, строку, правило, период и направление. Идемпотентность — по ссылке на строку: второе движение на ту же строку невозможно.
- «Начислить всё» по документу и «Начислить все документы месяца» по направлению — массовые операции; частичный сбой не оставляет половину строк проведёнными без записи об ошибке: каждая строка либо проведена вместе со своим движением, либо нет, результат массовой операции содержит перечень неудачных.
- Корректировка строки до проведения: новая сумма + обязательный комментарий + автор; хранится исходная сумма снапшота, корректированная сумма и история корректировок. При проведении скорректированной строки создаются **два** движения: `SALARY_ACCRUAL` на сумму снапшота и `ACCRUAL_ADJUSTMENT` на разницу (знак по знаку разницы) с комментарием корректировки и ссылкой на ту же строку; сумма двух движений равна корректированной сумме строки.
- Отмена проведённой строки: движения `SALARY_ACCRUAL` и `ACCRUAL_ADJUSTMENT`, созданные этой строкой, **удаляются** с баланса (не сторнируется), строка возвращается в `DRAFT`, документ пересчитывает статус. Удаление и смена статуса строки — одна транзакция. Отмена запрещена, если документ уже `PAID` (PRD 3). Это единственное исключение из правила неизменяемости ленты: начисление до выплаты — черновик расчёта, а не факт движения денег, поэтому след в ленте ему не нужен.

### Баланс сотрудника (`EmployeeBalance`)

- Баланс — производная величина: сумма всех движений сотрудника. Хранимого поля «остаток» нет; для списков допускается материализованное представление, которое пересчитывается из ленты.
- Баланс **общий по сотруднику** — один остаток и одна лента на `employeeId`, без деления на сервис/магазин (и на бэкенде тоже). `direction` у движения — необязательный атрибут происхождения (начисление создано документом направления; выплата уйдёт в кассу конкретной ERP — PRD 3), на остаток и группировку он не влияет.
- Движение (`BalanceTransaction`): сотрудник, направление, тип, знак (приход/расход определяется типом), сумма, дата движения (`occurredAt`), дата создания записи, автор, комментарий, период (опционально), ссылки на источник (документ начисления / строка).
- Типы движений этой итерации:

| Тип | Знак | Создаёт | Комментарий |
|---|---|---|---|
| `SALARY_ACCRUAL` | + | проведение строки начисления; удаляется при отмене начисления | нет |
| `ACCRUAL_ADJUSTMENT` | ± | проведение скорректированной строки (разница с суммой снапшота); удаляется при отмене начисления | обязателен (из корректировки) |
| `ADVANCE` | − | руководитель вручную | нет |
| `EXTRA_ADVANCE` | − | руководитель вручную | нет |
| `BONUS` | + | руководитель вручную | нет |
| `SICK_LEAVE` | + | руководитель вручную | нет |
| `VACATION_PAY` | + | руководитель вручную | нет |
| `PENALTY` | − | руководитель вручную | обязателен |
| `ADJUSTMENT` | ± | руководитель вручную | обязателен, знак задаётся явно |
| `PAYOUT` | − | PRD 3 | — |

- Исправление любого движения — **удаление**: ручное движение руководитель удаляет (`DELETE`), запись исчезает из ленты; ручное движение с документом ERP и выплата удаляются вместе с документом ERP (PRD 3); движения `SALARY_ACCRUAL` / `ACCRUAL_ADJUSTMENT` удаляются только действием «Отменить начисление» на строке документа (не прямым `DELETE` движения). `PATCH` движения не существует. Перечень типов закладывается целиком, включая `PAYOUT`, чтобы контракт не менялся в PRD 3.
- У каждого ручного движения есть признак, должно ли оно отражаться в кассе ERP (`erpSyncRequired`, по умолчанию `false`). Сама синхронизация — PRD 3; в этой итерации признак только хранится и показывается.
- Движение задним числом разрешено; дата движения может быть в закрытом периоде, снапшот и документы начисления закрытого периода при этом не меняются.
- Баланс может быть отрицательным (аванс больше начисленного) — это штатная ситуация, показывается явно. Лимитов на аванс и предупреждений об уходе в минус нет.

### Страницы

- Карточка документа начисления (из PRD 1) получает действия: «Начислить» у строки, «Начислить всё», корректировка строки, «Отменить начисление» у проведённой строки; прогресс и статус документа.
- Список начислений за месяц получает прогресс проведения и массовое «Начислить все документы месяца».
- Страница баланса сотрудника: в шапке одна главная цифра — общий баланс (никаких карточек с остатками по направлениям и прочими цифрами), лента движений с фильтрами по месяцу и типу, без раскрытия строк; у начисления — ссылка «открыть документ начисления». У руководителя — «Добавить приход» / «Добавить расход» (тип, сумма, дата, комментарий) и «Удалить» у ручных движений.
- Сводка балансов по отделу за месяц: остаток, начислено, авансы, ручные движения по каждому сотруднику; переход в баланс сотрудника. Отдел берётся текущий (из Bitrix24 на момент запроса), в движении не хранится.
- Личный кабинет сотрудника: баланс доступен только на чтение, только собственный.

### Контракты

- В `ireports-contracts`: `SalaryAccrualLineStatus`, расширение `SalaryAccrualStatus`, `BalanceTransactionType`, `BalanceTransaction`, ответ баланса сотрудника (`{ employeeId, balance, transactions[] }`), ответ сводки по отделу, запросы на проведение / отмену начисления / корректировку / ручное движение / удаление ручного движения.
- Эндпоинты (уточняются в реализации, независимо для `service` и `shop`):
  `POST /v1/{direction}/accounting/salary_accruals/:id/lines/:lineId/accrue`,
  `POST /v1/{direction}/accounting/salary_accruals/:id/accrue`,
  `POST /v1/{direction}/accounting/salary_accruals/accrue?period`,
  `PATCH /v1/{direction}/accounting/salary_accruals/:id/lines/:lineId` (корректировка, только в `DRAFT`),
  `POST /v1/{direction}/accounting/salary_accruals/:id/lines/:lineId/unaccrue`,
  `GET /v1/accounting/balance/employee/:id?from&to&types` (общий, без направления в пути),
  `GET /v1/accounting/balance/department/:id/:period`,
  `POST /v1/accounting/balance/employee/:id/transactions`,
  `DELETE /v1/accounting/balance/transactions/:id` (ручные движения без документа ERP).

## Не в скоупе

- Выплата (`PAYOUT`), статус документа `PAID`, сводный экран дня выплаты — PRD 3.
- Создание кассовых документов в RemOnline / МойСклад — PRD 3; здесь только признак `erpSyncRequired`.
- Автоматический расчёт больничных и отпускных по ТК — вводятся руками суммой.
- Плановые авансы (автоматическое создание аванса N-го числа) — вручную.
- Уведомления сотруднику о начислении (Bitrix24 / почта).
- Ограничение доступа: «сотрудник видит только свой баланс» и «только руководитель создаёт движения» — отдельная задача после готовности всего модуля (PRD 1–3); в этой итерации эндпоинты без гарда и действия руководителя в UI видны всем, как у плана продаж.
- Лимиты на аванс и предупреждения об отрицательном балансе.
- Отдельные статьи компенсаций (проезд, связь) — используется `BONUS` с комментарием.
- Хранение отдела сотрудника на дату движения; сводка по отделу — по текущему отделу.
- Переводы между балансами направлений одного сотрудника.
- Экспорт ленты в Excel / Google Sheets.

## Технические ограничения

- Лента движений — единственный источник истины об остатке. Остаток на чтении — агрегат `SUM` по `employeeId`; при росте объёма допускается материализованное представление, обновляемое в той же транзакции, что и запись/удаление движения, с тестом на расхождение. Полного event sourcing нет — по решению пользователя движения удаляемы, история ошибочных записей не сохраняется.
- Проведение строки и запись движения — одна транзакция `UnitOfWork`; уникальный индекс на ссылку «строка начисления → движение `SALARY_ACCRUAL`» даёт идемпотентность на уровне БД, а не только проверкой в коде.
- Суммы — `Int` в той же единице, что снапшот (зафиксировать копейки/рубли в контракте до реализации).
- Баланс — кросс-доменная сущность: живёт вне доменов `service`/`shop` (общий модуль уровня `accounting`), проведение начисления из любого домена пишет в одну ленту. Кросс-доменных импортов service↔shop по-прежнему нет — оба зависят от общего модуля баланса.
- Переоткрытие периода (PRD 1) блокируется при любом документе не в `DRAFT` — после проведения хотя бы одной строки месяц можно переоткрыть только после отмены начисления всех проведённых строк.
- Изменение мотивационной схемы или плана продаж после закрытия не влияет ни на снапшот, ни на документы, ни на баланс (уже гарантируется заморозкой снапшота; документ начисления копирует строки, а не ссылается на живой расчёт).
- Ссылки на источники в движении хранятся как идентификаторы (`accrualId`, `lineId`, `ruleId`, `reversedTransactionId`), а не как сериализованная копия — иначе разбивка начисления в ленте разойдётся с документом.
- Текущего пользователя в бэкенде нет — `createdBy` / `accruedBy` передаются в теле запроса, как `closedBy` / `approvedBy` у периода и плана.

## Критерии готовности

### Проведение начисления

- [ ] Проведение строки создаёт ровно одно движение `SALARY_ACCRUAL` с суммой строки и ссылками на документ, строку, правило, период, направление; строка переходит в `ACCRUED`.
- [ ] Повторное проведение той же строки (повторный запрос, параллельные запросы) не создаёт второго движения — проверяется тестом на уникальный индекс.
- [ ] «Начислить всё» проводит все непроведённые строки документа; документ переходит в `ACCRUED`; в ответе — перечень строк, которые провести не удалось, если такие были.
- [ ] «Начислить все документы месяца» проводит все документы направления за период; результат содержит статистику и перечень ошибок.
- [ ] Статус документа вычисляется из статусов строк: `DRAFT` / `PARTIALLY_ACCRUED` / `ACCRUED`.
- [ ] Корректировка строки возможна только в `DRAFT`, требует комментария, сохраняет исходную сумму снапшота и историю корректировок; корректировка строки в `ACCRUED` — `409`.
- [ ] Проведение скорректированной строки создаёт `SALARY_ACCRUAL` на сумму снапшота и `ACCRUAL_ADJUSTMENT` на разницу с комментарием корректировки; их сумма равна корректированной сумме строки; нескорректированная строка `ACCRUAL_ADJUSTMENT` не создаёт.
- [ ] «Отменить начисление» удаляет движения `SALARY_ACCRUAL` и `ACCRUAL_ADJUSTMENT` строки с баланса и возвращает строку в `DRAFT` в одной транзакции; остаток уменьшается на сумму строки; после отмены строку можно скорректировать и провести заново.
- [ ] Отмена начисления строки документа в статусе `PAID` — `409`.
- [ ] После проведения остаток баланса сотрудника по направлению равен сумме всех движений по этому направлению (проверяется тестом на смешанной ленте с приходами, расходами, отменёнными начислениями и удалёнными движениями).

### Баланс

- [ ] Баланс общий по сотруднику: один остаток, одна лента; движения из документов обоих направлений попадают в неё.
- [ ] Хранимого изменяемого поля «остаток» нет; остаток равен `SUM` ленты (если есть материализация — тест на совпадение).
- [ ] Руководитель может создать движение каждого из типов `ADVANCE`, `EXTRA_ADVANCE`, `BONUS`, `SICK_LEAVE`, `VACATION_PAY`, `PENALTY`, `ADJUSTMENT`; знак определяется типом, для `ADJUSTMENT` задаётся явно.
- [ ] Создание `PENALTY` и `ADJUSTMENT` без комментария отклоняется (`400`).
- [ ] `PATCH` движения не существует; ручное движение без документа ERP удаляется `DELETE` (запись исчезает, остаток пересчитан); движение начисления удаляется только через «Отменить начисление» строки; удаление движений с документом ERP — PRD 3.
- [ ] Движение с датой внутри закрытого периода записывается; снапшот и документы начисления этого периода не изменяются (проверяется тестом).
- [ ] Баланс может уходить в минус; ответ и UI показывают отрицательный остаток явно; создание аванса при любом остатке не блокируется.
- [ ] Признак `erpSyncRequired` сохраняется и отдаётся в ответе; в этой итерации ничего в ERP не отправляется.
- [ ] Лента фильтруется по диапазону дат и типам; итог по выборке равен сумме отфильтрованных движений.
- [ ] Строка ленты не раскрывается; у начисления есть ссылка на документ начисления.
- [ ] Сводка по отделу за месяц отдаёт по каждому сотруднику остаток, начислено за месяц, авансы, ручные движения; суммы по отделу равны сумме по сотрудникам.
