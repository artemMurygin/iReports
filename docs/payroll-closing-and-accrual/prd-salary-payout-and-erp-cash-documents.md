# PRD: Выплата зарплаты и кассовые документы в ERP

**Дата**: 2026-08-20
**Статус**: Draft
**Часть**: 3 из 3, см. [README](./README.md)
**Зависит от**: [PRD 2 — баланс сотрудника](./prd-salary-accrual-and-employee-balance.md)

---

## Цель

В день выплаты руководитель на одном экране видит всех сотрудников направления с остатком баланса (с учётом авансов), создаёт выплаты и получает расходные кассовые документы в нужной ERP — RemOnline для сервиса, МойСклад для магазина — не переключаясь между системами и не теряя, кому уже выплатил. Тот же механизм проводит в кассу ERP ручные приходы и расходы по сотруднику (премии, штрафы, возврат аванса).

Движение на балансе и документ в ERP — одно целое: либо есть оба, либо нет ни одного.

---

## Пользовательские сценарии

### День выплаты

- Руководитель открывает страницу «Выплата зарплаты» за месяц по направлению → видит таблицу сотрудников: начислено за месяц, выдано авансов, ручные движения, остаток баланса, выплачено за месяц, статус («Не выплачено» / «Выплачено частично» / «Выплачено»), а сверху — итог: суммарный остаток, уже выплачено.
- Руководитель открывает строку сотрудника → видит ленту баланса за месяц (как в PRD 2), из которой складывается остаток, и форму выплаты с предзаполненной суммой = остаток баланса.
- Руководитель создаёт выплату на сумму остатка → в ERP направления создаётся расходный кассовый документ на сотрудника, на балансе появляется движение «Выплата» со ссылкой на документ ERP, документ начисления за месяц переходит в «Выплачено», остаток — ноль.
- Руководитель создаёт выплату на часть остатка (договорились выплатить остальное позже) → документ ERP и движение на указанную сумму, остаток уменьшается, статус «Выплачено частично».
- Руководитель указывает сумму **больше остатка** (выдаёт вперёд) → выплата создаётся, баланс уходит в минус; форма показывает, каким станет остаток после выплаты.
- У сотрудника **нулевой или отрицательный остаток** и руководитель создаёт выплату → форма показывает предупреждение «остаток N, после выплаты будет N − сумма», требует явного подтверждения; после подтверждения выплата создаётся как обычно.
- Руководитель не выбирает кассу: для сервиса документ всегда создаётся в единственной кассе RemOnline, для магазина — расходным ордером МойСклада с заданной статьёй расходов «Зарплата»; обе настройки задаются один раз в конфигурации направления.
- Руководитель выбирает несколько сотрудников и нажимает «Выплатить выбранным» → по каждому создаётся выплата на его остаток и документ ERP; сотрудники с нулевым/отрицательным остатком перечислены в подтверждении отдельно; по завершении виден отчёт: кто выплачен, у кого ошибка ERP.
- **ERP недоступна или вернула ошибку** в момент выплаты → ничего не создаётся: ни документа в ERP, ни движения на балансе; руководитель видит ошибку с текстом от ERP и создаёт выплату заново, когда ERP доступна. Никаких «повисших» движений и статусов «Ошибка ERP» не существует.
- Руководитель повторно нажимает «Выплатить» у уже выплаченного сотрудника → то же предупреждение о нулевом остатке; при подтверждении создаётся вторая выплата.
- **Руководитель ошибся** (сумма, не тот сотрудник) → нажимает «Удалить выплату»: кассовый документ удаляется в ERP, движение удаляется с баланса, документы начисления возвращаются в «Ожидает выплаты»; если ERP не дала удалить документ — удаления не происходит, руководитель видит ошибку и повторяет позже.
- Руководитель закрывает страницу и возвращается через час → видит актуальные статусы по каждому сотруднику, включая выплаты, сделанные другим руководителем.
- Сотрудник открывает личный кабинет → видит движение «Выплата» с датой и суммой и обновлённый остаток.

### Проведение ручных движений через кассу ERP

- Руководитель создаёт ручной расход (доп. аванс наличными из кассы) с признаком «провести в кассе ERP» → в ERP направления создаётся расходный документ на сумму, затем движение на балансе со ссылкой на него.
- Руководитель создаёт ручной приход (сотрудник вернул аванс в кассу) с признаком «провести в кассе ERP» → в ERP создаётся приходный документ, затем движение.
- Руководитель создаёт премию без признака «провести в кассе» → в ERP ничего не уходит, премия ляжет в выплату в день зарплаты.
- ERP вернула ошибку при создании ручного движения с признаком «провести в кассе» → движение не создаётся, руководитель видит ошибку и повторяет.
- Руководитель удаляет ошибочное ручное движение, проведённое через кассу → документ в ERP удаляется, затем движение удаляется с баланса (вместо сторно из PRD 2 — для движений с документом ERP действует то же правило, что и для выплаты).

## В скоупе

### Выплата (`SalaryPayout`)

- Выплата — движение баланса типа `PAYOUT` (тип заложен в PRD 2) плюс связанный кассовый документ ERP. Создаётся по `(employeeId, direction)` на любую сумму `amount > 0`, с датой, автором, комментарием. Ограничений по остатку нет: сумма может превышать остаток, остаток может быть нулевым или отрицательным.
- При нулевом или отрицательном остатке, а также при сумме больше остатка — предупреждение в UI с явным подтверждением; на API это флаг `confirmNegativeBalance: true`, без которого запрос отклоняется с кодом «требуется подтверждение» и текущим остатком в ответе.
- Документы начисления сотрудника направления в статусе `ACCRUED` переходят в `PAID`, когда остаток баланса после операции ≤ 0 — независимо от того, чем он закрыт: выплатой, ручным приходом (возврат аванса) или их комбинацией; пока остаток > 0, документ остаётся `ACCRUED` с признаком «выплачено частично». Проверка выполняется после каждого движения, уменьшающего остаток.
- Удаление выплаты: сначала удаляется документ в ERP, затем в одной транзакции — движение с баланса и возврат документов начисления из `PAID` в `ACCRUED`. Если ERP отказала в удалении — ничего не меняется, ошибка возвращается руководителю. Сторно (`PAYOUT_REVERSAL`) для выплат не используется.

### Кассовые документы ERP (`ErpCashDocument`)

- Сущность-связка: движение баланса → документ ERP: система (`ROAPP` / `MOY_SKLAD`), тип (`OUTCOME` / `INCOME`), сумма, внешний ID, время создания. Для RemOnline документ — движение по кассе (доход/расход); для МойСклада — расходный ордер (`cashout`) или приходный ордер (`cashin`) со статьёй расходов/доходов. Статусов отправки нет — документ либо существует в обеих системах, либо нигде.
- Создаётся для каждой выплаты и для ручного движения с `erpSyncRequired = true`.
- Порядок операции **синхронный, всё или ничего**: сначала запрос в ERP; успех → запись движения и связки в одной транзакции; ошибка ERP → ничего не записано, ошибка возвращена пользователю. Если ERP ответила успехом, а запись в нашу БД не удалась — компенсация: созданный документ ERP удаляется, и только потом возвращается ошибка.
- Удаление движения с документом ERP — зеркально: сначала удаление в ERP, затем удаление движения; отказ ERP → ничего не удалено.
- Контрагент / сотрудник в документе ERP определяется через `EmployeeIdentity` направления; у сотрудника без идентичности в этой ERP операция отклоняется до обращения в ERP с понятным текстом «нет связи с RemOnline / МойСклад».
- Выбора кассы у пользователя нет. Конфигурация направления: для `service` — ID единственной кассы RemOnline; для `shop` — статья расходов для расходного ордера и статья доходов для приходного ордера МойСклада (по умолчанию одна статья «Зарплата» для обоих; отдельные статьи по типу движения — аванс, премия, штраф — открытый вопрос). Конфигурация редактируется администратором в настройках, не в форме выплаты.
- Назначение документа ERP содержит период и тип движения («Зарплата за 2026-07», «Аванс», «Премия»), чтобы бухгалтер в ERP понимал происхождение.

### Уточнение к PRD 2: ручные движения с документом ERP

- Ручное движение с `erpSyncRequired = true` исправляется **удалением** (ERP + баланс), а не сторно. Сторно `MANUAL_REVERSAL` остаётся только для ручных движений без документа ERP.

### Страницы

- «Выплата зарплаты» за месяц по направлению: таблица сотрудников с колонками начислено / авансы / ручные / остаток / выплачено / статус, итоги, выбор нескольких строк, «Выплатить выбранным», переход в баланс сотрудника, фильтр «только невыплаченные».
- Форма выплаты: сумма (предзаполнена остатком), дата, комментарий, предпросмотр остатка после выплаты; предупреждение и подтверждение при нулевом/отрицательном остатке или сумме больше остатка.
- Действие «Удалить выплату» у движения `PAYOUT` в ленте баланса и на странице выплаты.
- Форма ручного движения (PRD 2) получает только переключатель «провести в кассе ERP»; касса/статья подставляются из конфигурации направления.
- В ленте баланса у движения с документом ERP видна ссылка на документ и внешний ID.

### Контракты

- В `ireports-contracts`: `ErpCashDocument`, `ErpCashConfig` (касса RemOnline / статьи МойСклада по направлению), ответ страницы выплаты (`{ period, direction, totals, employees: [{ employeeId, name, accrued, advances, manual, balance, paid, payoutStatus }] }`), запросы на выплату (с `confirmNegativeBalance`) / массовую выплату / удаление выплаты.
- Эндпоинты (уточняются в реализации, независимо для `service` и `shop`):
  `GET /v1/{direction}/accounting/payout/:period`,
  `POST /v1/{direction}/accounting/payout` (`{ employeeId, amount, occurredAt, comment, createdBy, confirmNegativeBalance? }`),
  `POST /v1/{direction}/accounting/payout/batch`,
  `DELETE /v1/{direction}/accounting/payout/:id`,
  `DELETE /v1/{direction}/accounting/balance/transactions/:id` (только для ручных движений с документом ERP),
  `GET|PUT /v1/{direction}/accounting/erp_cash_config`.

## Не в скоупе

- Асинхронная очередь / outbox отправки в ERP, статусы «Ошибка ERP», повтор отправки — по решению: запись синхронная, при ошибке пользователь повторяет сам.
- Чтение кассовых операций из ERP обратно в iReports и сверка «выплачено в iReports vs выдано в ERP» — не делаем.
- Безналичные выплаты, банковские реестры, интеграция с банком.
- НДФЛ, страховые взносы, расчётные листки по ТК.
- Автоматическая выплата по расписанию.
- Выплата по нескольким направлениям одной кнопкой (две ERP в одной операции).
- Уведомление сотруднику о выплате.
- Закрытие кассовой смены / инкассация в ERP.
- Ограничение доступа — без гарда, как весь `accounting`.

## Технические ограничения

- Интеграций с кассой ERP в проекте нет ни для RemOnline, ни для МойСклада: есть только чтение заказов / отгрузок (`integrations/roapp`, `integrations/moySklad`). Перед реализацией подтвердить по документации API: RemOnline — создание и **удаление** движения по кассе (`POST /cashbox/{id}/payment`, наличие `DELETE`); МойСклад — приходный/расходный ордер (`cashin` / `cashout`) с `DELETE`. Возможность удаления документа в ERP — обязательное условие сценария «руководитель ошибся»; если какая-то ERP удаление не поддерживает, это блокер, а не деградация.
- Запись в ERP — первое место, где iReports **пишет** в ERP. Операция синхронная: таймаут запроса к ERP ограничен (предварительно 15 секунд), по таймауту — ошибка пользователю без записи движения. Риск «ERP создала документ, но ответ потерян»: перед компенсацией/повтором адаптер проверяет наличие документа в ERP по идемпотентному ключу или назначению+сумме+дате, чтобы не задвоить.
- Компенсация при сбое записи в нашу БД после успеха ERP — удаление только что созданного документа ERP; если и она не удалась — запись в лог ошибок с внешним ID для ручной сверки (единственный случай, когда системы могут разойтись).
- `EmployeeIdentity` сотрудника в ERP направления обязательна; для RemOnline тип `EMPLOYEE_ID`, для МойСклада — ссылка на `MoySkladEmployee`. Проверка выполняется до обращения в ERP.
- Выплата, связка ERP и переход документов начисления в `PAID` — одна транзакция `UnitOfWork`; запрос в ERP — до неё.
- Касс у МойСклада в этом сценарии нет: расходный/приходный ордер создаётся с обязательной статьёй расходов/доходов (`expenseItem`) и организацией; сотрудник — контрагент/агент ордера через `MoySkladEmployee`. У RemOnline касса одна на направление `service` — её ID хранится в конфигурации, а не выбирается пользователем.
- Суммы — `Int`, единица измерения как в балансе; ERP принимают рубли с копейками — конвертация в адаптере интеграции, а не в домене.
- Страница выплаты должна переживать параллельную работу двух руководителей: статусы читаются с сервера при каждом открытии и после каждого действия; массовая выплата берёт остаток по каждому сотруднику на момент операции, а не по данным экрана.
- Блокировка по сотруднику на время операции выплаты/удаления, чтобы два руководителя не провели две операции одновременно.

### Открытые вопросы

- ~~Где создавать выплату~~ — решено: основной вход — сводная страница, из баланса сотрудника доступна та же форма.
- ~~Сторно выплаты / отмена в ERP~~ — решено: удаление и в ERP, и на балансе; API удаления в RemOnline и МойСкладе нужно подтвердить до начала реализации (блокер).
- ~~Выплата при нулевом/отрицательном остатке~~ — решено: разрешена с предупреждением и подтверждением.
- ~~Одна касса по умолчанию на направление или на отдел/точку~~ — решено: у сервиса одна касса RemOnline; у магазина касс нет, создаётся расходный ордер МойСклада со статьёй расходов.
- Нужна ли в МойСкладе отдельная статья расходов/доходов на каждый тип движения (зарплата, аванс, премия, штраф) или одна «Зарплата» на всё.
- ~~Долг сотрудника при увольнении~~ — решено: списывается ручным `ADJUSTMENT` с комментарием, отдельного типа нет.
- ~~Сверка «выплачено в iReports vs выдано в ERP»~~ — решено: не нужна; неудавшаяся компенсация пишется в лог, этого достаточно.
- ~~`PAID` при закрытии остатка ручным приходом~~ — решено: да, статус зависит от остатка, а не от типа движения.

## Критерии готовности

### Выплата

- [ ] Создание выплаты на любую сумму `amount > 0` записывает движение `PAYOUT`; `amount ≤ 0` — `400`.
- [ ] При нулевом/отрицательном остатке или сумме больше остатка запрос без `confirmNegativeBalance` отклоняется с текущим остатком в ответе; с флагом — выплата создаётся, баланс уходит в минус.
- [ ] Когда остаток баланса после операции ≤ 0, документы начисления сотрудника направления в `ACCRUED` переходят в `PAID` — и при выплате, и при ручном приходе, закрывшем остаток; пока остаток > 0 — остаются `ACCRUED` с признаком частичной выплаты (тест на оба способа закрытия).
- [ ] Массовая выплата создаёт по каждому выбранному сотруднику выплату на его остаток по данным сервера на момент операции; сотрудники с нулевым/отрицательным остатком требуют подтверждения; результат содержит перечень успешных и неудачных.
- [ ] Удаление выплаты удаляет документ в ERP, затем движение с баланса и возвращает документы начисления в `ACCRUED`; при отказе ERP ничего не меняется и возвращается ошибка.
- [ ] Типа `PAYOUT_REVERSAL` и эндпоинта сторно выплаты не существует.

### ERP

- [ ] Для каждой выплаты создаётся `ErpCashDocument` типа `OUTCOME` в ERP направления: `ROAPP` для `service`, `MOY_SKLAD` для `shop`; для `service` документ никогда не уходит в МойСклад и наоборот.
- [ ] Ручное движение с `erpSyncRequired = true` создаёт документ ERP с типом по знаку (`INCOME` для прихода, `OUTCOME` для расхода); с `erpSyncRequired = false` — ничего не создаёт.
- [ ] Ошибка или недоступность ERP при создании → движение на балансе не создано, `ErpCashDocument` не создан, пользователю возвращён текст ошибки (тест с замоканной ERP, возвращающей ошибку и таймаут).
- [ ] Успех ERP + сбой записи в БД → документ ERP удалён компенсацией; при неудаче компенсации — запись в лог с внешним ID (тест с инъекцией ошибки после ответа ERP).
- [ ] Сотрудник без `EmployeeIdentity` в ERP направления — операция отклонена до обращения в ERP с понятным сообщением, ни движения, ни документа нет.
- [ ] Удаление ручного движения с документом ERP удаляет документ в ERP, затем движение; для ручного движения без документа ERP `DELETE` недоступен (только сторно, PRD 2).
- [ ] Назначение документа ERP содержит тип движения и период.
- [ ] Документ `service` создаётся в кассе RemOnline из конфигурации направления; документ `shop` — расходный/приходный ордер МойСклада со статьёй из конфигурации; в формах выплаты и ручного движения выбора кассы нет.
