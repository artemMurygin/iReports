# PRD: Закрытие месяца из плана продаж и документы начисления зарплаты

**Дата**: 2026-08-20
**Статус**: Draft
**Часть**: 1 из 3, см. [README](./README.md)
**Зависит от**: реализованных `AccountingPeriod`, `AccountingPeriodSnapshot`, `POST /v1/{service,shop}/accounting/period/:period/close` (Фаза 6 `docs/payroll/plan-payroll-calculation.md`)

---

## Цель

Руководитель закрывает месяц по направлению одной кнопкой на странице плана продаж и получает на выходе готовые к проверке документы начисления зарплаты по каждому сотруднику — с финально пересчитанными план/фактом и разбивкой по зарплатным правилам. До этой итерации закрытие периода существует только как API и создаёт снапшот, из которого ничего дальше не рождается.

---

## Пользовательские сценарии

### Закрытие месяца

- Руководитель открывает страницу плана продаж за прошедший месяц → видит статус периода направления («Открыт» / «Закрыт», кем и когда закрыт) и кнопку «Закрыть месяц».
- Руководитель нажимает «Закрыть месяц» → видит окно подтверждения с контрольными цифрами: число сотрудников, которым будет создано начисление (уволенные помечены отдельно), суммарный фонд оплаты по направлению, список неутверждённых строк плана (если есть).
- Руководитель подтверждает закрытие при полностью утверждённом плане → план/факт месяца пересчитываются финально, зарплаты фиксируются снапшотом, период переходит в «Закрыт», по каждому сотруднику создаётся документ начисления в статусе «Черновик»; руководитель переходит на список начислений за месяц.
- Руководитель пытается закрыть месяц с неутверждёнными строками плана → закрытие отклоняется, в окне показан перечень строк со ссылкой «утвердить», кнопка «Закрыть месяц» неактивна до утверждения.
- Руководитель пытается закрыть текущий (ещё не истёкший) месяц → действие недоступно с пояснением «месяц ещё не закончился».
- Руководитель закрывает `service` → период `shop` того же месяца остаётся открытым, его начисления не создаются.
- Руководитель подтверждает закрытие → перед расчётом система сама дотягивает свежие данные из ERP направления за закрываемый месяц; руководитель видит обычный индикатор выполнения, никаких отдельных шагов или уведомлений о синхронизации нет.
- ERP недоступна и синхронизация не удалась → закрытие отклоняется с сообщением «не удалось получить данные из ERP, повторите позже»; период остаётся открытым, снапшот и документы не создаются.
- Сотрудник уволен до закрытия месяца, но за месяц имеет расчёт → документ начисления создаётся как для остальных, в списке сотрудник помечен «уволен».
- Во время закрытия происходит ошибка → период остаётся открытым, документов начисления не появляется (всё или ничего).

### Блокировка графика работы и ручных часов

- Руководитель закрывает месяц → график работы и ручные часы (`EmployeeHoursEntry`) сотрудников направления за этот месяц блокируются: создать, изменить или удалить запись за закрытый месяц нельзя.
- Сотрудник пытается внести переработку за закрытый месяц (через график работы) → запрос к API отклоняется гардом «месяц закрыт»; отображение read-only состояния — зона ответственности графика работы (`docs/employee-work-schedule`).
- Руководитель пытается изменить часы сотрудника за закрытый месяц → то же: отказ с указанием, кем и когда месяц закрыт.
- В окне подтверждения закрытия руководитель видит число сотрудников с правилом `PayPerHour`, у которых за месяц нет ни одной записи часов → может отменить закрытие и дозаполнить часы.
- Руководитель переоткрывает период → блокировка снимается, часы снова редактируются.

### Документы начисления

- Руководитель открывает список начислений за закрытый месяц → видит по каждому сотруднику строку: ФИО, отдел, направление, сумма начисления, статус («Черновик»), число правил в разбивке.
- Руководитель открывает документ начисления сотрудника → видит строки по каждому зарплатному правилу: название, тип, роль, сумма, источники (заказы / продажи / часы / задачи), а также компактный блок план/факта отдела, по которому считались процентные правила.
- Сотрудник, у которого за месяц насчитан ноль по всем правилам → документ начисления всё равно создаётся с нулевой суммой, чтобы руководитель видел полную картину и мог добавить ручное начисление (PRD 2).
- Руководитель переоткрывает закрытый период, пока все документы начисления в статусе «Черновик» → снапшот и черновики удаляются, период снова открыт.
- Руководитель пытается переоткрыть период, где хотя бы один документ уже начислен на баланс (PRD 2) → отказ с перечнем таких документов; переоткрытие возможно только после сторно начислений.
- Сотрудник открывает свой зарплатный отчёт за закрытый месяц → видит статус «Месяц закрыт».

## В скоупе

### Кнопка и сценарий закрытия на странице плана продаж

- На странице плана продаж (`pages/SalesPlan`) появляется блок статуса расчётного периода текущего направления и действие «Закрыть месяц». Данные статуса — `GET /v1/{direction}/accounting/period/:period`.
- Окно подтверждения с предварительной сводкой: количество сотрудников с начислением (и сколько из них уволены), фонд оплаты по направлению, перечень неутверждённых строк плана.
- Закрыть можно только истёкший календарный месяц (первое число следующего месяца и позже).
- `service` и `shop` закрываются всегда отдельно, каждое со своей страницы плана продаж; общей кнопки «закрыть оба направления» нет.
- Действие «Переоткрыть месяц» с явным подтверждением — на той же странице, доступно только для закрытого периода.

### Финальный пересчёт при закрытии

- Закрытие начинается с **неявной принудительной синхронизации** ERP направления за закрываемый месяц (RemOnline для `service`, МойСклад для `shop`) — без отдельной кнопки, подтверждения или уведомления пользователя; это внутренний шаг операции закрытия.
- Если синхронизация завершилась ошибкой, закрытие отклоняется целиком (ошибка с текстом «не удалось получить данные из ERP»); снапшот на частично обновлённых данных не создаётся.
- После синхронизации инвалидируется кэш расчёта периода и план/факт пересчитывается по актуальным данным локальной БД — закрытие никогда не фиксирует устаревший кэш.
- Результат финального пересчёта и снапшот идентичны: сумма документа начисления равна `total` снапшота сотрудника.

### Документ начисления (`SalaryAccrual`)

- Создаётся транзакционно вместе со снапшотом при закрытии периода: один документ на `(direction, period, employeeId)`, уникальность по этой тройке.
- Состав: сотрудник, направление, период, статус, итоговая сумма, строки.
- Строка документа (`SalaryAccrualLine`) — одна на зарплатное правило из разбивки снапшота: ссылка на правило, тип, роль, сумма, база, количество, ставка, ссылки на источники. Строки повторяют `RuleBreakdownLine` снапшота один в один.
- Статусы документа в этом PRD: `DRAFT`. Переходы `ACCRUED` / `PAID` — в PRD 2 и 3; перечень статусов закладывается целиком, чтобы не менять контракт.
- Документы создаются для всех сотрудников, попавших в снапшот (личная схема или схема отдела с правилами этого направления), включая нулевые и уволенных; у документа уволенного сотрудника признак `isDismissed` (по статусу активности сотрудника в Bitrix24 на момент закрытия).
- Список документов за период и карточка документа — чтение.

### Блокировка графика работы и ручных часов

- Закрытый период направления блокирует запись в источники часов за этот месяц: `EmployeeHoursEntry` (`POST/PATCH/DELETE /v1/{direction}/accounting/employee_hours*`) и график работы / переработки из `docs/employee-work-schedule`, когда он появится.
- Проверка выполняется на бэкенде по статусу `AccountingPeriod` направления и месяца записи; ответ — `409` с `closedBy` / `closedAt`. Отдельного экрана часов в этом PRD нет: часы приходят из графика работы (реализуется параллельно, `docs/employee-work-schedule`), и read-only состояние закрытого месяца в UI рисует график, подключая этот же гард.
- Блокировка распространяется на все источники часов, из которых считает `PayPerHour`, — иначе часы закрытого месяца разойдутся со снапшотом.
- Сводка окна подтверждения дополняется числом сотрудников с `PayPerHour` без записей часов за месяц (`employeesWithoutHours`).
- Переоткрытие периода снимает блокировку.

### Переоткрытие периода

- `reopen` дополняется проверкой: все документы начисления периода в `DRAFT` → документы и снапшот удаляются; иначе `409` с перечнем документов не в `DRAFT`.

### Отчёт сотрудника

- В ответе зарплатного отчёта за закрытый период добавляется статус документа начисления сотрудника, чтобы UI показывал «ожидает начисление» / «начислено» / «выплачено».

### Доменное событие

- `AccountingPeriodClosedDomainEvent` (уже порождается) становится триггером создания документов начисления в том же домене; событие `SalaryAccrualDocumentsCreated` публикуется после создания — на него подпишется PRD 2.

### Контракты

- В `ireports-contracts`: `SalaryAccrualStatus`, `SalaryAccrualLine`, `SalaryAccrual`, ответ списка начислений за период, расширение ответа `AccountingPeriodResponse` сводкой для окна подтверждения (`employeesCount`, `dismissedEmployeesCount`, `totalAmount`, `unapprovedPlanRows`, `employeesWithoutHours`).
- Эндпоинты (уточняются в реализации, независимо для `service` и `shop`):
  `GET /v1/{direction}/accounting/period/:period/close-preview`,
  `GET /v1/{direction}/accounting/salary_accruals?period`,
  `GET /v1/{direction}/accounting/salary_accruals/:id`.

## Не в скоупе

- Проведение начисления на баланс, кнопка «Начислить», баланс сотрудника и ручные движения — PRD 2.
- Выплата, расходные документы ERP — PRD 3.
- Ручная правка суммы строки начисления в черновике — PRD 2 (как корректировка с комментарием).
- Автоматическое закрытие месяца по крону или напоминания руководителю в Bitrix24.
- Закрытие периода по отделу (только по направлению целиком).
- Общее закрытие `service` и `shop` одной кнопкой.
- Ручной запуск синхронизации ERP как самостоятельное действие пользователя — синк запускается только внутри закрытия, неявно.
- Ограничение доступа к закрытию по правам Bitrix24 — как и у остальных эндпоинтов `accounting`, без гарда.
- Сам график работы (смены, переработки, согласование) — `docs/employee-work-schedule`; здесь только его блокировка закрытым месяцем.
- Влияние возвратов на закрытый месяц.

## Технические ограничения

- Закрытие уже реализовано двумя независимыми хендлерами (`CloseAccountingPeriodHandler`, `CloseShopAccountingPeriodHandler`) без общего кода — создание документов начисления добавляется в каждый домен отдельно, кросс-доменных импортов нет. `get`/`reopen`/`recalculate` — generic-классы по `direction`, проверка документов при `reopen` добавляется в общий хендлер через порт.
- Снапшот и документы начисления пишутся в одной транзакции `UnitOfWork` с переводом периода в `CLOSED`; падение на любом шаге откатывает всё. Синхронизация выполняется до транзакции: её результат (обновлённые заказы/отгрузки) остаётся в БД и при откате закрытия — это штатно, данные просто стали свежее.
- Расчёт идёт по локальной БД: `RoappSyncCron` — каждые 5 минут и только в проде (`@ProdCron`). Ручного запуска синхронизации сейчас нет — нужен вызов того же синка по требованию из хендлера закрытия (для `service` — заказы RemOnline, для `shop` — отгрузки МойСклада), ограниченный диапазоном дат закрываемого месяца, чтобы закрытие не ждало полной пересинхронизации. Синк внутри закрытия и тик крона не должны работать параллельно (блокировка по направлению). В dev-среде, где крон не тикает, именно этот шаг делает данные актуальными.
- Признак увольнения берётся из Bitrix24 (активность `BitrixEmployee`) на момент закрытия и фиксируется в документе, а не вычисляется на чтении.
- Денежные поля снапшота — `Int`; единица измерения (рубли/копейки) наследуется из снапшота и фиксируется в контракте документа.
- Строки `RuleBreakdownLine` хранятся в снапшоте как `Json`; документ начисления хранит строки нормализованно (отдельная таблица), потому что в PRD 2 они становятся самостоятельными объектами с собственным статусом и движением по балансу.
- Единственный существующий источник часов — `EmployeeHoursEntry` (`direction`-зависимые эндпоинты `employee_hours`). Проверка «месяц закрыт» должна жить в одном месте (доменный сервис/гард по `AccountingPeriod`), чтобы график работы из `docs/employee-work-schedule` переиспользовал её, а не дублировал; PRD графика ещё не написан (файлы пустые), поэтому контракт проверки фиксируется здесь.
- Страница плана продаж сейчас не запрашивает статус периода (комментарий в `pages/SalesPlan/ui/PageHeader.tsx`) — это первое место, где он появляется; `PeriodPicker` должен уметь показывать признак закрытого месяца.
- Страницы зарплатного отчёта на фронтенде пока нет — список и карточка начисления становятся первой страницей, где руководитель видит разбивку по правилам; стиль и расположение — рядом с «Зарплатные правила» в разделе зарплаты.

### Открытые вопросы

- Таймаут синхронизации внутри закрытия, после которого закрытие считается неудавшимся, — предварительно 2 минуты.
- ~~Порог устаревания синхронизации~~ — решено: закрытие само синхронизирует ERP неявно, поэтому порога нет; при ошибке синка закрытие отклоняется.
- ~~Принудительная синхронизация из окна закрытия~~ — решено: да, неявно, без уведомления пользователя.
- ~~Уволенный сотрудник с расчётом~~ — решено: документ создаётся, помечается `isDismissed`.
- ~~Закрывать `shop` и `service` одной кнопкой~~ — решено: всегда отдельно.

## Критерии готовности

- [ ] На странице плана продаж для выбранного месяца и направления отображается статус расчётного периода (открыт / закрыт, кем, когда).
- [ ] Кнопка «Закрыть месяц» недоступна для текущего и будущих месяцев с пояснением.
- [ ] Окно подтверждения показывает число сотрудников (и число уволенных среди них), фонд оплаты и перечень неутверждённых строк плана; значения совпадают с ответом `close-preview`.
- [ ] При наличии неутверждённых строк плана закрытие отклоняется с их перечнем (существующее `409`), кнопка подтверждения неактивна.
- [ ] Закрытие запускает синхронизацию ERP направления за закрываемый месяц до расчёта; заказ/отгрузка, появившиеся в ERP после последнего тика крона, попадают в снапшот (тест с замоканной ERP).
- [ ] В UI нет отдельного шага или уведомления о синхронизации — только общий индикатор выполнения закрытия.
- [ ] При ошибке синхронизации закрытие отклоняется с понятным сообщением; период остаётся открытым, снапшот и документы не созданы.
- [ ] Синхронизация внутри закрытия не выполняется параллельно с тиком крона по тому же направлению (тест на параллельный запуск).
- [ ] Уволенный сотрудник с расчётом за месяц получает документ начисления с `isDismissed = true` и помечен в списке начислений.
- [ ] Эндпоинта и кнопки общего закрытия обоих направлений нет; закрытие `service` и `shop` — две независимые операции.
- [ ] Перед созданием снапшота кэш расчёта периода сброшен: сумма снапшота равна результату расчёта по текущим данным БД, а не ранее закэшированному значению (проверяется тестом с изменением данных после прогрева кэша).
- [ ] После успешного закрытия по каждому сотруднику снапшота существует ровно один документ начисления `(direction, period, employeeId)` в статусе `DRAFT`; сумма документа равна `total` снапшота, строки один в один соответствуют `lines` снапшота.
- [ ] Сотрудник с нулевой суммой получает документ с нулевой суммой.
- [ ] Закрытие `service` не создаёт документов `shop` и не меняет статус периода `shop`.
- [ ] Ошибка на любом шаге закрытия оставляет период открытым, снапшот и документы не создаются (проверяется тестом с инъекцией ошибки).
- [ ] Список начислений за период отдаёт по каждому сотруднику ФИО, отдел, сумму, статус, число строк; карточка — строки с правилом, ролью, суммой, базой, количеством, ставкой и источниками.
- [ ] Переоткрытие периода, все документы которого в `DRAFT`, удаляет документы и снапшот; при наличии документа не в `DRAFT` — `409` с их перечнем, ничего не удалено.
- [ ] Ответ зарплатного отчёта за закрытый период содержит статус документа начисления сотрудника.
