# Закрытие расчётного периода, начисление и выплата зарплаты — обзор

**Дата**: 2026-08-20
**Статус**: Draft
**Источники**: [`docs/payroll/prd-payroll-calculation.md`](../payroll/prd-payroll-calculation.md) (раздел «Не в скоупе» — отсюда начинается эта работа), EventStorming-доска [SalaryReport](https://miro.com/app/board/uXjVH2hS6p0=/), модули `domains/{service,shop}/modules/accounting`.

Функционал разнесён на **три PRD**, реализуемых строго последовательно — каждый следующий опирается на сущности предыдущего:

| # | PRD | Что даёт бизнесу | Зависит от |
|---|---|---|---|
| 1 | [Закрытие месяца и документы начисления](./prd-accounting-period-closing-pipeline.md) | Кнопка «Закрыть месяц» в плане продаж; финальный пересчёт; по каждому сотруднику создан документ начисления с разбивкой по правилам | уже реализованные `AccountingPeriod` / снапшот |
| 2 | [Начисление на баланс и баланс сотрудника](./prd-salary-accrual-and-employee-balance.md) | Руководитель проверяет и проводит начисления; у сотрудника появляется баланс с лентой движений; ручные приходы/расходы (аванс, премия, штраф, больничный, отпускные) | PRD 1 |
| 3 | [Выплата зарплаты и кассовые документы ERP](./prd-salary-payout-and-erp-cash-documents.md) | День выплаты: сводный экран по всем сотрудникам, создание выплаты с баланса и расходного кассового документа в RemOnline / МойСклад | PRD 2 |

## Сквозной процесс

```
План продаж (страница) ──「Закрыть месяц」──▶ AccountingPeriod: CLOSED
                                              │  финальный пересчёт, снапшот
                                              ▼
                                  SalaryAccrual (DRAFT) × сотрудник × направление
                                  строки = зарплатные правила из снапшота
                                              │
            Руководитель проверяет ──「Начислить」(по правилу / по документу) ──▶
                                              │
                                              ▼
                       EmployeeBalance ◀── движение SALARY_ACCRUAL по каждой строке
                       (лента движений)       SalaryAccrual: ACCRUED («Ожидает выплаты»)
                              ▲
     ручные движения ─────────┤  аванс, доп. аванс, премия, штраф, больничный, отпускные
                              │
                              ▼
       День выплаты ──「Выплатить」──▶ движение PAYOUT ──▶ расходный кассовый документ в ERP
                                      SalaryAccrual: PAID      (RemOnline — сервис, МойСклад — магазин)
```

## Границы между PRD (чтобы не разъезжались)

- **PRD 1 заканчивается** созданием документов начисления в статусе `DRAFT` и блокировкой графика работы / ручных часов за закрытый месяц. Денег на балансе ещё нет, баланса как сущности ещё нет.
- **PRD 2 заканчивается** тем, что любое движение денег сотрудника (начисление, аванс, премия, штраф) существует как запись ленты баланса и меняет остаток. В ERP ничего не уходит.
- **PRD 3** добавляет единственный новый тип движения — выплату — и связывает его с кассовым документом ERP. Ручные приходы/расходы из PRD 2 получают возможность «провести в кассе ERP» тем же механизмом.

## Общие решения, принятые для всех трёх PRD

- Начисление, баланс и выплата ведутся **по направлению** (`service` / `shop`): у сотрудника, работающего в обоих, два независимых начисления за месяц и два баланса, потому что кассы у направлений разные (RemOnline и МойСклад). Общая сумма по сотруднику — только на уровне отображения.
- Снапшот закрытого периода остаётся источником истины о **расчёте**; документ начисления — источник истины о том, **что из рассчитанного руководитель решил выплатить**. Они могут расходиться только через явную ручную корректировку с комментарием.
- Баланс — не хранимое число, а сумма ленты движений (event sourcing по доске). Ручные движения без документа ERP не правятся — только сторно. Два исключения с удалением вместо сторно: отмена ещё не выплаченного начисления (движение удаляется, строка документа возвращается в черновик) и движения с кассовым документом ERP — выплаты и ручные движения «через кассу» (документ удаляется в ERP, затем движение с баланса, PRD 3).
- Запись в ERP синхронная и атомарная с движением: ошибка ERP → ничего не создано, пользователь повторяет сам; очереди и статуса «Ошибка ERP» нет.
- Собственной ролевой модели не заводим; действия руководителя в этой итерации, как и у `accounting` / `sales`, без гарда — ограничение доступа по Bitrix24 вынесено в открытые вопросы PRD расчёта.
