# PRD: Учёт типов заказов в плане продаж сервиса и в зарплатных правилах

**Дата**: 2026-08-24
**Статус**: Draft

## Терминология

«Категория заказа» из формулировки задачи — это **тип заказа RoApp** (`RoappOrderType`, таблица
`roapp_order_types`: «Ремонт», «Диагностика», «Возврат» и т.п.), а не `SalesPlan.category`
(существующее поле плана — категория оказанной услуги, отдельная ось группировки строк плана,
резолвится через `service-categories`) и не `RoappServiceCategory`/`RoappProductCategory`. Уточнено
с пользователем.

## Цель

Дать руководителю возможность на каждом плане продаж сервиса и на каждом зарплатном правиле,
завязанном на заказ/услугу, выбрать типы заказов RoApp, которые учитываются в выполнении этого
плана или в начислении по этому правилу — вместо текущего поведения, где план и правила либо не
учитывают заказы вовсе (план), либо учитывают заказы любого типа без возможности сузить выборку
(правила).

## Пользовательские сценарии

- Руководитель создаёт или редактирует план продаж отдела на период → выбирает из справочника типов
  заказов RoApp те, которые должны учитываться в выполнении этого плана.
- Руководитель не выбирает ни одного типа заказа при создании/редактировании плана → план учитывает
  заказы всех типов (поведение по умолчанию, как сейчас).
- Руководитель видит на странице плана продаж, что факт и прогноз выполнения пересчитаны только по
  заказам выбранных типов.
- Наступает новый период, и план автоматически создаётся из плана предыдущего месяца или из
  шаблона → выбор типов заказов переносится вместе с остальными значениями плана.
- Руководитель создаёт зарплатное правило типа `OrderPayed` или `ServiceCompleted` → выбирает типы
  заказов, за которые начисляется вознаграждение по этому правилу.
- Руководитель не указывает типы заказов в правиле `OrderPayed`/`ServiceCompleted` → правило
  учитывает заказы всех типов (поведение по умолчанию).
- Руководитель создаёт правило `PayPerHour` (почасовая оплата) или `TaskCompleted` (оплата за
  задачу) → форма не предлагает настройку типов заказов, так как начисление по этим правилам не
  привязано к конкретному заказу.
- Руководитель видит в форме плана и в форме правила человекочитаемые названия типов заказов, а не
  их числовые id.

## В скоупе

- Возможность указать набор типов заказов RoApp на плане продаж сервиса (`SalesPlan`) при создании и
  редактировании; пустой набор — «учитывать все типы».
- Расчёт факта и прогноза выполнения плана — только по заказам выбранных типов (для плана без выбора
  — по всем типам).
- Перенос выбора типов заказов при автосоздании плана на новый период (крон и ленивое достраивание)
  — из плана предыдущего месяца, либо из шаблона плана (`SalesPlanTemplate`), если плана предыдущего
  месяца нет.
- Возможность указать набор типов заказов RoApp на зарплатных правилах `OrderPayed` и
  `ServiceCompleted` (для направления «сервис») при создании; пустой набор — «учитывать все типы».
- Расчёт начисления по правилам `OrderPayed`/`ServiceCompleted` с указанными типами заказов — только
  по заказам этих типов.
- Отображение справочника типов заказов RoApp (человекочитаемые названия) в формах плана и правила.
- Обратная совместимость: планы и правила, созданные до этой фичи, не имеют выбора типов заказов и
  продолжают учитывать заказы всех типов без миграции данных.

## Не в скоупе

- Направление «магазин» (`shop`) — у МойСклад нет понятия «тип заказа», аналогичного
  `RoappOrderType`; эта фича только про направление «сервис».
- Изменение существующего поля `SalesPlan.category`/`SalesPlanTemplate.category` (категория услуги,
  ось группировки строк плана) — новая настройка вводится отдельным полем и не заменяет его.
- Настройка типов заказов у правил `PayPerHour` и `TaskCompleted` — они не привязаны к заказу
  (почасовая оплата и внутренний ручной учёт задач без связи с ERP-заказом).
- Глобальный флаг «этот тип заказа никогда не участвует ни в одном плане/правиле» на уровне
  справочника типов заказов — настройка делается индивидуально на каждом плане и на каждом правиле,
  а не системно.
- Управление самим справочником типов заказов (переименование, скрытие, создание новых типов) —
  справочник остаётся read-only списком, синхронизируемым из RoApp.
- Пересчёт задним числом уже закрытых расчётных периодов (`AccountingPeriod.status = CLOSED`) при
  изменении настройки типов заказов на плане или правиле — снапшот закрытого периода не
  пересчитывается.
- Направление «магазин» в зарплатных правилах — у `ProductSold`/`UsedProductSold` уже есть свой,
  отдельный фильтр по категории товара (`category: string | null`), эта задача его не трогает и не
  унифицирует с новым полем.

## Технические ограничения

- `RoappOrder.orderTypeId` сейчас нигде не участвует в расчёте: агрегация факта плана
  (`RoappSalesFactSourceRepository.aggregate`) группирует заказы только по отделу и всегда
  возвращает `category: null`; данные, которые видят зарплатные правила
  (`OrderPayedErpItem`/`ServiceCompletedErpItem`) не содержат `orderTypeId`. Оба места должны быть
  расширены источником этого поля, прежде чем в них можно будет что-то фильтровать.
- У справочника типов заказов (`RoappOrderType`) нет собственного HTTP-эндпоинта для чтения списка —
  потребуется новый эндпоинт `GET /v1/service/reports/order-type` для выпадающего списка в формах
  плана и правила.
- `OrderPayedEntity`/`ServiceCompletedEntity` сейчас не принимают ничего, кроме `targetRole` и
  `config.award` — добавление фильтра по типам заказов расширяет контракт правила
  (`salary-rule.types.ts`, `contracts/commands/salary-rule.ts`) и затрагивает существующие тесты
  (`order-payed.entity.spec.ts`, `service-completed.entity.spec.ts`).
- Автосоздание плана на новый период (`EnsureSalesPlansForPeriodService`) уже переносит `turnover`,
  `margin`, `growthPercent` с предыдущего месяца или из шаблона — новое поле выбора типов заказов
  должно попасть в тот же перенос, иначе автосозданные планы каждый месяц теряют настройку.
- Ранее сохранённые планы и правила без нового поля должны интерпретироваться как «учитывать все
  типы заказов» — без разовой миграции данных.

## Критерии готовности

- [ ] При создании и при редактировании плана продаж сервиса можно выбрать один или несколько типов
      заказов RoApp; пустой выбор означает «все типы».
- [ ] Факт и прогноз выполнения плана с указанными типами заказов считаются только по заказам этих
      типов; план без выбора — по-прежнему по всем типам.
- [ ] Автоматически создаваемый на новый период план наследует выбор типов заказов от плана
      предыдущего месяца или, если его нет, от шаблона плана.
- [ ] При создании зарплатного правила `OrderPayed` или `ServiceCompleted` можно выбрать один или
      несколько типов заказов; пустой выбор означает «все типы».
- [ ] Начисление по правилу `OrderPayed`/`ServiceCompleted` с указанными типами заказов считается
      только по заказам этих типов.
- [ ] Правила `PayPerHour` и `TaskCompleted` не показывают настройку типов заказов и не принимают её
      в запросе на создание.
- [ ] Форма выбора типов заказов (в плане и в правиле) отображает человекочитаемые названия из
      справочника RoApp, а не числовые id.
- [ ] Планы и правила, созданные до появления этой настройки, продолжают учитывать заказы всех
      типов без ручной миграции данных.
- [ ] Изменение выбора типов заказов на плане или правиле не меняет уже посчитанные снапшоты
      закрытых расчётных периодов.
