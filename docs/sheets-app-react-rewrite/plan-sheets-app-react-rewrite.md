# Plan: Переписать Google Sheets Interface на React в отдельном воркспейсе `sheets-app`

**PRD**: [docs/sheets-app-react-rewrite/prd-sheets-app-react-rewrite.md](./prd-sheets-app-react-rewrite.md)
**Дата**: 2026-08-13

## Фазы реализации

### Фаза 1: Скелет воркспейса `sheets-app` (Tracer Bullet)
**Цель**: доказать техническую основу всего проекта — что `sheets-app` собирается npm-воркспейсом монорепо в один инлайновый HTML-файл, пригодный для `HtmlService`.
**Что затрагивает?** infra / frontend (новый воркспейс)
**Задачи:**
- [ ] Создать каталог `sheets-app/` с `package.json`, `tsconfig.json`, `vite.config.ts` (React + TS + `vite-plugin-singlefile`)
- [ ] Добавить `sheets-app` в `workspaces` корневого `package.json` (по аналогии с `backend`/`contracts`) и корневые npm-скрипты (`sheets-app:dev`, `sheets-app:build`, `sheets-app:lint`)
- [ ] Минимальный React root (`src/main.tsx`, `src/App.tsx`) — заглушка, без бизнес-логики
- [ ] Настроить ESLint/Prettier конфиги, переиспользуя базовые правила монорепо
- [ ] Проверить сборку: `npm run sheets-app:build` из корня даёт единый HTML-файл без внешних ссылок на ассеты
**Тесты**: сборка проходит без ошибок; итоговый `dist/index.html` — один файл, все `<script>`/`<style>` инлайн (нет внешних `src=`/`href=` на локальные ассеты); `npm run sheets-app:lint` проходит.
**Когда готово**: `npm run sheets-app:build` из корня монорепо стабильно производит один самодостаточный HTML-файл.

### Фаза 2: Типизированный мост к `google.script.run`
**Цель**: дать React-коду единый типобезопасный способ вызывать серверные Apps Script функции, с моками для локальной разработки вне контекста Google Таблицы.
**Что затрагивает?** frontend (`sheets-app`)
**Задачи:**
- [ ] Описать интерфейс всех серверных функций (`processFile`, `loadPricesFromMS`, `uploadPricesToMS`, `uploadSalePricesToMS`, `uploadPricesToRO`, `getAccrualsSheetEntries`, `fetchServiceBonusesMap`, `applyAccrualsUpdates`, `getServiceCategories`, `writeCategoryPathToActiveCell`, `createServiceInRoapp`, `writeCreateServiceResult`)
- [ ] Реализовать promise-обёртку над `google.script.run.withSuccessHandler/withFailureHandler`
- [ ] Реализовать мок-реализацию того же интерфейса для `npm run sheets-app:dev` (детект окружения без `google.script`)
- [ ] Настроить npm-скрипт локальной разработки со включёнными моками
**Тесты**: юнит-тест на переключение реальный/мок клиент по признаку окружения; ручной smoke-тест `sheets-app:dev` — приложение открывается в браузере на моках без ошибок в консоли.
**Когда готово**: любой React-компонент может вызвать типизированную функцию моста и получить ответ — как от мока в `dev`, так и (в теории) от `google.script.run` в реальной панели.

### Фаза 3: UI-каркас — вкладки, лоадер, тултип (визуальный паритет на shadcn/ui)
**Цель**: воссоздать статичную оболочку интерфейса (без бизнес-логики) визуально эквивалентной текущей версии.
**Что затрагивает?** frontend (`sheets-app`), design
**Задачи:**
- [ ] Подключить необходимые компоненты shadcn/ui (button, tabs, tooltip и т.д.)
- [ ] Компонент вкладок «Мой склад» / «Ремонлайн» с той же цветовой индикацией активной вкладки
- [ ] Компонент `GlassLoader` (кольцо-спиннер, заголовок, лог шагов с анимацией появления)
- [ ] Компонент `InfoTooltip` с тем же содержимым подсказки по обязательным полям создания услуги
- [ ] Верстка статус-строки под кнопками
**Тесты**: ручное визуальное сравнение бок-о-бок с `frontend/GoogleSheetsInterface/index.html` (цвета `#4CAF50`/`#2e7d32`/`#2955af`/`#e65100`, отступы, форма лоадера); рендер-смоук всех новых компонентов без исключений в консоли.
**Когда готово**: статичная оболочка (вкладки, лоадер, тултип) визуально неотличима от текущего интерфейса при ручном сравнении.

### Фаза 4: Вкладка «Мой склад» — загрузка прайса и синхронизация с МойСклад
**Цель**: воспроизвести весь функционал вкладки «Мой склад» поверх моста из Фазы 2 и оболочки из Фазы 3.
**Что затрагивает?** frontend (`sheets-app`)
**Задачи:**
- [ ] Dropzone с drag-and-drop и выбором `.xlsx`/`.xls`-файла (визуальная реакция на выбор файла, как в оригинале)
- [ ] SSE-клиент прогресса (`EventSource`) с обработкой `COMPLETED`/`FAILED`/heartbeat, привязанный к логу `GlassLoader`
- [ ] Кнопка «Загрузить прайс» → `processFile` → запуск SSE-потока
- [ ] Кнопки «Обновить РЦ в МС» / «Обновить акционную РЦ в МС» / «Получить цены из МС» с состояниями загрузки/успеха/ошибки
**Тесты**: с мок-мостом из Фазы 2 — проверка всех состояний UI (idle/loading/success/error) для каждой кнопки и для SSE-потока (мок эмулирует сообщения прогресса и терминальные статусы); ручной прогон в `sheets-app:dev`.
**Когда готово**: вкладка «Мой склад» полностью функциональна на моках, включая живой лог прогресса загрузки прайса.

### Фаза 5: Вкладка «Ремонлайн» — синхронизация цен и начислений мастеров
**Цель**: воспроизвести синхронизацию цен и начислений мастеров с RemOnline.
**Что затрагивает?** frontend (`sheets-app`)
**Задачи:**
- [ ] Кнопка «Загрузить цены в RO» → `uploadPricesToRO` → блок сводки (всего/валидных/создано/обновлено/ошибок)
- [ ] Кнопка «Обновить начисления мастеров» → последовательный вызов `getAccrualsSheetEntries` → `fetchServiceBonusesMap` → `applyAccrualsUpdates`, с обновлением текста лоадера на каждом шаге
- [ ] Итоговое сообщение с перечнем обновлённых ID
- [ ] Состояния ошибок для обоих сценариев
**Тесты**: мок-сценарии с разным количеством ошибок/обновлений — проверка рендера блока сводки и итогового сообщения; ручной прогон в `sheets-app:dev`.
**Когда готово**: обе кнопки синхронизации на вкладке «Ремонлайн» полностью функциональны на моках, включая построчный лог обновления начислений.

### Фаза 6: Массовое создание услуг и каскадный выбор категории
**Цель**: воспроизвести самый сложный сценарий — валидацию, построчное создание услуг в RemOnline и выбор категории для активной ячейки.
**Что затрагивает?** frontend (`sheets-app`)
**Задачи:**
- [ ] Каскадные `Select`-компоненты дерева категорий (`getServiceCategories` → построение дерева → выбор уровня за уровнем)
- [ ] Кнопка «Записать категорию» → `writeCategoryPathToActiveCell`
- [ ] Портирование чистой логики валидации строки (`buildCreateServicePayload`, `resolveCategoryId`, `parseWarrantyPeriod`, `toNumber`, `buildServiceTitle`) в типизированные функции с юнит-тестами
- [ ] Построчная обработка `getCreateServiceRows` → `createServiceInRoapp`/`writeCreateServiceResult` с логом и итоговой сводкой (обработано/создано/ошибок)
**Тесты**: юнит-тесты на портированные функции валидации (обязательные поля, разбор гарантии, резолв категории, формирование заголовка услуги) — по одному тесту на правило из PRD; мок-сценарий построчной обработки с частичными ошибками.
**Когда готово**: раздел «Создать услуги в Ремонлайн» и «Добавить новую услугу» работают на моках идентично текущей логике валидации.

### Фаза 7: Серверная часть — типизированный рефакторинг `index.gs`
**Цель**: переписать Apps Script backend с сохранением всех внешних контрактов (URL, координаты листа, `scriptId`).
**Что затрагивает?** backend (Apps Script)
**Задачи:**
- [ ] Настроить TypeScript + `clasp`-совместимую сборку `.gs`-файлов внутри `sheets-app` (например, `apps-script/` подкаталог)
- [ ] Портировать все серверные функции 1:1 с сохранением имён, URL (`BASE_URL`, n8n-вебхуки) и констант листа (`ACCRUALS_SHEET_GID`, столбцы E/G–N/AW/AY/BH/BS/BU)
- [ ] Портировать чистые хелперы (`toNumber_`) с юнит-тестами на Node (до компиляции в Apps Script)
- [ ] Настроить `.clasp.json` на существующий `scriptId` (без выполнения `clasp push`)
- [ ] Чек-лист сверки: построчное сравнение нового и старого `index.gs` на совпадение URL/констант/сигнатур функций
**Тесты**: юнит-тесты портированных чистых функций (`toNumber_` и аналоги) на Node; ручная сверка по чек-листу, что ни один URL/номер столбца не изменился относительно `frontend/GoogleSheetsInterface/index.gs`.
**Когда готово**: переписанный backend типобезопасен, компилируется, и построчная сверка подтверждает идентичность внешних контрактов оригиналу — при этом `clasp push` не выполнялся.

### Фаза 8: Сборочный пайплайн деплоя (фронт + сервер) без автопуша
**Цель**: собрать фронтенд- и серверную часть в структуру, готовую к ручному `clasp push`, без какой-либо автоматизации деплоя в CI.
**Что затрагивает?** infra
**Задачи:**
- [ ] Скрипт сборки, копирующий инлайновый HTML-бандл фронтенда в `apps-script/Sidebar.html`
- [ ] npm-скрипт `sheets-app:build` объединяет фронт-сборку и копирование в один шаг
- [ ] Отдельный (неавтоматический) npm-скрипт `sheets-app:push`, вызывающий `clasp push` — не вызывается ни из CI, ни автоматически агентом
- [ ] README в `sheets-app/` с инструкцией по dev/build/ручному деплою
**Тесты**: `npm run sheets-app:build` из корня успешно производит готовую к `clasp push` структуру; `sheets-app:push` не вызывается ни разу в рамках автоматизации (проверка отсутствия его в CI-конфигах).
**Когда готово**: есть воспроизводимый билд, готовый к ручному деплою пользователем; сам деплой в этой фазе не выполняется.

### Фаза 9: Ручная верификация в боевой Таблице и финализация (выполняется пользователем)
**Цель**: подтвердить работоспособность в реальной Google Таблице и завершить миграцию, не подвергая риску боевые данные.
**Что затрагивает?** frontend / backend / данные боевой Таблицы
**Задачи:**
- [ ] Пользователь вручную выполняет `sheets-app:push` (деплой в существующий `scriptId`)
- [ ] Пользователь вручную проходит все пользовательские сценарии из PRD в реальной Таблице (без участия ИИ-агента, см. предупреждение в PRD)
- [ ] Пользователь подтверждает отсутствие регрессий по сравнению с текущим `GoogleSheetsInterface`
- [ ] После подтверждения — удаление каталога `frontend/GoogleSheetsInterface`
**Тесты**: чек-лист по каждому пользовательскому сценарию из PRD, пройденный вручную пользователем в реальной Таблице.
**Когда готово**: пользователь подтвердил полный паритет функциональности в боевой Таблице; старый каталог `frontend/GoogleSheetsInterface` удалён.
