# PRD: API для страницы создания зарплатного правила

**Дата**: 2026-08-12
**Статус**: Draft
**Источники**: `backend/prisma/schema/salary.prisma`, `backend/src/config/app.routes.ts`, `contracts/commands/{salary-rule,motivation-schema,shop-salary-rule,shop-motivation-schema}.ts`, `ENDPOINTS.md`

---

## Цель

Зафиксировать полное устройство backend API, которое уже существует и доступно для реализации страницы **создания** зарплатного правила — для направлений «сервис» и «магазин». Документ описывает точные пути, тела запросов/ответов и все варианты типов правил, чтобы фронтенд мог построить динамическую форму (направление → тип правила → специфичные поля) без дополнительных вопросов к бэкенду.

---

## Пользовательские сценарии

- Руководитель открывает страницу создания зарплатного правила → выбирает направление («сервис» или «магазин») → форма запрашивает каталог допустимых типов правил и ролей для этого направления.
- Руководитель выбирает цель правила — конкретного сотрудника или отдел (`targetType`, `targetId`).
- Руководитель выбирает тип правила (например, `OrderPayed` для сервиса или `ProductSold` для магазина) → форма показывает поля, специфичные для этого типа (вариант награды, база начисления, пороги, категория и т.д.), и предлагает на выбор только роли, допустимые для этого направления.
- Руководитель добавляет к схеме несколько правил разных типов за один заход → все правила уходят одним запросом и сохраняются атомарно.
- Руководитель второй раз создаёт правило для той же цели (тот же сотрудник/отдел) → новое правило добавляется к уже существующей мотивационной схеме, а не создаёт вторую схему-дубликат.
- Руководитель указывает индивидуальный разовый бонус к правилу → бонус сохраняется вместе с правилом.
- Руководитель выбирает правило `ProductSold`/`UsedProductSold` → указывает категорию товара либо оставляет пустой («все товары»).
- Руководитель отправляет форму с невалидными данными (несуществующая для направления роль, отсутствует обязательное поле `award` и т.п.) → запрос отклоняется целиком до сохранения.

## В скоупе

### 1. Создание/дозаполнение мотивационной схемы

| Направление | Метод | Путь | Контроллер |
|---|---|---|---|
| Сервис | `POST` | `/v1/service/motivation-schema` | `create-motivation-schema.http.controller.ts` |
| Магазин | `POST` | `/v1/shop/accounting/motivation-schema` | `create-motivation-schema.http.controller.ts` |

**Тело запроса** — `MotivationRequestSchema` (сервис) / `ShopMotivationRequestSchema` (магазин), обе формы идентичны по структуре, различается только discriminated union `rules`:

```ts
{
  targetType: 'Department' | 'Employee',
  targetId: number,
  name: string,
  rules: SalaryRuleRequest[]   // 1..N штук, service- или shop-union — см. §3
}
```

**Ответ**: `{ id: string }` — id мотивационной схемы. Список сохранённых правил в ответе не возвращается (см. «Технические ограничения»).

**Поведение (find-or-create)**: бэкенд ищет существующую схему по паре `(targetType, targetId)`. Если найдена — новые `rules` добавляются к ней (данные `name` при этом не обновляются). Если не найдена — создаётся новая схема. Операция атомарна: транзакция откатывается целиком, если хотя бы одно правило из массива не проходит валидацию/создание.

Таблицы `motivation_schemas`/`salary_rules` общие для обоих направлений — одна и та же схема (по `targetType`+`targetId`) может содержать вперемешку правила `direction: 'service'` и `direction: 'shop'`, разграничение идёт только по полю `direction` каждого правила.

### 2. Каталог типов правил и допустимых ролей

| Направление | Метод | Путь | Контроллер |
|---|---|---|---|
| Сервис | `GET` | `/v1/service/accounting/salary_role_types` | `list-salary-rule-types.http.controller.ts` (service) |
| Магазин | `GET` | `/v1/shop/accounting/salary_role_types` | `list-salary-rule-types.http.controller.ts` (shop) |

**Ответ** — `SalaryRuleTypesResponse`:

```ts
{ type: string, allowedRoles: TargetRole[] }[]
```

Сейчас каталог отдаёт **один и тот же** список ролей для всех типов правил направления (различие в ролях — только между сервисом и магазином, не между типами внутри направления). Форма не должна ожидать пер-типовой фильтрации ролей от бэкенда.

### 3. Общие поля правила

Каждый элемент `rules[]`, независимо от типа и направления, содержит:

| Поле | Тип | Обязательность | Описание |
|---|---|---|---|
| `type` | строковый литерал | да | Дискриминатор типа правила (см. §4/§5) |
| `name` | `string` | да | Название правила, вводится руководителем |
| `targetRole` | `TargetRole` (enum) | да | Роль, за которую платит правило — см. допустимые значения по направлениям ниже |
| `bonus` | `int`, опционально | нет | Индивидуальный разовый бонус, не влияет на тип правила |
| остальные поля | зависят от `type` | — | См. §4 (сервис) / §5 (магазин) |

**`targetRole` — общий enum, но допустимые значения различаются по направлению:**

- Сервис (6 ролей): `ENGINEER`, `ONLINE_MANAGER`, `OFFLINE_MANAGER`, `ORDER_MANAGER`, `CREATED_BY`, `CLOSED_BY`.
- Магазин (4 роли): `ONLINE_MANAGER`, `OFFLINE_MANAGER`, `ONLINE_PURCHASER`, `OFFLINE_PURCHASER`.

Роли `ONLINE_MANAGER`/`OFFLINE_MANAGER` есть в обоих направлениях, но с разным смыслом (продавец в отгрузке vs. менеджер заказа). У магазина нет роли инженера, у сервиса нет роли закупщика.

**Общие вспомогательные формы** (переиспользуются между direction, но не смешиваются в одном discriminated union):

- `percentBordersSchema` — ровно 3 порога, каждый `{ name: string, fromPlanPercent: number, multiplier: number, mode: 'FIX' | 'LINEAR' }`. `FIX` — множитель ступенькой по достижении порога, `LINEAR` — линейная интерполяция между порогами.

### 4. Типы правил — направление «сервис» (4 варианта)

Все 4 типа образуют `salaryRuleRequestSchema = z.discriminatedUnion('type', [...])` (`contracts/commands/salary-rule.ts:177-182`).

| `type` | Специфичные поля | Варианты `award` | `salaryBasis` |
|---|---|---|---|
| `PayPerHour` | `price: number` | — | — |
| `ServiceCompleted` | `award` | `{type:'Fixed', price}` \| `{type:'ServiceFixed'}` \| `{type:'ServicePercent', percent}` | — |
| `OrderPayed` | `award` | `{type:'Fixed', price}` \| `{type:'FixedPercent', percent, salaryBasis}` \| `{type:'FloatPercent', basePercent, salaryBasis, percentBorders: [3]}` | `REVENUE` \| `MARGIN` \| `SALARY_MINUS_ENGINEER_SALARY` |
| `TaskCompleted` | `award` | `{type:'Fixed', price}` \| `{type:'FloatPercent', basePrice, percentBorders: [3]}` | — |

`salaryBasis` (только у `OrderPayed`, только у вариантов award с процентом): `REVENUE` — выручка, `MARGIN` — маржа, `SALARY_MINUS_ENGINEER_SALARY` — сумма за вычетом зарплаты инженера.

### 5. Типы правил — направление «магазин» (4 варианта)

Все 4 типа образуют отдельный (не смешанный с сервисным) `shopSalaryRuleRequestSchema = z.discriminatedUnion('type', [...])` (`contracts/commands/shop-salary-rule.ts:154-159`).

| `type` | Специфичные поля | Варианты `award` | `salaryBasis` |
|---|---|---|---|
| `PayPerHour` | `price: number` | — | — |
| `ProductSold` | `category: string \| null` (UUID `MoySkladProductFolder`, `null` = «все товары»), `award` | `{type:'Fixed', price}` \| `{type:'FixedPercent', percent, salaryBasis}` \| `{type:'FloatPercent', basePercent, salaryBasis, percentBorders: [3]}` | `REVENUE` \| `MARGIN` |
| `UsedProductSold` | `category: string \| null`, `award` | `{type:'Fixed', price}` \| `{type:'FixedPercent', percent, salaryBasis}` — **без `FloatPercent`** | `REVENUE` \| `MARGIN` |
| `TaskCompleted` | `award` | `{type:'Fixed', price}` \| `{type:'FloatPercent', basePrice, percentBorders: [3]}` | — |

`salaryBasis` у магазина — только 2 варианта (`REVENUE`, `MARGIN`), без `SALARY_MINUS_ENGINEER_SALARY` — в магазине нет роли инженера.

### 6. Валидация и ошибки

- Валидация — Zod через `nestjs-zod` (`createZodDto`), на границе HTTP-контроллера. Ошибка валидации возвращает `400` с деталями по конкретному полю (стандартный формат ошибок `nestjs-zod`) — форма должна уметь сопоставить путь поля из ошибки с конкретным контролом в UI.
- Ошибка в любом одном правиле массива `rules` отклоняет весь запрос — ни схема, ни остальные правила из этого же вызова не сохраняются.

## Не в скоупе

- **Страница списка существующих зарплатных правил** (карточки). Backend не отдаёт список или постраничное чтение мотивационных схем/правил напрямую — единственный способ увидеть уже сохранённые правила сегодня косвенный, через `GET .../salary_report/{employee|department}/:id/:period`, который отдаёт правила в разрезе расчёта зарплаты за период, а не как самостоятельный CRUD-объект. Требует новых эндпоинтов и отдельного PRD.
- **Страница редактирования существующего зарплатного правила**. Backend не поддерживает ни `GET по id`, ни `PATCH`/`PUT` для схемы или отдельного правила. Требует новых эндпоинтов и отдельного PRD; модель редактирования (полная замена набора правил vs. точечные операции над одним правилом) в этой итерации не определена и не проектируется.
- **Удаление** схемы или правила. Route-константа `DELETE /v1/service/motivation-schema/:id` объявлена в `app.routes.ts`, но не подключена ни к одному контроллеру — реально не работает.
- Любые изменения самого backend API. Этот документ только описывает то, что уже реализовано и доступно для использования фронтендом.
- Справочник категорий МойСклада (`MoySkladProductFolder`) для выпадающего списка в поле `category` у `ProductSold`/`UsedProductSold` — в этом PRD не описан ни один эндпоинт для его получения; это отдельная задача, без которой поле `category` в форме нельзя реализовать как выпадающий список.

## Технические ограничения

- Одна и та же строка `MotivationSchema` (по паре `targetType`+`targetId`) может содержать правила обоих направлений одновременно — различие только в поле `direction` каждого правила внутри неё. Форма создания обязана явно передавать направление через выбор эндпоинта (`/v1/service/...` либо `/v1/shop/accounting/...`), не полагаясь на то, что схема «принадлежит» одному направлению.
- `type: 'PayPerHour'` и `type: 'TaskCompleted'` совпадают по имени между сервисом и магазином, но это независимые ветки двух разных discriminated union на бэкенде (разные реестры и фабрики). Фронтенд обязан выбирать контракт (`salaryRuleRequestSchema` либо `shopSalaryRuleRequestSchema`) по выбранному направлению, а не по имени типа правила.
- Ответ создания — только `{ id }`. Получить состояние только что созданной схемы со всеми правилами отдельным запросом нельзя (см. «Не в скоупе»); если форме нужно показать подтверждение с деталями сохранённого — придётся собрать его из данных, уже введённых в форме, а не из ответа сервера.
- Поле `category` — UUID `MoySkladProductFolder`, не свободный текст; ввод категории как текстового поля будет отклонён валидацией.
- Полный список типов ошибок и их коды не описаны в контрактах отдельно от стандартного поведения `nestjs-zod` — перед реализацией обработки ошибок в форме стоит явно проверить реальный формат ответа `400` на живом стенде.

## Критерии готовности

- [ ] Описаны оба эндпоинта создания схемы (`POST /v1/service/motivation-schema`, `POST /v1/shop/accounting/motivation-schema`) с точным путём, методом, полной формой тела запроса и ответа.
- [ ] Описаны оба эндпоинта каталога типов (`GET /v1/service/accounting/salary_role_types`, `GET /v1/shop/accounting/salary_role_types`) с точным путём и формой ответа.
- [ ] Для каждого из 4 типов правил сервиса перечислены все поля (`price`/`award`/`salaryBasis`/`percentBorders`/`bonus`), обязательность каждого поля и допустимые значения enum.
- [ ] Для каждого из 4 типов правил магазина перечислены все поля (`category`/`price`/`award`/`salaryBasis`/`percentBorders`/`bonus`), обязательность каждого поля и допустимые значения enum.
- [ ] Указан полный список `targetRole` отдельно для сервиса (6 ролей) и для магазина (4 роли).
- [ ] Описано поведение find-or-create мотивационной схемы и то, что ответ создания не возвращает список сохранённых правил.
- [ ] Явно зафиксировано, что чтение списка, чтение по id, обновление и удаление схемы/правила отсутствуют в API и не входят в эту итерацию.
- [ ] Документа достаточно, чтобы разработчик мог реализовать форму создания правила (выбор направления → цели → типа → динамические поля → отправка) без дополнительных вопросов к бэкенду.
