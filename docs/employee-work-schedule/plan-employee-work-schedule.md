# Plan: График работы сотрудников

**PRD** [prd-employee-work-schedule.md](./prd-employee-work-schedule.md)
**Дата** 2026-08-20
**Дизайн** `design/sallary-first-iteration.pen` — узлы `Cko6w` (Календарь), `vO4tI` (Роли), `A5SbT` (Мобильный)

## Фазы реализации

### Фаза 1: Модель смены и запись дня
**Цель** В системе можно сохранить и удалить факт «сотрудник в этот день работает N часов в роли R / отсутствует по причине C» — минимальный сквозной путь от контракта до БД.
**Что затрагивает?** database / backend
**Задачи:**
- [ ] Prisma-модель `WorkScheduleEntry` (`employeeId`, `date`, `status`, `hours?`, `role?`) с `@@unique([employeeId, date])` и миграция
- [ ] Zod-контракты в `contracts/commands/work-schedule.ts`: статусы `WORKING/DAY_OFF/TIME_OFF/SICK_LEAVE/VACATION`, часы 2–16 с шагом 0,5, роль из `TargetRole`
- [ ] Домен + CQRS: upsert записи дня (`PUT /v1/work-schedule/entries`) и удаление (`DELETE /v1/work-schedule/entries/:id`), модуль общий на компанию (без `direction`)
- [ ] Валидация инварианта: `hours`/`role` допустимы только при `status = WORKING`
- [ ] Unit-тесты доменной валидации + e2e на upsert/повторный upsert/удаление/`400` на невалидные часы и на часы при не-`WORKING`
**Когда готово** Повторный upsert на ту же пару (сотрудник, дата) меняет запись, а не создаёт вторую; часы вне 2–16, не кратные 0,5, или переданные не с `WORKING`, дают `400`; тесты зелёные.

### Фаза 2: Роль «Офис» в справочнике ролей
**Цель** Роль `OFFICE` доступна везде, где используется `TargetRole`, — без неё вкладка «Роли» не покрывает дизайн.
**Что затрагивает?** backend / frontend / contracts
**Задачи:**
- [ ] Добавить `OFFICE` в `targetRoleSchema` (`contracts/commands/salary-rule.ts`)
- [ ] Обновить `salary-rule-role-catalog.ts` так, чтобы `GET /v1/{service,shop}/accounting/salary_role_types` не начал предлагать `OFFICE` для существующих типов правил
- [ ] Добавить `OFFICE: 'Офис'` в `ROLE_LABELS` на фронте
- [ ] Прогнать и починить существующие тесты зарплатных правил и мотивационных схем
**Когда готово** `OFFICE` принимается контрактами и рендерится как «Офис»; ответы `salary_role_types` не изменились; существующие тесты salary-модулей зелёные.

### Фаза 3: Чтение графика за месяц
**Цель** Фронт может получить всю таблицу «сотрудники × дни месяца» одним запросом, с итогами и отпусками.
**Что затрагивает?** backend
**Задачи:**
- [ ] `GET /v1/work-schedule?month=YYYY-MM&departmentId=` — строки сотрудников отдела с ячейками дней месяца
- [ ] По каждому сотруднику: итог часов за месяц, использованные дни отпуска и годовой лимит (единая константа/настройка)
- [ ] Агрегаты месяца: число людей в смене по каждому дню и общий фонд часов
- [ ] Одна выборка смен на весь месяц + один запрос списка сотрудников отдела, без N+1
- [ ] Unit-тесты агрегации + e2e: месяц с данными, месяц без данных, фильтр по отделу
**Когда готово** Ответ содержит 28–31 ячейку на сотрудника, корректные итоги и агрегаты; месяц без данных отдаёт пустые ячейки и нули, а не ошибку; в логе запросов на месяц — фиксированное число SQL-запросов независимо от числа сотрудников.

### Фаза 4: Состав смены на дату
**Цель** Данные для мобильного экрана «Отдел сегодня»: кто на смене, кто нет и почему.
**Что затрагивает?** backend
**Задачи:**
- [ ] `GET /v1/work-schedule/shift?date=YYYY-MM-DD&departmentId=` — на смене (сотрудник, роль, часы) и не на смене, сгруппированные по причине отсутствия
- [ ] Счётчики ролей на смене и суммарные часы дня
- [ ] Сотрудники без записи на дату попадают в «не на смене» с отдельной причиной «не заполнен»
- [ ] e2e: сумма «на смене» + «не на смене» равна числу сотрудников отдела; счётчики ролей сходятся со списком
**Когда готово** Ответ покрывает все блоки узла `A5SbT`, суммы сходятся, тесты зелёные.

### Фаза 5: График как источник часов для PayPerHour
**Цель** Зарплата считается по реальному графику; ручной ввод часов исчезает из системы.
**Что затрагивает?** database / backend
**Задачи:**
- [ ] `hoursWorked` в `build-service-calculation-context` и `build-shop-calculation-context` — сумма часов смен `WORKING` за период вместо чтения `EmployeeHoursEntry`
- [ ] Data-миграция: каждая запись `EmployeeHoursEntry` переносится в смены так, чтобы сумма часов за период совпала
- [ ] Сброс `AccountingCalculationCache` открытых периодов после миграции; закрытые периоды и их снапшоты не трогаются
- [ ] Удалить модель `EmployeeHoursEntry`, её эндпоинты, DTO, порты, хендлеры, репозиторий и упоминания в `ENDPOINTS.md`
- [ ] Тесты: `PayPerHour.quantity` равен сумме часов смен; период без смен даёт `0`; e2e отчёта сотрудника до/после миграции совпадают
**Когда готово** Отчёт сотрудника за мигрированный период даёт то же `quantity` у `PayPerHour`, что и до миграции; `grep employee_hours` по `backend/src` и `ENDPOINTS.md` пуст; сборка и тесты бэкенда зелёные.

### Фаза 6: Страница «График работы» — вкладка «Календарь»
**Цель** Руководитель видит месячную таблицу с часами и итогами (узел `Cko6w`, режим просмотра).
**Что затрагивает?** frontend / design
**Задачи:**
- [ ] Роут `/work-schedule`, пункт навигации «График работы», страница в `pages/WorkSchedule` по FSD
- [ ] Таблица «сотрудники × дни месяца»: липкая колонка сотрудника, заголовок дня с числом и днём недели, выделение сегодня и выходных, легенда обозначений
- [ ] Колонки итогов: часы за месяц, использованные дни отпуска из годового лимита
- [ ] Строка «Человек в смене» по дням и общий фонд часов за месяц
- [ ] Переключение месяца и фильтр по отделу через TanStack Query; тесты рендера ячеек и итогов
**Когда готово** Страница открывается из навигации и визуально соответствует `Cko6w` (без поповера и вкладки «Роли»); переключение месяца и отдела перезапрашивает данные; `npm run build` фронтенда проходит.

### Фаза 7: Редактирование дня
**Цель** График можно заполнять прямо из таблицы (поповер узла `Cko6w`).
**Что затрагивает?** frontend
**Задачи:**
- [ ] Поповер по клику на ячейку: дата, имя сотрудника, выбор статуса из пяти вариантов
- [ ] Слайдер часов 2–16 с шагом 0,5, активный только для статуса «Работает»
- [ ] Остаток дней отпуска в поповере
- [ ] Сохранение через upsert-эндпоинт с инвалидацией месяца: пересчитываются часы сотрудника, «Человек в смене» за день и общий фонд
- [ ] Тесты: сохранение статуса и часов, пересчёт итогов, рост счётчика отпуска при статусе «Отпуск»
**Когда готово** Изменение ячейки сохраняется и обновляет все три итога без перезагрузки страницы; статус «Отпуск» увеличивает использованные дни и уменьшает остаток в поповере.

### Фаза 8: Вкладка «Роли»
**Цель** Видно и редактируется, в какой роли сотрудник работал каждый день (узел `vO4tI`).
**Что затрагивает?** frontend / design
**Задачи:**
- [ ] Вкладки «Календарь» / «Роли» с сохранением выбранного месяца и отдела при переключении
- [ ] Таблица ролей: в ячейке рабочего дня — сокращение роли (И / ОН / ОФ / ОС), у нерабочего — прочерк; своя легенда
- [ ] Назначение роли рабочему дню из ячейки с сохранением через тот же upsert
- [ ] Тесты: переключение вкладок не теряет фильтры, назначение роли обновляет ячейку
**Когда готово** Вкладка соответствует `vO4tI`, роль сохраняется и отображается сокращением, фильтры переживают переключение вкладок.

### Фаза 9: Мобильный экран «Отдел сегодня»
**Цель** С телефона видно текущий состав смены (узел `A5SbT`).
**Что затрагивает?** frontend / design
**Задачи:**
- [ ] Мобильная вёрстка страницы: лента дней недели с числом людей и выбором дня
- [ ] Блоки «На смене · N из M», «Часы · N ч» и счётчики «Роли на смене»
- [ ] Список на смене (аватар, имя, роль, часы) и блок «Не на смене» с группировкой по причинам
- [ ] Переход с карточки сотрудника на его график
- [ ] Тесты рендера состава смены и переключения дня
**Когда готово** На мобильной ширине страница соответствует `A5SbT`, переключение дня недели меняет состав смены, тап по сотруднику ведёт на его график.
