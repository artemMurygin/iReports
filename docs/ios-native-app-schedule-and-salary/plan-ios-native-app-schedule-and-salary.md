# Plan: Нативное iOS-приложение — график работы и зарплата

**PRD**: `docs/ios-native-app-schedule-and-salary/prd-ios-native-app-schedule-and-salary.md`
**Дата**: 2026-09-10

## Фазы реализации

### Фаза 1: Backend — OAuth-логин для мобильного клиента
**Цель**: сделать существующий OAuth callback-эндпоинт способным принимать вход от нативного iOS-клиента (не браузера).
**Что затрагивает?**: backend
**Задачи:**
- [ ] Проверить `/v1/auth/oauth/callback` на поддержку `redirect_uri` в виде custom URL scheme / universal link
- [ ] Уточнить/донастроить формат доставки сессии для non-cookie клиента (сценарий iOS из `openspec/specs/auth/spec.md`)
- [ ] Зарегистрировать `redirect_uri` мобильного приложения в конфигурации Bitrix24-приложения
- [ ] Добавить backend-тесты на приём OAuth callback от мобильного `redirect_uri`
**Когда готово**: запрос на `/v1/auth/oauth/callback` с мобильным `redirect_uri` и кодом авторизации возвращает валидную сессию; тесты зелёные.

### Фаза 2: Mobile — каркас приложения и авторизация (tracer bullet)
**Цель**: получить первый сквозной рабочий путь — сотрудник логинится через Bitrix24 и остаётся авторизованным между запусками.
**Что затрагивает?**: frontend (mobile), design
**Задачи:**
- [ ] Инициализировать RN/Expo проект как отдельный пакет, подключить `ireports-contracts`
- [ ] Настроить deep link (custom scheme/universal link) под OAuth callback
- [ ] Реализовать экран логина: построение authorize URL, открытие системного браузера, обработка callback и обмен кода на сессию
- [ ] Реализовать хранение сессии (secure storage): восстановление при перезапуске, если сессия валидна, иначе — переход на экран логина; экран logout
**Когда готово**: на симуляторе iOS 26 сотрудник проходит вход через Bitrix24, попадает в приложение, при перезапуске не видит повторный логин, может выйти через logout.

### Фаза 3: Mobile — экран «Моя зарплата»
**Цель**: сотрудник видит свой отчёт по зарплате за период, как на вебе.
**Что затрагивает?**: frontend (mobile), design
**Задачи:**
- [ ] Реализовать API-клиент под `employeeSalaryReportResponseSchema`
- [ ] Экран «Моя зарплата»: выбор периода, отображение итоговой суммы и разбивки по направлениям/правилам
- [ ] Liquid Glass компоненты для карточек отчёта (переиспользуемые в фазе 4)
- [ ] Обработка состояний загрузки/ошибки/пустых данных
- [ ] Сверить отображаемые суммы с веб-отчётом `/salaries/employee/:employeeId` для тестового сотрудника и периода
**Когда готово**: данные на экране «Моя зарплата» совпадают с веб-отчётом для того же сотрудника и периода.

### Фаза 4: Mobile — экран «Зарплата отдела»
**Цель**: сотрудник/руководитель видит суммы по всем сотрудникам отдела за период, как на вебе.
**Что затрагивает?**: frontend (mobile)
**Задачи:**
- [ ] Реализовать API-клиент под `departmentSalaryReportResponseSchema`
- [ ] Экран «Зарплата отдела»: список сотрудников с итоговыми суммами за период
- [ ] Фильтры выбора отдела/направления и периода (аналогично вебу)
- [ ] Навигация (табы) между «Моя зарплата» и «Зарплата отдела»
- [ ] Сверить список и суммы с веб-отчётом `/salaries` для того же отдела и периода
**Когда готово**: список и суммы на экране «Зарплата отдела» совпадают с веб-отчётом для того же отдела и периода.

### Фаза 5: Mobile — экран «Мой график»
**Цель**: сотрудник видит свои смены и статусы за период.
**Что затрагивает?**: frontend (mobile), design
**Задачи:**
- [ ] Реализовать API-клиент для чтения графика сотрудника (месячная сетка из `work-schedule.ts`)
- [ ] Экран «Мой график»: отображение смен и статусов (рабочий день/выходной/отгул/больничный/отпуск) за неделю/месяц
- [ ] Liquid Glass компоненты для карточек дня/статусов (переиспользуемые в фазе 6)
- [ ] Обработка состояний загрузки/ошибки/пустых данных
- [ ] Сверить отображаемые статусы с веб-данными для тестового сотрудника и периода
**Когда готово**: статусы дней на экране «Мой график» совпадают с веб-данными для того же сотрудника и периода.

### Фаза 6: Mobile — экран «График отдела»
**Цель**: сотрудник/руководитель видит смены всех сотрудников отдела за день/неделю, как на вебе («Отдел сегодня»).
**Что затрагивает?**: frontend (mobile)
**Задачи:**
- [ ] Реализовать API-клиент для чтения графика отдела (shift-of-day response из `work-schedule.ts`)
- [ ] Экран «График отдела»: список смен сотрудников за выбранный день/неделю
- [ ] Выбор отдела и дня/недели
- [ ] Навигация (табы) между «Мой график» и «График отдела»
- [ ] Сверить данные с веб-экраном `/work-schedule/today` для того же отдела и дня
**Когда готово**: список смен на экране «График отдела» совпадает с веб-экраном «Отдел сегодня» для того же отдела и дня.

### Фаза 7: Backend — команды для действий с графиком
**Цель**: дать возможность сотруднику вносить изменения в свой график из приложения.
**Что затрагивает?**: backend
**Задачи:**
- [ ] Проверить наличие command-эндпоинта отметки отсутствия (больничный/отгул); реализовать при отсутствии
- [ ] Проверить наличие command-эндпоинта запроса смены дня; реализовать при отсутствии
- [ ] Уточнить/добавить zod-схемы этих команд в `ireports-contracts`
- [ ] Backend-тесты (e2e) на оба новых/уточнённых эндпоинта
**Когда готово**: команды отметки отсутствия и запроса смены доступны, покрыты e2e-тестами, схемы опубликованы в `ireports-contracts`.

### Фаза 8: Mobile — действия с графиком в приложении
**Цель**: сотрудник может отметить отсутствие или запросить смену прямо из «Моего графика».
**Что затрагивает?**: frontend (mobile)
**Задачи:**
- [ ] UI-сценарий отметки отсутствия: выбор дня -> выбор типа (больничный/отгул) -> подтверждение
- [ ] UI-сценарий запроса смены дня: выбор дня -> запрос -> отображение статуса запроса
- [ ] Обновление статуса дня в UI после успешного ответа сервера
- [ ] Обработка ошибок отправки (сеть, отказ сервера)
- [ ] Ручная проверка обоих сценариев на симуляторе iOS 26 поверх эндпоинтов из фазы 7
**Когда готово**: сотрудник отмечает отсутствие и отправляет запрос на смену из приложения, статус дня обновляется после подтверждения.

### Фаза 9: Полировка дизайна и сквозная проверка
**Цель**: убедиться, что всё приложение целиком соответствует требованиям PRD по дизайну и работоспособности.
**Что затрагивает?**: frontend (mobile), design
**Задачи:**
- [ ] Ревью всех экранов на соответствие визуальному стилю текущего мобильного фронтенда iReports (цвета, типографика, компоновка)
- [ ] Проверить, что ключевые интерактивные элементы (карточки, панели, табы) используют Liquid Glass компоненты
- [ ] Полный ручной regression-прогон: логин -> график (свой/отдел) -> зарплата (своя/отдел) -> действия с графиком -> logout
- [ ] Проверить корректный переход на экран логина при истёкшей/невалидной сессии
- [ ] Подтвердить запуск и корректное отображение Liquid Glass на устройстве/симуляторе iOS 26
**Когда готово**: все критерии готовности PRD выполнены на симуляторе/устройстве с iOS 26.
