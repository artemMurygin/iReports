# Plan: Создание зарплатной схемы — реализация макетов на фронтенде

**PRD** Необходимо создать план реализации данных макетов на фронтенде. Изучены эндпоинты для создания
salary schema на бэкенде и фронтенде. Макеты — файл `design/sallary-first-iteration.pen`, ноды:
`tSYIw` (Зарплатное правило · Создание, Сервис, десктоп), `l0o4nP` (Пороги · Развёрнуто, десктоп),
`aJ2lQ` (Пороги · Развёрнуто, мобильный), `vtDMA` (Категория товара · Выпадающее меню, десктоп),
`xF4KU` (Категория товара · Меню, мобильный), `ZMEof` (Зарплатное правило · Создание, Магазин,
десктоп), `IScAL` (Схема начисления · Создание, мобильный, Сервис), `AmfHy` (Схема начисления ·
Магазин, мобильный). Создание salary schema для сервиса и магазина — два отдельных, несмешиваемых
эндпоинта/контракта.
**Дата** 2026-08-14

## Контекст (из изучения кода)

- Бэкенд создания схемы уже реализован и не требует изменений:
  - `POST /v1/service/motivation-schema` — тело `MotivationRequestSchema` (`contracts/commands/motivation-schema.ts`), `rules: SalaryRuleRequest[]` из `contracts/commands/salary-rule.ts` (`PayPerHour`/`ServiceCompleted`/`OrderPayed`/`TaskCompleted`).
  - `POST /v1/shop/accounting/motivation-schema` — тело `ShopMotivationRequestSchema` (`contracts/commands/shop-motivation-schema.ts`), `rules: ShopSalaryRuleRequest[]` из `contracts/commands/shop-salary-rule.ts` (`PayPerHour`/`ProductSold`/`UsedProductSold`/`TaskCompleted`). Пути и наборы типов правил у сервиса и магазина **разные**, роль-справочник (`targetRole`) — общий enum.
  - Список типов правил и допустимых ролей: `GET /v1/service/accounting/salary_role_types`, `GET /v1/shop/accounting/salary_role_types` (форма `{ type, allowedRoles }[]`).
  - Дерево категорий товара для правил `ProductSold`/`UsedProductSold`: `GET /v1/shop/warehouse/catalog` (`id`/`name`/`pathName`/`children`).
  - Оба POST-эндпоинта делают find-or-create по `(targetType, targetId)` и принимают **весь набор правил одним запросом** — черновик схемы (цель + список правил) собирается на фронтенде локально, запрос к бэкенду уходит один раз по кнопке «Сохранить схему».
- Найден пробел: в макетах Шаг 1 требует выбрать «Отдел» или «Сотрудника» из списка с человекочитаемыми именами, но в бэкенде нет эндпоинта, отдающего список отделов/сотрудников (`BitrixDepartment`/`BitrixEmployee` есть в БД, наружу не отдаются). Решение (согласовано с пользователем) — добавить отдельный бэкенд-эндпоинт, см. Фазу 1.
- Фронтенд payroll-раздела ещё не реализован (`pages/SalaryReport` и т. п. отсутствуют), пункты меню «Зарплата» в `frontend/src/app/Header.tsx` (`/salaries`, `/salaries/rules`, `/salaries/period`) стоят с `disabled: true`.
- Новый UI Kit (`frontend/src/shared/ui-kit/{tokens,atoms,organisms}`) — обязателен для новых страниц (см. `frontend/CLAUDE.md`), но пока содержит только `Button`, `IconButton`, `Avatar`, `Divider`, `BellBadge` и `organisms/Header`. Для форм из макетов не хватает: текстовое поле, переключатель (Сервис/Магазин), радио-карточка (Отдел/Сотрудник, варианты награды), select/комбобокс, слайдер процента, таблица/карточки порогов, комбобокс-дерево категорий с поиском, мобильная шторка (bottom sheet), информационный баннер, бейдж счётчика правил — их придётся создать по ходу фаз.

## Фазы реализации

### Фаза 1: Бэкенд · справочник отделов и сотрудников
**Цель** Дать фронтенду данные для селектов «Отдел» / «Сотрудник» на Шаге 1 формы (сейчас такого эндпоинта нет).
**Что затрагивает?** backend
**Задачи:**
- [ ] Добавить Zod-контракт списка (`contracts/queries/directory.ts` или аналог): `departmentSchema { id, name }`, `employeeSchema { id, name, departmentId }`.
- [ ] Новый модуль `backend/src/modules/directory` (по аналогии с `modules/employee-identity` — общий, не привязанный к домену `service`/`shop`), репозиторий поверх `BitrixDepartment`/`BitrixEmployee`.
- [ ] `GET /v1/directory/departments` — список отделов.
- [ ] `GET /v1/directory/employees?departmentId=` — список сотрудников (опциональный фильтр по отделу).
- [ ] Обновить `ENDPOINTS.md` новым разделом.
**Тесты** e2e-тест контроллера (запрос отдаёт непустой список с `id`/`name`), unit-тест репозитория с фильтром по `departmentId`.
**Когда готово** Оба GET-эндпоинта возвращают реальные синхронизированные данные Bitrix (id + имя), покрыты тестами, задокументированы в `ENDPOINTS.md`.

### Фаза 2: Фронтенд · базовые атомы UI Kit + рабочий путь создания схемы (Сервис, tracer bullet)
**Цель** Минимальный сквозной путь: пользователь выбирает цель начисления и создаёт схему с одним правилом — запрос реально уходит на бэкенд и получает успешный ответ.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Добавить в `shared/ui-kit/atoms` недостающие для Шага 1 примитивы: текстовое поле (`Input`), переключатель на две опции (`SegmentedControl`, для «Сервис/Магазин»), радио-карточка (`RadioCard`, для «Отдел/Сотрудник»), базовый `Select`.
- [ ] `pages/SalaryRules` — Шаг 1 «Кому начисляем»: направление, цель начисления, зависимый select отдела/сотрудника (данные из Фазы 1), название схемы; локальное состояние черновика схемы.
- [ ] `model/api.ts` страницы — `queryOptions` для `GET /v1/directory/departments|employees` и `GET /v1/service/accounting/salary_role_types`, мутация `POST /v1/service/motivation-schema` (по паттерну `pages/ServicesReport/model/api.ts`).
- [ ] Минимальный Шаг 2: одно правило типа `PayPerHour` (название, роль, ставка) — кнопка «Сохранить схему» реально отправляет собранный `MotivationRequestSchema`.
- [ ] Включить пункт «Правила начисления» в `Header.tsx` (снять `disabled`), добавить маршрут `/salaries/rules` в `router.tsx`.
**Тесты** Ручная проверка в браузере: выбрать отдел, создать схему с одним `PayPerHour`-правилом, убедиться в успешном ответе `{ id }` и отсутствии ошибок в консоли/сети.
**Когда готово** На `/salaries/rules` можно выбрать отдел или сотрудника и создать зарплатную схему сервиса с одним правилом почасовой оплаты — запрос доходит до бэкенда и подтверждается.

### Фаза 3: Фронтенд · полный редактор правил — Сервис (десктоп)
**Цель** Реализовать десктопную форму создания схемы сервиса полностью по макету `tSYIw` (+ пороги `l0o4nP`), все 4 типа правил.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Компонент карточки правила (название, роль из `allowedRoles` выбранного типа, тип правила) со списком уже добавленных правил в схему и раскрытием одной карточки на редактирование (как в макете).
- [ ] Варианты награды: «Фиксированная сумма» / «Фиксированный процент» / «Плавающий процент» — переключатель + под-поля (слайдер «Базовый процент» 1–100%, переключатель «База начисления»: Выручка/Маржа/Маржа минус зарплата инженера).
- [ ] Компонент «Пороги» (`percentBorders`, ровно 3 строки: Название / От % плана / Множитель / Режим Фиксированный-Линейный), сворачивание/разворачивание — по макету `l0o4nP`.
- [ ] Реализовать 4 типа правил сервиса по `contracts/commands/salary-rule.ts`: `PayPerHour`, `ServiceCompleted` (награды `Fixed`/`ServiceFixed`/`ServicePercent`), `OrderPayed`, `TaskCompleted` (оба с `Fixed`/`FixedPercent`/`FloatPercent` где применимо).
- [ ] Добавление/удаление черновых правил в списке схемы, кнопки «Добавить правило» / «Добавить ещё одно правило» / «Отмена».
**Тесты** Ручная проверка в браузере: создать схему сервиса с несколькими правилами всех 4 типов, включая `FloatPercent` с настроенными порогами; unit-тест валидации формы правила (zod-резолвер) на граничные случаи (ровно 3 порога, обязательные поля award).
**Когда готово** Десктопная форма создания схемы сервиса покрывает все элементы макетов `tSYIw` и `l0o4nP`, отправляет валидный `MotivationRequestSchema` для любого из 4 типов правил.

### Фаза 4: Фронтенд · Магазин (десктоп) и выбор категории товара
**Цель** Аналогичная форма для направления «Магазин» по макетам `ZMEof` + `vtDMA`, включая выбор категории товара.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Переиспользовать компоненты Фазы 3 (карточка правила, награды, пороги) для направления «Магазин» без смешения типов/контрактов сервиса и магазина.
- [ ] Комбобокс выбора категории товара с деревом и поиском (`vtDMA`): данные из `GET /v1/shop/warehouse/catalog`, отображение количества товаров, пункт «Все категории», подсветка выбранной, «Сбросить».
- [ ] Реализовать 4 типа правил магазина по `contracts/commands/shop-salary-rule.ts`: `PayPerHour`, `ProductSold` (с обязательным полем категории), `UsedProductSold` (без `FloatPercent`), `TaskCompleted`.
- [ ] Подключить `GET /v1/shop/accounting/salary_role_types` и `POST /v1/shop/accounting/motivation-schema`.
- [ ] Расширить Шаг 1 (селект цели начисления) под сотрудников/отделы магазина.
**Тесты** Ручная проверка: создать схему магазина с `ProductSold`-правилом и выбранной категорией товара; проверить, что запрос уходит на `.../shop/accounting/motivation-schema`, а не на сервисный эндпоинт.
**Когда готово** Десктопная форма создания схемы магазина покрывает макеты `ZMEof` и `vtDMA`, использует отдельный от сервиса контракт `ShopMotivationRequestSchema`.

### Фаза 5: Фронтенд · адаптив (мобильная версия)
**Цель** Мобильная раскладка обеих форм по макетам `IScAL`, `AmfHy`, `aJ2lQ`, `xF4KU`.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Мобильная раскладка Шаг 1 + Шаг 2 одной колонкой со sticky-кнопкой «Сохранить схему» снизу (`IScAL` — Сервис, `AmfHy` — Магазин).
- [ ] Мобильное представление порогов — карточки вместо таблицы (`aJ2lQ`).
- [ ] Мобильная шторка (bottom sheet) выбора категории товара с поиском и кнопками «Сбросить»/«Применить» (`xF4KU`).
- [ ] Брейкпоинты переключения десктоп/мобильных презентационных компонентов поверх общей `model`-логики Фаз 3–4 (без дублирования бизнес-логики).
- [ ] Визуальная сверка реализации со всеми 8 нодами макета.
**Тесты** Ручная проверка в браузере на мобильном вьюпорте (DevTools) для обоих направлений: полный цикл создания схемы с несколькими правилами и порогами.
**Когда готово** Обе формы (Сервис и Магазин) корректно работают и выглядят на мобильном вьюпорте, полностью соответствуют макетам `IScAL`, `AmfHy`, `aJ2lQ`, `xF4KU`.
