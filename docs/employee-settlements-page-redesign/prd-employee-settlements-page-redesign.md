# PRD: Редизайн страницы «Выплата» → «Взаиморасчёты с сотрудниками»

**Дата**: 2026-08-25
**Статус**: Draft

## Цель

Страница «Выплата» (`/payout`) сейчас показывает только сотрудников одного направления (сервис или магазин) за период и набор финансовых колонок (начислено/авансы/ручные/остаток/выплачено/статус), без деления по отделам — это неудобно и малоинформативно для руководителя, которому нужно быстро увидеть, кому компания должна и кто должен компании, по отделам. Страница переделывается в «Взаиморасчёты с сотрудниками»: сквозной (без деления сервис/магазин) список всех сотрудников с их текущим общим балансом, с фильтром по отделу из Bitrix24 и переходом в детализацию по конкретному сотруднику, где уже видно разбиение движений по сервису/магазину. Дополнительно обновляется дизайн страницы баланса сотрудника, куда ведёт переход из списка.

## Пользовательские сценарии

- Руководитель открывает раздел «Зарплата» → «Взаиморасчёты» → видит сквозной список всех сотрудников всех отделов с их текущим балансом и три общих показателя (общий остаток, к выплате сотрудникам, долг сотрудников компании) → быстро оценивает общую картину без переключения между сервисом и магазином.
- Руководитель выбирает конкретный отдел в фильтре → список и итоговые показатели пересчитываются только по сотрудникам этого отдела (состав отдела берётся из Bitrix24).
- Руководитель ищет сотрудника по имени в строке поиска → список сужается до совпадений (в рамках выбранного отдела или всех отделов).
- Руководитель кликает по строке сотрудника → попадает на страницу баланса сотрудника, где видит ленту всех движений с разбивкой по направлению (сервис/магазин) для каждого движения, суммарный баланс, и может добавить приход/расход (включая тип «Выплата») или выгрузить ленту.
- Руководитель на странице баланса сотрудника фильтрует ленту по типу движения (чипы: начисление, аванс, премия, штраф, выплата и т.д.) и ищет по комментарию.
- Руководитель открывает ленту движений сотрудника без выбора конкретного периода — по умолчанию видит последние 20 движений за всё время — и, прокручивая ленту вниз (или нажимая «Показать ещё»), подгружает следующие 20 более ранних движений, и так далее, пока не долистает до самого начала истории.
- Руководитель видит уволенного сотрудника с ненулевым балансом в общем списке взаиморасчётов (с бейджем «Уволен»), чтобы не потерять долг/задолженность по нему.
- Руководитель выгружает список взаиморасчётов или ленту конкретного сотрудника в таблицу.

## В скоупе

### Список «Взаиморасчёты с сотрудниками» (замена `/payout`)
- Новая страница со сквозным (не привязанным к сервису/магазину) списком сотрудников и их текущим балансом, с колонками: сотрудник (аватар+имя+должность), отдел, дата последнего движения, остаток (₽).
- Фильтр «Отдел» (выпадающий список, источник — Bitrix24 через уже существующий `features/TargetDirectory`/`GET /v1/directory/departments`), значение по умолчанию — «Все отделы» с агрегацией по всем сотрудникам компании.
- Поиск по имени сотрудника.
- Три показателя над таблицей: «Общий остаток» (сальдо всех выбранных сотрудников на текущий момент), «К выплате сотрудникам» (сумма положительных остатков + число сотрудников), «Долг сотрудников компании» (сумма отрицательных остатков + число сотрудников).
- Отметка времени актуальности данных («Данные на …»).
- Группировка по отделам с промежуточным итогом на отдел при просмотре «Все отделы» (обязательно для мобильной раскладки; для десктопной раскладки — плоская таблица с колонкой «Отдел», группировка не обязательна, см. дизайн `IFJW2`).
- Строка итогов внизу таблицы («Итого · N сотрудников» + сумма).
- Бейдж «Уволен» для сотрудников, уволенных по данным Bitrix24, но всё ещё присутствующих в списке из-за ненулевого баланса.
- Клик по строке ведёт на страницу баланса сотрудника (`/balance/employee/:id`).
- Выгрузка таблицы в файл (аналог существующей выгрузки ленты).
- Обновление пункта меню «Зарплата → Выплата» на «Зарплата → Взаиморасчёты» с новым роутом.

### Страница баланса сотрудника (редизайн `/balance/employee/:id`)
- Новая шапка: имя, отдел + должность + отметка о связке с ERP-системами (RemOnline/МойСклад), общий баланс сотрудника крупной цифрой.
- Действия: «Добавить приход», «Добавить расход» (единая точка входа для всех типов движений, включая тип «Выплата» — см. открытый вопрос ниже), «Выгрузить ленту».
- Фильтрация ленты по типу движения чипами (все 10 существующих типов `BalanceTransactionType` + «Все типы»), с сворачиванием лишних чипов («Ещё N») на мобильной раскладке.
- Поиск по комментарию.
- Лента движений с колонками (десктоп): дата, тип (с указанием направления «Сервис»/«Магазин» под названием типа), сумма, комментарий, автор, документ (ссылка на ERP-документ или документ начисления, если есть), удаление (для движений, не привязанных к ERP/начислению).
- Мобильная раскладка ленты — карточный список с той же информацией.
- Лента показывается «за всё время» (без обязательного выбора периода), отсортирована от новых движений к старым, с постраничной подгрузкой: изначально последние 20 движений, далее — подгрузка следующих 20 более ранних при прокрутке до конца ленты (или по кнопке), с индикатором загрузки, как в макетах `L73YCK`/`JTc29`.
- Сохранение существующей логики удаления ручного движения (подтверждение, пересчёт остатка, запрет для движений с ERP-привязкой).

### Backend
- Провести ревизию доменов/контроллеров/сервисов, названных под «выплату» именно как страницу-отчёт (`get-payout-page` и связанные `GetPayoutPageService`, `payoutPageResponseSchema`, `payoutEmployeeRowSchema`, `payoutPageTotalsSchema` в `service`- и `shop`-доменах) — переименовать или заменить эндпоинт под новую сквозную (без направления) агрегацию по сотрудникам с поддержкой: без фильтра по отделу (все сотрудники всех отделов), с фильтром по отделу, поиском по имени, последней датой движения на сотрудника. Технически ближе всего к уже существующему `GET /v1/accounting/balance/department/:id/:period` (`GetDepartmentBalancesService`) — рассмотреть его расширение вместо создания третьего похожего эндпоинта.
- Домен/контроллеры/команды, отвечающие за само действие выплаты (`create-payout`, `create-payout-batch`, `delete-payout` и зеркала в `shop`, тип `PAYOUT` в `BalanceTransactionType`, `SalaryPayout`/ERP cash document логика) — оставить как есть по смыслу (это отдельное бизнес-действие «выплатить», не «страница»), при необходимости только скорректировать точку вызова из фронтенда.
- Обновить/расширить контракты в `contracts/commands/`, если меняется форма ответа списка (например, замена `payoutPageResponseSchema` на новую схему сквозного списка сотрудников с балансом, отделом и датой последнего движения).
- Если для бейджа «Уволен» и должности нет уже готового поля в `BitrixEmployee`/`DirectoryRepository` — добавить/прокинуть недостающие поля.
- Обеспечить консистентность именования: не переименовывать сущности, отражающие реальное действие «выплата» (`PAYOUT`), переименовать только то, что отражает старую страницу-отчёт.

## Не в скоупе

- Изменение перечня типов движений (`BalanceTransactionType`) и логики начисления/закрытия периода (`SalaryAccrual`, pipeline закрытия месяца).
- Изменение бизнес-логики создания выплаты и интеграции с ERP-кассой (RemOnline/МойСклад) — сохраняется как есть.
- Отдельный экран/UI для массовой выплаты нескольким сотрудникам сразу (`PayoutBatchConfirmDialog`, `PayoutResultModal`) — в предоставленных макетах такого UI на новом списке взаиморасчётов нет; решение о том, где (и нужно ли) сохранить массовую выплату как отдельный флоу, выносится за рамки этого PRD (см. «Технические ограничения»).
- Редизайн drawer’ов «Новое движение» и модалки «Удалить движение» — они уже существуют (`NewTransactionDrawer`, `DeleteTransactionDialog`) и переиспользуются без изменений внешнего вида, кроме случаев, где текущая реализация расходится с макетами `A03HSv`/`w3wDY`/`EOWaY`/`Kclux`.
- Страница `/salaries` (отчёт начислений по правилам) и страницы правил/схем мотивации — не затрагиваются.
- Мобильное нативное приложение — только адаптивная вёрстка веб-версии.

## Технические ограничения

- Ключевая архитектурная особенность, которую нужно сохранить: баланс сотрудника — единая сквозная сущность (`BalanceTransaction.employeeId`), не привязанная к направлению; направление (`direction`) — атрибут каждого отдельного движения, а не самого баланса. Список «Взаиморасчёты» показывает баланс без учёта направления, страница сотрудника — с разбивкой по направлению на уровне движений.
- Существующая страница `/balance/department` (`DepartmentBalancesPage`) и её API (`get-department-balances`) уже частично реализуют нужную модель данных (общий баланс, фильтр по отделу) — рассмотреть слияние/эволюцию этой страницы в новую «Взаиморасчёты», а не создание параллельной с нуля.
- Открытый вопрос, требующий решения перед реализацией: куда переносится создание движения типа «Выплата» и особенно **массовая** выплата нескольким сотрудникам разом — в макетах кнопки «Выплатить» на странице сотрудника нет (есть только «Добавить приход»/«Добавить расход»), что указывает на объединение флоу выплаты с общим drawer’ом добавления движения. Уже реализованная логика подтверждения при уходе баланса в минус (409 `PayoutConfirmationRequired`) и создания ERP-документа должна быть сохранена независимо от того, через какую точку входа в UI её вызывают.
- Список отделов и состав сотрудников берутся из уже синхронизированных данных Bitrix24 (`backend/src/modules/directory`, `BitrixDepartment`/`BitrixEmployee`), без прямых обращений к Bitrix API на каждый запрос страницы.
- Данные о связке сотрудника с ERP-системами (RemOnline/МойСклад) для шапки страницы баланса — проверить наличие в модели `EmployeeIdentity`/сопоставлении (`/settings/employee-identity`), при отсутствии готового поля — добавить.
- Признак «Уволен» для сотрудника — проверить, есть ли уже статус активности сотрудника из Bitrix24 в `BitrixEmployee`; при отсутствии — добавить синхронизацию поля.
- **Решение по открытому вопросу (Фаза 6)**: создание движения типа «Выплата» (включая обработку 409 `PayoutConfirmationRequired` и создание ERP-документа) переезжает в единый drawer «Добавить расход» (`NewTransactionDrawer`, `features/EmployeeBalance`) — выбор типа «Выплата» вызывает тот же `create-payout`, что и раньше, просто из общей точки входа вместо отдельной кнопки/страницы. **Массовая** выплата (`create-payout-batch`/`create-shop-payout-batch`) остаётся без UI: ни один из предоставленных макетов не показывает множественный выбор строк или «Выплатить выбранным», поэтому фронтенд-точки входа (`PayoutBatchConfirmDialog`, чекбоксы `SelectionBar`, кнопка массовой выплаты) удалены вместе со старой страницей `/payout`. Сами эндпоинты `POST .../payout/batch` — не удалены, остаются рабочими и покрытыми тестами (см. WHY-комментарий в `create-payout-batch.handler.ts`/`create-payout-batch.handler.ts`); появление UI для них — отдельная будущая задача, а не часть этого PRD.

## Критерии готовности

- [ ] Пункт меню «Зарплата» ведёт на новую страницу «Взаиморасчёты с сотрудниками» вместо «Выплата»; старый роут `/payout` и его компоненты (`PayoutPage`, `PayoutTable`, `PayoutKpiRow`, `PayoutFilters`, `PayoutCardList`, Direction Tabs) удалены или заменены.
- [ ] Список взаиморасчётов по умолчанию показывает всех сотрудников всех отделов с общим (не по направлению) балансом, без переключателя «Сервис/Магазин».
- [ ] Фильтр «Отдел» сужает список и три показателя (общий остаток / к выплате / долг) до сотрудников выбранного отдела; значение «Все отделы» агрегирует по всей компании.
- [ ] Поиск по имени сотрудника работает в рамках текущего фильтра по отделу.
- [ ] В списке отображаются: сотрудник, должность, отдел, дата последнего движения, остаток; уволенные сотрудники с ненулевым балансом помечены бейджем.
- [ ] Клик по сотруднику открывает страницу его баланса.
- [ ] Страница баланса сотрудника показывает единый общий баланс без деления на сервис/магазин в шапке, но каждое движение в ленте помечено направлением (сервис/магазин).
- [ ] На странице баланса сотрудника доступны фильтр по типу движения (чипы), поиск по комментарию, добавление прихода/расхода, выгрузка ленты, удаление ручных движений — с сохранением существующих бизнес-правил (обязательность комментария для штрафа/корректировки, запрет удаления ERP-движений).
- [ ] Лента движений сотрудника по умолчанию открывается «за всё время» (без обязательного выбора периода) и показывает последние 20 движений; долистывание до конца ленты (или кнопка) подгружает следующие 20 более ранних движений, и так до конца истории.
- [ ] Backend: эндпоинт(ы) старой страницы `/payout` (`get-payout-page` и зеркало в shop), использовавшиеся только для неё, заменены на сквозной (без направления) эндпоинт с фильтром по отделу/поиском, либо явно выведены из эксплуатации с обоснованием в коде/доке.
- [ ] Backend: сущности, отвечающие за реальное действие «выплатить» (`create-payout`, `create-payout-batch`, `delete-payout`, тип `PAYOUT`), не переименованы и продолжают работать через актуальную точку входа в UI.
- [ ] Обновлённые Zod-контракты в `contracts/commands/` соответствуют новой форме ответа списка взаиморасчётов и не ломают типизацию на фронтенде и бэкенде.
- [ ] Верстка корректно адаптируется под мобильный вид (группировка по отделам, карточный список) согласно макетам `wZnzC`/`JTc29`, и под десктоп — согласно `IFJW2`/`L73YCK`.
