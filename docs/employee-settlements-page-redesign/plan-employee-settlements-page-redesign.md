# Plan: Редизайн страницы «Выплата» → «Взаиморасчёты с сотрудниками»

**PRD**: `docs/employee-settlements-page-redesign/prd-employee-settlements-page-redesign.md`
**Дата**: 2026-08-25

## Фазы реализации

### Фаза 1: Backend — сквозной эндпоинт баланса сотрудников (Tracer Bullet)
**Цель**: получить один рабочий эндпоинт, который отдаёт сквозной (без направления сервис/магазин) список сотрудников с балансом — либо по всем отделам сразу, либо по одному отделу, с поиском по имени и датой последнего движения. Это основа для всех последующих фаз.
**Что затрагивает?** backend, database
**Задачи:**
- [ ] Расширить `GetDepartmentBalancesService`/эндпоинт `GET /v1/accounting/balance/department/:id/:period` (или создать соседний эндпоинт, если расширение невозможно без ломающих изменений) поддержкой режима «все отделы» без обязательного `departmentId`.
- [ ] Добавить поиск по имени сотрудника и вычисление даты последнего движения (`max(occurredAt)` по `employeeId`) в ответ.
- [ ] Добавить агрегаты для трёх KPI: общий остаток, сумма и количество сотрудников с положительным остатком («к выплате»), сумма и количество сотрудников с отрицательным остатком («долг»).
- [ ] Проверить наличие полей должности и статуса увольнения в `BitrixEmployee`/`DirectoryRepository`; при отсутствии — добавить синхронизацию/проброс полей.
- [ ] Написать/обновить unit- и e2e-тесты нового поведения эндпоинта (все отделы, один отдел, поиск, KPI-агрегаты, уволенный сотрудник с ненулевым балансом).
**Когда готово**: эндпоинт возвращает корректные данные для «всех отделов» и для конкретного отдела с фильтром/поиском/KPI, все новые и существующие тесты зелёные.

### Фаза 2: Contracts — Zod-схема списка взаиморасчётов
**Цель**: закрепить форму ответа фазы 1 в общем пакете контрактов, чтобы backend и frontend типизировались от одного источника истины.
**Что затрагивает?** backend, frontend (через `contracts`)
**Задачи:**
- [ ] Добавить в `contracts/commands/` новую схему(ы) сквозного списка взаиморасчётов (сотрудник, отдел, должность, статус увольнения, дата последнего движения, остаток) и схему KPI-показателей.
- [ ] Пометить как устаревшие/удалить схемы, специфичные только для старой страницы `/payout` (`payoutPageResponseSchema`, `payoutEmployeeRowSchema`, `payoutPageTotalsSchema`), если они более не используются после фазы 6.
- [ ] Подключить новые схемы к контроллеру/сервису из фазы 1 (`nestjs-zod` валидация).
- [ ] Прогнать сборку `contracts` и убедиться, что типы применяются в backend и frontend без ошибок компиляции.
**Когда готово**: пакет `ireports-contracts` собирается, новая схема используется в реальном ответе эндпоинта, типы доступны на фронтенде.

### Фаза 3: Frontend — страница списка «Взаиморасчёты с сотрудниками» (десктоп)
**Цель**: новая десктопная страница списка, подключённая к эндпоинту из фазы 1, с фильтром по отделу, поиском, KPI-карточками и переходом на баланс сотрудника — по макету `IFJW2`.
**Что затрагивает?** frontend
**Задачи:**
- [ ] Создать страницу и роут «Взаиморасчёты» с фильтром «Отдел» (`useDepartments()` из `features/TargetDirectory`, значение по умолчанию «Все отделы») и строкой поиска по имени.
- [ ] Реализовать три KPI-карточки (общий остаток / к выплате / долг сотрудников) и отметку «Данные на …».
- [ ] Реализовать таблицу (сотрудник+должность, отдел, последнее движение, остаток) со строкой итогов и бейджем «Уволен»; клик по строке ведёт на `/balance/employee/:id`.
- [ ] Обновить пункт меню «Зарплата» на «Взаиморасчёты» с новым роутом.
- [ ] Написать unit/RTL-тесты страницы и её хука состояния (фильтрация по отделу, поиск, отображение KPI).
**Когда готово**: страница отображает реальные данные с бэкенда, фильтр и поиск работают, переход в навигации ведёт на новую страницу, тесты зелёные.

### Фаза 4: Frontend — адаптивная (мобильная) вёрстка списка
**Цель**: мобильная раскладка списка взаиморасчётов с группировкой по отделам и промежуточными итогами — по макету `wZnzC`.
**Что затрагивает?** frontend, design
**Задачи:**
- [ ] Реализовать карточный список для мобильной ширины с группировкой по отделу и подытогом на группу при режиме «Все отделы».
- [ ] Адаптировать KPI-блок, фильтр и поиск под мобильную раскладку.
- [ ] Добавить кнопку выгрузки таблицы (десктоп и мобайл).
- [ ] Визуально сверить раскладку с макетом `wZnzC` на нескольких ширинах экрана (скриншот в браузере).
- [ ] Добавить тесты/снапшоты компонентов группировки и подытогов.
**Когда готово**: страница корректно адаптируется на мобильной ширине, группировка по отделам и подытоги считаются верно, вёрстка соответствует макету `wZnzC`.

### Фаза 5: Frontend — редизайн страницы баланса сотрудника
**Цель**: обновить `/balance/employee/:id` по макетам `L73YCK` (десктоп) и `JTc29` (мобайл) — новая шапка, чипы типов движений, поиск по комментарию, направление на каждой строке ленты.
**Что затрагивает?** frontend, design
**Задачи:**
- [ ] Обновить шапку страницы (имя, отдел, должность, отметка о связке с ERP-системами, крупный общий баланс) и панель действий («Добавить приход», «Добавить расход», «Выгрузить ленту»).
- [ ] Заменить текущий мультиселект типов движений на чипы («Все типы» + 10 типов) со сворачиванием лишних («Ещё N») на мобильной раскладке.
- [ ] Добавить поиск по комментарию.
- [ ] Обновить строки ленты (десктоп-таблица и мобильные карточки), добавив отображение направления («Сервис»/«Магазин») под типом движения в каждой строке.
- [ ] Написать RTL-тесты фильтрации по типу, поиска по комментарию и отображения направления в строке.
**Когда готово**: страница баланса сотрудника визуально соответствует макетам `L73YCK`/`JTc29`, фильтрация и поиск работают, направление показывается для каждого движения, существующая логика удаления/добавления не сломана.

### Фаза 6: Backend + Frontend — единая точка входа для «Выплаты» и очистка старой страницы `/payout`
**Цель**: обеспечить создание движения типа «Выплата» (с сохранением подтверждения при уходе в минус и созданием ERP-документа) через общий drawer добавления движения, зафиксировать судьбу массовой выплаты и удалить неиспользуемый код старой страницы `/payout`.
**Что затрагивает?** backend, frontend
**Задачи:**
- [ ] Backend: адаптировать вызов `create-payout` (и его логику подтверждения 409 / создания ERP-документа) под вызов из единого флоу добавления движения; принять и задокументировать решение по `create-payout-batch` (сохранить точку входа отдельно или явно вывести из эксплуатации).
- [ ] Backend: удалить неиспользуемые после фазы 1 контроллеры `get-payout-page`/`get-shop-payout-page` и завершить пометку/удаление схем из фазы 2.
- [ ] Frontend: подключить тип «Выплата» в drawer «Добавить расход» к реальному вызову создания выплаты, включая обработку подтверждения отрицательного остатка и результата ERP-документа.
- [ ] Frontend: удалить старые компоненты страницы `/payout` (`PayoutPage`, `PayoutTable`, `PayoutKpiRow`, `PayoutFilters`, `PayoutCardList`, Direction Tabs) и сам роут.
- [ ] Обновить/дописать e2e-тест `payout.e2e.spec.ts` и RTL-тест сценария создания выплаты через общий drawer (включая ветку подтверждения отрицательного остатка).
**Когда готово**: выплата создаётся через единый drawer на странице сотрудника с сохранением всей текущей бизнес-логики, старый код и неиспользуемые эндпоинты `/payout` удалены, все тесты (unit/RTL/e2e) зелёные.

### Фаза 7: Backend — пагинация ленты баланса сотрудника + «за всё время»
**Цель**: убрать обязательность выбора периода в эндпоинте ленты баланса сотрудника и добавить курсорную пагинацию, чтобы лента отдавалась порциями по 20 движений (от новых к старым), без ограничения по месяцу.
**Что затрагивает?** backend
**Задачи:**
- [ ] Сделать параметр периода в эндпоинте ленты баланса сотрудника (`GetEmployeeBalanceService`/`get-employee-balance.http.controller.ts`) необязательным: при отсутствии — выборка «за всё время», без ограничения по месяцу.
- [ ] Добавить курсорную пагинацию: `limit` (по умолчанию 20) + `cursor`, сортировка по дате движения (и id как тай-брейкер) по убыванию; в ответе — `nextCursor`/признак наличия следующей страницы.
- [ ] Проверить, что существующие серверные фильтры (тип движения, если применяются на бэкенде) применяются до пагинации, а не после — иначе разбивка на страницы будет некорректной.
- [ ] Обновить схему запроса/ответа в `contracts/commands/employee-balance.ts` (курсор, limit, признак «есть ли ещё записи»).
- [ ] Багфикс сортировки: сейчас при добавлении нового движения (приход/расход) оно попадает в конец ленты вместо начала — найти и исправить причину (сортировка по `id`/порядку вставки вместо `occurredAt`, либо стабильный порядок ties по `createdAt`/`id` по убыванию так, чтобы только что созданное движение с сегодняшней датой всегда оказывалось первым). Зафиксировать это явным тестом.
- [ ] Тесты: unit + e2e на пагинацию — первые 20 записей, следующие 20 по курсору, режим «за всё время» не режет по периоду, совместная работа с фильтром по типу; отдельный тест на то, что только что созданное движение оказывается первым в ленте независимо от порядка вставки в БД.
**Когда готово**: эндпоинт по умолчанию отдаёт последние 20 движений сотрудника за всё время в правильном порядке (новые сверху, включая только что добавленные); при передаче курсора — следующие более ранние 20; тесты зелёные.

### Фаза 8: Frontend — «за всё время» и бесконечная подгрузка ленты баланса
**Цель**: на странице баланса сотрудника лента по умолчанию показывает последние 20 движений за всё время и подгружает ещё 20 более ранних при прокрутке/по кнопке — по индикатору «Загружаем более ранние движения…» из макетов `L73YCK`/`JTc29`.
**Что затрагивает?** frontend, design
**Задачи:**
- [ ] Обновить `frontend/src/pages/EmployeeBalance/model/api.ts` на курсорную пагинацию из Фазы 7 (например, через `useInfiniteQuery`), убрав обязательную зависимость от выбранного периода.
- [ ] Добавить в фильтр периода (или заменить его по умолчанию на) режим «За всё время»; согласовать итоговый UX с текущим `BalanceActions.tsx`/`BalanceFilters.tsx` (месячный `PeriodPicker` был сохранён в Фазе 5 — решить, оставлять ли его как дополнительное сужение поверх «за всё время» или убрать).
- [ ] Реализовать подгрузку следующих 20 движений при достижении конца ленты (десктоп `TransactionsLedger.tsx`, мобайл `TransactionsCardList.tsx`) с индикатором загрузки.
- [ ] Согласовать фильтр по типу и поиск по комментарию с пагинацией: если раньше поиск/фильтр были клиентскими на одной загруженной странице — перевести на серверные параметры запроса (чтобы «загрузить ещё» подгружало следующие подходящие записи, а не следующие 20 без учёта фильтра), либо явно задокументировать ограничение, если оставлено клиентским.
- [ ] Багфикс сортировки на фронтенде: после создания нового движения (приход/расход через `NewTransactionDrawer`) убедиться, что кэш TanStack Query для ленты инвалидируется/обновляется так, чтобы новое движение сразу отображалось первым (сверху), а не в конце текущей загруженной страницы — проверить, что оптимистичное обновление (если есть) не просто добавляет запись в конец локального массива, а вставляет её в правильную позицию согласно сортировке.
- [ ] RTL-тесты: подгрузка следующей страницы по прокрутке/кнопке, отображение индикатора, режим «за всё время» по умолчанию, отображение только что созданного движения первым в списке.
**Когда готово**: страница по умолчанию показывает последние 20 движений сотрудника за всё время в правильном порядке; новое движение после создания сразу появляется первым в ленте; долистывание/кнопка подгружает следующие 20 более ранних; тесты зелёные.
