# PRD: Эндпоинт каталога склада магазина (новый модуль `warehouse` в домене shop)

**Дата**: 2026-08-12
**Статус**: Draft

## Цель

Дать фронтенду iReports единый API-эндпоинт для получения каталога магазина (дерева категорий), который сейчас нужен во многих местах интерфейса, но в домене `shop` нет сущности, которой он логически принадлежит — ни `accounting` (зарплаты), ни `sales` (план/факт продаж). Эндпоинт размещается в новом модуле `warehouse`, внутри которого выделяется сущность `catalog`, переиспользующая уже синхронизированную из МойСклад таблицу категорий товаров.

## Пользовательские сценарии

- Пользователь фронтенда открывает экран с фильтром/выбором категории товара магазина -> фронтенд запрашивает каталог через новый эндпоинт и получает дерево категорий.
- Разработчик фронтенда добавляет новый экран, которому нужен список категорий магазина -> использует один и тот же эндпоинт вместо дублирования логики получения справочника в разных фичах.

## В скоупе

- Новый NestJS-модуль `warehouse` в `backend/src/domains/shop/modules`, зарегистрированный в модуле домена `shop`.
- Внутри модуля `warehouse` — сущность `catalog`, отвечающая за каталог (дерево категорий) конкретного склада.
- Один HTTP GET-эндпоинт сущности `catalog`, возвращающий каталог магазина — дерево категорий товаров (без самих товаров).
- Эндпоинт читает данные из уже существующей и синхронизируемой таблицы категорий (`MoySkladProductFolder`, "дерево категорий" из Фазы 10) — без создания новой Prisma-модели и без нового синка складов из МойСклад.
- Структура ответа отражает иерархию категорий (родитель/дети, название, путь), пригодную для переиспользования как единый справочник на разных экранах фронтенда.
- Эндпоинт задокументирован в `ENDPOINTS.md`.
- Эндпоинт задокументирован Swagger-декораторами над контроллером (`@ApiTags`, `@ApiOperation`, `@ApiResponse` и т.п.), чтобы данные отображались в Swagger — по тому же принципу, что и у остальных HTTP-контроллеров проекта.
- Эндпоинт без авторизации — по тому же принципу, что и остальные внутренние эндпоинты `domains/shop` (`accounting`, `sales`).

## Не в скоупе

- Синхронизация складов (сущность Store из МойСклад) как отдельной сущности/Prisma-модели.
- Список товаров с остатками/количеством по конкретному физическому складу — по итогам уточнения каталог ограничен категориями, товары в ответ не входят.
- Публичный или партнёрский доступ к эндпоинту (авторизация по конкретному складу/франчайзи) — эндпоинт только для внутреннего фронтенда iReports.
- Создание, редактирование или удаление категорий через API — эндпоинт только на чтение.
- Каталог для доменов `opt` и `service` — фича касается только домена `shop`.
- Другие сущности модуля `warehouse` (например, сами склады как физические объекты, остатки по складам) — в этой итерации модуль ограничен одной сущностью `catalog`.

## Технические ограничения

- В домене `shop` нет модуля, которому каталог/справочники магазина принадлежат по смыслу: `accounting` отвечает за зарплаты, `sales` — за план/факт продаж. Поэтому сущность `catalog` и её эндпоинт размещаются в новом модуле `warehouse`, а не в одном из существующих модулей.
- "Каталог склада" по итогам уточнения — это уже существующее дерево категорий товаров магазина (`MoySkladProductFolder`, синхронизируется из МойСклад начиная с Фазы 10), а не список товаров с остатками по конкретному физическому складу. Сущности "Склад" (МойСклад Store) в системе нет, и её синхронизация не входит в эту итерацию — модуль `warehouse` пока состоит из одной сущности `catalog`.
- Название "склад" в исходной формулировке задачи расходится с фактическим содержимым (категории, а не физический склад с остатками) — точное бизнес-название сущности/модуля стоит зафиксировать на ревью PRD, чтобы не создавать путаницу в будущих итерациях (например, если позже в модуль `warehouse` добавится сущность с реальными остатками по физическим складам).
- Эндпоинт без авторизации: в `domains/shop` уже есть прецедент (`accounting`, `sales`) — эндпоинты без гарда, доступны любому, кто может обратиться к backend.

## Критерии готовности

- [ ] В `backend/src/domains/shop/modules` существует новый модуль `warehouse`, зарегистрированный в модуле домена `shop`.
- [ ] Внутри модуля `warehouse` выделена сущность `catalog` с собственным HTTP-контроллером.
- [ ] Эндпоинт сущности `catalog` возвращает каталог магазина в виде дерева категорий.
- [ ] Эндпоинт возвращает данные из существующей таблицы категорий (`MoySkladProductFolder`) без создания нового источника данных или синка.
- [ ] Эндпоинт задокументирован в `ENDPOINTS.md`.
- [ ] Контроллер эндпоинта покрыт Swagger-декораторами, и эндпоинт отображается в Swagger.
- [ ] Ответ эндпоинта отражает иерархию категорий (родитель/дети), а не плоский список.
