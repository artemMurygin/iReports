# PRD: Рефакторинг архитектуры модуля SalaryRules (frontend)

**Дата**: 2026-08-18
**Статус**: Реализовано (2026-08-18), кроме ручной проверки в браузере

## Цель

Привести `frontend/src/pages/SalaryRules` к архитектуре, описанной в `frontend/CLAUDE.md` (mediator/model/ui, папка на компонент, именованные слоты, отсутствие условного рендера в медиаторе), чтобы разработчик по структуре папок понимал, где лежит логика, где верстка и где направление-специфичная часть, — и мог найти нужный код без чтения всего модуля. Поведение страницы и её внешний вид не меняются.

## Проблемы текущей реализации

Зафиксированы как отправная точка (замеры на коммите `3fcdfcf`):

1. **`ui/SalaryRulesRuleFormCard.tsx` — 411 строк** — один файл держит: локальный стейт ошибок, сброс роли при смене типа, сброс ошибок при смене награды, шапку карточки, сетку полей, тип-зависимое тело (5 вариантов награды), пороги, футер, плюс вложенный компонент `SalaryBasisField`. Это ровно тот случай, для которого `frontend/CLAUDE.md` требует `ui/<Компонент>/{model,ui}`.
2. **`ui/SalaryRulesPage.tsx` — 244 строки** — страница одновременно является медиатором (вызывает 8 хуков), содержит бизнес-логику отправки (два независимых `handleSubmit`-ветвления с формированием payload и тостами), верстает header/success-баннер/двухколоночный layout и содержит условный рендер (`successId && ...`). Проектная конвенция: страница — «чистая склейка» `useXPage()` → пропсы `Layout`.
3. **7 ветвлений `direction === '...'`**, все в `SalaryRulesPage.tsx`, — выбор черновика, выбор query типов правил, выбор конфига, выбор мутации, выбор текста тоста, два ветвления для каталога. Логика одного направления не собрана в одном месте.
4. **Плоские папки**: `ui/` — 10 файлов вперемешку (страница, layout-части шага 1, шага 2, оверлеи полей, мобильный бар); `model/` — 17 файлов вперемешку (общие утилиты, сервисные схемы, магазинные схемы, api, хуки). Нет группировки, нет `index.ts` у компонентов — по имени файла не видно, к какому блоку страницы он относится.
5. **Нет `Layout`-компонента со слотами**, в отличие от `pages/ServicesReport`, `pages/FunnelReport`, `pages/SalesPlan`: разметка страницы (`main` → header → две колонки → sticky bar) вшита в `SalaryRulesPage`.
6. **Проброс props насквозь**: `SalaryRulesRuleList` принимает 15 props, из которых 9 просто транслируются в `SalaryRulesRuleFormCard` без использования.
7. **Префиксы вместо структуры**: `SalaryRules*` в имени 5 файлов внутри папки `SalaryRules` — префикс компенсирует отсутствие вложенности.

## Пользовательские сценарии

Пользователь здесь — разработчик, который дорабатывает модуль.

- Разработчик открывает `pages/SalaryRules` → по именам папок первого уровня понимает: `core` — общее ядро, `service`/`shop` — направления, `ui` — каркас страницы, `model` — состояние страницы.
- Разработчик ищет, где валидируется поле «Процент» для магазина → идёт в `shop/model/`, не читая сервисный код и не читая UI.
- Разработчик ищет, как выглядит футер раскрытой карточки правила → идёт в папку карточки правила и видит один файл на один блок разметки.
- Разработчик добавляет новый тип правила магазину → правит только `shop/`, `core` и `service` не трогает.
- Разработчик меняет расположение блоков на странице → правит только `Layout`, не трогая контент слотов.
- Разработчик читает медиатор → видит только вызовы хуков и передачу пропсов, без `&&`/тернарников, решающих что показывать.

## В скоупе

### 1. Целевая структура папок

```
pages/SalaryRules/
├── index.ts                  # только SalaryRulesPage
├── mediator/                 # оркестрация: вызов хуков → пропсы, без своей логики и без условного рендера
├── model/                    # состояние страницы: направление, шаг 1 (targetType/targetId/schemaName), сабмит
├── ui/                       # каркас страницы: Layout со слотами, PageHeader, TargetCard, MobileSaveBar, SaveStatusBanner
├── core/                     # направление-агностичное ядро
│   ├── model/                # RuleDraft, useSalaryRulesDraft, ruleSummary, formNumberUtils, catalogTree, roleLabels
│   └── ui/                   # RuleList, RuleRow, RuleFormCard (+ подкомпоненты), ThresholdsEditor, CategoryField, PercentSliderField
├── service/                  # направление «Сервис»
│   ├── model/                # api, ruleTypes, ruleFormSchema, хуки запросов/мутации, сборка адаптера направления
│   └── ui/                   # точка входа направления: связывает core/ui с сервисным конфигом
└── shop/                     # направление «Магазин» — зеркально service/
    ├── model/
    └── ui/
```

- Каждый компонент — папка с `index.ts` (публичный API) и файлами внутри; компонент с собственной логикой (стейт, валидация, сайд-эффекты) делится на `model/` и `ui/` внутри своей папки.
- Импорт компонента — только через его `index.ts`.
- Префикс `SalaryRules` из имён файлов убирается — его роль выполняет путь.

### 2. Разделение service/shop на два поддерева

- Каждое направление владеет своим: `api`-фабрикой запросов, конфигом типов правил и наград, резолвером черновика, хуками запросов и мутации, текстами тостов, точкой входа в UI.
- Всё, что нужно странице от направления, отдаётся одним объектом (адаптером направления) единой формы, реализованной обоими направлениями.
- Внутри `core/` и `ui/` не остаётся ни одного ветвления по направлению: 7 текущих `direction === '...'` схлопываются в одну точку выбора адаптера.
- Два независимых черновика (по одному на направление) и раздельная отправка в свои эндпоинты сохраняются как есть — контракты `MotivationRequest`/`ShopMotivationRequest` по-прежнему не смешиваются.

### 3. Слоты и разбиение крупных компонентов

- `Layout` страницы принимает именованные слоты (`header`, `target`, `rules`, `mobileBar`) вместо `children` и не знает содержимого.
- Содержимое слота собирается в переменную выше `return`, а не инлайнится в JSX-проп.
- `RuleFormCard` разбивается на: модель (стейт ошибок, обработчики смены типа/награды/сохранения) + презентационные подкомпоненты (шапка, сетка основных полей, блок награды, футер). Аналогично разбираются `RuleList` (шапка / список / пустое состояние / кнопка добавления) и `TargetCard`.
- Условный рендер выносится из медиатора и страницы в презентационные компоненты.
- Сквозной проброс props сокращается: компонент не принимает props, которые сам не использует.

### 4. Ограничения на размер и границы

- Ни один `.tsx`/`.ts` файл модуля (кроме `*.test.ts`) не превышает 150 строк.
- Сохраняются границы FSD: модуль не выходит за пределы `pages/SalaryRules`, импортирует только `shared`/`kernel`/`ireports-contracts`.

## Не в скоупе

- Любые изменения верстки, копирайта, состава полей, шагов и поведения формы — рефакторинг строго behaviour-preserving.
- Вынос чего-либо в `features/` или `shared/ui-kit/` (новый `FormField`, `ResponsiveOverlay`, `StickyActionBar` и т. п.) — отдельная задача.
- Изменения backend, контрактов в `contracts/`, эндпоинтов.
- Страница редактирования/просмотра существующей схемы (см. `docs/payroll/prd-salary-schemas-view-edit-pages.md`).
- Хранение направления/черновика в URL или в сторе, автосохранение черновика.
- Новые unit-тесты помимо уже существующих (`ruleFormSchema.test.ts`, `shopRuleFormSchema.test.ts`).
- Замена `RuleDraft` на react-hook-form/Zustand или другой механизм формы.

## Технические ограничения

- **Тесты `model/ruleFormSchema.test.ts` и `model/shopRuleFormSchema.test.ts` переносятся вместе со своими модулями; в них меняются только пути импортов** — сами кейсы и ожидания остаются прежними и служат страховкой рефакторинга. Тестовый раннер в `package.json` не настроен (см. `frontend/CLAUDE.md`) — запуск тестов нужно уточнить до старта работ.
- Единственный внешний потребитель модуля — роутер (`app/router.tsx`) через `pages/SalaryRules/index.ts`; экспорт `SalaryRulesPage` не меняется.
- Файлы модуля содержат объёмные комментарии со ссылками на узлы Pencil (`design/sallary-first-iteration.pen`) и на фазы `docs/salary-schema-creation-ui` — при переносе кода эти комментарии сохраняются и переезжают вместе с кодом, ссылки на соседние файлы обновляются под новые пути.
- Мобильный sticky-бар работает только пока он остаётся последним потомком `<main>` с `mt-auto` (стыковка с глобальным `BottomNav` без хардкода высоты) — новая структура слотов обязана сохранить это положение в DOM.
- `CategoryBottomSheet` импортирует `CATEGORY_TRIGGER_CLASS` из `CategoryCombobox` — при разнесении по папкам общий триггер должен остаться в одном месте.
- Валидация допускает только один источник — резолверы направлений; собственной zod-логики в UI-компонентах по-прежнему быть не должно.
- Ветка работы — `feat/salary`, в которой уже есть незакоммиченные изменения по backend-части зарплат; рефакторинг фронтенда не должен смешиваться с ними в одном коммите.

## Результат реализации

Модуль: 83 файла (было 30). Проверено на 2026-08-18:

- `npx tsc --noEmit` — чисто; `npx eslint src/pages/SalaryRules` — 0/0; `npm run build` — успешно;
  `npx vitest run src/pages/SalaryRules` — 28 тестов в 2 файлах проходят; `prettier --check` по модулю — чисто
  (до рефакторинга модуль не проходил форматирование: 16 файлов).
- Самый длинный файл модуля (кроме тестов) — 139 строк.
- `grep "direction ==="` — 1 совпадение (`model/useSalaryRulesPage.ts`). Импортов `core → service/shop` и
  кросс-импортов `service ↔ shop` нет. `index.ts` у всех 13 папок-компонентов.
- Сверка «до/после» по всем CSS-классам и всем русским строкам модуля (скриптом, включая `.ts`-константы):
  расхождений по существу нет — единственные отличия это перенос трёх лейблов полей из inline-JSX в проп
  `label` и переименование переменной `successId` → `savedSchemaId` в том же шаблоне строки.

Отклонения от целевой структуры PRD (осознанные, по итогам фазы проверки):
`core/model/ruleAwards.ts` (общий для обоих резолверов, изначально лежал в `service/`),
`core/model/useAllowedRolesByType.ts` (дедупликация одинакового `useMemo` в обоих адаптерах),
`core/model/ruleResolver.ts` (типы контракта резолвера, отделены от хука),
`core/ui/RuleFormCard/model/types.ts`, `core/ui/CategoryField/model/useCategoryOverlay.ts`
(общее состояние popover-а и bottom sheet-а).

Не выполнено: ручная проверка обоих направлений в браузере на desktop и mobile — требует запущенного
backend. Зоны наибольшего риска при ней: блок «Вариант награды» в карточке правила, тело карточки
(`PayPerHour` против награды), оба оверлея выбора категории (включая «Применить»/«Сбросить» в bottom sheet).
