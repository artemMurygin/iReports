# Plan: Drag-and-drop переупорядочивание строк плана продаж

**PRD**: docs/sales-plan-row-drag-and-drop-reorder/prd-sales-plan-row-drag-and-drop-reorder.md
**Дата**: 2026-09-03

## Фазы реализации

### Фаза 1: Backend — хранение и API порядка (домен service)
**Цель**: сервер умеет хранить порядок строк на уровне категории/направления/подразделения (переживает смену расчётного периода) и отдавать/принимать его для домена `service`.
**Что затрагивает?** backend, database
**Задачи:**
- [x] Добавить поле `sortOrder` в модель `SalesPlanTemplate` (Prisma) + миграция; для существующих строк заполнить начальный порядок по текущей сортировке `categoryId`.
- [x] Добавить `sortOrder` в контракты (`salesPlanTemplateSchema`/`salesPlanSchema`) и обновить `GetSalesPerformanceService`/`list-sales-plans`, чтобы строки возвращались отсортированными по `sortOrder`, а категории без сохранённого порядка — в конце списка.
- [x] Реализовать батч-эндпоинт обновления порядка для домена `service` (команда/хендлер/HTTP-контроллер), принимающий список `{categoryId, sortOrder}` для направления и подразделения.
- [x] Убедиться, что обновление порядка изолировано от остальных полей строки плана (не затрагивает `status`, `approvedBy`, `turnover`, `margin` и т.д.).
- [x] Тесты: unit-тесты хендлера обновления порядка и сортировки в репозитории; интеграционный тест батч-эндпоинта (сохранение, чтение с учётом порядка, категория без сохранённого порядка идёт последней).

**Когда готово**: батч-эндпоинт домена `service` сохраняет порядок в БД, `GET`-эндпоинт плана продаж возвращает строки в заданном порядке, все тесты фазы зелёные.

### Фаза 2: Frontend — drag-and-drop в модалке редактирования плана
**Цель**: пользователь может перетаскивать строки в таблице модалки редактирования плана (`EditPlanTable`), новый порядок уходит на сервер только при подтверждении сохранения модалки, вместе с остальными изменёнными полями.
**Что затрагивает?** frontend
**Задачи:**
- [x] Подключить `@dnd-kit` (`DndContext`, `SortableContext`, `useSortable`) в `EditPlanTable`/`EditPlanTableRow`, добавить drag-handle для строки.
- [x] Расширить `useEditPlanForm` локальным состоянием порядка строк, обновляемым при перетаскивании, без немедленного запроса к серверу.
- [x] Расширить сохранение модалки: при наличии изменённого порядка вызывать батч-эндпоинт из Фазы 1 вместе с сохранением изменённых полей (turnover/margin/orderTypeIds).
- [x] Обработать отмену/закрытие модалки без сохранения (сброс локального порядка к серверным данным) и ошибку сохранения (модалка остаётся открытой, показывает сообщение об ошибке, сохраняет введённые пользователем изменения, включая порядок).
- [x] Тесты: unit-тесты reorder-логики (перетаскивание → новый порядок массива строк), тест сценария сохранения (поля + порядок одним действием), тест отмены (порядок не сохраняется), тест ошибки сохранения (состояние модалки не теряется).

**Когда готово**: в модалке редактирования плана строки можно перетаскивать мышью; порядок и остальные правки сохраняются одним нажатием "Сохранить"; отмена и ошибка сохранения не портят и не теряют состояние.

### Фаза 3: Frontend — отражение сохранённого порядка на странице и в мобильной раскладке
**Цель**: страница плана продаж (десктопная таблица `SalesPlanTable`) и мобильная карточная раскладка (`SalesPlanCardList`) показывают актуальный сохранённый порядок строк без ручной перезагрузки страницы.
**Что затрагивает?** frontend
**Задачи:**
- [x] Убедиться, что `useSalesPlan` использует порядок строк, пришедший от API (по `sortOrder`), не переопределяя его на клиенте.
- [x] Проверить/адаптировать рендер `SalesPlanTable`, чтобы список строк корректно следовал новому порядку (стабильные ключи, без интерактивности drag на странице).
- [x] Проверить/адаптировать `SalesPlanCardList`, чтобы карточки шли в том же порядке, что и десктопная таблица.
- [x] Добавить инвалидацию/рефетч данных плана продаж после успешного сохранения модалки, чтобы новый порядок отобразился на странице сразу.
- [x] Тесты: unit-тест `useSalesPlan` на сортировку по данным API; интеграционный/e2e тест сценария "сохранил порядок в модалке → таблица и мобильный список показывают новый порядок без reload"; тест, что новая категория без сохранённого `sortOrder` отображается в конце списка.

**Когда готово**: после сохранения порядка в модалке страница плана продаж и мобильная раскладка сразу показывают новый порядок; заданный одним пользователем порядок виден всем остальным при следующем открытии страницы/модалки.

### Фаза 4: Backend — паритет для домена shop и правило закрытого периода
**Цель**: сохранение и отображение порядка одинаково работают для направлений `service` и `shop`; определено и реализовано поведение при закрытом расчётном периоде.
**Что затрагивает?** backend
**Задачи:**
- [x] Продублировать батч-эндпоинт обновления порядка в `domains/shop/modules/sales` (контроллер/DTO), переиспользуя команду/хендлер из Фазы 1 через общий `CommandBus`, как это сделано для остальных операций модуля.
- [x] Проверить, что `GetSalesPerformanceService`/`list-sales-plans` возвращают строки в сохранённом порядке и для направления `shop`.
- [x] Принять и реализовать поведение изменения порядка при закрытом расчётном периоде (`AccountingPeriod`) — заблокировать так же, как остальное редактирование плана, либо явно разрешить; задокументировать выбор в коде.
- [x] Тесты: e2e тест батч-эндпоинта для домена `shop` (аналогично `service`); тест поведения сохранения порядка при закрытом расчётном периоде.

**Когда готово**: направления `service` и `shop` одинаково поддерживают сохранение и отображение общего порядка строк; поведение при закрытом периоде определено, реализовано и покрыто тестами.
