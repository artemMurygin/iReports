# Research: расчёт заработной платы — как это устроено у других

**Дата**: 2026-08-10
**Статус**: Исследование, решений не принимает
**Связанный документ**: [`prd-payroll-calculation.md`](./prd-payroll-calculation.md)

Цель — посмотреть, как задачу «гибкие правила мотивации + расчёт по данным ERP + закрытие периода + баланс сотрудника» решают в готовых системах, и вытащить альтернативы тем решениям, которые заложены в PRD.

**Дисциплина источников.** Ниже помечено, что проверено чтением исходного кода, а что взято из документации или маркетинговых материалов вендора. Это существенно: вендорские тексты про «миллионы вычислений в секунду» проверить нельзя, а код Odoo/OCA — можно.

| Метка | Значение |
|---|---|
| 🟢 | прочитан исходный код |
| 🟡 | официальная документация проекта |
| 🔴 | маркетинговый материал вендора, проверке не поддаётся |

---

## 1. Обзор изученных систем

| Система | Класс | Лицензия | Что оттуда полезно |
|---|---|---|---|
| **Odoo / OCA `payroll`** 🟢 | ERP, модуль расчёта ЗП | AGPL-3 | Модель «правило = условие + формула + последовательность», единый контекст расчёта `localdict`, результат-строка вместо числа |
| **OCA `commission`** 🟢 | Модуль комиссий к Odoo | AGPL-3 | Ближайший аналог задачи: комиссия агенту, база «выручка / маржа», пороги-секции, `settlement` как расчётный период |
| **ERPNext / Frappe HR** 🟡 | ERP, HR-модуль | GPL-3 | Effective dating через `Salary Structure Assignment`, разделение «условие» и «формула», `safe_eval` как граница безопасности |
| **Payroll Engine** 🟡 | Специализированный движок ЗП (.NET) | открытый | Слоистые версионированные «регуляции», ретроактивный пересчёт, тесты как спецификация |
| **CaptivateIQ / Xactly** 🔴 | Коммерческие ICM/SPM | проприетарные | Колоночная модель расчёта, граф зависимостей, «умный кэш», реальная витрина требований к прозрачности |
| **Mettle (WODE)** 🟡 | Банк, реализация реестра | — | Паттерн Write Once Double Entry для баланса |

Отдельно: **специализированного opensource-движка «мотивация сотрудников розницы/сервиса по данным ERP» не существует**. Всё, что близко, — либо кадровый payroll (оклады, налоги, табель), либо sales commission (комиссия с продаж). Наша задача — гибрид: комиссионная логика, но применённая к сотруднику в кадровом контуре. Это объясняет, почему готовое решение не подобрать и почему PRD пишется с нуля.

## 2. Как устроено «зарплатное правило» в зрелых системах

### 2.1 Odoo / OCA `payroll` — эталон структуры 🟢

`payroll/models/hr_salary_rule.py`. Правило — это не «класс с методом `calculate()`», а **запись со следующими осями**:

```python
sequence          = fields.Integer(...)   # порядок вычисления
code              = fields.Char(...)      # другие правила ссылаются на результат по коду
category_id       = fields.Many2one("hr.salary.rule.category")
parent_rule_id    = fields.Many2one("hr.salary.rule")  # иерархия
condition_select  = Selection([("none","Always True"),("range","Range"),("python","Python Expression")])
amount_select     = Selection([("percentage","Percentage"),("fix","Fixed Amount"),("code","Python Code")])
```

Четыре вывода, каждый напрямую применим к iReports:

**(а) Условие применимости отделено от формулы.** `_satisfy_condition()` и `_compute_rule()` — два разных метода. Правило может «не сработать» вообще, и это не то же самое, что «сработать и вернуть 0». В текущих контрактах iReports такого разделения нет: `salaryRuleRequestSchema` содержит только `config` с формулой. Пример, где это нужно: «бонус за перевыполнение плана начисляется, только если выполнение ≥ 100 %» — сейчас это придётся зашивать внутрь формулы `FloatPercent`.

**(б) Единый контекст расчёта `localdict`.** Он собирается один раз на расчёт и передаётся в каждое правило:

```python
localdict = {
    "categories":   BrowsableObject(...),   # суммы по категориям правил
    "rules":        BrowsableObject(...),   # уже вычисленные правила
    "result_rules": BrowsableObject(...),   # их полные результаты
    "payroll":      BrowsableObject(...),
    "tools":        BrowsableObject(...),
}
```

Это **прямой ответ на блокер из PRD**: сигнатура `SalaryRule.calculate(): number` без аргументов. Odoo решает это не добавлением параметров в каждый метод, а единым объектом контекста, который наполняется по мере вычисления правил в порядке `sequence`.

**(в) Правило возвращает не число, а строку расчёта.**

```python
def _get_rule_dict(self, localdict):
    return {
        "name":     name,
        "quantity": quantity,
        "rate":     rate,
        "amount":   float(localdict["result"]),
    }
```

Требование PRD «сотрудник видит разбивку по правилам с указанием, на каких заказах она получена» **несовместимо** с `calculate(): number`. Возврат должен быть агрегатом строк: `{ ruleId, ruleName, basis, quantity, rate, amount, sourceRefs[] }`. Это надо решить до реализации, иначе придётся переписывать все правила второй раз.

**(г) Правила вычисляются последовательно и видят результаты предыдущих.**

```python
for rule in sorted_rules:
    if rule._satisfy_condition(localdict) and rule.id not in blacklist:
        localdict, _dict = payslip._compute_payslip_line(rule, localdict, lines_dict)
    else:
        blacklist += [rule.id, *children]   # правило не сработало — дети тоже
```

Цена: порядок вычисления становится частью бизнес-логики, а не деталью. Выгода: правило «10 % от суммы всех предыдущих начислений» выражается тривиально. В iReports сейчас правила независимы и просто суммируются — этого хватит для первой итерации, но стоит заранее решить, закладываем ли `sequence` в модель данных (добавить поле дешевле, чем мигрировать потом).

### 2.2 ERPNext / Frappe HR — то же, но через формулы-строки 🟡

Salary Component имеет `condition` и `formula` как текстовые Python-выражения, вычисляемые через `_safe_eval` с контекстом из `base`, аббревиатур других компонентов (`BS`), полей сотрудника и полей расчётного листа (`payment_days`). Есть утилита `sanitize_expression`, нормализующая пробелы — характерный признак того, что «формулы строкой» приносят свой класс багов.

Существенное отличие от Odoo: **`Salary Structure Assignment`** — отдельная сущность «сотрудник × структура × `from_date` × `base`». Это ответ на вопрос, которого в PRD iReports нет вообще: **с какой даты мотивационная схема применяется к сотруднику**. Сейчас в модели `MotivationSchema` есть `targetType`/`targetId`, но нет периода действия. Если сотруднику в середине месяца поменяли схему, текущая модель не сможет посчитать половину месяца по старой и половину по новой — она просто перезапишет схему.

### 2.3 OCA `commission` — самый близкий аналог 🟢

`commission/models/commission.py`:

```python
commission_type  = Selection([("fixed","Fixed percentage"), ("section","By sections")])
amount_base_type = Selection([
    ("gross_amount", "Sale/Invoice Amount"),
    ("net_amount",   "Margin (Amount - Cost)"),
])
```

Это **буквально** `salaryBasis: REVENUE | MARGIN` из контрактов iReports. Совпадение не случайно — задача одна и та же, и это подтверждает, что выбранная в контрактах ось моделирования правильная.

Дальше — важная деталь про пороги:

```python
def calculate_section(self, base):
    for section in self.section_ids:
        if section.amount_from <= base <= section.amount_to:
            return base * section.percent / 100.0
    return 0.0
```

Здесь **некумулятивная** схема: попали в интервал — весь объём умножается на процент этого интервала. Альтернатива (прогрессивная, как подоходный налог) — каждый транш считается по своей ставке и суммируется. Разница на реальных числах громадная, и **PRD этот вопрос не закрывает**: описание `percentBorders` с `mode: FIX | LINEAR` определяет форму перехода между порогами, но не отвечает, применяется ли множитель ко всей базе или только к части сверх порога.

Заодно видно, чего в OCA не сделано: валидации, что секции не пересекаются и не оставляют дыр. `calculate_section` при дырке молча вернёт `0.0` — то есть сотрудник получит ноль вместо ошибки. В iReports `percentBorders` — кортеж ровно из трёх элементов, что снижает риск, но валидацию монотонности `fromPlanPercent` всё равно надо писать явно.

**`commission.settlement`** — расчётный период как first-class сущность: `date_from`, `date_to`, `agent_id`, `line_ids`, `state ∈ {settled, cancel}`, `can_edit` (вычисляемое поле, разрешающее правку только ручным расчётам). Строки расчёта хранятся отдельно и являются снапшотом. Это ровно та модель, что заложена в PRD под `AccountingPeriod` + снапшот, и она подтверждается практикой.

Нюанс, который стоит забрать: настройка `settlement_type` — «по факту выставления счёта» против «по факту оплаты». Аналог для iReports: считать ли `OrderPayed` по статусу заказа или по факту поступления денег. В PRD это записано в открытые вопросы — OCA показывает, что делать это **настройкой**, а не хардкодом.

### 2.4 Payroll Engine — слоистые версионированные регуляции 🟡

Наиболее интересная идея: правила расчёта организованы в **стек версионированных слоёв** (базовый → страна → отрасль → компания), объекты нижних слоёв переопределяются верхними. Плюс период-ориентированная модель данных с **ретроактивным пересчётом**.

Прямая аналогия для iReports: слой «правила направления» (сервис / магазин) → слой «правила отдела» → слой «правила сотрудника». Сейчас в модели `MotivationSchema` есть `targetType: 'Department' | 'Employee'`, но **не описано, что происходит, если у сотрудника есть и своя схема, и схема его отдела**. Побеждает индивидуальная? Складываются? Индивидуальные правила переопределяют одноимённые правила отдела? Это дыра в текущем PRD, и слоистая модель Payroll Engine даёт готовый ответ: переопределение по коду правила.

Второе: ретроактивный пересчёт. Данные из RemOnline могут прийти задним числом (заказ закрыт 31-го, синхронизирован 1-го). PRD говорит «закрытый период не пересчитывается» — но не говорит, что делать с суммой, которая пришла после закрытия. В payroll-системах это решается **ретро-начислением в следующем периоде**, а не правкой закрытого. Стоит зафиксировать явно.

### 2.5 CaptivateIQ — колоночная модель и граф зависимостей 🔴

По описанию вендора: расчёт устроен как таблицы «строки × столбцы», формулы ссылаются на столбцы других таблиц, платформа строит **граф зависимостей** (столбцы — вершины, ссылки — рёбра), и «умный кэш пересчитывает только релевантные ячейки».

Как заявление о производительности — непроверяемо. Но как **архитектурная идея инвалидации кэша** это точнее того, что заложено в PRD. В PRD кэш инвалидируется по штампу синхронизации целиком: пришли новые данные — сбрасываем всё. Граф зависимостей позволил бы пересчитать только затронутых сотрудников. Для масштабов iRepair (десятки сотрудников, тысячи заказов в месяц) это оверинжиниринг, и грубая инвалидация правильнее — но знать об альтернативе полезно, если объёмы вырастут.

## 3. Ключевые развилки и альтернативные точки зрения

### 3.1 Как хранить правила: четыре подхода

| Подход | Кто применяет | Плюсы | Минусы |
|---|---|---|---|
| **Классы + реестр** (текущий выбор iReports) | — | Типобезопасность, тестируемость, IDE-поддержка, отсутствие `eval` | Новый тип правила = деплой. Регистрация в 3 местах (реестр, фабрика, контракты) |
| **Данные + интерпретатор формул** | ERPNext, Odoo (`amount_select='code'`) | Новое правило без деплоя, настраивается бизнесом | `eval` даже «безопасный» — поверхность атаки; ошибки только в рантайме; невозможно отрефакторить; отладка мучительна |
| **JSON rules engine** (`json-rules-engine`, `node-rules`) | — | Правила сериализуемы, без `eval`, читаемы | Заточены под булеву логику «условие → действие», а не под арифметику с агрегацией; forward chaining тяжело отлаживать |
| **Табличный/колоночный движок** | CaptivateIQ | Гибкость на уровне Excel, понятен финансистам | Огромная стоимость реализации |

**Альтернативная точка зрения к выбранному в iReports.** Мартин Фаулер в [заметке о rules engine](https://martinfowler.com/bliki/RulesEngine.html) предупреждает: цепочки правил, где действие одного меняет условия другого, «легко становятся очень трудными для понимания и отладки». Это аргумент **в пользу** текущего выбора iReports — классы с явным типом и без цепочек — и **против** соблазна позже добавить «формулу строкой, чтобы бухгалтер настраивал сам».

Практический компромисс, который видно у Odoo: три `amount_select` — `fix`, `percentage`, `code`. Первые два покрывают 90 % случаев декларативно, `code` оставлен как аварийный выход. iReports сейчас идёт по декларативному пути целиком, и это разумно — но стоит понимать, что «аварийного выхода» не будет, и каждый нестандартный случай = задача разработчику.

### 3.2 Классы против «правило = данные»: что реально болит

Текущая модель iReports хранит правило как строку в `salary_rules` с `props Json`, а поведение — в классе, найденном по `type` через `salaryRuleRegistry`. Это стандартный паттерн, но с двумя известными ловушками:

1. **`Json` в БД не валидируется схемой.** Если контракт изменится, старые записи в `props` останутся в старом формате и упадут при чтении. У Odoo этой проблемы нет — там поля типизированы на уровне ORM. Решение: версия схемы правила внутри `props` и миграция при чтении в мапере, либо строгая Zod-валидация в `SalaryRuleMapper.toDomain` с внятной ошибкой вместо падения.

2. **Регистрация в трёх местах** (`salary-rule-registry.ts`, `SalaryRuleFactory`, `discriminatedUnion` контрактов) — уже сейчас рассинхронизирована: `TaskCompleted` есть в контрактах, но нет в реестре. Альтернатива — генерировать реестр из контрактов (единый источник), а не поддерживать руками. Стоит рассмотреть, потому что цена ошибки — правило молча не применяется.

### 3.3 Расчётный период: три модели

| Модель | Как работает | Кто применяет |
|---|---|---|
| **Флаг на периоде + снапшот** (выбор PRD) | Сущность `AccountingPeriod` со статусом; при закрытии пишется снапшот | OCA `commission` (`settlement.state`) |
| **Только документ-расчёт** | Периода нет; есть документ (payslip/settlement), сам факт его существования = период закрыт | Odoo payroll, ERPNext |
| **Период-ориентированная модель с ретро** | Все данные привязаны к периодам валидности, закрытие не запрещает изменения — они уходят ретро-начислением в следующий период | Payroll Engine |

Выбор PRD (первая модель) правильный для iRepair, но у него есть слепое пятно, закрытое в третьей модели: **данные, пришедшие после закрытия**. RemOnline синхронизируется раз в 5 минут и только по обновлённым заказам; заказ, закрытый 31-го в 23:58, может приехать 1-го. Если период уже закрыт — сумма просто потеряется. Варианты:

- запретить закрытие раньше, чем через N дней после конца месяца (простое, работает);
- при обнаружении расхождения после закрытия создавать корректирующее начисление в текущем периоде (правильное, дороже);
- ничего не делать, но показывать руководителю расхождение перед закрытием (компромисс).

Ни один в PRD не описан. Это стоит закрыть.

### 3.4 Версионирование правил и effective dating

PRD говорит: «редактирование правила в открытом месяце → пересчёт; после закрытия → не меняется». Это работает, пока правило меняют **до** закрытия. Не покрыты два случая:

- смена схемы в середине месяца (нужен расчёт по частям периода);
- необходимость понять задним числом, **по какой версии правила** была посчитана зарплата за март.

Индустриальный ответ — **SCD Type 2 / bitemporal**: правило не редактируется, а создаётся новая версия с `effectiveFrom` / `effectiveTo`, старая остаётся неизменной. Снапшот тогда ссылается на конкретную версию правила, и вопрос «почему в марте вышло столько» получает точный ответ.

ERPNext реализует ослабленный вариант: `Salary Structure Assignment` с `from_date` — то есть версионируется не правило, а **назначение** правила сотруднику. Это дешевле и покрывает главный сценарий (сотруднику поменяли условия с 1-го числа).

**Альтернативная точка зрения.** Полноценная битемпоральность заметно усложняет схему и запросы. Для iRepair, где месяц закрывается раз в месяц и снапшот всё равно фиксирует итог, вероятно достаточно: (1) хранить в снапшоте не только суммы, но и **полный слепок конфигурации правил** на момент закрытия, и (2) добавить `effectiveFrom` в назначение схемы. Это даёт 90 % пользы битемпоральности за 20 % сложности.

### 3.5 Баланс сотрудника: event sourcing или двойная запись?

PRD выносит баланс за скоуп, но фиксирует требование «восстановимая история начислений». Здесь есть выраженная альтернативная позиция.

**Позиция «event sourcing».** Баланс — проекция потока событий; храним события, состояние выводим. Даёт полную историю и возможность восстановить состояние на любой момент.

**Позиция «двойная запись достаточна».** Двойная бухгалтерская запись — это уже event-sourced система, где проводки и есть события, а баланс — производное состояние. То есть **не нужно строить event sourcing поверх бухгалтерии — бухгалтерия уже им является**. Mettle формализовали это как **WODE (Write Once Double Entry)**: единственный способ подвинуть деньги — парная проводка; события неизменяемы и не удаляются; сумма дебетов и кредитов гарантированно равна нулю.

Практическая разница для iReports существенная. Event sourcing в общем виде требует event store, проекций, обработки версий событий — это инфраструктура. Реестр проводок — это **одна append-only таблица** `(id, employeeId, date, type, amount, direction, sourceRef, comment)` с запретом `UPDATE`/`DELETE`, и баланс = `SUM`. Второе даёт ровно тот результат, который описан в PRD («сотрудник прозрачно видит движение по балансу, где за что начислено и где депремирование»), но без инфраструктурной цены.

**Рекомендация к следующему PRD:** начинать с append-only реестра проводок, а не с полноценного event sourcing. Апгрейд возможен позже, обратный путь — нет.

### 3.6 Идентичность сотрудника между системами

Выбранный в PRD `EmployeeIdentity` (many-to-many «сотрудник × система × роль × внешний ID») — это стандартная **correlation table** из интеграционной практики: локальный идентификатор, удалённый идентификатор, система, состояние связи. Дополнения, которые видно в чужих реализациях:

- **Состояние связи** (`active` / `inactive`), а не удаление записи. Сотрудник уволился из сервиса, но исторические заказы должны продолжать к нему относиться. Если запись удалить, зарплата закрытых периодов «отвяжется». В PRD этого нет.
- **Период действия связи.** Тот же аргумент, что и с правилами: `roappOnlineName` мог измениться, и заказы до и после смены должны относиться к одному человеку.
- **Дисциплина «золотой записи»**: одна система объявляется источником истины по каждому атрибуту. В PRD это сделано верно (Bitrix — источник истины о человеке), и это стоит зафиксировать как инвариант, а не как случайность.

**Отдельный риск, который стоит проговорить.** `RoappOrder.onlineManager` — строка. Строковый ключ в correlation table хрупок: переименование в справочнике RemOnline тихо разрывает связь, и зарплата просто перестанет начисляться, без ошибки. Минимальная защита — отчёт «заказы за период, где значение `onlineManager` не сопоставлено ни с одной записью `EmployeeIdentity`». Без него сбой обнаружит сотрудник, недосчитавшийся денег.

### 3.7 Границы контекстов: дублирование против общего ядра

Решение из PRD — «service и shop считают независимо, общий код не создаём» — соответствует принятому в DDD взгляду. Аргументы за, из литературы по context mapping: shared kernel даёт высокую связанность, требует согласования изменений между владельцами контекстов и обычно рассматривается как **временная** мера при модернизации легаси, которую со временем сокращают или убирают.

**Альтернативная точка зрения, которую стоит услышать.** Полное дублирование тоже имеет цену: `PayPerHour` (`часы × ставка`) будет написан дважды, и разойдётся. Компромисс, применяемый на практике, — разделять **механику** и **политику**:

- общими делаются технические примитивы: `Money`, интерполяция порогов, порядок вычисления правил, контекст расчёта, форма результата-строки;
- доменными остаются сами правила и источники данных.

То есть общим становится не «правило PayPerHour», а базовый класс/интерфейс правила и калькулятор порогов. В проекте для этого уже есть подходящее место — `src/shared/domain/`, где лежат `entity.base.ts`, `value-object.base.ts` и прочие примитивы. Это не нарушает независимость доменов и не создаёт shared kernel в опасном смысле.

### 3.8 Деньги и округление

Тема, которой в PRD отведена одна строка («зафиксировать единицу измерения»), а в реальности это источник самых неприятных багов.

Каноническое решение — **Money pattern** Фаулера: хранить сумму целым числом в минимальных единицах и инкапсулировать правила округления в сам объект, потому что «поведение округления вещественных чисел почти никогда не соответствует нужному для денег». В `RoappOrder` / `MoySkladDemandPosition` суммы уже `Int`, что удачно — надо лишь зафиксировать, копейки это или рубли, и не выпускать «сырое» число за пределы расчёта.

Второй, менее очевидный аспект — **задача распределения (allocation)**. Она возникнет ровно в тот момент, когда премию за заказ надо разделить между онлайн- и офлайн-менеджером: 5 копеек в пропорции 70/30 дают 3.5 и 1.5, и любое независимое округление либо теряет копейку, либо создаёт лишнюю. Фаулер описывает `allocate()`, распределяющий остаток детерминированно, без потерь. Учитывая, что в iRepair один сотрудник может быть в нескольких ролях по одному заказу, эта ситуация не гипотетическая.

### 3.9 Тестирование

Из практики payroll-проектов: базовый инструмент — **характеризационные тесты (golden master)**. Фиксируется вход (набор заказов за месяц + конфигурация правил) и эталонный выход, и любой рефакторинг проверяется на неизменность результата.

Для iReports это особенно уместно, потому что зарплатные отчёты **уже существуют в компании** — в виде таблиц. Это готовый эталон: взять реальный закрытый месяц, прогнать через новый движок и сверить с тем, что бухгалтерия посчитала руками. Такой тест ловит непонимание предметной области, чего юнит-тесты на отдельные правила не делают.

Payroll Engine идёт дальше и рассматривает тесты как **исполняемую спецификацию** правил: тест пишется до реализации правила и служит документацией того, как правило должно себя вести. Учитывая, что правила расчёта в iRepair сейчас существуют только в головах и в Excel, такой формат заодно решает задачу их фиксации.

## 4. Что стоит забрать в iReports

Отсортировано по соотношению «польза / цена». Пункты 1–3 стоит решить **до** начала реализации — потом они превращаются в переписывание.

1. **Изменить контракт `SalaryRule.calculate()`**: принимать контекст расчёта, возвращать не `number`, а строку расчёта `{ ruleId, name, basis, quantity, rate, amount, sourceRefs[] }`. Без этого требование PRD о разбивке невыполнимо. *(Odoo `_get_rule_dict`)*
2. **Разделить «условие применимости» и «формулу»** на уровне контракта правила. *(Odoo `_satisfy_condition` / `_compute_rule`, ERPNext `condition` / `formula`)*
3. **Определить семантику порогов**: кумулятивные или нет. Развилка меняет суммы кратно. *(OCA `calculate_section`)*
4. **Добавить `effectiveFrom` в назначение мотивационной схемы** сотруднику/отделу. *(ERPNext `Salary Structure Assignment`)*
5. **Определить приоритет схемы сотрудника над схемой отдела** — переопределение по коду правила, а не «какая-нибудь одна». *(Payroll Engine, слои регуляций)*
6. **Хранить в снапшоте слепок конфигурации правил**, а не только итоговые суммы — дешёвая замена битемпоральности.
7. **Состояние и период действия у `EmployeeIdentity`** вместо удаления связи, плюс отчёт о несопоставленных значениях `onlineManager`.
8. **`Money` как value object** с `allocate()` для дележа премии между ролями. *(Фаулер)*
9. **Явное решение по данным, пришедшим после закрытия периода** — ретро-начисление, задержка закрытия или отчёт о расхождении.
10. **Golden master на реальном закрытом месяце** из существующих таблиц компании.
11. **Для будущего PRD по балансу — append-only реестр проводок**, не полноценный event sourcing. *(WODE)*
12. **Общими сделать примитивы, не правила**: `Money`, калькулятор порогов, контекст и форма результата — в `src/shared/domain/`.

## 5. Что копировать не стоит

- **Формулы строкой с `eval`** (Odoo `amount_select='code'`, ERPNext `formula`). Дают гибкость ценой безопасности, отладки и невозможности рефакторинга. Наличие в ERPNext утилиты `sanitize_expression`, чинящей переносы строк в формулах, — хороший индикатор того, во что это выливается.
- **Forward-chaining rules engine** для арифметики. Эти движки заточены под «условие → действие», а не под суммирование с агрегацией; цепочки правил трудно отлаживать.
- **Колоночный движок с графом зависимостей** (CaptivateIQ). Решает проблему масштаба, которой у iRepair нет.
- **Полноценная битемпоральность** на старте — пункт 6 выше даёт основную пользу дешевле.
- **Единый кросс-доменный «оркестратор» расчёта.** Решение PRD о независимости `service` и `shop` подтверждается практикой; сводить их в общий движок ради «переиспользования» — известная ошибка.

## 6. Вопросы, оставшиеся открытыми после исследования

Ни один из изученных проектов не даёт готового ответа — это решения предметной области iRepair:

- Кумулятивные пороги или нет (п. 3 выше) — решается бизнесом, не архитектурой.
- Что делать, если сотрудник числится в обеих системах и один и тот же заказ RemOnline попадает под два правила разных ролей — правила складываются, или срабатывает приоритетная роль.
- Считать ли `OrderPayed` по статусу заказа или по факту оплаты — OCA показывает, что это должно быть настройкой (`settlement_type`), но значение по умолчанию выбирает бизнес.
- Как считать прогноз продаж — линейная экстраполяция или с учётом рабочих дней и сезонности.
