# PRD: Страницы просмотра и редактирования зарплатных схем

**Дата**: 2026-08-18
**Статус**: Draft

## Терминология

В коде «зарплатное правило» из пользовательской формулировки — это **мотивационная схема** (`MotivationSchema`): цель начисления (`targetType: Department | Employee`, `targetId`) + название + набор правил (`SalaryRule[]`). Карточка на странице списка = одна мотивационная схема. «Правила внутри» = элементы массива `rules`.

## Цель

Дать администратору возможность видеть все созданные зарплатные схемы в одном месте (карточки со сводной информацией), быстро находить нужную по сотруднику, отделу или названию и переходить к её редактированию. Сейчас схемы можно только создавать вслепую — просмотреть и изменить существующие невозможно.

## Пользовательские сценарии

- Пользователь открывает «Зарплата → Правила начисления» → видит карточки всех зарплатных схем (обоих направлений: Сервис и Магазин).
- Пользователь смотрит на карточку → видит название схемы, направление (Сервис/Магазин), цель (отдел или конкретный сотрудник), количество правил в схеме и краткий состав правил (типы).
- Пользователь фильтрует список по сотруднику → видит только схемы, привязанные к этому сотруднику.
- Пользователь фильтрует список по отделу → видит только схемы этого отдела.
- Пользователь вводит текст в поиск → список фильтруется по названию схемы.
- Пользователь переключает направление (Сервис/Магазин/Все) → список фильтруется по направлению.
- Пользователь нажимает на карточку (или кнопку «Редактировать») → переходит на страницу редактирования схемы.
- Пользователь на странице редактирования меняет название схемы, добавляет/изменяет/удаляет правила → сохраняет → возвращается к списку и видит обновлённые данные.
- Пользователь нажимает «Создать схему» на странице списка → переходит на существующую страницу создания (`/salaries/rules/…`).

## В скоупе

### Backend (новые эндпоинты — сейчас есть только POST создания)

- `GET` список мотивационных схем: id, название, направление, цель (тип + id + имя отдела/сотрудника), количество и типы правил. Поддержка фильтров: направление, targetType/targetId, поиск по названию.
- `GET` схема по id со всеми правилами и их конфигурацией (для страницы редактирования).
- Обновление схемы: название, состав правил (добавление, изменение, удаление правил внутри схемы) — раздельно для `service` и `shop`, по аналогии с существующими POST.
- Контракты в `contracts/` (zod-схемы) для всех новых эндпоинтов.

### Frontend

- **Страница списка** (заменяет/расширяет текущий роут раздела): грид карточек схем.
  - Карточка: название, бейдж направления, цель (иконка + «Отдел: …» / «Сотрудник: …»), число правил («N правил»), список типов правил, дата обновления.
  - Панель фильтров: поиск по названию, селект отдела, селект сотрудника, переключатель направления.
  - Пустые состояния: «схем ещё нет» (с CTA на создание) и «ничего не найдено по фильтрам».
  - Кнопка «Создать схему» → существующая страница создания.
- **Страница редактирования** схемы: форма предзаполнена данными схемы; редактирование названия, добавление/изменение/удаление правил. Переиспользует формы правил со страницы создания (`SalaryRulesRuleFormCard` и связанную model-логику). Цель схемы (отдел/сотрудник) на редактировании отображается, но не меняется.
- Роутинг: список и редактирование по id в разделе `/salaries/…`; обновление навигации.
- Адаптив: мобильная версия списка (карточки в одну колонку) и редактирования — по паттернам существующих мобильных экранов раздела.
- Инвалидация кэша TanStack Query после сохранения.

### Дизайн

- Макеты в **Pencil** в существующем файле `design/sallary-first-iteration.pen` до начала вёрстки, с переиспользованием библиотеки «ERP · UI Kit (Atomic)» (`ERP/Atom/*`, `ERP/Molecule/*`, `ERP/Organism/*`, `ERP/Mobile/*`):
  - страница списка карточек (десктоп + мобайл), включая состояния фильтров и пустые состояния;
  - страница редактирования схемы (десктоп + мобайл).

## Не в скоупе

- Направление «Опт» (`opt`) — в кодовой базе зарплатных правил не существует.
- Удаление всей схемы целиком (удаление отдельных правил внутри схемы — в скоупе).
- Статусы схем (активна/черновик/архив) — поля статуса нет в модели; не добавляем в этой итерации.
- Изменение цели схемы (перепривязка с отдела на сотрудника и т.п.).
- История изменений / аудит.
- Копирование (дублирование) схемы.
- Пагинация списка — объём данных мал (десятки схем), грузим целиком.
- Ограничение доступа (роли, экран «Доступ запрещён», `PortalAdminGuard`) — в этой итерации страницы доступны всем; закроем доступы отдельной итерацией.

## Технические ограничения

- Backend хранит правило как `SalaryRule.props Json` — при чтении для редактирования конфиг нужно валидировать контрактами; направление лежит на уровне `SalaryRule.direction`, а не схемы, поэтому направление схемы для карточки выводится из её правил.
- Наборы типов правил у `service` и `shop` разные и несмешиваемые — страница редактирования должна работать с обоими наборами форм.
- Существующий POST работает как find-or-create по `(targetType, targetId)` — при появлении редактирования это поведение нужно учесть, чтобы создание не «дописывало» правила в существующую схему неожиданно для пользователя.
- Имена отделов/сотрудников для карточек берутся из справочника Bitrix (`GET /v1/directory/departments|employees`) — на карточке отображаем имя, а не голый `targetId`.

## Критерии готовности

- [ ] В Pencil-файле `design/sallary-first-iteration.pen` есть согласованные макеты списка и редактирования (десктоп + мобайл).
- [ ] `GET` списка схем возвращает все схемы обоих направлений с названием, направлением, целью (с именем из справочника), количеством и типами правил.
- [ ] `GET` схемы по id возвращает полные данные всех правил, достаточные для предзаполнения форм редактирования.
- [ ] Эндпоинт обновления сохраняет изменение названия, добавление, изменение и удаление правил; изменения видны при повторном `GET`.
- [ ] На странице списка отображаются карточки всех схем; фильтры по отделу, сотруднику, направлению и поиск по названию работают и комбинируются.
- [ ] Пустые состояния (нет схем / ничего не найдено) отображаются корректно.
- [ ] Клик по карточке открывает страницу редактирования с предзаполненными данными этой схемы.
- [ ] После сохранения на странице редактирования пользователь видит актуальные данные в списке без перезагрузки страницы (инвалидация кэша).
- [ ] Кнопка «Создать схему» ведёт на существующую страницу создания.
- [ ] Мобильная версия обеих страниц соответствует макетам.
