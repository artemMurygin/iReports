# PRD: Расчёт заработной платы сотрудников (сервис и магазин)

**Дата**: 2026-08-10
**Статус**: Draft
**Источники**: EventStorming-доска [SalaryReport](https://miro.com/app/board/uXjVH2hS6p0=/), модуль `backend/src/domains/service/modules/accounting`, пакет `contracts`

---

## Цель

Дать руководителю возможность собирать гибкую систему мотивации (набор зарплатных правил) для отдельного сотрудника или целого отдела и автоматически считать по ней зарплату на основании данных из ERP — RemOnline для сервиса и МойСклад для магазина. Сотрудник в любой момент видит свою текущую зарплату за месяц, прогноз до конца месяца и понимает, из чего они сложились и как на них влияет выполнение плана продаж.

Итерация закрывает фундамент: единую идентификацию сотрудника между Bitrix24 / RemOnline / МойСклад, работающие методы расчёта для всех типов зарплатных правил, расчётный период с заморозкой закрытого месяца и сущность плана продаж, без которой не считается ни одно процентное правило.

## Пользовательские сценарии

### Идентификация сотрудника

> Весь блок доступен **только администратору портала Bitrix24**. Руководитель, не являющийся администратором портала, страниц управления связями не видит и соответствующих эндпоинтов вызвать не может.

- Администратор портала открывает карточку сотрудника → видит его связи с внешними системами: ID в RemOnline, ID в МойСкладе, значение кастомного поля «онлайн-менеджер» в RemOnline.
- Администратор портала добавляет сотруднику связь «RemOnline, ID 412» → сотрудник опознаётся во всех данных RemOnline, где встречается этот ID, независимо от того, в каком качестве он там указан.
- Администратор портала заводит сотруднику второй идентификатор в той же системе (например, значение строкового поля «онлайн-менеджер» в RemOnline вдобавок к его ID сотрудника) → расчёт видит обе привязки.
- Администратор портала открывает список сотрудников без сопоставления → видит, кто из сотрудников Bitrix ещё не связан ни с одной внешней системой, и может это исправить.
- Руководитель (не администратор портала) пытается открыть управление связями → пункт меню недоступен, прямой переход по ссылке и прямой вызов API отклоняются.

### Мотивационные схемы и зарплатные правила

- Руководитель открывает страницу создания правила мотивации → выбирает цель (сотрудник или отдел), направление (сервис или магазин), добавляет одно или несколько зарплатных правил → схема сохранена и применяется к следующему расчёту.
- Руководитель добавляет в схему правило «процент от маржи» и рядом фиксированный бонус за выполненную задачу → в расчёте суммируются оба правила.
- Руководитель при создании правила указывает, за какую роль оно платит («инженер», «онлайн-менеджер», «менеджер заказа») → правило само знает, какие данные ERP по этой роли брать и как посчитать свой KPI.
- Руководитель заводит одному сотруднику два правила с разными ролями (инженер + онлайн-менеджер) → сотрудник получает вознаграждение по обоим правилам, при этом одна и та же сумма не начисляется дважды.
- Сотрудник часть месяца работал инженером, часть — онлайн-менеджером → ничего перенастраивать не нужно: правила отработают ровно по тем заказам, где сотрудник указан в соответствующей роли.
- Руководитель редактирует правило в открытом месяце → зарплата за текущий месяц пересчитывается по новой версии правила.
- Руководитель редактирует правило после закрытия месяца → зарплата закрытого месяца не меняется.
- Руководитель удаляет мотивационную схему → она перестаёт применяться к открытым периодам, но снапшоты закрытых месяцев остаются нетронутыми.
- Руководитель запрашивает список доступных типов зарплатных правил → получает типы, доступные именно для выбранного направления (набор правил сервиса и магазина различается).

### План продаж (PlanFact)

- Руководитель открывает страницу создания плана продаж → задаёт на месяц по отделу и, опционально, по категории плановый оборот и плановую маржу → план сохранён.
- Руководитель открывает страницу выполнения плана продаж → видит план, факт, процент выполнения и прогноз до конца месяца по каждому отделу и категории.
- Руководитель меняет план продаж в открытом месяце → факт и прогноз пересчитываются, зарплаты сотрудников с процентными правилами меняются соответственно.
- Руководитель удаляет план продаж → факт и прогноз по нему удаляются.
- Наступает первое число месяца → крон создаёт планы по всем отделам и категориям, прибавив 10 % к значениям предыдущего месяца. Руководителю не нужно заводить их заново, план месяца из коробки не пустой.
- Руководитель неделю не доходит до плана → расчёты всё это время идут по автоматически созданному плану в статусе «Создан», зарплаты считаются, отчёты не падают.
- Руководитель открывает план месяца → видит по каждой строке статус («Создан» / «Утверждён») и источник значения (из прошлого месяца, из шаблона, вручную).
- Руководитель проверяет цифры и утверждает план — построчно или весь месяц сразу → строки переходят в статус «Утверждён», плашка «план не утверждён» в отчётах пропадает.
- Руководитель правит план на конкретный месяц (сезонный всплеск, разовая акция) → меняется только этот месяц, следующий месяц отсчитывается уже от новых значений.
- Руководитель правит уже утверждённую строку → она возвращается в статус «Создан» и требует повторного утверждения.
- Руководитель пытается закрыть месяц с неутверждёнными строками плана → закрытие отклоняется со списком того, что осталось утвердить.
- Руководитель редактирует дефолтный шаблон → новые значения применяются к будущим месяцам, где нет плана предыдущего месяца; уже созданные планы открытых и закрытых месяцев не меняются.

### Расчёт и просмотр зарплаты

- Сотрудник открывает отчёт по своей зарплате за текущий месяц → видит две суммы рядом: **фактическую** зарплату, заработанную на сегодня, и **прогнозную** — сколько выйдет к концу месяца, если динамика продаж сохранится. Ниже — разбивка по каждому правилу схемы с указанием, на каких заказах/продажах она получена.
- Сотрудник смотрит разбивку по правилам → у каждого правила тоже видит пару «факт / прогноз», а не только текущее значение: понятно, какое правило сколько даст к концу месяца.
- Сотрудник видит в отчёте компактный блок плана продаж — план, факт и процент выполнения по своему отделу (и категории, если правило завязано на категорию) → понимает, почему прогноз именно такой и что нужно дотянуть до следующего порога.
- Сотрудник с правилом `FloatPercent` не дотягивает до следующего порога → в компактном блоке видно, до какого порога и сколько осталось по обороту/марже, и как изменится прогноз при его достижении.
- Сотрудник, работающий и в сервисе, и в магазине, открывает отчёт → видит два независимых расчёта (по каждому направлению отдельно), каждый со своей парой «факт / прогноз» и своим блоком плана, и общую сумму по обоим направлениям. Справа видит отдельное меню в котором отображается факт по всем правилам.
- Сотрудник открывает отчёт за закрытый месяц → прогноз не показывается, остаётся только зафиксированный факт.
- Руководитель открывает отчёт по зарплатам отдела за месяц → видит по каждому сотруднику общую сумму и раскрывающуюся разбивку по каждому его зарплатному правилу, плюс итог по отделу. Для открытого месяца рядом с фактом показывается прогноз — и по сотруднику, и по отделу.
- Руководитель закрывает расчётный период по направлению «сервис» → зарплаты сервиса за этот месяц фиксируются снапшотом и больше не пересчитываются; период магазина при этом остаётся открытым.
- Сотрудник открывает зарплату за закрытый месяц → видит зафиксированные цифры, идентичные тем, что были на момент закрытия.
- Руководитель нажимает «пересчитать» на открытом периоде → кэш сбрасывается и расчёт выполняется заново по актуальным данным.

## В скоупе

### 1. Идентификация сотрудника между системами

- Новая сущность `EmployeeIdentity` — связь «сотрудник Bitrix × внешняя система × внешний идентификатор», many-to-many. Один сотрудник может иметь несколько записей: разные системы и, при необходимости, несколько идентификаторов в одной системе.
- **Роли в идентификации не хранятся.** Сотрудник в течение месяца свободно работает то инженером, то менеджером, поэтому привязывать роль к человеку нельзя — она бы устаревала на следующий день. Идентификация отвечает только на вопрос «кто этот человек во внешней системе», а роль — атрибут зарплатного правила (см. п. 2).
- Поддерживаемые системы: `ROAPP` (RemOnline), `MOY_SKLAD` (МойСклад).
- Внешний идентификатор хранится как строка, потому что в RemOnline онлайн-менеджер проставляется кастомным полем со **строковым значением** (`RoappOrder.onlineManager`), а не ссылкой на ID сотрудника, тогда как в МойСкладе это ссылка на сущность сотрудника (`MoySkladDemand.onlineManagerId`).
- У записи есть технический тип идентификатора (`EMPLOYEE_ID` — ссылка на сотрудника в ERP, `ONLINE_MANAGER_FIELD` — значение строкового кастомного поля RemOnline). Это описание того, **где в ERP лежит значение**, а не роль сотрудника: правило, оплачивающее роль онлайн-менеджера в RemOnline, знает, что искать человека нужно по идентификатору типа `ONLINE_MANAGER_FIELD`.
- Bitrix-сотрудник — основная сущность и единственный источник истины о человеке. Все расчёты адресуют сотрудника через него.
- Существующие поля `BitrixEmployee.roappId`, `BitrixEmployee.moySkladId`, `BitrixEmployee.roappOnlineName` мигрируются в `EmployeeIdentity` и помечаются как устаревшие.
- CRUD-экран управления связями и список сотрудников без сопоставления.
- **Доступ:** все операции блока (чтение, создание, изменение, удаление связей и список несопоставленных сотрудников) разрешены **только администратору портала Bitrix24** — не руководителю. Ограничение реализуется на бэкенде гардом, а не только скрытием пунктов в UI: фронтенд прячет вкладку, бэкенд отдаёт `403` любому неадминистратору.
- Признак «администратор портала» берётся из Bitrix24 (метод REST `user.admin` / флаг `IS_ADMIN` в контексте установленного приложения) и не хранится как самостоятельная роль в iReports — источник истины по правам остаётся за порталом.

### 2. Зарплатные правила сервиса — реализация расчёта

Реализовать метод `calculate()` для всех типов правил домена `service` (сейчас это заглушки или пустые файлы):

| Тип правила | Что считает | Статус кода |
|---|---|---|
| `PayPerHour` | `hours × price` | реализовано, требует источник часов вместо ручного ввода |
| `ServiceCompleted` | вознаграждение за выполненную услугу: `Fixed` (фикс. сумма), `ServiceFixed` (ставка из справочника услуги), `ServicePercent` (процент от стоимости услуги) | `calculate()` возвращает константу `10` — заглушка |
| `OrderPayed` | вознаграждение за оплаченный заказ: `Fixed`, `FixedPercent` (процент от базы), `FloatPercent` (плавающий процент по порогам выполнения плана) | файл сущности пустой |
| `TaskCompleted` | вознаграждение за выполненную задачу: `Fixed`, `FloatPercent` | файл сущности пустой |

- **Роль — атрибут правила, а не сотрудника.** Каждое правило хранит `targetRole` — роль, за которую оно платит (`ENGINEER`, `ONLINE_MANAGER`, `OFFLINE_MANAGER`, `ORDER_MANAGER`, `CREATED_BY`, `CLOSED_BY`; набор расширяемый и свой для каждого направления). Правило само знает три вещи: какой роли оно соответствует, по какому полю ERP искать сотрудника в этой роли и как из найденных данных посчитать свой KPI. Расчёт зарплаты не спрашивает «какие роли у сотрудника» — он берёт сотрудника, берёт его зарплатные правила и по каждому правилу проверяет, где сотрудник встречается в данных периода.
- Следствие: правило `ENGINEER` считает по позициям заказов, где сотрудник указан как инженер, правило `ONLINE_MANAGER` — по заказам, где совпало значение его строкового идентификатора, и так далее. Один и тот же сотрудник в разные дни месяца может попадать под разные правила без каких-либо перенастроек.
- Один заказ, где сотрудник выступил сразу в двух ролях, обрабатывается двумя правилами независимо, но каждое правило берёт свою базу начисления, поэтому одна и та же сумма не оплачивается дважды. Для правил с одинаковой базой и пересекающейся выборкой действует дедупликация по паре «правило × источник (заказ/позиция/продажа)».
- База начисления (`salaryBasis`) для `OrderPayed`: `REVENUE` (выручка), `MARGIN` (маржа), `SALARY_MINUS_ENGINEER_SALARY` (сумма за вычетом зарплаты инженера).
- `FloatPercent` использует три порога (`percentBorders`), каждый — `{ fromPlanPercent, multiplier, mode: FIX | LINEAR }`. `FIX` даёт множитель ступенькой при достижении порога, `LINEAR` — линейную интерполяцию между порогами.
- Каждое правило дополнительно принимает необязательный индивидуальный бонус (разовая надбавка за задачу), не меняющий тип правила.
- Правило `TaskCompleted` добавляется в `salaryRuleRegistry`, `SalaryRuleFactory` и в `discriminatedUnion` контрактов — сейчас его там нет.
- `targetRole` добавляется в контракты как поле правила (общее для всех типов, рядом с `type` и `name`), и в список типов правил, отдаваемый фронтенду, входит перечень допустимых для типа ролей.

#### Контекст расчёта

Текущая сигнатура `calculate(): number | Promise<number>` не принимает аргументов и не позволяет посчитать ничего, кроме почасовой ставки: правилу неоткуда узнать, какому сотруднику оно считает, за какой период и какие заказы попали в выборку. Сигнатура меняется на приём **единого объекта контекста**.

Контекст собирается **один раз на весь расчёт** — оркестратором расчёта периода, а не каждым правилом по отдельности — и передаётся во все правила схемы неизменным. Правило не обращается к репозиториям и не ходит в БД само: оно получает всё необходимое из контекста. Это даёт три вещи: отсутствие N+1 при расчёте отдела, возможность тестировать правило чистой функцией без поднятия инфраструктуры и одинаковую выборку данных для всех правил одного сотрудника.

Состав контекста:

| Что | Зачем |
|---|---|
| Сотрудник и его связи `EmployeeIdentity` | правило ищет себя в данных ERP по идентификатору нужной ему роли |
| Период: границы дат, направление, статус `OPEN`/`CLOSED` | выборка данных и запрет пересчёта закрытого месяца |
| Данные ERP за период | заказы/позиции сервиса или отгрузки/позиции магазина — уже загруженные, а не запрашиваемые правилом |
| `SalesPerformance` за период | план, факт, прогноз — вход для правил с процентом от выполнения плана |
| Режим расчёта: `FACT` или `PROGNOSE` | в режиме прогноза правило получает прогнозный процент выполнения вместо фактического (см. раздел о прогнозе) |

Что в контекст **не** входит:

- **Роль.** Она лежит в самом правиле (`targetRole`) — правило знает, за какую роль платит, и само решает, где искать сотрудника в данных.
- **Другие правила схемы и их результаты.** В этой итерации правила независимы и их результаты складываются; правило не может ссылаться на результат другого правила. Если такая потребность появится (например, «10 % от суммы всех предыдущих начислений»), в контекст добавляется доступ к уже вычисленным правилам, а в модель правила — поле порядка вычисления. Закладывать это сейчас не нужно, но и исключать архитектурно не следует.

**Результат `calculate()` — не число, а строка расчёта.** Сценарий «сотрудник видит разбивку по каждому правилу с указанием, на каких заказах она получена» невыполним при возврате скаляра. Правило возвращает объект вида «правило, база начисления, количество, ставка, сумма, ссылки на источники (заказы/позиции/продажи)». Итог по сотруднику — сумма таких строк, и он же ложится в снапшот при закрытии периода.

Форма контекста и форма результата одинаковы для `service` и `shop` — различается только наполнение (какие данные ERP и какие роли). Сами интерфейсы контекста и строки расчёта — технические примитивы без бизнес-логики, поэтому их место в `src/shared/domain/`, а не в доменных модулях; это не нарушает независимость доменов, описанную в разделе «Архитектура».

### 3. Зарплатные правила магазина

- Модуль `accounting` в домене `shop` по образцу `domains/service/modules/accounting` (сейчас в `domains/shop` нет ни одного модуля — только `integrations` и `sync`).
- Собственный набор типов правил, отличный от сервиса, со своим реестром и фабрикой. Общий код с сервисом не переиспользуется — зеркальные, но независимые модули.
- Источник данных для расчёта — `MoySkladDemand` / `MoySkladDemandPosition` (отгрузки, позиции, себестоимость, прибыль, онлайн- и офлайн-менеджер).

#### Роли магазина

| Роль | Где лежит в ERP | Смысл |
|---|---|---|
| `ONLINE_MANAGER` | `MoySkladDemand.onlineManagerId` | продажа оформлена онлайн-менеджером (заявка с сайта, мессенджеры) |
| `OFFLINE_MANAGER` | `MoySkladDemand.offlineManagerId` | продажа в торговой точке, продавец-консультант |
| `ONLINE_PURCHASER` | доп. поле товарной позиции | онлайн-закупщик БУ техники — кто выкупил устройство удалённо |
| `OFFLINE_PURCHASER` | доп. поле товарной позиции | офлайн-закупщик БУ техники — кто принял и выкупил устройство в точке |

Принципиальное различие: **менеджеры продажи лежат на уровне отгрузки, закупщики — на уровне товарной позиции.** Продавец один на всю отгрузку, а закупщик у каждого БУ-устройства свой: в одном чеке могут оказаться два бывших в употреблении айфона, выкупленные разными людьми.

`ONLINE_MANAGER` / `OFFLINE_MANAGER` — нормальные внешние ключи на `MoySkladEmployee`, сопоставление надёжное. Закупщики приходят доп. полями МойСклада, и их значения предстоит сопоставлять с `EmployeeIdentity` тем же механизмом. Роль инженера в магазине отсутствует.

#### Типы правил

В первой итерации магазина — четыре типа правил:

| Тип правила | Что считает | Варианты `award` | Источник данных |
|---|---|---|---|
| `PayPerHour` | `hours × price` — оплата по часам | — | ручной ввод часов (график работы вне скоупа) |
| `ProductSold` | вознаграждение за проданный товар в категории | `Fixed` — сумма за единицу; `FixedPercent` — процент от базы позиции; `FloatPercent` — процент от базы с множителем по порогам выполнения плана продаж | `MoySkladDemandPosition` + `MoySkladProduct.folderId` |
| `UsedProductSold` | вознаграждение закупщику за продажу выкупленной им БУ техники | `Fixed` — сумма за единицу; `FixedPercent` — процент от базы позиции | `MoySkladDemandPosition` + доп. поле закупщика |
| `TaskCompleted` | вознаграждение за выполненную задачу | `Fixed`; `FloatPercent` | задача (как в сервисе) |

- **Категория — обязательная часть `ProductSold`**: правило задаётся парой «категория × награда», потому что процент за аксессуары и процент за технику разные. Категория указывается папкой `MoySkladProductFolder`, под правило попадают все её потомки (дерево `parentId` / `pathName`). Правило без категории означает «все товары».
- **База начисления (`salaryBasis`) магазина**: `REVENUE` (`MoySkladDemandPosition.sum`) и `MARGIN` (`MoySkladDemandPosition.profit`). `SALARY_MINUS_ENGINEER_SALARY` в магазине не существует.
- `FloatPercent` привязан к плану/факту продаж: множитель берётся по проценту выполнения плана из `SalesPerformance` домена `shop`. Пороги те же три (`percentBorders` с `fromPlanPercent`, `multiplier`, `mode: FIX | LINEAR`), но это **независимая реализация** в домене `shop`, а не переиспользованный код сервиса.
- Каждое правило магазина, как и в сервисе, принимает необязательный индивидуальный бонус.
- Правило `ProductSold` считает только те позиции, чья отгрузка содержит сотрудника в поле, соответствующем `targetRole` правила. Одна и та же отгрузка может оплачиваться и онлайн-, и офлайн-менеджеру — это два разных человека и два разных правила, двойным начислением не считается. Если один сотрудник указан в отгрузке в обоих полях, применяется дедупликация по паре «правило × позиция».
- Позиция попадает в период по `MoySkladDemand.moment` своей отгрузки. Частичная оплата (`payedSum < sum`) в этой итерации не учитывается — расчёт идёт по факту отгрузки.

#### Закупщики БУ техники (`UsedProductSold`)

Компания одновременно магазин и сервисный центр, поэтому заметная часть продаж — бывшая в употреблении техника, выкупленная у клиентов. Деньги за неё получает не только продавец, но и закупщик, который эту технику нашёл и выкупил.

- Роль правила — `ONLINE_PURCHASER` или `OFFLINE_PURCHASER`. Правило считает те позиции, где в доп. поле закупщика указан сотрудник, соответствующий его `targetRole`.
- Начисление **за единицу проданного устройства** или процентом от базы позиции: `Fixed` и `FixedPercent`. `FloatPercent` для закупщиков не предусмотрен — их вознаграждение не привязано к выполнению плана продаж.
- Базы те же, что у `ProductSold`: `REVENUE` (`MoySkladDemandPosition.sum`) и `MARGIN` (`MoySkladDemandPosition.profit`). Для БУ техники маржа — основная база: она отражает разницу между ценой выкупа и ценой продажи, то есть качество работы закупщика.
- Момент начисления — **продажа**, а не выкуп: закупщик получает вознаграждение, когда выкупленное им устройство продано и попало в отгрузку периода. Позиции невыкупленного/непроданного остатка в расчёт не идут.
- Одна и та же позиция порождает начисления и продавцу (`ProductSold`), и закупщику (`UsedProductSold`) — это разные люди и разные правила, двойным начислением не считается. Дедупликация нужна лишь в вырожденном случае, когда продавец и закупщик — один сотрудник и правила бьют по одной паре «правило × позиция».
- Как и у `ProductSold`, у правила есть необязательная категория: ставка за БУ айфон и за БУ ноутбук может отличаться.

**Требуется расширение синхронизации.** Ни `MoySkladProduct`, ни `MoySkladDemandPosition` сейчас не хранят закупщиков, а `products.schema.ts` вообще не читает `attributes` из МойСклада (в отличие от `demands.schema.ts`, где доп. поля уже разбираются). До реализации правила нужно: научить синк читать доп. поля товара/позиции, добавить поля в схему Prisma и мигрировать историю — без этого расчёт по закупщикам работать не будет.

Остальные обсуждавшиеся правила магазина (за отгрузку целиком, за проданную услугу, премия за достижение планки плана) и фильтр по каналу продаж — вне этой итерации, см. «Не в скоупе».

### 4. Расчётный период (`AccountingPeriod`)

- Сущность периода: направление (`service` / `shop`), месяц, статус `OPEN` / `CLOSED`, кто и когда закрыл.
- Периоды сервиса и магазина закрываются **независимо друг от друга**.
- Открытый период: зарплата считается в рантайме по данным локальной БД (уже синхронизированной из ERP).
- Ленивый кэш результата по ключу `(направление, период, сотрудник, версия мотивационной схемы)` со штампом последней успешной синхронизации домена. Кэш отдаётся, если штамп и версия схемы совпадают с текущими; иначе — пересчёт с перезаписью. Ручное принудительное «пересчитать» доступно руководителю.
- Закрытие периода создаёт снапшот: зафиксированные суммы по каждому сотруднику с разбивкой по правилам. Снапшот неизменяем и после закрытия отдаётся вместо расчёта.
- Событие `Месяц закрыт` → формирование `salaryReport` за месяц.
- Повторное открытие закрытого периода — только руководителем, с явным подтверждением и удалением снапшота.

### 5. План и факт продаж (PlanFact)

Отдельный модуль в каждом домене (`service`, `shop`), сущности по схемам с доски:

- `SalesPlanTemplate` — **дефолтный шаблон плана**: `{ direction, department, category (nullable), turnover, margin, growthPercent }` без привязки к периоду, уникальность по `(direction, department, category)`. Используется как стартовые значения для самого первого месяца и как запасной вариант, если плана за предыдущий месяц нет. `growthPercent` — процент, на который автоматически растёт план от месяца к месяцу, по умолчанию **10 %**.
- `SalesPlan` — `{ direction, department, category (nullable), period, turnover, margin, source: PREVIOUS_MONTH | TEMPLATE | MANUAL, status: CREATED | APPROVED, approvedBy, approvedAt }`, уникальность по `(direction, department, category, period)`.
- `SalesFact` — `{ period, department, category, turnover, margin, marginPercent, cost, quantity, averageCheck, percentCompletion }`, считается по данным ERP.
- `SalesPrognose` — прогноз до конца месяца: `{ turnover, margin, marginPercent, quantity, percentCompletion }`.
- `SalesPerformance` — агрегат `{ period, department, category, plan, fact, prognose }` для страницы выполнения плана.
- Изменение плана → пересчёт факта и прогноза. Удаление плана → удаление факта и прогноза.
- Зарплатные правила с процентом от выполнения плана читают `SalesPerformance` как вход расчёта.

#### Автоматическое создание плана на месяц

Первого числа каждого месяца крон создаёт планы на новый период — руководителю не нужно заводить их руками:

- Для каждой комбинации `(direction, department, category)` берётся **план** предыдущего месяца (именно план, не факт — решение зафиксировано) и увеличивается на `growthPercent` (по умолчанию +10 %) по обороту и по марже. Источник новой строки — `source = PREVIOUS_MONTH`.
- Если плана за предыдущий месяц нет (новый отдел, первый запуск), строка создаётся из `SalesPlanTemplate` без надбавки, `source = TEMPLATE`.
- Все созданные кроном строки получают статус `CREATED`.
- Крон **идемпотентен**: повторный запуск в том же месяце не создаёт дублей, не перезатирает уже утверждённые строки и не трогает строки, отредактированные руководителем вручную.
- Крон оборачивается в `@ProdCron` и реально тикает только в проде, поэтому дополнительно предусмотрен ленивый запуск: при первом обращении к периоду, для которого планов нет, они достраиваются по той же логике. Без этого в dev-среде и после простоя план был бы пустым.

#### Статус плана: `CREATED` → `APPROVED`

План живёт в двух состояниях, и это разделение существует ровно затем, чтобы расчёты не ждали руководителя:

- `CREATED` — план создан автоматически. **Он полноценно участвует в расчётах**: проценты выполнения считаются, зарплатные правила с `FloatPercent` работают, отчёты не падают. Это и есть «хоть какой-то план» на время, пока руководитель не дошёл до утверждения.
- `APPROVED` — руководитель проверил цифры и утвердил их. Менять статус может **только руководитель**; автоматически план не утверждается никогда.
- Руководитель правит значения плана в любом статусе. Ручная правка переводит строку в `source = MANUAL`; статус при этом сбрасывается в `CREATED`, если строка была утверждена, — утверждать нужно то, что видишь.
- Пока план в статусе `CREATED`, отчёты по зарплате помечаются признаком «план не утверждён, цифры предварительные». Признак едет в ответе отчёта, чтобы UI мог показать плашку.
- Утверждение и любое изменение плана инвалидируют кэш зарплатного расчёта — суммы пересчитываются по новым цифрам.
- **Закрыть расчётный период с неутверждёнными планами нельзя**: закрытие фиксирует зарплаты снапшотом, а значит план, по которому они посчитаны, должен быть подтверждён человеком. При попытке закрыть период система показывает список неутверждённых строк.
- Утверждение доступно и построчно, и массово («утвердить весь месяц по направлению»).

### 6. Зарплатный отчёт сотрудника: факт и прогноз

Отчёт сотрудника за открытый месяц отдаёт **две суммы**: фактическую и прогнозную.

**База начисления в обеих суммах одна и та же — фактические продажи сотрудника на сегодня.** Отличается только множитель, зависящий от выполнения плана продаж:

```
Факт    = множитель(текущий % выполнения плана)   × фактические продажи сотрудника
Прогноз = множитель(прогнозный % выполнения плана) × фактические продажи сотрудника
```

- Личная база сотрудника (его заказы, услуги, часы) **не экстраполируется** — прогноз не додумывает продажи, которых ещё не было. Прогноз отвечает на вопрос «сколько я получу за уже сделанное, если отдел закроет месяц с ожидаемым процентом выполнения плана», а не «сколько я заработаю, если продолжу в том же темпе».
- Следствие: прогноз выше факта, когда отдел идёт к более высокому порогу выполнения плана, и ниже — когда прогноз выполнения хуже текущего процента. При достижении сотрудником конца месяца факт и прогноз сходятся.
- Технически прогноз считается тем же `calculate()` в режиме прогноза: правило получает `SalesPrognose.percentCompletion` вместо `SalesFact.percentCompletion`, всё остальное в контексте расчёта идентично. Отдельной ветки расчёта под прогноз нет.
- Для правил, не зависящих от выполнения плана (`Fixed`, `FixedPercent`, `PayPerHour`, `ServiceFixed`, `ServicePercent`), факт и прогноз совпадают — множитель от плана в них не участвует.
- Пара «факт / прогноз» отдаётся и в итоге, и в разбивке по каждому правилу схемы.
- Прогноз имеет смысл прежде всего для `FloatPercent`: при прогнозном проценте правило может попасть в другой порог, чем сейчас. Ответ содержит текущий порог, следующий порог и разницу до него, чтобы UI мог показать «до следующего порога осталось N по обороту».
- Прогноз рассчитывается **только для открытого периода**. Для закрытого отдаётся факт из снапшота, поле прогноза пустое — снапшот прогноз не хранит.
- В ответе отчёта — компактный срез `SalesPerformance` по отделу сотрудника (и по категории, если правила схемы завязаны на категорию): план, факт, процент выполнения, прогноз. Отдельных запросов с фронтенда за планом не требуется.
- Компактный блок плана строится из тех же `SalesPlan` / `SalesFact` / `SalesPrognose` — дублирующего расчёта плана внутри зарплатного модуля нет, данные читаются из модуля `sales` через порт.
- Прогноз попадает в тот же ленивый кэш, что и факт: обе величины считаются за один проход и инвалидируются одними и теми же событиями.
- Отчёт по отделу — тот же расчёт, агрегированный по сотрудникам отдела: по каждому сотруднику общая сумма и разбивка по его зарплатным правилам, сверху итог по отделу. Отдельной «свёрнутой» логики расчёта для отдела нет — берётся результат по каждому сотруднику и суммируется.
- Разбивка по правилу в обоих отчётах (сотрудника и отдела) содержит: название и тип правила, роль (`targetRole`), сумму, применённый процент/множитель для процентных правил и ссылки на источники — заказы, позиции или продажи, на которых сумма получена.

### 7. Фронтенд

Отдельная вкладка рядом с дашбордами. Страницы:

- Создание мотивационной схемы / зарплатного правила.
- Редактирование и удаление мотивационной схемы.
- Отчёт по зарплате сотрудника: факт и прогноз на месяц, разбивка по правилам (тоже с парой «факт / прогноз»), компактный блок план/факт продаж; для закрытых месяцев — только зафиксированный факт.
- Отчёт по зарплатам отдела за месяц: строка на сотрудника с общей суммой, раскрывающаяся в суммы по каждому его зарплатному правилу, и итог по отделу.
- Редактирование дефолтного шаблона плана продаж и процента ежемесячного роста.
- План продаж на месяц: правка значений, статус каждой строки («Создан» / «Утверждён»), источник значения (прошлый месяц / шаблон / вручную), утверждение построчно и «утвердить весь месяц».
- Просмотр выполнения плана продаж (план / факт / прогноз), с действием «закрыть месяц»; при неутверждённых строках закрытие блокируется с их перечнем.
- Управление связями сотрудника с внешними системами — **только для администратора портала Bitrix24**; для остальных пользователей раздел скрыт из навигации, а прямой переход по URL ведёт на экран «нет доступа».

### 7. Контракты

Схемы Zod в пакете `ireports-contracts` обновляются **первыми** — для типов правил магазина (`PayPerHour`, `ProductSold`, `UsedProductSold`, `TaskCompleted` — отдельным `discriminatedUnion`, не смешанным с сервисным), `targetRole` в зарплатном правиле, `EmployeeIdentity`, `AccountingPeriod`, `SalesPlanTemplate` / `SalesPlan` / `SalesFact` / `SalesPrognose` / `SalesPerformance` и ответов зарплатного отчёта.

Ответ отчёта сотрудника: `{ period, isClosed, directions: [{ direction, total: { fact, prognose }, rules: [{ ruleId, type, name, targetRole, amount: { fact, prognose }, appliedPercent?, sources[] }], salesPerformance, isPlanApproved }], grandTotal: { fact, prognose } }`. Ответ отчёта отдела: `{ period, isClosed, department, employees: [{ employeeId, name, total: { fact, prognose }, rules: [...] }], total: { fact, prognose } }`. У закрытого периода поля `prognose` не заполняются.

## Не в скоупе

Всё перечисленное — отдельные PRD, зависящие от этого.

- **Баланс сотрудника и начисление зарплаты** (`salaryAccrual` → `employeeBalance`): формирование начислений при закрытии месяца, подтверждение начисления руководителем, лента движений по балансу с восстановимой историей начислений и депремирований (event sourcing), страница баланса.
- **Выплата и расходные документы**: создание расхода с баланса сотрудника и его синхронизация обратно в RemOnline / МойСклад.
- **Отчёт по оборачиваемости** (`stockReport`) и расчёт зарплаты отдела закупок на его основе.
- **График работы**: внесение сотрудниками переработок и блокировка графика при закрытии месяца. До его появления часы для правила `PayPerHour` вводятся вручную.
- **Возвраты** и их влияние на уже начисленную зарплату.
- **Автоматический онбординг сотрудника**: автоматическое сопоставление по ФИО, реакция на появление нового сотрудника в RemOnline / МойСкладе, изменение структуры кастомных полей в ERP. В этой итерации связи заводятся руками.
- **Остальные типы правил магазина**: вознаграждение за отгрузку целиком (`DemandPayed`), за проданную услугу магазина (`ServiceSold`), разовая премия за достижение планки выполнения плана (`PlanCompleted`), правила от среднего чека и глубины чека. В первой итерации магазина — только `PayPerHour`, `ProductSold` и `TaskCompleted`.
- **Фильтр по каналу продаж** (`MoySkladDemand.salesChannelId`) в правилах магазина.
- **Учёт частичной оплаты** отгрузки (`payedSum`) — расчёт магазина идёт по факту отгрузки.
- **Направление `opt`** (оптовые продажи) — домен пустой, зарплатных правил нет.
- **Единый кросс-доменный расчёт**: сервис и магазин считают зарплату независимо, единого «оркестратора» расчёта не создаём. Суммирование по двум направлениям происходит только на уровне отображения.
- **Миграция legacy-модуля `salary`** и `src/TODO/reports` — старый модуль продолжает существовать параллельно.

## Технические ограничения

### Идентификация сотрудника и роли правил

- В RemOnline онлайн-менеджер хранится в кастомном поле как **строка** (`RoappOrder.onlineManager String?`), а не как ссылка на `RoappEmployee`. Сопоставление возможно только по значению строки — она должна быть уникальной и стабильной; изменение подписи в справочнике RemOnline ломает связь.
- В МойСкладе онлайн- и офлайн-менеджер — нормальные внешние ключи на `MoySkladEmployee` (`onlineManagerId`, `offlineManagerId`), сопоставление надёжнее.
- В `RoappOrder` роли распределены по трём полям: `managerId`, `createdById`, `closedById`; инженер — на уровне позиции заказа (`RoappServiceOrder.engineerId`, `RoappProductsOrder.engineerId`). Правило должно явно указывать, какую роль оно оплачивает, и знать соответствующее ей поле ERP.
- Роль сотрудника **не фиксируется ни в одной сущности iReports** — она существует только как факт «в этом заказе/позиции указан такой-то сотрудник в таком-то поле». Сотрудник может месяц работать инженером, а с середины месяца — онлайн-менеджером; никаких переключений в системе для этого не требуется.
- Соответствие «роль правила → поле ERP» — часть кода правила (домен), а не конфигурируемая пользователем настройка: маппинг зависит от структуры данных ERP, а не от бизнес-решений руководителя.
- Один сотрудник может выступать в нескольких ролях по одному заказу — необходимо исключить двойное начисление одной и той же суммы (дедупликация по паре «правило × источник»).
- Существующие поля-связи в `BitrixEmployee` объявлены `@unique`, что запрещает несколько ID в одной системе — это одна из причин перехода на `EmployeeIdentity`.
- В проекте сейчас нет модели прав: ни флага администратора в `BitrixEmployee`, ни гардов авторизации — есть только `BitrixAuthService` с OAuth-токенами установки (`backend/src/integrations/bitrix/bitrix-auth.service.ts`). Для блока идентификации нужно завести определение текущего пользователя и признак администратора портала (Bitrix REST `user.admin`) и гард на эндпоинты `EmployeeIdentity`. Признак кэшируется на короткое время; при недоступности Bitrix доступ закрывается (fail-closed), а не открывается.

### Расчёт

- Расчёт выполняется по локальной БД, а не по живым запросам в ERP. Свежесть данных ограничена частотой синхронизации: `RoappSyncCron` — каждые 5 минут и только по обновлённым заказам. Данные магазина синхронизируются `moysklad-sync`.
- Крон обёрнут в `@ProdCron` и реально тикает только в проде — в dev-среде свежих данных не будет, тестировать расчёт нужно на заранее загруженном срезе.
- Справочники RemOnline (сотрудники, услуги, товары, бонусы инженеров) через крон не обновляются — только вручную через `npm run initial`. Появление нового сотрудника в ERP не подхватится автоматически.
- Денежные поля в `RoappOrder` / `RoappServiceOrder` / `MoySkladDemandPosition` объявлены как `Int` — перед реализацией зафиксировать единицу измерения (рубли или копейки) и не допускать потерь на округлении при расчёте процентов.
- `MoySkladDemandPosition.profit` приходит из МойСклада уже посчитанным — маржа магазина берётся из него, а не пересчитывается как `sum - cost`, иначе разойдёмся с отчётностью ERP. `quantity` — `Float` (весовой/дробный товар), поэтому правило `ProductSold` с `award: Fixed` должно явно определять поведение на дробном количестве.
- Закупщики БУ техники приходят доп. полями МойСклада на уровне товарной позиции, а не отдельной сущностью. Значение доп. поля нужно сопоставлять с сотрудником так же, как строковое поле «онлайн-менеджер» в RemOnline: связь ломается при переименовании значения в справочнике МойСклада.
- Категории в МойСкладе — дерево (`MoySkladProductFolder.parentId`, `pathName`). Фильтр правила по категории раскрывается до всех потомков; выборка по `pathName` через `LIKE` требует индекса, иначе на объёме позиций расчёт просядет.
- `RoappOrder` уже содержит предрассчитанные `cost`, `engineerSalary`, `managerSalary` (последний — жёстко зашитые 10% от `payed - cost - engineerSalary` в `sync/roapp`). Расчёт по правилам должен опираться на исходные суммы, а не на этот legacy-KPI, иначе получим двойную логику.
- Инвалидация кэша обязана срабатывать на три события: завершение синхронизации домена, изменение мотивационной схемы или правила, изменение плана продаж.

### Архитектура

- `service` и `shop` — параллельные независимые домены. Общий переиспользуемый код правил не создаётся: в перспективе магазин может работать без сервиса и наоборот.
- Новые модули следуют слоистости `domain` → `application` → `infrastructure` → `interface`, образец — `domains/service/modules/accounting`; `modules/sales` образцом не является.
- Правила хранятся полиморфно: `SalaryRule.props` — колонка `Json`, тип резолвится через `salary-rule-registry.ts` и `SalaryRuleFactory`. Новый тип правила надо регистрировать **в двух местах** плюс в контрактах.
- Знание о роли и о том, как считать KPI, инкапсулировано в сущности правила: расчёт периода не содержит `switch` по ролям или типам правил, а просто вызывает `calculate()` у каждого правила схемы сотрудника. Добавление новой роли не требует изменений в оркестраторе расчёта — только в правиле и в перечне ролей.
- Контракты в `contracts/` — единственный источник истины по форме данных; изменения начинаются с них.
- В проекте параллельно живёт незамигрированный модуль `salary` (эндпоинты `/salary-rules/*`), частично дублирующий предметную область `accounting`. Их нельзя путать; удаление legacy — вне этой итерации.
- Эндпоинты по доске (уточняются в реализации): `GET /accounting/salary_rule_types`, `POST|PATCH|DELETE /accounting/motivation_schema`, `GET /sales/salesPerformance/:period`, `POST|PATCH|DELETE /sales/plan`, `POST /sales/plan/approve`, `GET|PUT /sales/plan_template`, `GET /accounting/salary_report/employee/:id/:period`, `GET /accounting/salary_report/department/:id/:period`.
- Создание плана на месяц — идемпотентная операция: повторный вызов для того же периода не создаёт дублей и не затирает строки с `source = MANUAL` и статусом `APPROVED`.
- Крон создания планов, как и `RoappSyncCron`, оборачивается в `@ProdCron` и в dev-среде не тикает — поэтому ленивое достраивание планов при первом обращении к периоду обязательно, а не опционально.
- Крон запускается первого числа по времени сервера; границы месяца в кроне и в расчёте периода должны использовать одну и ту же зону, иначе план и факт разъедутся на сутки.

### Открытые вопросы к следующему этапу

- Формула расчёта прогноза продаж (`SalesPrognose`) — линейная экстраполяция по прошедшим дням месяца или учёт сезонности/рабочих дней. От неё напрямую зависит прогноз зарплаты в отчёте сотрудника, поэтому формулу нужно зафиксировать одну на оба модуля.
- Показывать ли прогноз зарплаты в первых числах месяца, когда прогноз выполнения плана ещё статистически бессмысленен, или прятать до накопления N дней.
- Что делать с зарплатой, если сотрудник переведён между отделами в середине месяца.
- Что считается «оплаченным заказом» для `OrderPayed` — статус заказа или факт полной оплаты (`payed`).
- Учитывать ли в магазине скидку продавца: сейчас `MoySkladDemandPosition.profit` уже учитывает `discount`, то есть продавец теряет в марже автоматически. Нужен ли сверх этого отдельный штраф за превышение допустимой скидки.
- Где физически лежат закупщики: доп. поле карточки товара `MoySkladProduct` (тогда одно значение на устройство, что естественно для уникальной БУ техники) или доп. поле позиции отгрузки. От ответа зависит схема Prisma и логика синка.
- Как отличить БУ технику от новой: по категории (папке) или по факту заполненного поля закупщика. Если по категории — правило `UsedProductSold` без указанной категории теряет смысл.
- Тип значения доп. поля закупщика: ссылка на сотрудника МойСклада или строка. Ссылка даёт надёжное сопоставление, строка потребует того же механизма, что `roappOnlineName`.
- Берёт ли `ProductSold` с `FloatPercent` процент выполнения плана по своей категории (если план на категорию задан) или по отделу целиком — при правиле на категорию логичнее первое, но план по категории заводится опционально.
- Что считается «задачей» для `TaskCompleted` в магазине — задача Bitrix24 или ручная отметка руководителя; источник данных по задачам в этой итерации не определён ни для сервиса, ни для магазина.
- Поведение при закрытии месяца, если синхронизация с ERP в этот момент падает.
- Распространяется ли ограничение «только администратор портала» на остальные блоки PRD (мотивационные схемы, планы, закрытие периода), которые пока остаются на руководителе. Собственную ролевую модель в iReports не заводим — права берутся из Bitrix24.
- Полный перечень ролей (`targetRole`), которые нужно поддержать в первой итерации для сервиса и для магазина.
- Нужна ли шаблону сезонность (коэффициенты по месяцам) — сейчас рост линейный +10 % к каждому месяцу, сезонные отклонения вносятся руками.
- Задаётся ли `growthPercent` на каждую строку шаблона отдельно или один на направление.
- Нужно ли уведомлять руководителя о неутверждённом плане (Bitrix-уведомление первого числа и напоминание перед закрытием месяца) — иначе блокировка закрытия периода станет неприятным сюрпризом.

## Критерии готовности

### Идентификация

- [ ] Сущность `EmployeeIdentity` создана; одному сотруднику Bitrix можно завести несколько записей — разные системы и несколько идентификаторов в одной системе.
- [ ] В `EmployeeIdentity` нет поля роли; роль хранится только в зарплатном правиле.
- [ ] Существующие значения `roappId`, `moySkladId`, `roappOnlineName` перенесены миграцией в `EmployeeIdentity` без потерь; количество перенесённых связей совпадает с количеством непустых значений в исходных полях.
- [ ] UI позволяет создать, изменить и удалить связь сотрудника с внешней системой.
- [ ] Список сотрудников без единой связи доступен в UI.
- [ ] Все эндпоинты `EmployeeIdentity` (чтение и запись) отдают `403` пользователю, не являющемуся администратором портала Bitrix24, включая руководителя.
- [ ] Администратор портала Bitrix24 выполняет полный CRUD связей без ограничений.
- [ ] Раздел управления связями отсутствует в навигации у неадминистратора, а прямой переход по URL ведёт на экран «нет доступа».
- [ ] Признак администратора читается из Bitrix24, а не хранится в iReports как отдельная роль; при недоступности Bitrix доступ закрывается.
- [ ] Заказ RemOnline, где сотрудник указан в строковом поле «онлайн-менеджер», корректно относится к нужному Bitrix-сотруднику.

### Правила и расчёт

- [ ] `calculate()` реализован и покрыт юнит-тестами для `PayPerHour`, `ServiceCompleted` (все три варианта `award`), `OrderPayed` (все три варианта `award`, все три `salaryBasis`, режимы порогов `FIX` и `LINEAR`), `TaskCompleted` (оба варианта `award`).
- [ ] `TaskCompleted` зарегистрирован в `salaryRuleRegistry`, доступен через `SalaryRuleFactory` и присутствует в `discriminatedUnion` контрактов.
- [ ] Ни один `calculate()` не возвращает захардкоженную константу.
- [ ] Правило `FloatPercent` при выполнении плана 50 / 70 / 120 % даёт три разных результата, соответствующих настроенным порогам.
- [ ] К любому правилу можно добавить индивидуальный бонус, и он попадает в итоговую сумму.
- [ ] Модуль `accounting` создан в домене `shop` с собственным набором типов правил и собственным реестром; типы правил сервиса и магазина не пересекаются.
- [ ] `GET` списка типов правил возвращает разные наборы для направлений `service` и `shop`.
- [ ] `calculate()` реализован и покрыт юнит-тестами для правил магазина: `PayPerHour`, `ProductSold` (все три `award`, обе `salaryBasis`, режимы порогов `FIX` и `LINEAR`), `UsedProductSold` (оба `award`, обе `salaryBasis`), `TaskCompleted` (оба `award`).
- [ ] Роли магазина: `ONLINE_MANAGER` / `OFFLINE_MANAGER` берутся с отгрузки, `ONLINE_PURCHASER` / `OFFLINE_PURCHASER` — с товарной позиции; правило считает только те записи, где сотрудник стоит в поле своей роли.
- [ ] Синхронизация МойСклада читает доп. поля закупщиков и сохраняет их в БД; значения сопоставляются с сотрудниками через `EmployeeIdentity`.
- [ ] Отгрузка с двумя БУ-устройствами от разных закупщиков начисляет каждому только его позицию.
- [ ] Продажа БУ-устройства начисляет и продавцу, и закупщику; если это один сотрудник, одна и та же сумма по одному правилу не начисляется дважды.
- [ ] Закупщик получает вознаграждение в периоде продажи устройства, а не в периоде его выкупа; непроданный остаток в расчёт не попадает.
- [ ] Одна отгрузка оплачивается онлайн- и офлайн-менеджеру независимо; если это один и тот же сотрудник, сумма не начисляется дважды.
- [ ] Категория в `ProductSold` захватывает вложенные папки: правило на родительскую категорию учитывает товары из дочерних.
- [ ] Правило с категорией не учитывает позиции вне этой категории, даже если они в той же отгрузке.
- [ ] `ProductSold` с `FloatPercent` меняет результат при разном проценте выполнения плана продаж магазина.
- [ ] Маржа магазина берётся из `MoySkladDemandPosition.profit`, а не пересчитывается из `sum - cost`.
- [ ] Сотрудник, имеющий связи в обеих системах, получает два независимых расчёта и корректную общую сумму.
- [ ] Сотрудник, выступающий по одному заказу в двух ролях, не получает одну и ту же сумму дважды.
- [ ] Правило хранит роль (`targetRole`), само определяет выборку данных ERP по этой роли и считает KPI; расчёт периода не содержит ветвлений по ролям.
- [ ] `calculate()` принимает контекст расчёта и возвращает строку расчёта (правило, база, количество, ставка, сумма, ссылки на источники), а не скаляр.
- [ ] Контекст собирается один раз на расчёт и передаётся во все правила схемы; ни одно правило не обращается к репозиториям и не выполняет запросов к БД самостоятельно.
- [ ] Юнит-тест любого правила выполняется на подготовленном объекте контекста, без поднятия БД и без моков репозиториев.
- [ ] Расчёт зарплат целого отдела не порождает запросов к БД, пропорциональных количеству сотрудников × количеству правил (отсутствие N+1).
- [ ] Интерфейсы контекста расчёта и строки расчёта лежат в `src/shared/domain/` и одинаковы для `service` и `shop`.
- [ ] Сотруднику можно назначить два правила с разными ролями, и оба отработают в одном месяце без изменений в его идентификации.
- [ ] Сотрудник, работавший в первой половине месяца инженером, а во второй — онлайн-менеджером, получает корректную сумму по обоим правилам без ручного переключения роли.

### Отчёты

- [ ] Отчёт сотрудника за открытый месяц возвращает и фактическую, и прогнозную сумму — и в итоге, и по каждому правилу.
- [ ] Обе суммы считаются от **фактических продаж** сотрудника; личная база в прогнозе не экстраполируется. Отличие только в множителе: факт берёт текущий процент выполнения плана, прогноз — прогнозный.
- [ ] Прогноз считается тем же `calculate()` в режиме прогноза (вход — прогнозный процент выполнения плана вместо фактического), отдельной ветки расчёта нет.
- [ ] Для правил, не зависящих от выполнения плана, факт и прогноз равны.
- [ ] При прогнозном проценте выполнения плана ниже текущего прогнозная сумма меньше фактической.
- [ ] Отчёт за закрытый месяц возвращает только факт из снапшота; поля прогноза пустые.
- [ ] Отчёт сотрудника содержит компактный срез плана продаж (план, факт, процент выполнения, прогноз) по его отделу и, при необходимости, категории; отдельного запроса за планом с фронтенда не требуется.
- [ ] Для правила `FloatPercent` в ответе есть текущий порог, следующий порог и разница до него.
- [ ] Прогнозный процент выполнения плана, попадающий в другой порог, чем фактический, меняет прогнозную сумму относительно фактической при неизменной базе продаж.
- [ ] Отчёт по отделу возвращает по каждому сотруднику общую сумму и разбивку по каждому его зарплатному правилу, а также итог по отделу.
- [ ] Итог по отделу равен сумме итогов сотрудников, а итог сотрудника — сумме его правил (проверяется тестом).
- [ ] Разбивка по правилу содержит роль, сумму, применённый процент для процентных правил и ссылки на источники (заказы/позиции/продажи).
- [ ] Факт и прогноз считаются за один проход и кэшируются вместе; инвалидация действует на обе величины.

### Период и снапшоты

- [ ] Расчётный период заводится отдельно для `service` и `shop`; закрытие периода сервиса не меняет статус периода магазина.
- [ ] Запрос зарплаты за открытый период возвращает результат, посчитанный по текущим данным БД.
- [ ] Повторный запрос за тот же открытый период без новой синхронизации отдаётся из кэша (подтверждается отсутствием повторного расчёта в логах/метриках).
- [ ] После завершения синхронизации домена следующий запрос пересчитывается заново.
- [ ] После изменения мотивационной схемы следующий запрос пересчитывается заново.
- [ ] Действие «пересчитать» сбрасывает кэш и возвращает свежий результат.
- [ ] Закрытие периода создаёт снапшот с суммами по каждому сотруднику и разбивкой по правилам.
- [ ] После закрытия месяца изменение правила, схемы или плана продаж не меняет цифры закрытого месяца.
- [ ] Значения из снапшота побайтово совпадают с последним расчётом до закрытия.
- [ ] Повторное открытие периода требует явного подтверждения и удаляет снапшот.

### План продаж

- [ ] Дефолтный шаблон плана (`SalesPlanTemplate`) заводится по отделу и, опционально, по категории, содержит процент роста (по умолчанию 10 %) и редактируется из UI.
- [ ] Крон первого числа создаёт планы на новый месяц: значения предыдущего месяца + `growthPercent`, `source = PREVIOUS_MONTH`, статус `CREATED`.
- [ ] При отсутствии плана за предыдущий месяц строка создаётся из шаблона без надбавки, `source = TEMPLATE`.
- [ ] Крон идемпотентен: повторный запуск не создаёт дублей, не перезатирает утверждённые и вручную изменённые строки.
- [ ] Если крон не отработал (dev-среда, простой), планы достраиваются лениво при первом обращении к периоду — пустого плана не бывает.
- [ ] План в статусе `CREATED` полноценно участвует в расчётах: проценты выполнения считаются, `FloatPercent` работает, отчёты не падают.
- [ ] Статус меняет только руководитель; автоматического перехода в `APPROVED` нет.
- [ ] Правка утверждённой строки возвращает её в `CREATED` и помечает `source = MANUAL`.
- [ ] Пока в периоде есть строки `CREATED`, зарплатные отчёты содержат признак «план не утверждён».
- [ ] Утверждение и изменение плана инвалидируют кэш зарплатного расчёта.
- [ ] Закрытие периода с неутверждёнными строками отклоняется и возвращает их перечень.
- [ ] Доступно массовое утверждение месяца по направлению.
- [ ] План продаж создаётся на месяц по отделу и, опционально, по категории; повторное создание плана на ту же комбинацию отклоняется.
- [ ] Факт и прогноз рассчитываются по данным ERP и отдаются в составе `SalesPerformance`.
- [ ] Изменение плана пересчитывает факт и прогноз, и это отражается на зарплате сотрудников с процентными правилами.
- [ ] Удаление плана удаляет связанные факт и прогноз.
- [ ] Правило с процентом от выполнения плана падает с внятной доменной ошибкой, если плана на период нет вообще (ни автоматического, ни ручного).
