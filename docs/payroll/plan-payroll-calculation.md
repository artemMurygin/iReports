# Plan: Расчёт заработной платы сотрудников (сервис и магазин)

**PRD**: [`docs/prd-payroll-calculation.md`](./prd-payroll-calculation.md)
**Дата**: 2026-08-10

---

## Порядок работы

1. **Фазы 1–13 — backend и база данных.** Полностью закрывают серверную часть PRD: контракты, схема Prisma, расчёт, планы, периоды, отчёты, оба направления.
2. **Фаза 14 — дизайн.** На основании этого файла и PRD формируем макеты в pencil.dev. До неё фронтенд не начинаем.
3. **Фазы 15–18 — frontend.** Реализуются по утверждённым макетам фазы 14.

## Правила, действующие во всех фазах

- Изменения начинаются с пакета `ireports-contracts` — он единственный источник истины по форме данных.
- Новые модули следуют слоистости `domain` → `application` → `infrastructure` → `interface`; образец — `domains/service/modules/accounting`, `modules/sales` образцом не является.
- Каждая фаза, добавляющая HTTP-маршруты, обновляет `ENDPOINTS.md`.
- Фаза считается завершённой только при зелёных `npm run lint`, `npm run test`, `npm run build`.

## Фаза 9: Отчёты — факт, прогноз, сотрудник и отдел

**Цель** Сотрудник видит пару «факт / прогноз» и понимает, из чего они сложились; руководитель видит то же по отделу.
**Что затрагивает?** backend, contracts

**Задачи:**
- [ ] Режим расчёта `FACT | PROGNOSE` в контексте: в прогнозе правило получает `SalesPrognose.percentCompletion` вместо `SalesFact.percentCompletion`, всё остальное идентично. Отдельной ветки расчёта нет, личная база сотрудника не экстраполируется.
- [ ] Пара «факт / прогноз» в итоге и в каждой строке разбивки; для правил, не зависящих от плана, значения равны. Для `FloatPercent` в ответе — текущий порог, следующий порог и разница до него.
- [ ] Компактный срез `SalesPerformance` по отделу сотрудника (и по категории, если правила схемы завязаны на категорию) и признак `isPlanApproved` в ответе отчёта — отдельного запроса за планом с фронтенда не требуется.
- [ ] `GET /accounting/salary_report/department/:id/:period`: результат по каждому сотруднику + итог по отделу, без отдельной «свёрнутой» логики расчёта. У закрытого периода прогноз не заполняется, факт берётся из снапшота. Факт и прогноз считаются за один проход и кэшируются вместе.
- [ ] Тесты: прогнозный процент в другом пороге меняет прогнозную сумму при неизменной базе; прогноз ниже текущего процента даёт сумму меньше факта; итог отдела = сумме сотрудников, итог сотрудника = сумме его правил; закрытый месяц отдаёт пустой прогноз; расчёт отдела не порождает N+1 запросов.

**Когда готово** Оба отчёта соответствуют формам ответа из раздела «Контракты» PRD.

- [ ] Категория как обязательная часть `ProductSold` (пара «категория × награда», правило без категории = все товары), захват вложенных папок; независимая реализация `FloatPercent` с тремя `percentBorders`; необязательный индивидуальный бонус; позиция попадает в период по `MoySkladDemand.moment`; явное поведение `Fixed` на дробном `quantity`; отдельный `discriminatedUnion` контрактов магазина, не смешанный с сервисным.
- [ ] Тесты: все три `award` × обе `salaryBasis` × `FIX` и `LINEAR`; правило на родительскую категорию учитывает товары дочерних и не учитывает позиции вне категории в той же отгрузке; одна отгрузка оплачивается онлайн- и офлайн-менеджеру независимо, а одному и тому же сотруднику — один раз (дедупликация по паре «правило × позиция»); `GET` списка типов правил возвращает разные наборы для `service` и `shop`.

**Когда готово** Правила магазина считают по своим данным, типы правил сервиса и магазина не пересекаются.

## Фаза 13: Магазин — `UsedProductSold` и `TaskCompleted`

**Цель** Вознаграждение закупщиков БУ техники и задачи — закрытие набора правил первой итерации магазина.
**Что затрагивает?** backend, contracts

**Задачи:**
- [ ] `UsedProductSold.calculate()`: роль `ONLINE_PURCHASER` или `OFFLINE_PURCHASER`, `award` `Fixed` (за единицу) и `FixedPercent`; `FloatPercent` не предусмотрен; базы `REVENUE` и `MARGIN`; необязательная категория.
- [ ] Момент начисления — продажа, а не выкуп: в расчёт идут только позиции отгрузок периода, непроданный остаток не учитывается.
- [ ] `TaskCompleted` магазина (`Fixed`, `FloatPercent`) + регистрация в реестре, фабрике и контрактах магазина.
- [ ] Дедупликация вырожденного случая «продавец и закупщик — один сотрудник» по паре «правило × позиция».
- [ ] Тесты: оба `award` × обе `salaryBasis`; отгрузка с двумя БУ-устройствами от разных закупщиков начисляет каждому только его позицию; продажа начисляет и продавцу, и закупщику; один сотрудник в обеих ролях не получает одну сумму по одному правилу дважды; сотрудник со связями в обеих системах получает два независимых расчёта и корректную общую сумму.

**Когда готово** Все правила первой итерации магазина реализованы и покрыты тестами; backend-часть PRD закрыта полностью.

**Цель** Сотрудник и руководитель видят зарплату и понимают, из чего она сложилась.
**Что затрагивает?** frontend
