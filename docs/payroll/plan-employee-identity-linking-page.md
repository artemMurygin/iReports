## Контекст

Backend-часть (родительская Фаза 2 «`EmployeeIdentity` и доступ администратора портала») уже полностью реализована и покрыта тестами:

- Контракты: `contracts/commands/employee-identity.ts` — `EmployeeIdentityResponse` (`id`, `bitrixEmployeeId`, `system: 'ROAPP' | 'MOY_SKLAD'`, `identifierType`, `externalId`, `createdAt`, `updatedAt`), `identifierType` — 4 значения (`EMPLOYEE_ID`, `ONLINE_MANAGER_FIELD`, `MOY_SKLAD_ONLINE_PURCHASER_FIELD`, `MOY_SKLAD_OFFLINE_PURCHASER_FIELD`), `CreateEmployeeIdentityRequest`, `UpdateEmployeeIdentityRequest` (без смены сотрудника/системы — только `identifierType`/`externalId`), `UnmatchedEmployeeResponse` (`id`, `firstName`, `lastName`, `departmentId`).
- Эндпоинты модуля `backend/src/modules/employee-identity/` (все под `PortalAdminGuard`):
  `POST /employee-identity`, `PATCH /employee-identity/:id`, `DELETE /employee-identity/:id`,
  `GET /employee-identity/employee/:employeeId`, `GET /employee-identity/unmatched`.
- `PortalAdminGuard` читает заголовок `x-bitrix-auth` (`BX24.getAuth().access_token`); без заголовка или без прав — `403`; fail-closed при недоступности Bitrix. **Фронтенд ещё не прокидывает этот заголовок** — это отдельная задача данного плана, а не что-то уже готовое.
- Справочник сотрудников/отделов уже есть и переиспользуется: `GET /v1/directory/employees` (`{ id, name, departmentId }`), `GET /v1/directory/departments` — на фронте уже есть хук `pages/SalaryRules/model/useTargetDirectory.ts`.
- Frontend: раздел «Зарплата» в навигации (`frontend/src/app/navigation.tsx`) уже существует и содержит пункты «Отчёт по зарплате» (disabled), «Правила начисления» (`/salaries/rules`, реализовано), «Отчётный период» (disabled). Пункта для связей — нет, добавляется в этой работе. Страницы монорепо верстаются на новом UI Kit (`shared/ui-kit/`, см. `SalaryRulesPage` как образец), а не на `shared/ui/`.
- В Pencil-файле `design/sallary-first-iteration.pen` уже есть готовая библиотека компонентов `ERP/Atom/*`, `ERP/Molecule/*`, `ERP/Organism/*`, `ERP/Mobile/*` (Data Table, Modal, Page Header, Filter Bar, Badge, Chip, Avatar, Cell Text/Status/Actions, Option Card, Section Card и т.д.) — макет собирается из них, а не с нуля.

Из PRD в скоуп этой страницы попадает **только раздел «Идентификация сотрудника»** — мотивационные схемы, планы и отчёты (родительские Фазы 16–18) не затрагиваются.

## Фаза 1: Макеты страницы связей в pencil.dev ✅

**Цель** Утверждённые макеты, покрывающие все пользовательские сценарии PRD по идентификации сотрудника, до начала вёрстки.
**Что затрагивает?** design
**Статус** Выполнено, макеты в `design/sallary-first-iteration.pen`.

**Задачи:**
- [x] Макет главного экрана — фрейм **«Связи сотрудников · Список»** (`CpVvw`, 1440): Topnav с активным разделом «Зарплата» и вкладкой «Связи сотрудников», Page Header, полоса покрытия ERP, Filter Bar, таблица «Сотрудник × RemOnline × МойСклад».
- [x] Макет добавления связи — **«Связь · Добавление»** (`NjnJ3`, модалка 720) и удаления — **«Связь · Удаление»** (`CweSL`, 520, destructive с описанием последствий).
- [x] Список сотрудников без связей — реализован не отдельной страницей, а состоянием того же экрана: вкладка «Без связей» в Filter Bar + сегмент «ни в одной» в полосе покрытия; строки без идентификаторов показывают плейсхолдер «Связать» в каждой системе.
- [x] Макет экрана «Нет доступа» — **«Связи сотрудников · Нет доступа»** (`VnGIh`, 1440): в subnav вкладки «Связи сотрудников» нет (раздел скрыт из навигации), в теле — состояние с объяснением и возвратом к правилам начисления.
- [x] Мобильные версии — **«Связи сотрудников · Мобильный»** (`Tu1Fs`, 390) и **«Связь · Добавление (Мобильный)»** (`jZ3oF`, 390).

**Ключевые решения дизайна**
- **Полоса покрытия ERP** вместо трёх KPI-карточек: один сегментированный индикатор «опознаны в обеих / только в одной / ни в одной». Экран отвечает не на вопрос «какие есть связи», а на вопрос «где ещё дырки, из-за которых не посчитается зарплата».
- **Идентификаторы — чипы внутри ячейки системы**, а не бейдж «есть/нет». Сценарий PRD «второй идентификатор в той же системе» (ID сотрудника + «онлайн-менеджер») виден прямо в строке таблицы, без раскрытия.
- **Действие живёт там же, где данные**: пустая ячейка системы — плейсхолдер «Связать», заполненная — компактный `+` для второго идентификатора. Идентичность принадлежит паре «сотрудник × система».
- Тип идентификатора в чипе подписан явно (`ID · 412`, `Онлайн-менеджер · Мурыгин А.`), у варианта «Онлайн-менеджер» в форме прямо указано ограничение из PRD: строковое поле, связь оборвётся при переименовании.
- Всё собрано из существующего UI Kit (`ERP/Atom/*`, `ERP/Molecule/*`, `ERP/Organism/*`, `ERP/Mobile/*`) и токенов `brand`/`ink`/`canvas`/`surface`/`hairline`/`warn`/`danger`; новых атомов не заводилось.

**Когда готово** Все пять пунктов раздела «Идентификация» из PRD (карточка со связями, добавление связи, второй идентификатор в системе, список несопоставленных, отказ в доступе) отражены в макетах.

## Фаза 2: Вёрстка страницы связей

**Цель** Администратор портала Bitrix24 управляет связями сотрудников из UI по утверждённым макетам Фазы 1; для остальных пользователей раздел недоступен.
**Что затрагивает?** frontend

**Задачи:**
- [ ] Определение прав администратора на фронте и передача `x-bitrix-auth`: клиентская подсказка через `BX24.isAdmin()` (для мгновенного скрытия пункта меню, без похода на бэкенд) + отдельный API-клиент/interceptor, прикладывающий заголовок `x-bitrix-auth: BX24.getAuth().access_token` ко всем запросам `/employee-identity/*` (источник истины по правам остаётся бэкенд-гардом, клиентский флаг — только для UX).
- [ ] Роут (например `/salaries/employee-identity`) и пункт навигации в секции «Зарплата»; экран «Доступ запрещён» при прямом переходе неадминистратора — реагирует на `403` от бэкенда, а не только на клиентский флаг `BX24.isAdmin()`.
- [ ] Экран связей: выбор сотрудника (переиспользуя существующий справочник), список его связей по системам, создание/редактирование/удаление связи через модалку.
- [ ] Список сотрудников без связей с переходом к созданию связи для выбранного.
- [ ] Тесты: пункт меню не отображается / недоступен у неадминистратора; прямой переход по URL ведёт на экран «Доступ запрещён»; полный CRUD-сценарий связи (создание, второй идентификатор в той же системе, редактирование, удаление) проходит целиком.

**Когда готово** Критерии готовности раздела «Идентификация» PRD, относящиеся к UI, выполнены: администратор портала выполняет полный CRUD связей из интерфейса, список несопоставленных сотрудников доступен, у неадминистратора раздел скрыт и прямой URL ведёт на «нет доступа».

```
Спроектируй в design/sallary-first-iteration.pen новый набор экранов «Связи сотрудника с внешними системами» — раздел раздела «Зарплата», доступный только администратору портала Bitrix24. Переиспользуй существующую библиотеку компонентов из фрейма «ERP · UI Kit (Atomic)» (ERP/Organism/Page Header, ERP/Organism/Filter Bar, ERP/Organism/Data Table, ERP/Organism/Modal, ERP/Molecule/Cell Text, ERP/Molecule/Cell Status, ERP/Molecule/Cell Actions, ERP/Molecule/Option Card, ERP/Molecule/Section Card, ERP/Atom/Badge, ERP/Atom/Chip, ERP/Atom/Avatar, ERP/Sidebar, ERP/Organism/Topnav) и мобильные аналоги (ERP/Mobile/*), а также стиль уже готовых фреймов «Зарплатное правило · Создание» — те же токены, отступы и типографику.

Нужны следующие фреймы, десктоп и мобильная версия для каждого (по образцу уже существующих пар «... (Десктоп)» / «... (Мобильный)»):

1. «Связи сотрудника · Список» — экран с поиском/выбором сотрудника (переиспользовать паттерн выбора сотрудника, как в карточке цели зарплатного правила) слева и карточкой выбранного сотрудника справа. Карточка сотрудника показывает его связи, сгруппированные по двум системам — RemOnline и МойСклад — каждая связь как строка/чип с типом идентификатора (ID сотрудника, «онлайн-менеджер», онлайн-закупщик, офлайн-закупщик) и значением, с иконками редактирования и удаления. У системы может быть больше одной связи (например ID сотрудника + «онлайн-менеджер» одновременно) — покажи такое состояние явно. Кнопка «Добавить связь».

2. «Связи сотрудника · Добавление/редактирование» — модальное окно (на базе ERP/Organism/Modal) с полями: выбор системы (RemOnline / МойСклад), выбор типа идентификатора (список зависит от системы), поле значения идентификатора, кнопки «Сохранить»/«Отмена». Отдельное состояние подтверждения удаления связи.

3. «Связи сотрудника · Сотрудники без связей» — список сотрудников Bitrix, у которых нет ни одной связи ни в одной системе (используй ERP/Organism/Data Table или ERP/Molecule/Option Card в виде списка), каждая строка — имя, отдел, кнопка «Добавить связь», ведущая к экрану 2 с предвыбранным сотрудником.

4. «Связи сотрудника · Доступ запрещён» — экран для пользователя, не являющегося администратором портала, при прямом переходе по URL: пояснение, что раздел доступен только администратору портала Bitrix24, без формы и без данных.

Также покажи, как пункт «Связи с внешними системами» встраивается в существующую навигацию раздела «Зарплата» (рядом с «Правила начисления», «Отчёт по зарплате», «Отчётный период») — как на десктопном Sidebar/Topnav, так и в мобильном Bottom Nav/Drawer.

Состояния, которые должны быть видны хотя бы в одном из фреймов: пустой список связей у сотрудника, несколько идентификаторов в одной системе, сотрудник со связями в обеих системах одновременно, пустой список «сотрудники без связей».
```
