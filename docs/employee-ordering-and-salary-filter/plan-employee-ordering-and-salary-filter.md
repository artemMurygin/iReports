# Plan: Единый порядок сотрудников и фильтр служебных аккаунтов в зарплате

**PRD**: docs/employee-ordering-and-salary-filter/prd-employee-ordering-and-salary-filter.md
**Дата**: 2026-09-03

## Фазы реализации

### Фаза 1: Backend — хранение и API порядка сотрудников
**Цель**: Появляется единое, независимое от Bitrix24-синхронизации поле порядка (order/weight) в сущности сотрудника, API для его изменения, и все существующие backend-эндпоинты со списками сотрудников начинают сортировать по этому полю вместо своих текущих правил (alphabet/id).
**Что затрагивает?**: backend, database

**Задачи:**
- [ ] Prisma-миграция: добавить локальное поле `order` (Int) в модель `BitrixEmployee` (`backend/prisma/schema/bitrix.prisma`), заполнить начальные значения для существующих записей (например, по текущему алфавитному порядку), исключить поле из цикла Bitrix24-синхронизации
- [ ] Эндпоинт для сохранения нового порядка (reorder) — принимает новый порядок сотрудников, обновляет `order`, доступен любому авторизованному пользователю без дополнительных прав
- [ ] Обновить сортировку в справочнике сотрудников (`directory.repository.ts`, `GET /v1/directory/employees`) на `orderBy: order`
- [ ] Обновить сортировку в эндпоинтах отчёта по зарплате, взаиморасчётов/баланса и зарплатных схем (оба домена service/shop) на `orderBy: order` вместо текущих `lastName/firstName asc` и `employeeId asc`
- [ ] Тесты: unit-тест на reorder-эндпоинт (сохранение и повторное чтение порядка), интеграционный тест, проверяющий одинаковый порядок при запросе к справочнику, отчёту по зарплате и взаиморасчётам после reorder

**Когда готово**: После вызова reorder-эндпоинта все перечисленные backend-эндпоинты возвращают сотрудников в одном и том же новом порядке; тесты зелёные.

### Фаза 2: Frontend — drag-n-drop и единый порядок на всех страницах
**Цель**: Пользователь может вручную поменять порядок сотрудников на странице «График работы», и этот порядок сразу виден на всех остальных страницах со списком сотрудников.
**Что затрагивает?**: frontend

**Задачи:**
- [ ] Drag-n-drop переупорядочивание сотрудников на странице «График работы» (переиспользовать паттерн `@dnd-kit` из `features/SalesPlan/ui/EditPlanModal`), вызывающее reorder-эндпоинт из Фазы 1
- [ ] Убедиться, что `SalaryReportV2` рендерит сотрудников в порядке ответа backend, без клиентской пересортировки
- [ ] Убедиться, что страница взаиморасчётов/баланса сотрудника рендерит сотрудников в порядке ответа backend
- [ ] Убедиться, что список/редактор зарплатных схем (`SalaryRuleList`/`SalaryRuleDetail`) и справочник выбора сотрудника при создании отчёта рендерят сотрудников в порядке ответа backend
- [ ] Тесты: e2e/ручная проверка — изменить порядок на графике работы, убедиться, что тот же порядок отражается на отчёте по зарплате, взаиморасчётах, зарплатных схемах и справочнике выбора; проверить, что менять порядок может пользователь без специальных прав

**Когда готово**: Перетаскивание сотрудников на странице «График работы» сохраняется и одинаково отражается на всех перечисленных в PRD страницах у всех пользователей.

### Фаза 3: Backend — признак «служебный аккаунт» и его исключение из зарплаты
**Цель**: Появляется независимый от `isActive` и от Bitrix24-синхронизации признак «служебный аккаунт», и все зарплатные backend-эндпоинты (кроме графика работы и связей сотрудников) исключают таких сотрудников из списков, расчётов и итоговых сумм.
**Что затрагивает?**: backend, database

**Задачи:**
- [ ] Prisma-миграция: добавить локальное поле `isServiceAccount` (Boolean, default false) в `BitrixEmployee`, исключить поле из цикла Bitrix24-синхронизации
- [ ] Эндпоинт для включения/выключения признака у сотрудника
- [ ] Исключить сотрудников с `isServiceAccount = true` из эндпоинтов отчёта по зарплате, взаиморасчётов/баланса, зарплатных схем и справочника выбора сотрудника при создании отчёта — из списков, расчётов и итоговых сумм
- [ ] Явно проверить, что эндпоинты графика работы и связей сотрудников (`EmployeeIdentity`) продолжают возвращать служебных сотрудников без изменений
- [ ] Тесты: unit/интеграционные тесты на исключение из зарплатных эндпоинтов (включая проверку итоговых сумм) и на сохранение видимости в графике работы/связях сотрудников

**Когда готово**: Сотрудник с включённым признаком «служебный» не попадает ни в списки, ни в расчёты, ни в итоги зарплатных эндпоинтов, но по-прежнему возвращается эндпоинтами графика работы и связей сотрудников; тесты зелёные.

### Фаза 4: Frontend — переключатель «служебный» на странице настроек
**Цель**: Администратор может на странице настроек отметить/снять отметку «служебный» у любого сотрудника, и увидеть эффект на зарплатных страницах.
**Что затрагивает?**: frontend

**Задачи:**
- [ ] Добавить в раздел «Настройки» список сотрудников с переключателем «исключить из зарплаты», вызывающим эндпоинт из Фазы 3
- [ ] Отобразить актуальное состояние признака при загрузке списка, обновлять его после переключения
- [ ] Тесты: ручная/e2e проверка — включить признак у сотрудника, убедиться, что он пропал из отчёта по зарплате, взаиморасчётов, зарплатных схем и справочника выбора сотрудника
- [ ] Тесты: ручная/e2e проверка — убедиться, что сотрудник остался виден в графике работы и на странице связей сотрудников
- [ ] Тесты: снять отметку «служебный», убедиться, что сотрудник вернулся во все зарплатные выборки

**Когда готово**: Переключатель на странице настроек управляет видимостью сотрудника во всех зарплатных страницах согласно критериям готовности PRD, без побочных эффектов на график работы и связи сотрудников.
